# Architecture v1.1（据评审修正）

> v1 的四个决定保留不动：`Capability ≠ Contract`、Worker 只管流程、CLI Contract 机器提取、平台差异收进 Adapter。
> 本次只改评审指出的 7 处。

## 修正 1：L1/L2 从「语法证明」拆成「语法 + 语义」

**v1 的错误**：`L2 = argv ⊆ parser 参数` 只能证明**语法契约**成立。
parser 注册了 `--foo` 不代表 `upload-video` 会读 `args.foo` —— 那会从
「`unrecognized arguments` 报错」退化成「**参数不报错了但没生效**」，更难查。

**v1.1 的拆分**：

| 契约 | 含义 | 怎么获得 |
| --- | --- | --- |
| **CLI Contract（Syntactic）** | parser **接受**什么 | `ast` 提取，可自动 |
| **Execution Contract（Semantic）** | action **实际消费**什么 | **不能靠 AST 完全证明** → 靠契约测试 |

**级别重新定义**：

| 级别 | v1 | v1.1 |
| --- | --- | --- |
| L1 | 有 CLI action | **能找到实际 action**（不变） |
| L2 | `argv ⊆ parser` | **action 能启动 + 参数被 action 正确消费** |
| L3 | 有成功记录 | **真实平台验证**（见修正 4） |

**落地方式**：为每个 Adapter 生成一组 **CLI contract test**，而不是试图做静态分析：

```
douyin + upload-video
  --title  --desc  --declaration  --headed
  ① parser 接受？（语法）
  ② 参数最终进入 action？（语义 —— 用 dry-run / 桩验证）
```

**这一条改变了 CLI Boundary 的产出**：它不只提供「参数集合」，还要提供**可生成契约测试的元数据**。

## 修正 2：`supports()` 必须拆成四个独立事实 + 一条产品规则

**v1 的危险**：`supports()` 若实现为 `level >= L0`，那么 `TencentNote`（L0）会再次被判为
「视频号支持图文」—— **换个名字重犯第一阶段抓出的原始事故**。

**v1.1**：注册表输出四个**互相独立**的事实，外加一条**产品规则**：

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| `claimed` | 产品**打算**支持吗 | 人工声明 |
| `implementationLevel` | 代码里有实现符号吗（L0） | 静态扫描 |
| `executionLevel` | 有 action + 参数被正确消费（L1/L2） | 契约提取 + 契约测试 |
| `verificationLevel` | 有真实平台验证（L3） | 验证事件（见修正 4） |

```
selectable = claimed && executionLevel >= L2      // 产品规则，独立表达
```

**关键区分**：

> **L0–L3 是事实状态；「用户能不能选」是产品规则。**
> 两者不能在同一个字段里混合，也不能让 UI 自行推导。

## 修正 3：`enforced` → `requiredInRequest` / `optionalInRequest`

**v1 的错误**：把「业务上必须提供这个信息」与「所有平台必须用同一个 CLI 参数表达它」混为一谈。

**反例**：某平台业务上需要 declaration，但它的 CLI 可能是 `--ai-generated=true`，甚至是**网页自动勾选**。

**v1.1**：

```
Publish Contract  →  requiredInRequest: 这个请求必须包含 declaration
Adapter           →  这个平台如何表达 declaration（--declaration / --ai-generated / 网页勾选 / 不需要）
```

**强制等级描述的是「请求」，不是「平台实现」。** 这样业务语义与平台实现才真正分离。

## 修正 4：L3 需要可审计的验证事件，不能只看 `status === success`

**v1 的问题**：开发者手工跑一次的记录，与真实生产账号的真实发布，会被视为同等证据。

**v1.1**：L3 由一个**可审计的验证事件**推导：

```json
{
  "platform": "douyin",
  "contentType": "video",
  "verificationType": "real_account_publish",
  "environment": "production",
  "accountId": "acc-...",
  "taskId": "pub-...",
  "result": "success",
  "verifiedAt": "..."
}
```

```
verificationLevel = derive(validVerificationEvidence)
```

**仍然全部是机器计算，不需要人工填写。** 但「什么叫有效证据」是一条**显式规则**（例如：
必须 `verificationType = real_account_publish` 且 `environment = production` 且有关联 `taskId`）。

## 修正 5：「新增平台改 2 处」加前提

**v1 的过度承诺** → **v1.1 的准确表述**：

> **在底层 `uploader` / CLI 能力已经存在的前提下**，接入一个新平台的产品发布层改动目标为 2 处
> （Capability 声明 1 行 + Adapter 1 个文件）。

如果是**真正全新的平台**，链路是：登录 → Cookie → uploader → CLI → 互动 → 同步 → 前端，
**绝不可能只有 2 处**。架构承诺必须写清前提。

## 修正 6：Adapter 之前预留 `Platform Publish Command` 层

**v1 的问题**：Adapter 直接产出 `string[] argv`，上层看到的已是「编译成 CLI 的东西」。
将来要加 Browser / API / MCP Adapter 时会被这个形状绑死。

**v1.1 的分层**（但**这一刀现在不砍**，只预留位置）：

```
Canonical Publish Request
        ↓
Platform Publish Command      ← 平台语义操作（新增层，v1.1 只定义接口，不实现多态）
        ↓
CLI Adapter
        ↓
argv
```

理由：Bosom Friend 当前只有 CLI 一种 transport，现在做多态是**投机性抽象**；
但接口形状要留对，否则将来重构要动所有 Adapter。

## 修正 7：平台身份与执行目标分离

**v1 的表述**：「平台键只在 Adapter 声明一次，其余全部派生」——容易被理解成让 `tencent` 成为产品身份。

**v1.1 的表述**：

```
platformId = "wxSph"          ← 产品世界的身份（稳定，不随底层实现变化）
Adapter:
  platformId  = wxSph
  cliPlatform = tencent        ← 引擎世界的身份（实现细节，可替换）
  actions     = {...}
```

> **平台身份由稳定的产品 ID 定义；Adapter 只负责声明该 ID 对应的执行目标。**

否则下次「某平台换了底层实现」，全系统的平台 ID 都要跟着改。

## v1.1 的完整分层

```
Publish Contract          = 业务语义（请求必须包含什么）
      ↓
Platform Capability       = 产品是否宣称支持（claimed，人工）
      ↓
Platform Publish Command  = 平台语义操作（预留层）
      ↓
Adapter                   = 平台语义 → 当前执行方式（字段怎么表达）
      ↓
CLI Contract              = 执行方式实际接受什么（语法，机器提取）
      ↓
CLI Execution             = 是否真的跑起来（语义，契约测试）
      ↓
Real Verification         = 是否真实验证过（可审计事件）
```

## 附：本次保留不动的四个 v1 决定

1. `Capability ≠ Contract`（意图人工、事实机器、交叉校验）
2. Worker 只管流程，不知道任何平台；argv 构造搬进 Adapter
3. CLI Contract 由机器提取（ast），是契约的唯一事实源
4. 平台差异收进 Adapter（一平台一文件，声明式）

*本文档为架构修正，不含实现，未修改任何产品代码。*
