## 0. 先看这三件事（按紧急度）

### 0.1 这台机器当前对局域网开放（实测，非推测）

    remote-access.json = {"enabled": true, "token": "faf4...94ac", "bindAll": true, "tunnelCommand": ""}
    Get-NetTCPConnection -LocalPort 31280  ->  0.0.0.0:31280  LISTEN  PID 19932
    进程 = node.exe --import tsx/esm products/bosom-friend/launcher/src/bin-desktop.ts
    本机局域网地址 = 192.168.2.117 (WLAN)

含义：同网段任何设备都能访问这个 App 的全部 **197** 个接口（含删账号、发布、改配置、读知识库）。
唯一门槛是一枚 64 位十六进制令牌，而该令牌明文存在数据根的 JSON 里，并且会经 URL 查询串传递
（?token=... 会进浏览器历史、Referer、代理日志）。

这不是代码漏洞，是用户主动打开的功能（remote-access.ts:1-15 自述三件事拆开生效）。但它此刻是开着的，
且当前组合层把 authEnabled 显式设为 false（bundle/desktop/cordis.patch.yml:36、bundle/app/cordis.patch.yml:9），
所以远程模式下没有会话鉴权，只有那一枚令牌。

关闭方式（需用户自行决定）：设置页关掉「远程访问 → 局域网可达」，然后**重启运行时**（监听地址是启动时定的，
launcher/src/bin-desktop.ts:40-54）；或直接把 remote-access.json 的 bindAll 改回 false。

### 0.2 抖音「图文发布」100% 失败，且已重复至少 3 次（实测）

  而图文走的正是 upload-note（worker.py:706）。--location 同理（sau_cli.py:828 vs worker.py:733-735）。
- 实测记录：pub-x3grj7jg、pub-axfyrpf4、pub-h69n4j7w 三条 ImageText 任务全部 failed，错误完全同型。
- 为什么排前面：项目铁律 #13 写明「同一问题第二次出现必须升级成门禁断言」。这条已出现第三次，
  缺陷台账未闭环 10 条里没有它。

## 1. 总体架构：它到底是什么

**一句话：这不是一个 SaaS，是一个装了 827MB 安装包的单机桌面应用。** 没有服务器、没有数据库、没有多租户。

    ┌─ Electron 壳（desktop/electron/main.cjs 53KB）
    │    解压内核 → 起运行时 → 探活 → 加载 127.0.0.1:31280/bosom-friend/ → 看护/重启
    │
    ├─ 本地 Node 运行时（launcher/src/bin-desktop.ts，tsx 直跑源码）
    │    └─ DSH Cordis 插件树（三层 bundle 补丁叠加，bin-desktop.ts:24-29）
    │         ├─ @deepseek-ai/dsh-base                      官方基座
    │         ├─ @deepseek-ai/dsh-host-webserver           官方 HTTP（node:http，无框架）
    │         ├─ @deepseek-ai/dsh-media + media-pi-ai      媒体能力面（图片/视频出网唯一出口）
    │         ├─ @deepseek-ai/dsh-bosom-friend-server/api  ★产品后端，197 条 REST 路由
    │         └─ @deepseek-ai/dsh-bosom-friend-kernel      ★产品内核，17 个 bosom_* 工具
    │
    ├─ 子进程（全部由 server 派生，登记后退出时整树回收）
    │    ├─ Python 引擎：worker.py daemon/publish/sync/interact/cover/profile
    │    │    └─ 真实 Chrome + CDP + 拟人化节奏（不是平台开放 API）
    │    ├─ 内核子进程：stdio JSON-RPC（@deepseek-ai/dsh-sdk-client）
    │    ├─ ffmpeg：合成/拼接/缩略图/时长探测
    │    └─ PowerShell：图片裁剪/排版
    │
    └─ 数据根 ~/.bosom-friend/bosom-friend/（27 个 JSON 域 + uploads + platform-login）

关键事实（都实测过）：

- 后端不是独立服务，是 DSH 的一个函数插件：api.ts:182-203 导出 name/inject/Config，api.ts:7447 导出 apply。
- HTTP 能力来自官方 packages/host/webserver（createServer 在 :242），产品只注册两个前缀
  （api.ts:7959 /bosom-friend/api、api.ts:8043 /bosom-friend）。
- 前缀以内是自研路由表：{m, p, h} 数组 + 线性匹配（api.ts:340-360），不是 Express。
- server 与 kernel 是两条通道：① stdio JSON-RPC（server→内核）；② 内核用 fetch 反调本机 31280
  （kernel/src/index.ts:929/974/1024/1078，不带任何鉴权头，能通过是因为 authEnabled=false）。
- 前端产物由产品服务托管，运行时注入 window.__BACKEND_BASE_URL__ 等（http.ts:302-335）。

## 2. 逐条回答那 18 个问题

### Q1 项目完整架构是什么

见第 1 节。四层：Electron 壳 → 本地 DSH 运行时（插件树）→ 子进程（Python 引擎 / 内核 / ffmpeg / PowerShell）→ 本地 JSON 数据根。
没有服务端、没有数据库、没有多租户；所有能力都跑在用户这一台 Windows 机器上。

### Q2 前端是什么

**修正一个常见误解：前端不是 Next.js 工程。**

- 构建宿主是 Electron 包（bosom-friend-electron/vite.config.mts:31-130），web 包的 package.json 只有 8 行、无依赖无 scripts；
  @web 别名指向 web 的 src（vite.config.mts:63-70）。
- 运行时路由是 **react-router-dom 的 hash 路由**，定义在壳侧 bosom-friend-electron/src/router/index.tsx:139（createHashRouter）。
- web 包的 app/[lng]/* 是「Next 风格目录 + 自研 shim」：src/next-shims/ 4 个文件把 next/navigation、next/link、
  next/image、next/dynamic 映射到 react-router，被引用 93 处；页面由 desktop-pages/*.tsx 薄壳懒加载。
- 技术栈：React 18 + Vite + TypeScript + zustand ^5.0.3 + i18next；UI 双栈（新代码 radix-ui + tailwind + lucide，旧代码 antd）；
  请求是自研 fetch 封装（axios 仍是依赖但 web src 内 0 处使用）。
- 7 个侧栏板块（app/layout/routerData.tsx:29-77）：/draft-box 内容创作 · /tasks-history 任务记录 · /calendar 发布日历 ·
  /data-statistics 数据中心 · /monitor 全局监控 · /ai-interaction AI互动 · /knowledge 知识库。底部「添加频道」不是路由项。
- 多语言是**名义上的**：locales 下有 7 套资源，但运行时语言表只剩 zh-CN（i18n/languageConfig.ts:21-32），壳层硬编码 lng=zh-CN（WebAppLayout.tsx:119）。
- 状态：22 个全局 zustand store；实时同步靠**一条 SSE + 14 处 setInterval 轮询**，无 WebSocket；AI 助手会话不持久化，每次启动清空（agent.methods.ts:723）。
- 结构性缺陷（台账 DEF-140）：前端**不在任何类型检查里**（vite build 走 esbuild 不做类型检查，CI typecheck 只覆盖 server 与 kernel），
  71 条类型错误长期无人可见，并直接放过三条产品缺陷。

### Q3 后端是什么

DSH 插件 + 自研路由 + 统一信封。197 条路由分布在 5 个文件：
api.ts 79 · routes-content.ts 65 · routes-channels.ts 37 · routes-knowledge.ts 9 · knowledge-distill.ts 7。

一次请求的管道：CORS 预检短路 → 远程令牌网关（api.ts:7874）→ 会话守卫（:7979）→ 路由匹配（:7983）
→ body 读取（1GB 上限，:7991）→ 处理器 → 异常信封（:8013-8023）。

鉴权现状：sessionRequired 第一句就是 if (!authEnabled) return false（api.ts:265），而两个组合层都把 authEnabled 设为 false
⇒ **本机任何进程都能调全部业务接口**。密码存储是合格的（scryptSync + 16 字节盐，api.ts:2249-2268）。
WebServer 没有任何 headers/request/keepAlive 超时设置（子智能体 grep 命中 0 条）。

### Q4 数据库是什么

**没有数据库。** 27 个根级 JSON（store.ts:438-509 是唯一权威清单），统一信封 {schemaVersion:1, value}。

写盘质量出乎意料地好（这是本项目最扎实的一处）：临时文件 → fsync → 目录 fsync → rename → **写后逐字回读比对**（store.ts:317-389）；
两道守卫：空值不许覆盖非空（:292-309）、非本实例读过的内容不许覆盖（:337-349，内容 sha256 定案）。
代价：**没有任何锁、没有串行队列**。

实测体量：knowledge.json 3.52 MB（1188 条蒸馏样本，上限 2000）· agent-tasks.json **1.69 MB 只有 17 条**（messages 全量保留、无条数上限）
· long-video-tasks.json 495 KB / 12 条 · publish-records.json 81 KB / 36 条。
二进制目录：platform-login/ **1.42 GB** · uploads/ 233 MB · long-video/ 148 MB。数据根合计约 1.96 GB / 4,842 文件。

**197 条，24 个分组。** 前 8 大组：v2/channels 33 · ai 24 · v2/customer-reception 19 · knowledge 18 · contents 17 · agent 16 · long-videos 12 · v2/statistics 11。
另有 4 条「显式不可用」占位（routes-content.ts:887-904）——这是诚实设计，不是缺陷。
历史基线 qa/golden/routes-master.txt 记 155 条（2026-09-02），已过期。
完整 197 条 method+path+行号清单已由子智能体导出（本轮会话记录可查）。

### Q6 AI 调用链在哪里

**产品代码里 0 处直连大模型**（有明文规范禁止，docs/过程档案/方案与路线/DSH内核统一执行方案.md:77）。

    前端 → POST /agent/tasks（SSE）
       → api.ts:2694 streamLlmWithDeltas（全产品 12 个 LLM 调用点汇聚到这一个函数）
          → kernel-client.ts:437 HarnessClient（官方 SDK，起内核子进程）
             → kernel 子进程 ctx.llm.stream（kernel/src/index.ts:603，唯一的真实发起点）
                → DSH 基座 llm-pi-ai 能力面 → 出网（Agnes AI / 自定义 baseURL）

- 12 个调用点：自进化复盘 ×3、历史补课、对象级动作、助手对话（唯一允许工具）、技能升格、ai/chat 旧路径、
  图文/短视频文案、长视频写稿、分镜/增强、客服建议。
- 超时 **240 秒**（kernel-client.ts:492）；会话池上限 **4** 个内核进程，LRU（api.ts:1768）。
- Prompt 三层：稳定语境（$DSH_HOME/AGENTS.md，实测 22,982 字节，含 243 行 AGENT_RULES）+ 每轮上下文（记忆 + 知识块）+ 任务前缀；
  Few-shot = 质量语境（最多 2 条成功样本）。
- 所有上下文都有硬上限（知识块 1200 字 / 记忆 2200 字 / 对话历史 12000 字 / 单条 ≤400 字），**但截断是静默的**。
- 媒体是另一条独立通道（ctx.media → media-pi-ai），文本挂了不影响媒体，反之亦然。

### Q7 RAG 在哪里

**没有真 RAG。** 这是最容易「被 AI 装懂」的一处，必须说清：

- 存储：单个 knowledge.json，纯文本笔记 + 蒸馏账本。**不是向量库**。
- 检索：extractTokens（中文按 **2 字滑窗**，knowledge-distill.ts:223-224）→ scorePassage
  （title.includes(token) +2、body.includes(token) +1，**纯子串包含**，:253）→ 取 Top3（MIN_SCORE=3）。
- 全仓 embedding | 向量 | vector 在 server/src 与 kernel/src **0 命中**；文档自证「不用向量库」
  并把「加一路向量检索」列为未做的作业（docs/协作/AI深度学习方案与学习计划.md:20/98/214）。
- 所以：没有 embedding、没有向量库、没有 rerank、没有混合检索。术语上这是「关键词打分 + 片段拼接」。
- 附带发现：**「AI 客服」正常路径根本不经过大模型**。接待引擎只做关键词规则匹配 + 登记待办
  （reception-engine.ts 全文无 LLM 调用）；replyMode==='ai' 只标记 aiUsed:true 不生成文本（reception-rules.ts:69）。
  AI 只用于「建议草稿」接口（routes-content.ts:1096），且不发送。

### Q8 Agent 在哪里

- **循环不在产品代码里**，在 DSH 基座：packages/core/agent-loop/src/agent.ts:269 turn() → :286 while(true)。
- **未找到轮数上限**（constants.ts:6 只有并行工具数 10）。产品侧只给 240 秒墙钟与「一个任务一个内核会话」。
- 产品侧角色是驱动器：每 50 ms 轮询 SDK 通知直到 idle（kernel-client.ts:493-529）。
- **17 个 bosom_* 工具**（文档里写「5 个」「10 个」，都已过时）：
  只读：kernel_ping · platform_list_accounts · reception_list_pending · material_list · data_dashboard ·
  platform_login_status · platform_sync_works · content_list_drafts · job_list · content_video_status；
  执行：content_generate_script（唯一带 LLM）· publish_content（只登记不执行）· content_update_draft ·
  content_create_draft · content_create_video · content_resume_video · learn_from_history。
- 工具面收敛（kernel/cordis.patch.yml:76-123）：pwsh / fs / fs-search / subagent×4 / workflow / ralph / jobs / goal / todo /
  plan-mode 全部 disabled: true；BF_TEXT_ONLY=1 时整个业务插件禁用，模型看不到任何工具。
- 「发布/建草稿/改草稿」三个动作只由前端动作卡执行（action.handlers.ts，7 类处理器；跟随模式自动执行集合

### Q11 哪些地方存在技术债

按「会不会真的伤人」排序：

1. **文档与代码系统性漂移**：工具数（注释写 5/10，实际 17）· platform-catalog.ts:30 指向**不存在的文件**
   （bilibili_uploader/login.py，只剩 .pyc 残骸）· ENGINE_PLATFORM 是空表死代码（platform-login.ts:20-21）·
   store/README.md 列了一个不存在的 configManagerDialog.ts · api.ts 行数在两处文档里都不一样。
2. **前端不在类型检查内**（DEF-140，71 条类型错误）。

### Q12 哪些地方最容易产生重复 Bug

用台账 229 条 + git 热点做实证，四个模式最突出：

1. **同一份契约在多处各写一遍，然后漂移**：DEF-142（更新清单契约在主进程 / global.d.ts / 设置页各一份，
   导致「打开下载页」永远是灰的）· DEF-139（请求层与按钮对返回信封的理解不一致，按钮**从来没成功过**）·
   DEF-153（平台内容上限在元数据与提示词里两个数字）· DEF-140（三处契约漂移）。
2. **跨越「前端轮询」这一动作的耦合**：DEF-184（登录其实成功了，但前端收到报错后停止轮询，账号没落库，
   用户看到「授权失败」）。状态机终态依赖前端还在不在轮询。
3. **AI 的输出被当成结构化字段直接写回**：DEF-159（模型说「我理解这是纯文本任务…」被写进配图建议）·
   DEF-155（对话回复被写成草稿标题，接口还回 code=0 像成功）· DEF-151（接口报「模型没给出可用内容」，而模型其实答了）。

   ⇒ 几乎每个升格技能都被静默丢弃，界面却显示「已升格」）· DEF-141（技能名被提示词脚手架污染）。

### Q14 哪些地方存在安全风险

按可利用性排序（前 6 条有明确证据）：

1. **远程隧道命令 = 任意命令执行**：remote-access.ts:258-265 把用户配置的字符串 replace({port}) 后
   spawn(line, { shell: true })；而配置接口 POST remote-access（api.ts:7926）只受令牌保护。
   远程模式下拿到令牌 = 能执行任意 shell 命令。
2. **令牌经 URL 查询串传递 + 明文落盘**（remote-access.ts:158-159、api.ts:7901/8066）⇒ 历史/代理日志/Referer 泄漏面。
3. **明文凭据五处**（见 0.3）。
4. **本机无鉴权**（authEnabled=false）⇒ 任何本机进程可调用全部 197 个接口。
5. **Electron 主进程硬编码长期 JWT**（backendBase.ts:20-23，含真实邮箱）；另 dsh-agent.ts:53-58 手工拼引号 + shell:true。
6. **SSRF**：POST ai/models/fetch 用用户给的 baseUrl（只校验 ^https?://）直接 fetch 并带上 Key（api.ts:3565-3586）
   ⇒ 可对内网任意主机/端口发起带凭据请求。
7. security.json 的 loopback 字段硬编码 true ⇒ **安全自检报告会说谎**（security.ts:160）。
8. 未加固但未证明可利用：ai/reference/fourview 是唯一没走净化器的本地文件读取点（api.ts:7055-7058）——
   被 split('/').pop() 间接挡住，属「未加固」而非「可利用」。

**做得对的地方（不要误判为脆弱）**：路径穿越在素材链路已加固（safeUploadPath routes-content.ts:200-216、
localAssetFile api.ts:4933-4959、SPA 前缀校验 http.ts:227-234）；令牌恒定时间比较（http.ts:91-97）；
CORS 只反射回环来源（http.ts:109-120）；密码 scrypt 加盐；备份排除密钥文件；空值覆盖守卫。

### Q15 从 100 人增加到 1 万人，哪里首先会崩

**这个问题在当前架构下问错了对象**——它是单机桌面应用，没有共享服务端。
「1 万用户」= 1 万台各自装 827MB 安装包的电脑，各跑各的。崩溃点不在服务器，在**每个用户自己的机器 + 上游配额**：

1. **上游视频额度最先生效（硬墙）**：VIDEO_FREE_TIER_RPM = 1、VIDEO_DAILY_QUOTA_SECONDS = 500
   （video-duration.ts:51/60）。一条 300 秒长片 = **75 个 4 秒片段**（CLIP_SECONDS=4），单片段延迟 35–250 秒（:68-70）。
   按 RPM=1 算，出完一条长片的理论下限就是 **75 分钟**——这是与用户规模无关的绝对瓶颈，先于任何服务器问题出现。
2. **用户机器本地资源**：真实 Chrome（每平台每账号一个会话）+ Python + Node（堆上限 4096MB）+ ffmpeg 转码同时跑。
3. **长片耗时体感**：MEDIA_COMPOSE_OVERHEAD_MS = 5 分钟合成 + 逐镜串行（long-video.ts:1516-1521）；
   实测 12 个长视频任务 7 成功 5 失败（**成功率 58%**）。
4. **数据层随使用变慢**：全量 JSON 读改写，每次保存都「序列化 + fsync + 回读全文再算 sha256」；
   knowledge.json 已 3.52 MB / 1188 条（上限 2000），agent-tasks.json 1.69 MB / 仅 17 条且无上限。
5. **若真要做成 SaaS（1 万人共用一套服务）**：当前架构**不支持**，缺的不是性能而是地基——
   无多租户、无鉴权、无数据库、无任务队列、数据在单机文件系统、引擎依赖用户本机的真实 Chrome 与登录态。

### Q16 如果 LLM API 挂掉，系统哪里会跟着挂

- **会挂**（12 个调用点全部受影响）：内容脚本生成；图文/短视频文案（直接判 failed，不再继续出媒体）；
  长视频写稿（任务 fail）；对象级 AI 动作（报错且**不写回**，空值绝不覆盖）；技能升格；助手对话
  （回「大模型调用失败…」，落 agent_warning，并**不放行发布动作卡**）；自进化复盘（catch { continue }，不影响已交付）。
- **不会挂**：媒体通道独立（文本挂了不影响已配置的出图/出片通道）；分镜排序有确定性兜底（long-video.ts:1435）；
  平台登录/发布/数据同步/看门狗完全不依赖 LLM；**「AI 客服」自动路径不用模型**。
- **未配置 ≠ 挂了**：判据是「地址 + 密钥 + 型号」三样齐全，缺一即视为未配置，会回诚实引导文案
  （unconfiguredReply api.ts:1735、honestFallback :4282）。
- 一处弱点：客服建议失败是 catch {} 静默返回空（routes-content.ts:1122-1123），用户只看到空建议。

### Q17 如果第三方平台限流，会发生什么

- **没有指数退避**。全部手段是固定 sleep + 随机抖动（上传引擎共 95 处 sleep/random）。
- 验证码：抖音判定「验证码输入框 + 获取验证码按钮同时存在」后**暂停一切自动操作等真人**，上限 600 秒，
  超时不重发/不刷新/不重试，直接 Fatal（douyin_uploader/main.py:1547-1596）。实测有 3 条任务停在
  stage = 「等待真人完成短信验证（已暂停自动操作）」，其中一条从 18:53 挂到次日 02:55。
- **发布链路没有自动重试**，只能用户点重试（routes-channels.ts:718）。
- 并发闸门只有两处：同平台登录互斥、同账号发布串行；**互动链路没有闸门**（可并发起多个浏览器任务抢同一账号）。
- 「每账号每天 ≤3 条、互动 ≤20 次、间隔 5–25 分钟」只写在**提示词**里（agent-rules.ts:217），代码不强制。
- 快手/微博/虎扑/小红书上传模块 grep「验证码|captcha|风控|频繁」无命中（未找到处理逻辑）。

### Q18 数据库有没有一致性问题

**有，而且是结构性的**（无外键、无事务、无一致性校验）：

1. **删除级联不完整**：删账号只清 accounts / publish-records / metrics（routes-channels.ts:342-349），
   留下 6 类悬空引用：account-facts、share-tokens、agent-tasks、long-video-tasks、reception-*、session 目录。
2. **先删后写、无快照**：POST v2/data/cleanup（api.ts:5653-5691）按 scope 直接 saveEmpty，**没有任何留快照步骤**
   （对比账号删除走了 backupBeforeDestructive）；api.ts:4104 先清 generations 再清 contents，中途崩溃即留孤儿草稿。
3. **跨进程无锁**：server 与内核共用同一数据根、各自独立缓存，只靠「内容 sha256 守卫」互相拒写 ⇒
   并发时**后写方报错**（不是静默丢数据，但用户看到「操作失败」）。
4. **后端与 Python 引擎写同一个 state.json**：Node 侧是非原子 writeFileSync，Python 侧是 tempfile+replace（不对称）；
   且服务端先 spawn 后写 starting，理论上可覆盖引擎已写的终态（推测，窗口极窄）。
5. **守卫有盲区**：store.ts:337 的丢失更新守卫只在「有基线摘要且文件存在」时生效，
   首次创建或直接 save 自造值的路径没有基线可比。
6. **备份不覆盖大头**：只快照根级 .json，platform-login/（1.42 GB）、uploads/（233 MB）、long-video/（148 MB）都不在内。

## 4. 一句话结论

**这不是「一个做出来了的 AI 教培平台」，而是「一个把 DSH 当运行时、把 Windows 当服务器、把真实浏览器当接口的桌面自动化工具」。**
它的工程纪律（原子写、丢失更新守卫、门禁脚本、缺陷台账、铁律文档）明显高于它的架构水平
（一个 6,843 行的上帝文件 + 27 个全量读写的 JSON + 明文凭据 + 靠前端轮询维持的状态机）。
真正卡住它的不是缺技术，而是三个具体的东西：**图文发布那条参数不匹配、上游 RPM=1 的绝对产能上限、
以及登录/发布/互动三条主链路上没有任何自动化测试。**
