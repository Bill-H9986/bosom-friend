# 平台能力声明核对：platform-catalog.ts ↔ (platform, action, capability)

> 本轮任务：**验证一个假设**，不是找 Bug。
> 假设：`platform-catalog.ts` 的产品能力声明，与实际的 `(platform, action, capability)` 能力模型是否一致。
> 方法：先取证，不改代码。A = 运行时验证，B = 静态代码事实，C = 推测。

## 一、先说清楚 catalog 到底是什么机制（这决定了后面所有判断）

它**不是**一张手工维护的表，而是三样东西的混合体：

| 层 | 来源 | 性质 |
| --- | --- | --- |
| 平台列表 | 扫描引擎 `uploader/*` 目录（`collectEnginePlatforms`，:177） | **自动** |
| 内容类型 | 对 `main.py`/`main_chrome.py` 跑类名正则（:191-194） | **自动，但判据是 uploader 类名** |
| 能力声明 | 五组手工数组：`ENGINE_LOGIN_PLATFORMS` / `ENGINE_PUBLISH_PLATFORMS` / `DATA_CAPABLE` / `ENGINE_PRESENT_BUT_NOT_READY` / `PRODUCT_CHANNEL_PLATFORMS` | **手工** |
| 编辑器类型 | `preset.platform === 'xhs' ? 'text' : 'normal'`（:206） | **硬编码** |

**关键**：内容类型的判据（uploader 里的类名）与真实能力（sau_cli 的 action 注册）**是两套独立判据**。

## 二、五个维度的核对结果

### 维度 1：平台枚举是否一致 → **一致（有意的抽象）**

| 层 | 数量 | 内容 |
| --- | --- | --- |
| 引擎 uploader 目录 | 13 | alipay / baijiahao / bilibili / douyin / hupu / ks / tencent / **tk** / weibo / xhs / xianyu / xiaohongshu / **youtube** |
| catalog 登记（PLATFORM_KEYS + PLANNED） | 10 | 上面去掉 tk / youtube，xhs 两个目录去重 |
| catalog 对外返回 | 10 | 9 个 channel=true + xianyu(channel=false, coming_soon) |
| sau_cli.py 注册 | 10 | douyin / kuaishou / xiaohongshu / bilibili / tencent / alipay / weibo / hupu / youtube / baijiahao |

- tk / youtube 被 `PLATFORM_KEYS` 有意跳过，注释写明「产品只做国内平台」（:100-101）→ **有意的抽象**
- xianyu 引擎有目录、产品标 coming_soon（:122）→ **有意的设计**，且如实置灰
- **结论：平台枚举在产品范围内自洽，差异都有人为声明和注释。**

### 维度 2：内容类型粒度是否一致 → **部分一致（互动能力完全缺失）**

catalog 的 `PlatformCatalogItem.publish: Array<'video' | 'image_text'>`（:78）**确实有内容类型粒度**，
而且经 `routes-channels.ts:81` 的 `contentLimits.modes` **一路传到了前端**，前端**真的在用**：

```js
// store/platformMetadata/utils.ts:259-280  derivePubTypes()
const modes = item.contentLimits.modes
if (item.capabilities.publish.supported === false) return pubTypes   // 不支持 → 空
if (!modes) { VIDEO + ImageText + Article }                          // 无 modes → 全支持
for (const mode of modes) pubTypes.add(getPubTypeFromContentMode(mode))
```

`pubTypes` 的消费点至少 14 处（`usePublishDialog.ts:492/496`、`CreateMaterialModal`、`platformCompatibility.ts:125/217` 等）——**粒度是活的，不是装饰**。

**但**：`capabilities` 的另外五个槽位在**所有平台**上都是空的：

```
engagement: {}      // 全部 10 个平台都是 {}
browse: {}   webhook: {}   optionSchema: {}   mediaRules: {}
```

而引擎**实际支持**抖音/小红书的评论与私信（`interactions.py` 实到 `xhs`/`douyin`；`reception-engine.ts:465` 同样限这两个平台）。
→ **能力缺失**：真实存在的互动能力，在能力声明里**没有位置**。

### 维度 3：动作粒度是否一致 → **抽象层级不同（靠约定对齐）**

| catalog 的抽象 | CLI 的抽象 | 对应关系 |
| --- | --- | --- |
| `video` | `upload-video` | 约定 |
| `image_text` | `upload-note` | 约定 |

两者是**隐式映射**：catalog 说「这个平台有图文形态」，CLI 说「这个平台注册了 upload-note 动作」。
**没有任何一处代码把这两个词绑定在一起**——对齐完全靠命名习惯。
→ 这一层差异本身**是有意的抽象**（产品形态 vs 引擎动作），但**缺少机械校验**，所以会漂移（见维度 4）。

### 维度 4：虚假支持 / 隐藏支持 → **1 处虚假支持，0 处隐藏支持**

用 catalog 的同一条正则跑一遍，与 CLI action 注册逐格比对（A 层：走前端监听到的真实响应）：

| 平台 | catalog 声明 modes | CLI 实际 | 判定 |
| --- | --- | --- | --- |
| xhs | video, image_text | upload-video + upload-note | 一致 |
| douyin | video, image_text | upload-video + upload-note | 一致 |
| KWAI | video, image_text | upload-video + upload-note | 一致 |
| **wxSph** | **video, image_text** | **只有 upload-video** | **虚假支持** |
| alipay / baijiahao / bilibili / hupu / weibo | video | upload-video | 一致 |
| xianyu | video, image_text | （无 CLI 注册） | 数据不自洽 |

**wxSph（视频号）虚假支持的完整链路（B 层静态 + A 层接口实测）**：

```
tencent_uploader/main.py 里存在 *Note / *Image 类
  → catalog 正则命中 → publish 含 'image_text'
    → routes-channels.ts:81 → modes = ['video','image_text']
      → 前端 derivePubTypes → pubTypes = {VIDEO, ImageText}   ← A 层：接口响应确认
        → 用户被允许选「视频号 + 图文」
          → worker.py:706  action = 'upload-note'
            → sau_cli.py tencent 没有 upload-note
              → argparse: invalid choice: 'upload-note'      ← 比 --declaration 崩得更早
```

**xianyu 的数据不自洽（另一类问题）**：
- `ch.publish = []`（不在 ENGINE_PUBLISH_PLATFORMS）
- `routes-channels.ts:81` 的兜底写成 `ch.publish.length > 0 ? ch.publish : ['video','image_text']`
- → 一个**明确不可用**的平台拿到了 `modes = ['video','image_text']`
- 只是前端 `derivePubTypes` 第一句就判 `supported === false` 返回空，**恰好掩盖**了矛盾
→ **事实漂移**：两个字段来自不同判据，表达互相矛盾。

### 维度 5：能不能机械生成？→ **现在两者都不是**

| 问题 | 答案 |
| --- | --- |
| 它是「事实来源」吗？ | **不是**。三个能力判据（平台级发布能力 / uploader 类名 / CLI action）各自独立，互不校验 |
| 它是「底层能力自动生成的产品视图」吗？ | **只是半个**。平台列表是扫出来的，但能力是五组手工数组 |
| 内容类型扫描有意义吗？ | **有，而且它是 wxSph 虚假支持的直接来源**。`publish` 数组被两处使用：`length > 0` → `supported`（:95），以及**整体作为 `modes` 传给前端**（:81）。**两个字段判据不同**：`supported` 由手工数组 `ENGINE_PUBLISH_PLATFORMS` 决定，`modes` 由 uploader 类名扫描决定——所以它们可以互相矛盾 |

→ 它是「**目录扫描 + 类名正则 + 五组手工数组**」的混合体，**且三套判据之间没有交叉校验**。
wxSph 的虚假支持正是这个结构的必然产物：**没有任何一步在问「CLI 到底注册了哪些 action」**。

**两个字段，两套判据（这是本轮的机械结论）**：

| 字段 | 判据 | 类型 |
| --- | --- | --- |
| `capabilities.publish.supported` | `ENGINE_PUBLISH_PLATFORMS.includes(platform)`（手工数组，平台级） | boolean |
| `contentLimits.modes` | `uploader/main.py` 的类名正则（自动扫描，形态级） | 数组 |

两者可以互相矛盾，**xianyu 就是现成例子**：`supported=false` 但 `modes=['video','image_text']`。
目前只是靠前端 `derivePubTypes` 先判 `supported` 才没有暴露出来。

## 三、不一致的分类（本轮专门训练的部分）

| # | 现象 | 分类 | 依据 |
| --- | --- | --- | --- |
| 1 | tk / youtube 目录被跳过 | **有意的抽象** | 注释明写「产品只做国内平台」 |
| 2 | xianyu 报 coming_soon、channel=false | **有意的设计** | 注释明写原因，且前端置灰 |
| 3 | **wxSph 声明 image_text 但 CLI 无 upload-note** | **能力缺失**（目录高估引擎） | 三套判据无交叉校验 |
| 4 | xianyu 的 modes 与 publish.supported 互相矛盾 | **事实漂移** | 两字段来源不同（扫描兜底 vs 手工数组） |
| 5 | engagement 全平台为空，而抖音/小红书实际支持互动 | **能力缺失** | 无对应声明槽位 |
| 6 | `editor` 硬编码 `platform === 'xhs'` | **事实漂移风险** | 当前正确，但靠单点硬编码维持 |
| 7 | video/image_text ↔ upload-video/upload-note 靠约定 | **有意的抽象**（缺校验） | 产品形态与引擎动作本就不同层 |

**没有发现「产品状态错误」这一类**——xianyu 的置灰、bilibili 的 coming_soon 处理都是正确的。

## 四、结论：这张表应该是什么

按当前证据，`platform-catalog.ts` **既不该当事实来源，也不该继续手工维护**。它应该是：

> **由底层能力（CLI action 注册表）机械生成的产品视图，叠加一层显式的产品决策（渠道开放、置灰、编辑器类型）。**

具体说，能力那半张表应该来自**解析 `sau_cli.py` 的 parser 树**（本轮已证明可行：`analysis/_contract/extract3.py` 用 ast 提出 33 个 (平台, 动作) 的参数集），
而不是扫描 uploader 的类名。产品决策（channel / status / editor / 内容上限）继续手工声明，但**必须与生成的能力对账**。

## 五、证据等级声明

- **A 层（运行时验证）**：走前端页面监听 `v2/channels/platforms` 的真实响应，拿到 10 个平台的 `modes` / `publish.supported` / `analytics` / `engagement`。wxSph 的 `modes=['video','image_text']` 与 `engagement={}` 都是**接口实测**。
- **B 层（静态代码事实）**：catalog 的扫描与合成逻辑（逐行照抄复现）、`sau_cli.py` 的 parser 参数集（ast 提取）、worker 的下发规则。
- **C 层（推测）**：wxSph 虚假支持的**用户可见后果**（会走到 `sau tencent upload-note` 报 invalid choice）——链路是静态推导的，**没有实际发过一次视频号图文**（账号库只有 1 个抖音账号）。
- 未验证：`tencent_uploader` 里那个被正则命中的 `*Note`/`*Image` 类**是否真能工作**（可能只是残留代码，也可能确实实现了图文发布但没接进 CLI）。这一点会改变「能力缺失」还是「只是没接线」的定性。

# 追加核验：`TencentNote` 到底是什么性质（2026-10-08 第二轮）

## 一、先接受一个挑战：我把「根因」和「用户可见错误」混为一谈了

上一轮我写「产品状态错误 = 0 处」。这个判断**不成立**，因为我把两个层级压成了一层：

```
根因层    ：能力缺失（catalog 的判据是类名，不是实现）
表现层    ：能力声明错误（产品告诉用户「视频号 + 图文」可用）
影响层    ：用户可选路径 ⊄ 真实可执行路径
```

用户看到的不是「能力缺失」这四个字，而是**一个能点、点完报错的选项**。
所以分类表要改成：**根因 4 类 + 表现 1 类**，`wxSph` 在根因上是「能力缺失」，在表现上是「能力声明错误」。

这和你早先指出的 `security.json` 那件事是同一个结构：**每层局部都有理由，跨层组合后的事实是假的**。

## 二、六条核验（逐条给证据）

### 1. 类是不是实际实现 → **不是。骨架，三个核心方法抛 NotImplementedError**

`tencent_uploader/main.py` 只有 3 个类：`TencentBaseUploader`(:501)、`TencentVideo`(:948)、`TencentNote`(:1155)。

`TencentNote` 的构成：

| 部分 | 状态 | 位置 |
| --- | --- | --- |
| `__init__` 参数接收 | 完整 | :1156-1180 |
| `validate_upload_args`（校验标题/图片） | 完整 | :1182-1195 |
| **`switch_to_note_mode`** | **`raise NotImplementedError`** | **:1197-1198** |
| **`upload_note_images`** | **`raise NotImplementedError`** | **:1200-1201** |
| **`fill_note_title_and_tags`** | **`raise NotImplementedError`** | **:1203-1204** |
| `fill_note_body` | 空实现（`return None`） | :1206-1207 |
| 流程串联 `prepare_note_for_publish` / `upload_note_content` | 完整 | :1209-1218 |
| `upload()` / `main()` | 完整 | :1220-1252 |

三条异常消息的原文就是「**请补充**视频号切换到图文发布模式的逻辑」「请补充视频号图文图片上传逻辑」
「请补充视频号图文标题/话题填写逻辑」——这是**写给未来实现者的骨架占位**，不是废弃标记。

对照 `TencentVideo`：它有 `open_thumbnail_dialog` / `set_thumbnail` / `prepare_video_for_publish` /
`handle_upload_error` 等**具体实现**（:1003-1114），**没有一条 NotImplementedError**。

### 2. 有没有被实例化 → **没有，全局 0 处**

用 Select-String 全量扫 `engine/` 与 `sau_cli.py`（绕过 ripgrep 的忽略规则）：

```
sau_cli.py:42    TencentVideo,                        ← 只导入了 Video
sau_cli.py:605   app = TencentVideo(                  ← 只实例化了 Video
__init__.py:10   from ...main import TencentNote      ← Note 只被导出
__init__.py:23   "TencentNote",                       ← 进了 __all__
```

**`TencentNote` 被 `__init__.py` 导出、进了 `__all__`，但没有任何一处导入它、实例化它、调用它。**
`TencentVideo` 则是完整的 import → instantiate → call。

### 3. CLI 有没有入口 → **没有**

`sau_cli.py` 的 tencent 段只有 `upload-video`（parser 枚举，ast 提取：13 个参数）。
没有 `upload-note`，也没有任何其它图文入口。

### 4. action 参数契约 → **链路在第一步就断**

```
input.json (type=ImageText)
  → worker.py:706   action = 'upload-note'
    → sau_cli.py tencent parser  → ✗ 没有这个 action（invalid choice）
      → （即使有）TencentNote    → ✗ 未导入、未实例化
        → （即使实例化）switch_to_note_mode → ✗ NotImplementedError
```

**三处断点叠加**，而不是一处。

### 5. 真实运行证据 → **没有，且不可能有**

`publish-records.json` 36 条记录**全部是 douyin**（账号库只有 1 个抖音账号），
`platform-login/publish/` 69 个任务目录的 `input.json` 里 `platform` **全部是 douyin**。
**视频号从未有过任何一次发布尝试**——所以既没有成功证据，也没有失败证据。

### 6. 是不是平台残留 → **是上游骨架，且本项目从未使用过它**

- `engine/.gitignore:4` 把 `social-auto-upload/` 整个排除 → **vendored 代码不入 git**
- `git log` 对该文件**为空**，`git ls-files` 报 **not known to git** → **无法用 git 历史考古**
- `VENDORED.md` 记录本项目改过 `tencent_uploader/main.py`，但**补丁只在 :390/:396（登录函数）**，
  没有触碰 `TencentNote`（:1155+）
- → **C 层推断**：`TencentNote` 是上游 `social-auto-upload` 自带的未实现骨架

## 四、最终判定

按你给的四个选项，它**都不是**，而是第五种：

| 你的选项 | 是否符合 | 原因 |
| --- | --- | --- |
| 残留代码 | ✗ | 残留意味着「曾经能用、现在废弃」；它**从未可用** |
| 真实实现但未接 CLI | ✗ | 实现本身也不完整（3 个 NotImplementedError） |
| 实现存在且 CLI 有其他入口 | ✗ | 没有任何入口 |
| 实现完整且可运行 | ✗ | 不成立 |
| **骨架级未实现 + 双重未接线** | **✓** | 类在、校验在、流程在，**平台交互没写、CLI 没接** |

**结论一句话**：

> `TencentNote` 是上游带来的**未实现骨架**。catalog 用 `/class\s+\w*Note/` 正则推断能力，
> **无法区分「骨架」与「实现」**，于是把「有个类叫 Note」当成了「支持图文」。

## 六、本轮暴露的一个方法论问题（必须报告）

**我的 grep 工具在 vendored 目录上会静默返回 0 命中。**

对照实验（同一模式 `TencentVideo`）：

| 方式 | 结果 |
| --- | --- |
| grep，`path = products/bosom-friend/engine`（目录） | **0 命中** |
| grep，`path = .../sau_cli.py`（单文件） | 5 命中 |
| Select-String，单文件 | 5 命中 |

**影响面（精确限定）**：
- 受影响：任何**以 `engine/` 或其子目录为 path** 的 grep 结论——例如「engine 下无 test 文件」
  「grep 验证码/captcha 无命中」「grep sk-/api_key 0 命中」。**这些结论不可信，需要重做。**
- 不受影响：以**具体文件**为 path 的 grep（如 `worker.py`、`sau_cli.py` 单文件）——已验证有效；
  以及用 Python `ast` 直接读文件得到的结论（本轮的矩阵、parser 枚举都不受影响）。
- `engine/worker.py`、`engine/interactions.py` 在 `engine/` **根目录**，不在 gitignore 范围内，相关结论仍然有效。
