# 消息链路归位 DSH 会话投影（2026-09-29 立项）

> 起因：2026-09-29 现场「对话框没有内容」——AI 回复已落库、界面却只剩用户那一句。
> 定位结论：**不是 DSH 内核的问题，是产品在核之外又手写了一套消息投影层**，那层有三个状态机缺陷。
> 本文是替换方案（合项目铁律 #0：能力先于功能、没有 Definition 不许在业务里拉直连）。

## 一、现状：产品自建了一条平行链路

| 环节 | 产品现在的做法 | DSH 官方已有的能力 |
| --- | --- | --- |
| 会话事件 | `server/src/api.ts` 自定义 `task.messages.push({ type: 'user' \| 'stream_event' \| 'assistant' \| 'result' })` | `packages/core/session`、`packages/session/session-format`（含 v0→v1→v2→v3 迁移） |
| 消息投影 | 前端 `components/Chat/utils/convertMessages.ts` 自己解析自建格式 | `packages/session/session-projection`（快照 + 变更通知，schema 校验）、`session-turn-outline`（轮次大纲） |
| 前端状态 | zustand `taskMessages[taskId]` **与** 页面本地 `localMessages` **两份**，再叠一套轮询 | 订阅投影快照即可，无需自建缓存与轮询 |
| 工具调用呈现 | 前端自己按 `stream_event` 拼步骤 | `packages/core/agent-tool-presentation`（`generic`/`terminal`/`diff` + locations） |

## 二、三个缺陷（均已修复，但说明这层的脆弱性）

1. `useChatState.ts`：`isActiveTask` 为真时无条件用**空的** store 消息，丢掉接口刚拉回的数据 → 详情页空白。
2. `useChatState.ts`：轮询与缓存耦合 `if (!hasCachedMessages) { ... startPolling() }` → 从右侧面板发起的会话（store 里已有用户消息 = 命中缓存）**永不轮询** → AI 回复永远不出现（现场表现就是「只有我说的话」）。
3. `page.tsx`：`if (isLoading && !isActiveTask)` → 活跃任务加载期连骨架屏都不显示。

## 三、选型：为什么**不**引入第三方

| 候选 | 结论 |
| --- | --- |
| Vercel AI SDK `useChat` | ✗ 它要求把服务端协议改成 AI SDK 的 streaming 协议；换完仍然是**一条与内核会话日志脱钩的平行链路**，违反「Model-visible ⟺ logged」（模型看得见的东西必须能从会话日志重建） |
| assistant-ui / CopilotKit | ✗ 只是渲染层组件库，解决不了"消息从哪来"的状态机问题；引入后仍要自己写投影 |
| **DSH `session-projection` + `session-turn-outline` + `core/session`** | ✅ **正解**：自家基座的成熟能力，快照 + 变更通知，schema 校验；且天然满足"日志是唯一事实源" |

依据：铁律 #0 第 1 条（能力缝三角色：Definition → Provider → Consumer）、第 2 条（不许在业务里拉直连）；
以及 DSH 仓库约定「Model-visible ⟺ logged」。

## 四、替换设计（三步，可增量）

### 第 1 步：服务端改为透传会话事件与投影（不动界面）
- `server/src/api.ts`：把自建 `task.messages` 的自定义事件，改为**投影自 `ctx.session` 的会话事件**；
  新增投影单元（`sessionProjections` 注册）：`turnOutline`（轮次大纲：user / assistant / 工具步骤）。
- 保持现有 REST 路径不变，前端仍能跑（**可单独发布、可回滚**）。

### 第 2 步：前端消费投影（去掉自建状态机）
- 删除 `convertMessages.ts` 的自建解析；`useChatState` 改为订阅投影快照 + 变更通知。
- **删掉本地 `localMessages` 与轮询**（两份状态 + 轮询正是缺陷 1/2 的土壤）。
- 工具步骤直接用 `agent-tool-presentation` 的意图字段渲染。

### 第 3 步：补门禁（防复发）
- 结构断言：前端不得再出现"自建消息类型解析"（禁止 `msg.type === 'assistant'` 这类本地判别）；
- 端到端断言：发起会话 → 页面在**任意时刻**都能看到用户消息或明确的生成中状态（不允许空白），
  且 AI 回复出现时间与服务端投影一致。
- 落进 `qa/verify-publish-pipeline.mjs` 同族的 `qa/verify-chat-projection.mjs`，并接入 `run-gate.mjs`。

## 五、风险与验收

- **风险**：第 2 步会动到对话主链路（用户可见核心功能）→ 必须每步单独验证、可回滚（铁律 #12 开发期 Web 迭代，不打包）。
- **验收**（S 级前端监考，只操作页面）：① 新会话从发起到完成，中间区域**任何时刻不空白**；
  ② 刷新页面后 AI 回复与评分/收藏状态完整；③ 工具步骤、发布动作卡齐全；
  ④ `node qa/verify-chat-projection.mjs` 全绿。
- **不做的**：不引入任何第三方聊天状态库；不新增与内核日志平行的第二份事实源。
