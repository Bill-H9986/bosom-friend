## 0. 一页结论

用户的分工判断成立，而且比"前端像飞书、后端像豆包"更精确：

| 一侧 | 它真正的价值 | 本产品的对应物 |
| --- | --- | --- |
| 飞书 | **对象自带结构与入口**：文档/表格/多维表格记录本身就是 AI 的入口与上下文，权限即上下文边界 | 前端（`bosom-friend-web` + `bosom-friend-electron`）：草稿、账号、发布记录、素材、待接待、知识笔记 |
| 豆包工作 | **围绕目标自主推进**：拆解 → 调用工具 → 落回现场；一次指令串联多个应用 | 后端 DSH 内核（`bundle/kernel` + `kernel/` 插件）：会话、上下文通道、工具 |

三条乘法（ADR-004 §1.2）：**对象即上下文** · **对象即 AI 入口** · **执行结果回流成更厚的上下文**。
本方案的每一步都对应其中一条，并按"这一条能不能被证伪"写判据。

## 1. 本轮实证：内核会话的真实面貌（探针可复现）

`qa/probes/probe-agent-instructions.mjs` 用官方模拟模型服务器 + 真实内核进程，
把**模型实际收到的那一份请求体**抓下来（这之前没人看过它）。

### 1.1 收敛前，模型的处境

| 项 | 实测 | 问题 |
| --- | --- | --- |
| 工具 | **35 个**：10 个 `bosom_*` 业务工具 + **25 个编码智能体工具**（`pwsh`/`read`/`write`/`edit`/`glob`/`grep`/`subagent`/`workflow`/`ralph`/`goal`/`jobs`/`todo`…） | 面向普通用户的桌面 APP，模型可以在客户的 Windows 上执行命令、读写任意文件、派生更多智能体。既不是能力也不是卖点，是风险 |
| 系统提示词 | DSH 默认人设，**不含任何产品身份** | 模型不知道自己是谁、在给谁干活 |
| 规则文本 | `agent-rules.ts` 第四条写着"**你只拥有只读工具**" | 与实际给的 `pwsh` **直接矛盾**：规则说不能动手，工具说随便动手 |
| 稳定语境 | `$DSH_HOME/AGENTS.md` 通道**可用**，但项目链把**仓库根的 `AGENTS.md`**（DeepSeek Harness 自己的开发说明）也注入了 | 模型被教"改 packages/ 之前先读 docs/architecture.md"——对内容营销 APP 是纯噪声 |

### 1.2 两个把诊断带偏过的坑（写下来省下一次）

1. **`HarnessClient` 没有 `command`/`args` 选项**。传了会被静默忽略，实际启起来的是通用 `sdk` profile——
   你会看到一个"没有产品工具、全是编码工具"的假内核，并据此得出错误结论。
   产品的启动契约是 **`dshBin` + `profile: 'bosom-friend-kernel'` + `processCwd`**（见 `server/src/kernel-client.ts`）。
2. **`launcher/lib/bin-kernel.mjs` 是坏入口**。它的配置目录（`launcher/config/`）没有完整插件闭包，
   实测以 `ERR_MODULE_NOT_FOUND` 掉一大片插件（`dsh-tool-subagent`、`dsh-workflow-worker-thread`…）。
   权威入口是 `bundle/kernel/runtime/bin-kernel.mjs`。`launcher/scripts/smoke-kernel-*.mjs` 仍在用坏入口，
   它们"通过"不代表产品内核可用。

### 1.3 注入副本的新鲜度（运维事实）

`node_modules/.pnpm/@deepseek-ai+dsh-bosom-friend-kernel/cordis.patch.yml` 是 pnpm 从工作区**注入的副本**。
实测：改完源码 `pnpm install` 报 "Already up to date" 且**不刷新副本**，`--force` 同样不刷新。
可行做法是删掉注入目录后重装，或按 `files` 字段重建副本；`desktop/verify-kernel-bundle-freshness.mjs` 就是为这条而存在的门禁。
**改内核补丁后必须验证副本内容，不能只看源码。**

## 3. 本轮已落地（带判据）

### 3.1 内核工具面收敛 + 产品语境通道（`kernel/cordis.patch.yml`）

- 覆盖 `agent-instructions` 行：项目链候选名改为产品专属的 `BOSOM.md`，
  **仓库 `AGENTS.md`/`CLAUDE.md` 不再可能进入产品会话**；用户全局 `$DSH_HOME/AGENTS.md` 通道照常（`USER_GLOBAL_FILE` 是固定常量）。
- 关掉 14 行编码智能体工具/服务：`tool-pwsh`、`tool-fs`、`tool-fs-search`、`tool-subagent`、`tool-subagent-fork`、
  `tool-subagent-list-agents`、`tool-subagent-control`、`tool-workflow`、`tool-ralph`、`tool-jobs`、
  `tool-goal`、`command-goal`、`tool-todo`、`plan-mode`。

判据（探针）：模型收到的工具只剩 `bosom_*` 与语境类工具；系统提示词里不再出现仓库开发说明。

### 3.2 稳定语境落盘（`server/src/agent-context.ts`）

- **约束语境**（标题 30 字、每镜 4~12 秒、每天 ≤3 条、间隔 5~25 分钟…）与
  **历史语境**（这台机器上真实的失败原文 + 反复踩过的坑）写进 `$DSH_HOME/AGENTS.md` 的自动区块。
- 区块外是用户的地盘：合并语义保证**手写内容逐字保留**，自动区块替换而不堆叠。
- 触发时机：助手对话**冷启动之前**（内核只在会话建立时读一次指令文件）。
- 判据：`server/test/functional/agent-context.spec.ts` 11 条（约束含产品数字 / 失败原文进块 / 空失败不留空标题 /
  两次合并完全一致 / 事实变了替换不追加 / 用户文字保留 / 内容没变不落盘）。

### 3.3 焦点对象进上下文（S1 的两侧都在了）

- **服务端**：`POST agent/tasks` 接受 `focus`；`parseAgentFocus` 校验字段（非字符串按空串、摘要截 600 字），
  `buildFocusContext` 渲染成每轮上下文块。**每轮都送**而不是写进指令文件——焦点每轮在变，
  而指令文件只在会话建立时读一次；这条界线不能混。
- **前端**：新增 `utils/agentFocus.ts`（登记当前对象 + 路由兜底），
  发送链路 `createTask`/`continueTask` 自动带上焦点（面板、首页、语音入口共用同一条链路），
  **草稿详情弹窗**是第一个登记方（打开即登记、关闭即清空）。
- 判据：`agent-focus-context.spec.ts` 7 条——带焦点提问时**送进内核的提示词里出现该草稿的标题与摘要**；
  不带焦点时不出现对象块；同一段对话里换了对象，第二轮送的是新的那一条（且仍只送本轮这一句）。

### 3.4 对象自带 AI 动作（S2 的服务端与草稿箱）

- **服务端**：新增 `object-actions.ts`——一条动作规格只说三件事：**改什么字段**、**给模型什么任务**、
  **把输出整理成什么值**；模型调用与落库留在 `api.ts`，因此规格表全是可单测的纯函数。
  两条路由：`GET ai/object-actions?kind=draft`（界面据此渲染按钮，不写死动作）、
  `POST ai/object-action`（跑动作并写回对象）。
- **三条"一个字都不许改"**：动作不认识、对象不存在、模型没给出可用内容——
  最后一条尤其重要：**用空值覆盖用户已有的内容比失败更糟**，所以整理不出内容时直接失败。
- **回流**：每次动作都写进蒸馏账本（`sourceId = object-action-<kind>-<id>-<action>`），
  与助手对话、生成共用同一个"质量语境"池——动作的产出同样会成为下一次的基准。
- **前端**：草稿详情弹窗新增动作按钮行（`data-testid="draft-ai-actions"`），
  点一次 → 结果写回**同一条草稿** → 更新正在看的那一条 + 让列表重新拉一次（两个面板不会各说各话）。
- 判据：`object-actions.spec.ts`（当时 9 条；铺到笔记之后共 15 条，见 §3.8）——落盘标题真的变了、
  只动被点的那个字段、模型爱加的外壳（Markdown 记号/字段前缀/引号）不会一起落库、三种情况都不改数据。

### 3.5 内核写回工具：对话也能改对象（P3.1）

- 新增 `bosom_content_update_draft`（改标题/正文并**直接写回那条草稿**）。在此之前是
  "按钮能写、对话只能读"——对助手说"把这条草稿标题改短"，它只能回一段文本让用户自己复制。
- 校验失败一律**大声拒绝并给出改法**（缺 id / 两项都空 / 标题超 30 字 / 正文超 2000 字 /
  草稿不存在）：模型看到的是工具错误，只能靠这句话自我纠正，静默截断会让它以为写成功了。
- 判据：探针抓到的真实模型请求里出现该工具（**13 → 14 个**）；
  `qa/verify-kernel-tools.mjs` 新增两条断言——**盘上那条草稿的标题真的变了**、
  只传 title 时 desc 不被写空（只断言"execute 不抛错"会让空实现也通过）。

### 3.6 顺带修掉的两个"细节缺陷"

1. **内核自带单测从来没跑过**：`kernel/test/drafts-consistency.test.mjs` 读着数据店里
   **根本不存在**的 `store.files.promotions` / `store.files.materials`（草稿与素材都住在
   `contents` 里，靠 `kind` 区分），每次都以 `TypeError` 结束；而它**不在任何门禁里**，
   于是"删除级联是对的"一直是自说自话。已修正用例并新增门禁检查项 **5k 内核包单测**
   （逐个跑 `kernel/test/*.test.mjs`，任一不过即红灯）。
2. **门禁文案写死数量**：`run-gate.mjs` 的成功文案写着"10 个内核业务工具"、
   `verify-kernel-tools.mjs` 的文件头写着"9 个工具"，实际已经是 11 个业务工具。
   两处都改成不写死数量——**写死的数字必然过期，而过期的文案会让下一个人相信一个假事实**。

## 5. 风险与纪律

1. **内核补丁改了必须重新物化运行时**：开发态走注入副本（见 §1.3），安装版走
   `desktop/rebuild-kernel-and-installer.ps1`。**只改源码不重物化 = 安装版行为与开发态不一致**。
2. **收敛工具面要复验 `qa/verify-kernel-tools.mjs`**：10 个业务工具必须一个不少（收敛的是编码工具，不是业务工具）。
3. **一次只改一条乘法**：P2/P3 动的是前后端两侧，必须能单独回退。
4. **语境文件是用户资产**：任何写入都必须保区块外内容；已用用例锁死。

### 3.21 焦点对象铺到其余对象（S1 的最后一公里）

**已登记对象级焦点**（页面知道"用户此刻在看哪一条"，随每轮请求发给后端）：

| 对象 | 在哪登记 | 登记的内容 |
| --- | --- | --- |
| 草稿 | 草稿详情弹窗 | 页面 / 对象种类 / id / 标题 / 正文摘要 |
| 知识笔记 | 知识库编辑器 | 同上（摘要取正文前 600 字） |
| 账号 | 账号管理页（当前选中账号） | 同上（摘要写平台与粉丝数） |

**页面级实测**（真实界面 + 真实请求体，不是单测）：打开一条笔记 → 在助手问"这条笔记怎么写更好？"→
抓到的请求体是：

```json
{"prompt":"这条笔记怎么写更好？","includePartialMessages":true,
 "focus":{"page":"知识库","objectKind":"笔记","objectId":"欢迎使用 Bosom Friend 知识库.md",
          "title":"欢迎使用 Bosom Friend 知识库","excerpt":"# 欢迎使用 Bosom Friend 知识库…"}}
```

**没有登记的两类（这是边界，不是遗漏）**：**发布记录**与**素材**在界面上**没有"当前对象"这个概念**——
它们是列表/网格，多选才是状态。硬造一个"焦点"（比如最后鼠标划过的卡片）是假的，
只会让助手在用户没选任何东西时凭空收到一个对象。它们真正需要的是**对象级 AI 动作**（记录上的「AI 复盘」、
素材上的「AI 配图建议」），而那条路要先有可写回字段——**等你定字段**。

其余页面只有**路由级焦点**（"用户在哪一页"）：比什么都不说强，也比编一个对象安全。

### 3.20 安装版运行时的陈旧：重建脚本漏同步内核补丁（DEF-146）

**先核实再动手**：磁盘上两棵运行时树里，内核补丁都是 **1243 字节的收敛前版本**（源码 3292 字节）——
也就是说这棵树上的安装版运行时仍然是"把 pwsh/读写文件/subagent 交给模型 + 让本仓库自己的 AGENTS.md 进产品会话"的那一版。

**根因**：`rebuild-kernel-and-installer.ps1` 第 2 步同步了 `lib/` 与**桌面 bundle** 的 `cordis.patch.yml`，
**唯独漏了内核包自己那一份**——而工具面收敛与语境通道恰恰写在那里。两个包长得很像，漏一个看不出来。

**边界要说准（我第一版判断错了，负向对照纠正了我）**：第 4 步的 `verify-runtime-config-drift.mjs`
**确实覆盖**这一层——把运行时那份补丁改脏后门禁判红（`exit=1`），还原后复绿。
所以真实风险**不是"静默发出错包"**，而是"这棵树上的运行时是旧的，只有等到有人跑完整重建才会暴露"。

**修**：第 2 步补上内核补丁同步（与桌面 bundle 同样的候选探测 + BCL 复制 + **落地后逐字比对、不符即抛**），
这样第 4 步不会再因为"漏同步"而中断整条流水线。实测：对真实运行时跑同一段逻辑
（3 个候选里 1 个真实副本，另 2 个是联接点、按脚本逻辑正确跳过）→ 与源码**逐字一致**；
打 zip 用的扁平树一并同步；门禁复绿。

> 一条方法论：**这条缺陷是我"顺手核实"发现的**，不在任何计划里。而它的边界又只有做负向对照才说得准——
> 我第一次写的是"用户会拿到错包"，对照一做，门禁其实守着这一层。**措辞的分量要靠证据定，不能靠直觉。**

### 3.19 把"越用越省"变成可测的

ADR-003 口径四的判据是"第 N 次**可测地**少于第 1 次"。没有度量时这句话只能靠感觉说——
而在这个问题上感觉一文不值（模型快一点慢一点都比"学会了"的影响大）。所以这一轮先把**裁判**立起来：

| 项 | 做法 |
| --- | --- |
| 记什么 | 账本新增三个度量：**`toolCalls`（模型调了几次工具）**、`elapsedMs`、`contextChars` |
| 为什么以轮数为主判据 | 耗时被模型与网络抖动淹没；**轮数反映"要不要反复试错"** |
| 怎么比 | `distillTrend`：只统计**有度量**的样本；"第 1 次"取最早那条；"最近"取最后 N 条的**中位数** |
| 怎么读 | `GET knowledge/distill/trend?task=chat` |

口径写死在 `distillTrend` 的注释里，避免每种用法各算一套；老样本没有度量就**如实缺省**，不拿 0 顶替（补 0 会把结论做假）。

**判据**：`knowledge-distill-trend.spec.ts` 6 条。

> **P5 的诚实边界**：这一轮交的是**裁判**，不是**结论**。"复利真的发生了"需要同类任务被真实重复若干次之后
> 才谈得上判断——现在的数据里还没有这样的重复。**裁判立起来了，"更省"这句话才有资格被说出口。**

### 3.18 查清 DEF-145：一条"单跑绿、全量红"的测试暴露了 harness 的隔离缺陷

**上一轮我如实记了它（Open），这一轮先查它再继续加功能**——理由是：测试本身不可信时，
后面所有"证据"都要打折。

**根因不是产品代码，是测试 harness 的目录布局**：

```
生产：  数据根 = $DSH_HOME/bosom-friend   →  稳定语境文件与技能目录写在 $DSH_HOME 自己那一层
harness：数据根 = mkdtemp(...)            →  dshHomeOf(dataRoot) 解析成**系统的 %TEMP%**
```

于是**所有 spec、所有并行 worker 共用同一个 `%TEMP%\skills`**。任何一个 harness 建路由表时跑的那次
Curator（那时账本为空、`keep=[]`）都会把别的 spec **刚升格的技能归档掉**——单文件跑的时候没有并发，
自然就绿。顺带这还往**用户的临时目录**里留了 `skills/` 与 `AGENTS.md` 残渣。

**修法**：harness 照抄真实布局（`home/bosom-friend`），`dispose` 收整个 home；
并清掉已经留在 `%TEMP%` 里的残渣。

**验证**：三个相关 spec 同跑 30/30 绿；**全量复跑 372 passed / 1 skipped，exit 0**；
跑完之后 `%TEMP%\skills` 与 `%TEMP%\AGENTS.md` **都不存在**（隔离与清理都成立）。

> 这条值得记下来的地方不在修法（很小），而在**它为什么会被放过**：
> 它不是"偶发 flake"，是一个**确定的竞态**——只要有两个 harness 同时在跑就会发生。
> 我上一轮先跑单文件看到绿才继续往下写，差一点把它当成噪声。


### 3.17 四类语境的最后两块：记忆与画像

ADR-003 口径四要求"成功经验、运行事实与用户偏好都变成下一次的上下文"。到这一轮为止，
**领域/约束/历史/质量**四类已经在跑，缺的是**记忆（运行事实）**与**画像（用户偏好）**：

| 语境 | 之前 | 现在住哪 |
| --- | --- | --- |
| 记忆 | 只有"最近几条真实失败"的流水 | 新增 **## 记忆** 段：**按平台聚合**的失败（同一个地方反复出问题才是记忆，单次失败留在流水里） |
| 画像 | 没有 | 新增 **## 用户画像** 段：绑定账号数 / 已发布（按平台）/ 生成过的内容（按类型）/ 打过高分的任务类型 |

**画像的红线是"只写有出处的事实"**：不写"用户喜欢简洁风格"这种没有出处的判断，
只写"这台机器上发生过什么"。模型可以据此调语气与选题，而每一条都能在数据里查到。

**真实数据实测**（重启运行时后读生成出来的那份文件，数据根里只有 1 个账号、0 条发布记录）：

```
## 用户画像（这台机器上真实发生的事，不是猜的）

- 已绑定账号：1 个
- 用户打过高分（≥4）的任务类型：chat
```

没有发布记录就**不写**"已发布"，没有生成记录就**不写**"生成过的内容"，没有聚合失败就**不出**记忆段——
**空就是空，不凑数**。这条由用例守着（画像在什么都没有时只写"已绑定账号 0 个"）。

判据：`agent-context.spec.ts` 15 条（含"按平台聚合并按次数降序"、"没有聚合失败时不出记忆段、
但单次失败那段照旧"、"画像只写有出处的事实"、"什么都没有时不编造发布与偏好"）。

### 3.16 技能环终于接上了（并发现它一直是断的）

**先补上上一轮标注的那条"未验证"**：探针现在也写一个技能进 `$DSH_HOME/skills`，然后看模型请求里有没有它。

**结果是一次打脸**：`SKILL_CATALOG=MISSING`——技能**根本没到模型手里**，连目录都没有。
也就是说 P5 第一块当时的状态是"文件写了、界面说成功、模型永远看不到"。

一路查下去是两层原因：

| 层 | 事实 | 判据 |
| --- | --- | --- |
| 技能目录到底有没有进请求 | 官方 `skill` 工具的描述写着"用**会话技能目录**里的确切名字"，目录由 `dsh-tool-skill` 发布成一条 `catalog` 形式的上下文 | 探针抓的请求体里搜技能名 |
| 为什么我们的技能不在目录里 | 官方 `@deepseek-ai/dsh-skill` 的技能名规则是 `/^[a-z0-9]+(?:-[a-z0-9]+)*$/`——**只认小写 ASCII**；而 `skillName()` 从**中文**指令生成名字，中文产品里几乎每一个技能都不合法，provider **静默丢弃**（只记一条 warning） | 决定性实验：同一个技能文件，名字非 kebab-case 时 `SKILL_CATALOG=MISSING`，改成 kebab-case 立刻 `OK` |

**修法**（DEF-144）：名字只留 ASCII（把规则来源与后果写进 `SKILL_NAME_PATTERN` 的注释），
中文人话走 `description` / `whenToUse`——那两处是自由文本，而模型在技能目录里看到的正是"名字 + 说明"。
`agent-skills.spec.ts` 新增一条**守住 provider 正则**的判据（多种输入都必须是合法 slug）。

**这一轮之后，技能环才是通的**：生成的名字合法（用例守）→ 官方 provider 收下 → 目录进模型请求（探针守）→
模型按需 `skill` 加载正文（`SKILL_BODY=MISSING` 是**正确**的，技能是懒加载的）。

> 尚未验证：真实模型"主动挑用"技能的行为（探针验的是目录可达，不是模型的选择）。

### 3.15 前端类型清零（web 13 → 0），顺带修掉两个真 bug

**把 web 应用清到 0**，门禁从"整包棘轮 58"改成**两侧分开**：
**web 上限 0（硬门禁）**、electron 主进程上限 45（棘轮）。理由是这两侧的处置代价完全不同——
前者是我天天改的代码，必须干净；后者多数是引用了本移植里不存在的 `bosom-friend-harness`。

清的过程中**类型检查又抓到两个真 bug**（都不是"类型洁癖"，是用户能遇到的）：

| --- | --- | --- |
| DEF-142 | 设置页「打开下载页」**永远灰着**，还显示"版本清单里没有给下载地址"——而清单里其实给了；`'ahead'`（本机版本比清单新）也是死分支 | 同一份桥契约在三处各写一遍（主进程 / `global.d.ts` / 设置页本地副本）后漂移；主进程从没回传 `url`。修法：主进程补 `url` 与 `ahead`，设置页**从桥声明派生类型**（`Awaited<ReturnType<Window['bosomUpdate']['check']>>`），不再自己抄一份 |

### 3.14 开发文档也按同一套思路优化（对象化 + 索引 + 门禁）

**同一套乘法用在开发上**：飞书那一侧的价值是"对象自带结构与入口"，豆包那一侧是"按上下文干活"。

### 3.36 E2E 那条「时好时坏」的红，其实是一个真 bug：删不掉最后一个账号（DEF-166）

同一支用例，19:35 那次 51 passed，20:06 那次挂一条：

```
specs\ac-verification.spec.ts:725:3 › AC-003-2 建分组→账号入组→解绑登录态→删除，每一步列表都跟着变
Error: expect(received).toBe(expected)   Expected: 0   Received: 50000
```

**先按「用例不稳定」去查就错了**。把用例的四步用探针照跑一遍，三次**全部**复现同一个 50000，而且带着原文：

```
delete=50000  msg=服务端处理失败：拒绝用空数据覆盖已有内容的文件：…\accounts.json。
              清空用户数据必须走显式接口（saveEmpty），并在此之前留下快照。
```

**根因**：删除账号走的是 `files.accounts.save(accounts)`（`routes-channels.ts`），而 `JsonFile.save` 有一条空值守卫——
「不允许用空数据覆盖一份非空文件」。它防的是真事故（读失败 → 内存空数组 → 回写，7 个数据文件被写成 40 字节空信封）。
守卫是对的，**错在删除路径没走它给出的显式接口** `saveEmpty`：库里只剩一个账号时，删完就是空数组，于是这一次保存被拒、删除整体失败。
**用例为什么时好时坏**：库里有别的账号时删完非空 → 通过；只剩一个时 → 失败。参数化在「当时库里有几个账号」上的红，是最难查的一种。

**修法**：删空时 `saveEmpty`，否则 `save`（快照在二次确认之后、删除之前已经留过，正是 `saveEmpty` 要求的前提）；同文件的发布记录级联清理早就这么写了。

**三层证据**：

```
负向对照  还原旧写法 → account-delete-last.spec.ts 判红，并打出守卫原文（2 failed）
服务端     448 passed / 1 skipped（新增 3 条：删最后一个 / 逐个删到空 / 守卫本身仍在）
真机复验   重启源码运行时后连跑三轮 register→logout→delete：全部 code=0 data=true，库归零
E2E        specs\ac-verification.spec.ts -g AC-003-2 --repeat-each=2 → 2 passed (1.2s)
```

**顺带记一条运行时的口径**：开发运行时加载的是**构建出来的 `lib/`**（包导出指向 `lib/types/*.js`），
所以后端改完必须先 build 再重启——我第一次复验时忘记这点，看到「修复没生效」，其实跑的还是旧 lib。
`dev-web.ps1` 已经把这两步串在一起（build → 停旧实例 → 起新实例，并刷新 `node_modules/.pnpm` 里的注入副本）。

```
BF_TEXT_ONLY=1  TEXT_ONLY_TOOLS=0                                                            TEXT_ONLY_NO_TOOLS_OK
```

**顺带补上一个更大的缺口**：工具面收敛（把 pwsh / 文件读写 / subagent 这类编码智能体工具拿掉）
当初只靠一次人工看请求体验证过，**没有任何可重复的门禁**——它挡的是「模型在客户的 Windows 上执行命令」，
却没有任何东西在下次有人改补丁层时判红。现在这支探针接进了门禁「有效工具面」：
产物不在判黄（环境未就绪）、探针跑得起来但断言不过判红（回归）。

**改补丁层当场踩到的两件事（都是老教训的复发）**：
① 改了 `kernel/cordis.patch.yml` 不生效——内核按**自己所在目录**解析插件，读到的是注入/部署树里的副本，
必须先刷新副本（DEF-146 同族）；
② 刷新后 `verify-runtime-config-drift.mjs` **判红**并逐个点名三处副本——这正是那盏灯存在的意义，
按它给的路径同步后 `RUNTIME_CONFIG_DRIFT PASS`（顺带当了一次免费的负向对照）。

**判据边界如实记**：预防层的证据是"模型请求里没有 tools 字段"（探针读真实请求体），
不是"模型不再尝试调工具"——后者无法确定性验证（要靠模型行为），而前者是**机制层的事实**。
### 3.27 平台上限只报「有出处的数字」（DEF-153 收口，含前端那个会把输入框锁死的坑）

**缺陷长什么样**：平台元数据给**所有**平台发同一套上限（正文 5000、图片 9、话题 10），
而模型侧的约束语境写的是「小红书正文不超过 1000 字」——同一个平台两个数字，
**用户按 5000 写、平台按 1000 收**。这些数字没有任何出处：引擎源码里根本没有这些常量。

**做法**：立一张**只登记有出处的数字**的平台事实表 `PLATFORM_CONTENT_LIMITS`，路由与约束语境都从它取数：

| 落点 | 内容 |
| --- | --- |
| 事实表 | 目前只登记小红书（正文 1000 字 / 话题 10 个，产品既定口径）|
| 路由 | 有出处的才报；没出处的**整个字段不发**（界面显示「未声明」，而不是显示一个假上限）|
| 标题 30 字 | 如实标成**产品自己的**上限（来自 `MAX_TITLE_CHARS`），与平台事实分开 |
| 约束语境 | 从同一张表渲染（「平台正文上限（按平台事实表）：小红书 1000 字」）——一个数字一个家 |
| 防漂移 | 判据里有一条：事实表里的平台名必须与平台目录扫描出来的名字一致 |

**前端那个坑（动手前就露出来了）**：`desMax = maxBodyLength ?? 0`，而输入框写的是 `maxLength={desMax}`——
服务端一旦「不报」，`maxLength` 就是 **0，什么都打不进去**。所以这条必须两边一起改：
前端把 0/undefined 当成**没有上限**（不设 maxLength、不显示剩余字数、提交校验也跳过），
并顺手去掉那个 `?? 2200` 的回落值——那同样是我们编的，不是平台的。
（顺带发现那个组件的 `maxLength` 参数**从来没被消费过**，所以假上限此前只影响计数器与提交校验。）

**真机实测**：
```
GET v2/channels/platforms
{"platform":"xhs",   "title":30, "body":1000, "topics":10}
{"platform":"douyin","title":30}                      ← 不再编正文/图片/话题
{"platform":"weibo", "title":30}
~/.bosom-friend/AGENTS.md：
- 话题标签不超过 8 个；…；平台正文上限（按平台事实表）：小红书 1000 字。
```

**判据**：`platform-limits.spec.ts` 5 条（小红书报出有出处的两个数 / 没出处的平台不报且标题仍如实报 /
标题来自产品常量而不是散落字面量 / 事实表与平台目录的名字不漂移 / 约束语境从同一张表渲染）。

**如实记下验证边界**：前端那三处改动只过了类型门禁与人工复核，
**没有**做发布弹窗的页面级验收（那条路要选素材、开弹窗，本轮没跑）。
### 3.26 草稿「AI 配图建议」：建议落在**你自己的素材库**上（ADR §2.2 的最后一个动作）

**至此 ADR-004 §2.2 点名的动作全部落地**（草稿四个 + 账号两个 + 发布记录一个）。

**配图建议的关键不是"描述几张好看的图"，而是"从你已有的素材里挑"**：
所以素材库进了事实——用第 30 轮扩的那条契约（`ObjectAdapter.find` 可以顺带返回 `facts`），
草稿适配器把"库里有什么图/视频"取给它。库里空着时如实写「素材库现在是空的」，
模型才有机会写"需要补拍几张"，而不是凭空描述。

**真机实测**：13.3 秒给出四段（几张 / 每张拍什么 / 从库里挑哪几张 / 封面用哪张与理由），
点名了库里的「材料平铺：柠檬与薄荷」，并明确指出「图2 需要从便利店场景补拍 1 张」——
**用已有的、说清缺的**，这正是这条动作该有的样子。

**这一轮自己踩出来的两个缺陷（都是真机复核抓到的）**：

| 缺陷 | 现象 | 修法 |
| --- | --- | --- |
| **DEF-158**（P3） | 第 24 轮我"加"的那条诊断日志（`object_action_tool_call`）**永远不会执行**——它排在"文本为空就返回"之后，而产出被丢弃时文本正是空的。台账里 DEF-155 那行还写着"已加" | 诊断挪到判空之前；判据补一条（调工具那一轮 `ai-logs.json` 必须有这条）。**没有任何症状的缺陷，正是"声称有诊断"最容易骗过自己的地方** |
| **DEF-159**（P2） | 模型回「我理解这是一个纯文本生成任务…不过我注意到您没有提供具体的创作需求」，**被当成了配图建议写进去** | 新增 `looksLikeMetaReply`：拒绝式开头（与助手的 `modelRefused` 同口径）**或**「套话开头 + 明说没拿到需求」两句同时满足；命中则不写回、如实报"请重试"并留诊断 |

**DEF-159 的口径被自己的判据纠正过一次**：第一版只看开头是不是"我理解/抱歉"这类套话，
于是把「我理解的用户是刚入行的运营：这条内容要讲清…」判成了元回应——**判据当场抓住**，
改成"两句都要满足"（拒绝式开头单独成立）。

**同一轮里 DEF-155 的兜底在真机上真发生了一次**（这是我们希望看到的证据）：
```
ACTION code=40400  SUGGESTION=大模型没有返回内容：模型这一轮去调工具了（这类任务不需要查询），请重试
TITLE_INTACT=true   SUGGESTION_WRITTEN=false
```
模型真的去调工具了，产出被整份丢弃、对象一个字没动、用户看到人话——
**第 24 轮那条兜底不是纸面上的**。（也正是这一次让 DEF-158 露了馅：说好的诊断没写下来。）

**判据**：`object-actions.spec.ts` 38 条（配图建议 2 条：库里空着要如实说 / 库里有图要点名且未命名要标出来；
元回应 2 条：不写回且留痕 / 正常内容不误判）+ `text-only-guard.spec.ts` 3 条（含诊断必须落盘）+
探针 `qa/probes/probe-draft-illustration.mjs`（`--seed-library` 种两张有名字的探针图）+
页面截图 `qa/evidence/illustration-2026-09-22/01-*.png`。
### 3.25 账号「AI 风险评估」：判断"这个号现在能不能干活"

**为什么是它**：ADR-004 §2.2 给账号列了两个动作，定位（该讲什么）在第三轮做了，
风险评估（现在能不能干活）一直空着——而它是**发布前最该问的那句话**。

**依据从哪来**（这是这个动作的价值所在）：全部是这台机器上的真实事实——
登录态（含平台给的原因，第 25 轮进的语境）、**这个号的发布失败史**、发布量。
其中失败史住在**发布记录**里，只有知道这条号住在哪的适配器拿得到。

**因此扩了一条契约**：`ObjectAdapter.find` 可以顺带返回 `facts`——
"与这条对象相关的其它事实"。为什么由适配器给而不是动作规格给：规格是**纯函数**（只有这条记录、可单测），
而"这个号失败过几次"在别的文件里。两路事实在运行器里合并，空的那一路不占位置。

**判据**（`object-actions.spec.ts` 34 条，新增 2 条）：
① 事实里有登录态、也有失败史（种两条失败记录 → 提示词里出现「失败 2 次」与失败原文）；
② 结论写回 `aiRisk`、昵称与登录态一个字不动、`aiRiskAt` 落时间。

**真机实测**（对第 25 轮那个"登录已失效"的探针号）：
```
TARGET acc-yr4gyxim 深夜食堂研究所 loginState=invalid
ACTION code=0 secs=3.4 field=aiRisk
风险等级：中
依据：抖音登录已失效，需重新扫码授权才能发布；已发布成功0条、失败0条，未测试发布链路是否顺畅。
先做什么：① 立即重新扫码完成抖音登录；② 登录后先试发1条测试笔记，确认发布链路正常后再投入正式内容。
NICKNAME_INTACT=true  LOGIN_STATE_INTACT=true  RISK_WRITTEN=true
```
页面：账号卡片上定位与风险并排（风险用琥珀色块），与「需重新登录」徽标一起构成
「该讲什么 + 现在能不能干活」的完整画面（截图 `qa/evidence/account-risk-2026-09-22/01-*.png`）。

**至此 ADR-004 §2.2 点名的动作只剩一个**：「AI 配图建议」（草稿）。
### 3.24 草稿「AI 合规检查」：不改内容、只给判断（以及它当场暴露的缺陷）

**为什么是它**：ADR-004 §2.2 给草稿列了四个动作，前三个（改标题 / 优化正文 / 生成话题）都是"改内容"，
合规检查是唯一一个**给判断**的——而平台拒发是这个产品真实的痛点（台账里就有违规词那一族）。

| 落点 | 内容 |
| --- | --- |
| 动作规格 | `draft-compliance`（写 `aiCompliance`）：逐条核标题字数 / 正文长度 / 话题数 / 绝对化用语 /
医疗功效承诺 / 诱导分享与站外引流；没问题只回一行「通过」 |
| 给模型的事实 | 标题（含字数与上限）、**正文原文**（≤600 字）、话题数与列表、目标平台 |
| 前端 | 结论在草稿详情里单独一块显示（按钮也是服务端清单给的，界面没写死）|

**分割线：哪些该由产品算，哪些该由模型判**。字数是产品数得准的，模型自己数会数错——
所以字数与数量由事实给出；**措辞风险**（绝对化用语、功效承诺、引流）才是模型该判断的。
这条分工写进了判据。

**这一轮自己写出来的缺陷（DEF-157，当场被真机抓到）**：第一版的事实里只有「正文共 N 字」，
**没有正文原文**。真机跑同一条故意违规的草稿，只报出 2 处且都在标题——
正文里的「七天包瘦」（功效承诺）与「加微信 xxx 领内部资料」（站外引流 + 索要联系方式）**一处没提**。
这是 DEF-151 的同一课：**检查类动作查不了它看不见的东西**，而且它更隐蔽——不报错、有产出、看着像通过。

修法：事实里补上正文原文（上限 600 字，超出时如实写「以上为前 600 字，正文共 N 字」，不假装看全）；
判据补两条（正文原文必须在事实里；长正文按上限截断并如实说明）。**真机复核**：
```
修前：发现 2 处（都在标题）        12.1s
修后：发现 5 处  ① 标题绝对化用语「最」「第一」
                ② 标题字数（模型把 14 字说成"超限"，判断对、理由不严谨——如实记下）
                ③ 正文「七天包瘦」属医疗/功效承诺
                ④ 正文「不瘦退款」属收益承诺
                ⑤ 正文「加微信 xxx 领内部资料」属站外引流 + 索要联系方式      4.0s
```
标题与正文**一个字都没动**（合规检查不是"顺手帮你改一遍"）。

**判据**：`object-actions.spec.ts` 32 条（合规检查 3 条：动作清单 / 事实里必须有正文原文且长文如实截断 /
写回结论且不改内容）+ 探针 `qa/probes/probe-draft-compliance.mjs` + 页面截图
`qa/evidence/compliance-2026-09-22/01-合规检查挑出5处.png`。

**如实记下的两点**：① 模型对个别条目的**理由**不严谨（把 14 字说成超限），
结论对、过程不严谨——这类"理由层面的小错"本轮不追，但值得单独看；
② 合规检查目前**只覆盖草稿**，发布记录那一侧（已发出去的内容被平台判违规）没有对应动作。
### 3.23 把「越用越省」做成看得见的东西：度量覆盖所有调用，趋势上面板

**起因**：S5 审计（§3.21）顺手发现两件事——**度量只有助手那条路在记**
（对象动作 / 接待建议 / 长视频写稿全都没记 `toolCalls`/`elapsedMs`/`contextChars`），
而趋势接口 `GET knowledge/distill/trend` 虽然早就有了，**界面上一次都没显示过**。
结果是：产品最想证明的那句话（"同类活儿越干越省"）在数据上只覆盖了聊天。

**做法**：

| 落点 | 内容 |
| --- | --- |
| 度量只在一处产出 | `streamLlmWithDeltas` 量耗时、上下文块长度、工具调用次数并回给调用方——口径只有一套，否则账本里会出现几种不可比的数字 |
| 四个记录点接上 | 对象动作 / 接待建议 / 长视频写稿 / 选题增强都写入同一套度量 |
| 面板 | 蒸馏页签新增「越用越省」：第一次 vs 最近几次的中位数（轮数 · 秒 · 上下文字数）|

**为什么 `toolCalls: 0` 也要记**：趋势的入选条件是"有度量值"，只记非零等于把"这一轮没调工具"这件事丢掉，
样本永远进不了统计（老样本就是这么被排除的——那是对的，但新样本不能再这样）。

**界面上的诚实口径**：没有度量样本时显示「还没有带度量的样本。老样本没有度量，**不拿 0 顶替**」；
有度量的样本少于 2 条时明说「少于 2 条，先别看结论」。

**真机实测**（重启后直接读接口）：
```
GET knowledge/distill/trend?task=chat&recent=5
{"measured":3,"first":{"createdAt":"2026-09-22T07:12:09.522Z","toolCalls":0,"elapsedMs":59,"contextChars":285},
 "recent":{"samples":3,"toolCalls":0,"elapsedMs":5406,"contextChars":375}}
```
页面截图 `qa/evidence/trend-2026-09-22/01-越用越省看板.png`。
**注意这组数字现在是"变慢"的**：第一个样本是一次很快的空回合，最近几条是真实模型调用——
面板照实显示，不做"看起来在进步"的加工。这也正是这条判据存在的意义：
**它必须能显示坏消息，否则它就不是判据。**

**判据**（`measure-and-trend.spec.ts` 4 条）：① 对象动作写下轮数/耗时/上下文（耗时>0）；
② 接待建议同样带度量；③ 趋势接口把非助手路径的样本算进 `measured` 并给出 first/recent；
④ 没有度量样本时不给结论（`measured=0`、first/recent 为 null）。

**门禁当场抓到的一处**：面板里 `trend.first.createdAt` 用了一个我自己写的接口没有的字段——
前端类型门禁（第 12 轮立的棘轮）当场判红。按后端真实形状补齐，而不是把字段删掉。
### 3.22 S5 收口：长视频那两条路也带上语境、也留痕（DEF-156）

上一轮的审计留下两条没接线的模型调用：**长视频写稿**与**选题增强/排分镜**。
这一轮接上，而且发现缺口是**两半**——不只是"不留痕"，另一半是**提示词里没有用户自己的资料**：
写内容却空手去问模型，等于把产品事实交给它编。

**做法**：

| 调用点 | 语境 | 留痕（sourceId） |
| --- | --- | --- |
| `completeWithModel`（选题增强 / 排分镜） | 知识 + 质量样例（task=video） | `text-call-h<内容寻址>` |
| `writeLongVideoScript`（写稿 / 补写） | 知识 + 质量样例（task=video） | `long-video-script-<任务 id>`，拿不到 id 时同样内容寻址 |

**为什么用内容寻址兜底**：这些调用点在编排层深处，有的连任务 id 都没有；
为了让 id 好看而把参数层层透下来，接错的概率比接对还高。代价是"同一段提示词重复跑会覆盖同一条"——
对留痕与复利来说这恰恰是要的。拿得到任务 id 的那一处（`extendLongVideoScript`）仍然按任务 id 走，
这样"这条稿属于哪条任务"查得到。

**判据怎么写出来的**（这两条路在编排层深处，正常要跑厂商 + ffmpeg）：
挑了**两个不需要厂商、不需要 ffmpeg** 的入口——`POST long-videos/enhance-topic`（走 `completeWithModel`）
与 `POST long-videos/:taskId/extend-script`（走 `writeScript`，用 `scene` 生成器 + 一条种子任务）。
三条判据：① 选题增强把资料原文带进了提示词，且账本记下命中哪几篇；
② 写稿按任务 id 留痕、提示词里带资料；③ **这次没达标也留痕**——
补写后仍不足字数时产品如实拒绝（40000），而账本照样记下"这一轮产出了什么、当时问了什么"：
账本记的是**真实发生过的事**，不是"有没有通过"。

**真机实测**：
```
POST long-videos/enhance-topic {topic: 露营地垫 收纳后只有矿泉水瓶大小 承重 200 公斤 偏远地区运费怎么算}
→ code=0；账本：text-call-he11ddbf6  task=video  paths=[探针资料：发货与售后.md, 欢迎使用 Bosom Friend 知识库.md]  chars=202
```

**判据当场纠正的一处**：我第一版把"达标"和"留痕"写成了同一个断言（路由返回 0 才有样本），
而实际情况是**留痕与成不成全无关**；拆成两条之后，第③条反而成了最有价值的一条——
它钉住了"账本是事实账，不是成绩单"。
### 3.21 S5 审计：把"每次调用都带上下文、都留痕"变成可查的账

**S5 是 S1–S5 里唯一整块没有证据的**（不是没做，是没人验过）。做法是把全部模型调用点列出来，
逐个问三件事：**带了上下文吗 / 留痕了吗 / 回放得了吗**。

| 调用点 | 用途 | 上下文 | 留痕 |
| --- | --- | --- | --- |
| `api.ts` 对象动作 | 按钮触发的对象改写 | 知识 + 质量样例 | ✅ 账本（带 objectKind/objectId） |
| `api.ts` 助手对话 | 每轮对话 | 知识 + 质量 + **焦点对象** | ✅ 账本（含 toolCalls / elapsedMs / contextChars 度量） |
| `api.ts` 生成（草稿/图文） | 批量生成 | 知识 + 质量 | ✅ 账本（sourceId = 生成记录 id） |
| `api.ts` 技能蒸馏 | 「蒸馏成技能」 | 按设计（样例自身即输入） | ✅ 账本 |
| `routes-content.ts` **接待建议** | 客人提问 → 建议回复 | **修前：空手去问模型** | **修前：无** |
| `api.ts` **长视频稿件** | 长视频写稿 | 空 | ❌ 未接线（DEF-156） |
| `api.ts` **分镜/选题增强** | `completeWithModel` | 空 | ❌ 未接线（DEF-156） |

**这一轮修的第一处（接待建议）**：`POST v2/customer-reception/suggest` 在规则没命中时去问模型，
而提示词里**只有那句来访原文**——产品自己的资料、话术、成功样例一条都没带上。
接待恰恰是"用你自己的知识回答客人"的场景，这是最不该空手的一条路。修法：带上知识语境与质量样例，
并留一条账本样本（`sourceId` 内容寻址：平台+账号+来访原文，同一句重复问覆盖同一条，不撑爆账本）。

**真机实测**（真模型 + 真数据根，先种一条探针资料）：
```
问：偏远地区的运费怎么加收？七天无理由怎么算？      → aiUsed=true matched=false
答：您好～偏远地区会加收15元顺丰运费哦；七天无理由退货支持，不过拆封后只能换货不能退啦…
账本：reception-suggest-45738f3d  paths=["探针资料：发货与售后.md"]  chars=67
```
回复里的 15 元、顺丰、拆封只换不退**全部来自用户自己的资料**——修之前这条路上模型手里什么都没有。
（顺带记一笔：我第一条自测问题被内置的「发货规则」接走了（`matched=true`），
那是设计意图；要验模型那条路得挑一个规则接不住的问题——这一点也写进了判据里。）

**判据**（`s5-traceability.spec.ts` 4 条）：① 接待建议的提示词里**真的有知识库原文**，
且账本记下命中了哪几篇；② 同一句重复问不新增样本（内容寻址）；③ 对象动作的样本带对象身份；
④ 助手每一轮都留样本、命中知识的那一轮要记下来。

**判据当场抓到的两处**：第一版把内置接待规则留着跑，结果 `aiUsed=false`（模型根本没被调用）——
用例要验的是模型那条路，就得把规则清掉；另一处是检索阈值（命中 3 个检索词才算命中，中文按 2 字滑窗提词），
"发货时间"这种问法在本例资料里一个词都不算命中，问法得真的落在资料上。
### 3.20 权限即上下文边界：助手要知道"哪些号现在做不了事"

**这一条是飞书侧四个要素里最后一个没有落点的**。飞书官方那句的原文是
「**权限即上下文边界**（豆包工作沿用用户本人的权限）」——在本产品里，它的具体含义是：
助手要知道**用户此刻真正能做什么**。

**缺口很具体**：语境里只写「已连接平台：抖音、小红书」，不写**这些号现在还能不能用**。
而产品规则又明令禁止模型说「我没有权限」「无法直接操作」（`agent-rules.ts` 第八节）。
于是模型会替用户答应一件做不到的事——最糟的一种是**声称已经发布**。
登录态在产品里是现成的（界面上就标着「需重新登录」），只是从来没进过语境。

**做法**：`AgentContextFacts.accountUsability`（可用数 / 需要重新登录 / 已失效），
渲染进「当前家底」：
```
- 现在能用的账号：5 个；另外 1 个需要重新登录（小红书·深夜食堂研究所：抖音登录已失效，请重新扫码登录）
  ——**这些号现在发不出去也拿不到数据**
```
（上面这行是从真实语境文件 `~/.bosom-friend/AGENTS.md` 里读出来的；那个探针账号的登录原因是探针写进去的，
产品如实转述了它写的东西——数据说什么就写什么，这正是这一块该有的样子。）

**写代码时当场纠正的一处口径**：第一版把「可用」算成「登录态不是 invalid」，
而界面的口径是 `status === 1 && loginState !== "invalid"`——两者不是一回事，
只按登录态算会**把失效号也算进可用**，那是在语境里给模型一个偏大的权限边界。
现在三个桶各说各的（可用 / 需要重新登录 / 已失效）。

**判据**（`agent-context.spec.ts` 22 条，新增 4 条）：
① 掉了登录的号要点名并说清"这些号做不了事"；② 失效与掉登录是两回事，各说各的；
③ 全都正常时不编出问题、也不重复说一遍；④ 一个账号都没有时不写"0 个可用"这种废话。

**判据当场抓到的两处**：一条断言写得太宽（"文档里不含'已失效'"——宪章里本来就有这个词，
改成只断言这一行）；一个旧夹具没给新字段（`accountUsability` 是必填，
没有加"防御性默认值"——同进程的类型边界上补默认值只会掩盖漏掉的地方，改夹具才对）。
### 3.19 纯文本任务调了工具：整份产出作废（DEF-155）

**缺陷长什么样**（上一轮跑真机探针时当场看到的）：「AI 改标题」把一句
「抱歉，当前草稿箱里没有…这条记录」**写成了草稿标题**，而接口回的是 `code=0`——
用户看到的是一次"成功"，内容却是一句对话。

**根因**：纯文本生成只在**提示词里**请求模型别用工具（`TEXT_ONLY_GUARD`），而内核会话**带着工具**
（`api.ts` 自己的注释就写着"内核会话带工具"）。模型一旦把生成请求当成待办去查数据，
最终正文就是一段工具驱动的回复，随后被 `normalize` 截断、写回对象。

**为什么规则放在传输层而不是各调用方**：产出"是不是这次任务的结果"只取决于**这一轮有没有调工具**，
与是哪个动作无关。放在 `streamLlmWithDeltas` 一处，所有纯文本调用（对象动作 / 写稿 / 分镜 / 接待回复…）
一视同仁：一旦调过工具，`text` 直接为空 + 一句人话原因。
放在各调用方自己判断的话，迟早有一个忘了判——而忘了判的那一个，就会把一段回复写进用户内容。

**为什么整份丢掉而不是"再问问它"**：调过工具的正文不是"这次任务的结果"，它是**会话的另一件事**；
丢掉 + 让用户重试是诚实的，而"再问一次"会把一次不确定变成两次。

**判据**（`text-only-guard.spec.ts` 3 条，替身内核按需发出 tool-call 步骤）：
① 调了工具 → 接口不报成功、原因说人话、**用户内容一个字都不动**；
② 没调工具 → 照常写回（把生成能力一起关掉同样是错的）；
③ 翻车这一轮**不记账本**——被丢弃的产出不能变成下一次的"成功样例"。

**预防那一层还没做，如实记**：内核客户端没有按次关工具的开关（`KernelClientOptions` 只有
provider/model/baseUrl/apiKey/sessionId），要真正禁掉得动内核侧的 profile 或补丁层。
在那之前，"模型白跑一轮再被丢掉"是这套兜底的已知代价。

**这条兜底押在"内核会把工具调用通知送到 onStep"上，所以单独验了这条通道**：
让助手（允许工具的那条路）回答"草稿箱里有几条草稿？"，响应流里出现 `tool_use` 帧，
账本里随即出现一条 `toolCalls: 1` 的样本——而那个计数与守卫用的是**同一个 onStep 回调**
（`api.ts` 的 `onKernelStep` 与 `streamLlmWithDeltas` 里新加的 `stepSink`）。
换句话：守卫的触发条件在真内核上是活的，不是"设计上应该会触发"。

**真机复核**：换上新代码后连跑三次真实「AI 改标题」，模型这三次都没有去调工具（三次都正常返回），
因此**没有**产生新的 `object_action_tool_call` 记录——这条兜底的确定性证据是那三条用例，
不是"祈禱模型再犯一次"。
### 3.18 让飞轮自己转：用发布后的真实表现给样本打分（ADR-004 附录 P1）

**为什么是它**：上一轮把飞轮（上一次被认可的产出 → 下一次的上下文）钉住了，但它**要人点五星才转**。
用户不点，账本里就永远是「评分 0」。而产品手里本来就有一条更硬的信号：这条内容发出去之后平台给了什么数据。

**先修前置缺口（DEF-154，P2）**：发布记录**丢掉了「这条内容来自哪条草稿」**——界面一直在传
`context.materialId`，服务端类型里也声明了它，但**从来没读过**。于是「作品 ↔ 草稿 ↔ 当时 AI 怎么改的」
这条链在落库这一步就断了，P1 整条不可能。修法是记录新增 `draftId`。

**口径（三条，都是为了不把弱信号说成强信号）**：

| 口径 | 为什么 |
| --- | --- |
| 只在**同一账号**内比 | 不同平台的量级不可比，同平台不同账号的粉丝基数也不可比 |
| **只有跑赢的才给分**（前 25% → 5，前 50% → 4），跑输的不打分 | 发布表现受封面、发布时间、平台分发影响，不全是文案的功劳；拿一次发布给内容判死刑是错的 |
| **用户打过的分机器绝不改** | 用户是看过产出之后的判断，机器只看得到数字 |

另外：**有数据的作品少于 5 条时一条都不评**（两条作品排名没有意义）；
分数从哪来记在样本的 `ratingSource`（`user` / `engagement`），蒸馏页签上标「按表现自动」，
用户点星会覆盖成他自己的判断。

**接线也换了地方**：不再靠拆 sourceId 找"这条样本改的是哪个对象"——草稿 id 自己就含连字符
（`cnt-3kk0i7m8`），动作 id 也含，按分隔符拆就是猜。现在对象动作落账本时直接记 `objectKind` + `objectId`。
（判据当场抓住了这个错：第一版按第一个连字符切，切出来是 `cnt`。）

**触发点**：稳定语境刷新（助手冷启动之前），与 Curator 同一处——两者都是"账本的投影"，
而且必须发生在会话建立**之前**：会话只在这时候读一次指令文件。

**真机实测**（真模型 + 真账本）：
```
DRAFT=cnt-3kk0i7m8  ACTION_CODE=0（AI 改标题留下一条样本）
SEEDED works=5 account=acc-probe-rating（探针种的发布数据 + 其中一条挂在这条草稿上）
--- 触发一次助手冷启动（走的是真实路径，不是直接调函数）---
SAMPLE objectId=cnt-3kk0i7m8   rating=5   ratingSource=engagement   AUTO_RATED=true
LOG=按真实表现给 1 条样本打上了分（参与排名 7 条作品）
```
**诚实说明**：探针种不出真实的平台数据（播放量只能由真实发布 + 平台采集产生），
种进去的 engagement 是探针造的，验的是**整条链的接线**；真实数据到位时跑的是同一段代码。

**同轮登记 DEF-155（P1，未修）**：真机跑探针时，「AI 改标题」把一句
「抱歉，当前草稿箱里没有…这条记录」**写成了草稿标题**（接口回 `code=0`，看着像成功）。
根因是纯文本生成只在**提示词里**请求模型别用工具，而内核会话**带着工具**
（`api.ts` 自己的注释就写着"内核会话带工具"）：模型一旦去调工具，最终正文就是一段工具驱动的回复，
随后被 normalize 截断、写回对象。方向有两条：调用侧真正禁工具；以及兜底——
这一轮只要发生过工具调用就拒绝写回并如实报错。宁可不写，也不把一段回复当成标题。

**判据**：`sample-rating.spec.ts` 7 条全绿（表现分口径 / 名次口径 / 对象身份是记下来的 /
跑赢的样本被打上分 / **用户的分不许改** / **样本太少不排名** / 发布记录留下来源草稿）+
探针 `qa/probes/probe-engagement-rating.mjs`（`--seed` 与读回两段）。
### 3.17 附录 P0 收口：约束语境从"手抄的数字"改成"从唯一出处派生"，并补齐成本与时长

**P0 原文**（ADR-004 附录 A 的优先级表）：
① 历史语境入上下文：把「常见坑速查表」与最近的真实失败原因做成上下文块；
② 约束语境入上下文：成本/限频/时长上限与字数门槛收敛成一份可维护的约束块。

**先说结论**：两条都已经有落点，但**都不是"可维护"的**——这一轮补的正是这一层。
前一版 `CONSTRAINT_LINES` 是**手抄**在文案里的六个数字；核对时发现两处已经和代码对不上，
而且有一句和宪章逐字重复。

| 发现 | 证据 | 处置 |
| --- | --- | --- |
| 「单条视频按 4~12 秒**一个镜头**」 | 代码里 4~12 秒是 `SEGMENT_MIN/MAX_SECONDS`（**配音段落**），镜头是 `SHOT_TARGET_SECONDS=5` / `SHOT_MAX_SECONDS=6` | 拆成两句、各自从来源 import；模型按老文案排镜头会排出产品不会剪的片子 |
| 「发布限频 3 条/20 次/5~25 分钟」 | 与 `agent-rules.ts` 第八节逐字重复，而两者会渲染进**同一份**语境文件 | 从约束块删掉，政策类数字留在宪章里；新增判据：同一份渲染结果里「不超过 3 条」「不超过 20 次」各只出现 **1 次** |
| 成本、时长上限**根本没写** | P0 明确点名这两类 | 新增成本条（行为约束：付钱的动作用户没说就不要做、失败不要反复重试）与时长口径条 |

**做法**：`ConstraintSources`（标题/笔记/话题上限、段落时长、镜头时长、长视频选题字数）全部 import 自各自模块，
`buildConstraintLines(sources)` 渲染文案，`CONSTRAINT_LINES = buildConstraintLines(CONSTRAINT_SOURCES)`。
判据里有一条**专门证明它是派生的**：换一组来源（标题 42、话题 3），文案跟着变——手抄的写法过不了这一条。

**真实产物核对**（不是看源码，是读模型真正会读的那份文件 `~/.bosom-friend/AGENTS.md`）：
```
## 约束语境
- 标题不超过 30 个字；标题里不要放表情符号。
- 话题标签不超过 8 个；给自己的笔记/长文写正文时不超过 8000 个字；小红书正文不超过 1000 字（平台限制）。
- 短视频配音按每段 4~12 秒切分；一个镜头的目标时长是 5 秒、不超过 6 秒。长视频按用户选的目标时长排镜头。
- 长视频的选题描述不超过 800 个字。
- 视频生成、配音合成、数字人这类动作会产生真实费用与额度消耗：用户没明确要求时不要主动触发…
```

**历史语境的判断（P0 ①）：不把速查表整份塞进去**。核对后的结论是——
`12-常见坑速查表.md` 的 56 条全是**开发/打包/交付**的坑（MAX_PATH 260、pnpm 联接点、zip 条目数…），
对一个内容运营助手是纯噪音，而且它们**已经作为知识库条目可被检索命中**（按相关度进上下文，而不是常驻）。
常驻的历史语境该放的是**产品行为级**的坑（"不确定的数量先用只读工具查"这类），也就是现在这几条；
「最近的真实失败原因」本来就是从本机数据实时渲染的。所以 P0 ① 的意图（模型看得到踩过的坑）由两条通道共同满足：
**常驻**（产品行为级）+ **检索**（开发级，按需）。

**同轮登记 DEF-153（未修）**：平台元数据给所有平台报同一套 `maxBodyLength: 5000`，而约束块写的是小红书 1000——
同一个平台两个数字，用户按 5000 写、平台按 1000 收。数字没有出处（引擎源码里没有这些常量）。
要修得先有一张"只登记有出处的数字"的平台事实表，路由与前端都从它取数。

**判据**：`agent-context.spec.ts` 18 条（新增 3 条：派生、段落与镜头不混、政策数字只出现一次）+
真实语境文件逐行核对（上面那段就是从文件里读出来的）。
### 3.16 复利飞轮被钉住了：上一次被认可的产出，进下一次的提示词（S4 的判据）

**为什么单独立一个判据**：S4 是全篇唯一"还没有证据"的主张。
这条链此前只有零件级用例——`buildQualityContext` 能挑出样本、`POST knowledge/distill/rate` 能改评分，
但**「评分之后，下一个动作真的带上了它」这一跳从没被验过**。零件都对、接线没接，飞轮就不会转（DEF-138 就是这么来的）。

**判据看的是"真实送进模型的那段提示词"**，不是"某个函数返回了非空字符串"：
测试里把内核客户端换成会记账的替身，逐次截下 `prompt()` 收到的内容。三条：

| 判据 | 断言 |
| --- | --- |
| 负向对照 | 没被认可的产出**不进**上下文（飞轮的起点是"认可"，不是"跑过一次"）|
| 这一跳 | 评 5 分之后，下一次同类动作的提示词里出现 `[你自己的成功样例` + 那条产出 + `用户评分 5/5` |
| 不被抹掉 | 同一条对象**再点一次同一个按钮**，用户认可的样本与评分都还在，新的一次也照样入账 |

**过程中抓出的缺陷（DEF-152，P1，已修）**：第三条一开始是**红的**。
对象动作的蒸馏来源 id 是稳定的（`object-action-<kind>-<id>-<action>`），而 `recordDistillation` 的口径是
「同一来源 id 覆盖」、新记录的 `rating` 固定写 0——于是「再点一次」把上一条**连同用户刚打的 5 分一起抹掉**：
飞轮转一次就停。修法是给覆盖加一条例外：旧样本若已被认可（评分 ≥ 门槛）或已升格成技能，就不覆盖，
新的一次另起一条记（id 加序号——评分与升格都是按 id 找样本的，撞车会让两者都指错）。
顺带把硬写在 `fewShotExamples` 里的 `4` 与 `agent-skills` 的 `MIN_SKILL_RATING` 归一：一个数一个家。

**真模型实测（同一动作跑两圈，中间评 5 分）**：
```
RUN1 code=0 value=自动更新中          SAMPLE1 rating=0
RATED ok=true
RUN2 code=0 value=自动更新中          SAME_SOURCE_ROWS=2   RATING_KEPT=true
RUN2_EXAMPLE_IDS=["dist-object-action-draft-cnt-vmsop3os-draft-title", ...]
RUN2_CONTEXT_INCLUDES_RUN1=true       INJECTED_OUTPUT=自动更新中   INJECTED_RATING=5
```

**这份证据是从账本自己身上读出来的**，没有为它加任何埋点：账本给每条样本记了 `exampleIds`
（这一次注入了哪几条样例），而样例的正文就在同一份账本里——「模型看得见的东西必须留痕」这条规矩，
第一次直接被拿来当验收手段用。

**一个如实记下的观察**：RUN2 把 RUN1 的产出原样抄了回来（标题仍是「自动更新中」）。
质量语境块里写的是「可借用结构与口吻，不要照抄其中的事实与数字」，模型仍可能整句复用。
这是选样口径（只按评分与时间）的固有风险，本轮不改——要改成"同一条样例别连续用太多次"或按相似度选，
得有真实样本分布做依据，不能凭感觉调。

**判据**：`quality-loop.spec.ts` 3 条 + `quality-context.spec.ts` 6 条 + `agent-skills.spec.ts` 12 条全绿；
探针 `qa/probes/probe-quality-loop.mjs`（真模型，读账本自证）。
### 3.15 草稿的「AI 生成话题」：动作契约放宽到列表字段，并抓出"提示词缺料"

**这一轮做了两件事**：把对象动作的写回值从"只能写字符串"放宽到字符串/字符串列表，
然后在草稿上落地 ADR-004 §2.2 点名的第二个草稿动作「AI 生成话题」。

| 落点 | 内容 |
| --- | --- |
| 契约 | `ObjectActionValue = string \| string[]`；`normalize` 返回它，运行器按"空串/空数组"两种形态判失败 |
| 解析 | `normalizeTopics`：认 Markdown 列表、顿号连写、JSON 数组三种形态；去重、丢碎片、丢整句，取 8 个 |
| 规格 | `draft-topics`（按钮「AI 生成话题」，写 `topics: string[]`） |
| 前端 | **一行都不用改**：按钮清单由 `ai/object-actions` 给，标签直接渲染 `topics`（只放宽了一处响应类型） |

**为什么值得先改契约**：话题是列表字段。只认字符串会逼着每个列表字段自己发明「用逗号拼起来再存」的私规，
落盘里看着像成功，读到的时候类型就不对了。判据里专门有一条：模型整理不出话题时**一条都不写**，
已有的那串话题也不会被清空——空串判空的写法在这里会静默清空用户数据。

**页面级验收抓出的缺陷（DEF-151，P1，已修）**：真模型上这个动作**一次也没成功过**。
第一次跑回的是 `40400 模型这次没有给出可用的内容`，而模型其实答了——原文是
「**理解，我将直接输出内容而不使用任何工具。**」。
根因不是模型：动作规格只声明了 `current`（被改字段的当前值），新草稿没有话题，
于是模型看到的是「当前内容：（当前为空）」+ 一句"读标题与正文"——**标题与正文一个字都没给它**。
同族的更大问题：`draft-title` 看不到正文、`draft-body` 看不到标题。修法是三个草稿动作都补上 `context`
（除被改字段之外的其他字段：标题 / 正文 / 已有话题）。

**修之前先补了诊断**：整理为空时把模型原文前 120 字写进 `ai-logs.json`（kind=`object_action_unusable`）。
没有这一行，"模型不行"和"提示词缺料"从现象上分不开——这次正是它把结论从猜测变成证据。
修后实测：真模型 4.7 秒给出 6 个话题（`["夏日特调","三种夏日特调","便利店买材料","在家做特调","低成本特调","夏日饮品"]`），
落盘 `topics` 是**数组**、标题与正文未动；页面点一次即把 6 个标签渲染出来（不刷新）。

**判据里当场抓到的一个语言细节**：话题分隔符不能包含全角逗号——中文列表用顿号，
而「，」是句子内部的停顿；用逗号切分会把"这一条其实是一整句解释，不该被当成话题"切成两半，
前半段长度正好合格，于是一句解释被写成话题。这条由单测当场拦下，没有出厂。

**判据**：`object-actions.spec.ts` 30 条全绿（话题 5 条：解析形态 / 提示词必须带标题与正文 /
写回是数组且标题正文不动 / 空结果不覆盖 / 动作清单）+ 探针 `qa/probes/probe-draft-topics.mjs` +
页面截图 `qa/evidence/draft-topics-2026-09-22/01-*.png`。

**顺手留下一个诊断工具**：`qa/probes/probe-action-prompts.mjs` 打印每个动作**真实送给模型的提示词**
（纯函数，不需要服务在跑、不花模型额度）——这是这一轮定位 DEF-151 用的那把尺子：
以后「动作没效果」先看提示词，再看模型。
### 3.14 第四种对象：发布记录的「AI 复盘」（ADR-004 §2.2 点名的最后一个对象动作）

**为什么是它**：ADR-004 §2.1 给发布记录写的能力是「复盘上下文（哪条好、为什么好）→ 回流成下一次选题的上下文」。
一行数据里最值钱的不是那几个数字，而是「为什么」——所以复盘结论必须**落在这条记录上**，
而不是在对话框里说完就散掉。

| 落点 | 内容 |
| --- | --- |
| 动作规格 | `work-review`（按钮「AI 复盘」，写 `aiReview`，≤200 字，明令不许编数字、不许写空话）|
| 提示词事实 | 平台 / 标题 / 发布时间 / 播放·点赞·评论·收藏·转发；**没采到的指标写「平台未采集」** |
| 对象适配器 | `work`：在 `files.records`（发布记录）里按 id 找，commit 走 `files.records.save` |
| 前端 | 数据中心「作品排行」行上的「AI 复盘」按钮 + 复盘回显 |
| 投影 | 作品行补 `recordId`——写回要的是**记录 id**，`dataId` 是平台侧作品 id，拿它当记录 id 会写错对象 |

**实测（真模型，实时运行时）**：`POST ai/object-action {kind:work,id:probe-work-review-1,action:work-review}` → `code=0`、8.1 秒，
复盘里用的是真实数字（播放 1200 / 点赞 88 / 评论 7 / 收藏 31，互动率 9.2%），并给出下一条的具体调整；
落盘回读：标题与互动数据一字未动、`aiReviewAt` 是能解析的时间。页面验收：点按钮后**不刷新页面**该行出现复盘文本、
按钮翻成「重新复盘」（截图 `qa/evidence/work-review-2026-09-22/01-*.png`）。

**「未采集 ≠ 0」这条设计穿到了模型**：第二条探针作品**只有点赞 12 / 评论 1、没有播放量**，
模型的开头是「**播放量未采集**，实际可见互动仅 12 赞 1 评……」——如果提示词里写成「播放量：0」，
它会得出「没人看」的结论，那是编出来的事实。

**回流是可验的**：每一次对象动作都进蒸馏账本。判据里有一条断言
`sourceId=object-action-work-rec-review-2-work-review` 的样本存在、`instructionLabel` 是人话（「AI 复盘：…」）、
`output` 是这条结论、`status=success`——账本进得去，下一次的语境才可能更厚。

**页面级验收又抓出一条（DEF-149，已修）**：作品行右侧的「贡献占比」在**没有采样行**时显示 `120000.0%`——
分母 0 被 `sumMetric(...) || 1` 兜成了 1；而前端在占比为空时又 `?? 0` 显示成 `0.0%`。
两头都是编出来的数字（与 DEF-008/015/020 同一族）。修法：分母为 0 时服务端给 `null`（未知），前端只在它是数字时显示；
修复前/后各一张截图：`qa/evidence/work-review-2026-09-22/01-*.png`（行上有复盘、右侧写着 120000.0%）与 `02-*.png`（那个数字消失）。

**顺带补齐 S1 的最后一种对象**：ADR-004 S1 点名的是「草稿/账号/**记录**」。记录这一侧的"当前对象"
是**详情 Popover**（日历里每条记录都是一张卡片，按渲染登记等于让最后渲染的那条胜出）。
登记挂上去之后，真实请求体里第一次读到的却是 `objectKind:""`——**DEF-150**：焦点在详情关闭时被清掉，
而点到助手输入框必然让 Popover 失焦关闭，问题是关掉之后才问的。改成"本页最后打开过的那条记录"（换页由路由校验作废）后，
请求体里带上了 `objectKind:发布记录 / objectId:probe-work-review-2 / excerpt:平台：xhs；发布时间：…；互动：点赞 12 / 评论 1`。
两次为空、一次带值，都是**真实请求体**，不是推断。

**判据**：`object-actions.spec.ts` 26 条全绿（发布记录五条：动作清单 / 写回且标题与数据不动 / 时间戳 /
不存在如实拒绝 / 复盘进蒸馏账本）+ `dashboard-honesty.spec.ts` 5 条 + 探针 `qa/probes/probe-work-review.mjs`。
### 3.13 对象动作铺到第三种对象：账号（以及「账号级 AI 事实的家在哪里」）

**起因**：四类语境里「用户画像」的源头就是账号——定位不清，模型给的选题与文案全都在猜。
S2 此前只铺了草稿与笔记两种对象，账号是第三种：账号卡片上的「AI 定位」。

**这一轮做的**：

| 落点 | 内容 |
| --- | --- |
| 动作规格 | `account-positioning`（按钮「AI 定位」，写 `aiPositioning`，≤80 字，不许编账号数据）|
| 对象适配器 | `account`：按 `String(item.id)` 在 `files.accounts` 里找，commit 走 `files.accounts.save` |
| 提示词新通道 | `ObjectActionSpec.context?` + 【已知事实】段（平台 / 昵称 / 粉丝数）|
| 前端 | 账号卡片「AI 定位」按钮 + 定位回显；`store.account.patchAccount` 就地改写列表、索引与当前选中 |

**为什么必须加 `context`**：`current` 给的是「被改字段的当前值」，而账号第一次做定位时它是空的——
模型只看到「当前定位：（空）」，连这是哪个平台、多少粉丝都不知道，**只能编**。
把对象事实单独走一路之后，送进模型的是「平台：xhs / 昵称：… / 粉丝数：…」，
粉丝数缺失时如实写「平台未提供」，而不是写 0 冒充真值。

**真模型实测**（实时运行时 `http://127.0.0.1:31280/bosom-friend/`，探针账号 `ai-pos-probe`）：
`POST ai/object-action {kind:account,id:acc-xt5ikucd,action:account-positioning}` → `code=0`、**6.4 秒**，
写回内容「小红书 AI 账号，面向对人工智能感兴趣的用户，靠持续输出 AI 工具用法与避坑经验留住人。」；
读回接口里昵称与粉丝数一字未动。

**过程中抓出的缺陷**：`aiPositioningAt` 是**类型里声明了、服务端从来不写**的字段——
运行器写时间戳用的是 `updatedAt in target` 这种猜法，而账号没有 `updatedAt`（只有 `updateTime`，
那是账号资料自己的更新时间），于是那个字段永远是空的；更糟的是前端按钮还乐观地自己 `new Date()` 盖了一个，
**同一件事实又有了两处来源**。修法是把它变成规格里的一条声明：`ObjectActionSpec.stampField`——
草稿 `updatedAt`、账号 `aiPositioningAt`、笔记不写；前端不再自盖时间戳。

**同一轮登记 DEF-147（未修，如实记）**：账号这个实体在**两个家**里各有一份权威——
网页模式读服务端账号文件（`files.accounts`），而**装出来的桌面应用读的是本机 SQLite**（`isDesktopEnv()` 分支让本机行优先），
本机库没有 AI 列，且本机扫码登录的账号从不登记到后端（唯一的登记路径是抖音云授权回调）。
也就是说：这条「AI 定位」在装好的应用里、对本机账号点了会**静默无效**。
本轮的处置是**让失败可见**而不是假装成功：web 侧 `SocialAccount.accountSource`（`backend` / `desktop-local`）
在两个生产端盖章，本机行的按钮置灰并写明原因。账号权威归一（登录即登记到后端，或把账号级 AI 事实挪到
按 `(type, uid)` 寻址、两端共读的存储）留给下一轮。

**页面级验收当场抓出的第 2 条缺陷（DEF-148）**：服务端日志与回读接口都显示定位写进去了，
而页面上的卡片**一动不动**。根因是同一个账号在账号 store 里有**三处引用**
（`accountList` / `accountMap` / `accountGroupList[].children`），而页面渲染的是最后那处；
改写只替换了 `accountList` 里那一个对象。这类"账面上成功、界面上没发生"的缺陷
**规格用例与接口回读都看不见**——它们只看服务端。修法是把"改一处必须三处一起改"抽成纯函数
`patchAccountHomes` 并配 6 条前端单测；复验方式是重建 UI 后**不刷新页面**点按钮，
卡片自己出现「定位：…」、按钮翻成「重新定位」（截图见 `qa/evidence/account-positioning-2026-09-22/`）。

**判据**：`server/test/functional/object-actions.spec.ts` 21 条全绿，其中账号四条（动作清单 /
写回且昵称不动 / 留时间戳且 `updateTime` 不变 / 不存在如实拒绝）+ 一条钉住三个对象各自声明的时间戳字段；
前端 `test/unit/accountPatch.test.ts` 6 条；页面级验收两张截图（修复前卡片不动 / 修复后不刷新即更新）。
### 3.12 前端类型检查终于有了（棘轮），并抓出三条被它放过的真缺陷

**起因**：给蒸馏面板加升格按钮时顺手复核，发现"信封当载荷读"这一族错误已经出现三次。
查下去发现根因不是粗心——**前端从来没有任何类型检查在跑**：`vite build` 走 esbuild（不查类型），
CI 的 typecheck 只覆盖 `server` 与 `kernel` 两个包。这与我第四轮修掉的内核包缺口**是同一族**。

**实测**（`npx tsc --noEmit -p products/bosom-friend/project/bosom-friend-electron/tsconfig.json`）：
修前 **71 条**错误（electron 主进程 45、web 应用 26）。类型检查当场指出的三条真缺陷：

| 缺陷 | 后果 |
| --- | --- |
| `DraftDetailDialog`: `http.get(...).then(res => res?.list)` | 读错层级（应在 `res.data.list`）→ **动作按钮从来就没显示过** |
| `DraftDetailDialog` / `KnowledgePage` / `KnowledgeDistillPanel`：把信封类型又套了一层 | 我第五轮"修复"写成了 `http.post<{code?, data?}>`——泛型是**载荷**类型，于是 `envelope.data.field` 依旧取不到 |
| `VoiceProviderTab`：`apply(view)` / `saved.activeName` | 配音来源设置页读到的永远是信封，配置显示与"当前来源"都不对 |

**这一轮的处理**：修掉 13 条（我这几轮引入的全部 7 条 + 语音设置页 6 条），剩 58 条；
新增 **`qa/verify-frontend-types.mjs`（棘轮门禁）**——把水位钉在实测值，**只能降不能升**，
任何新增的前端类型错误立刻判红，接进 `run-gate.mjs` 检查 5l 与 CI。

**为什么是棘轮而不是直接判零**：剩下 58 条全是既有的，其中 45 条在 electron 主进程
（多数是引用了本移植里不存在的 `bosom-friend-harness`），13 条在 web 应用
（三个 store 的 `combine` 类型只覆盖 state 切片，方法不能从 `get()` 上取）。
一次性清完要动三个 store 的类型设计，风险与收益不成比例；先把水位钉住，
**目标是把它降到 0，到 0 之后它就是一个完整的前端类型门禁**。

### 3.11 经验升格为技能 + Curator（P5 的第一块）

**落在官方技能通道上，而不是又一段提示词**：技能写成 `$DSH_HOME/skills/<name>-<hash>.md`
（官方 `dsh-skill-filesystem` 扫描的 user-dsh 根，与 `AGENTS.md` 同一个家）。
区别是实质的——拼进提示词的东西是**被动接受**的一段上下文，
而技能进的是**会话技能目录**：模型可以按名字挑用，用户可以打开文件读、改、删。

| 设计点 | 做法 | 为什么 |
| --- | --- | --- |
| 升格门槛 | 成功 **且** 用户评分 ≥4 | 技能会被模型当成"以后照做的流程"，把失败或不满意的产出固化下来比不升格糟得多 |
| 谁来触发 | **用户点**（`POST knowledge/distill/promote`），不自动 | 自动升格等于让模型自己决定以后怎么做 |
| 蒸馏要什么 | 要**流程**（分几步、每步做什么、怎么算做完），并明说"不要照抄产出" | 模型的天性是复述输入；与质量语境（喂样例）分工：样例是原料，技能是方法 |
| 一条样例 ↔ 一个文件 | slug = 安全短名 + sourceId 哈希后缀 | 两条不同指令压出同一个短名时，不带后缀会**静默覆盖** |
| Curator | 账本是事实源，目录是它的投影：按（评分降序、时间降序）留前 12，其余归档到 `skills/archive/` | 归档不是删除——技能是用户认可过的经验，删了找不回来 |
| **归属** | Curator **只搬本应用写的**技能文件（frontmatter 里的 `managed-by`） | 技能根是用户的空间；不分青红皂白地"投影"会把他手写的技能搬走，那是数据丢失 |

**顺带补的接口缺口**：`GET knowledge/distill/dataset` 的投影把 `sourceId` 漏掉了——
而升格接口正是认这把钥匙的，不补上，界面永远没法把一条样例变成技能。

判据：`agent-skills.spec.ts` 10 条（命名与 slug 稳定性 / frontmatter 必填字段与归属标记 /
升格门槛 / 排序与上限 / **用户手写的技能不被搬走** / 围栏剥离 /
端到端升格后文件落盘且账本留痕 / 未达 4 分拒绝且不写文件 / 样例不存在如实拒绝）。

### 3.10 领域语境搬家：产品规则不再每轮拼提示词（P4 / ADR-003 口径二完成）

**改了什么**：`AGENT_RULES`（4175 字、10 节、身份/红线/流程）从 `streamLlmWithDeltas` 的
提示词拼接里摘掉，改由 `buildAgentContext` 写进 `$DSH_HOME/AGENTS.md` 的**领域语境**区块，
经官方 `dsh-agent-instructions` 通道在会话建立时注入。`api.ts` 里现在**零处**引用规则。

**为什么这样做**：拼接进 prompt 的文本在会话日志里看不出来源、用户也改不了；
落在数据根的指令文件三条都成立——可读、可编辑、可审计。四类语境里"稳定"的三类
（领域/约束/历史）现在都住在这一个文件里，每轮变的东西（焦点对象、本轮知识）仍走每轮请求。

**三个必须在同一轮里做掉的配套**（少一个就会静默失去规则）：

1. **启动时就写文件**：刷新挂在 `buildRoutes` 末尾（服务启动期，早于任何请求）。
   否则新装的机器在第一次助手对话之前，生成/长视频/接待调用会在**没有规则的会话**里跑。
2. **助手冷启动前刷新**（上一轮已做）：让"这台机器上真实的失败"这类动态事实保持新鲜。
3. **`/ai/chat` 的第二份拼装**同步摘掉（它自己有 `TEXT_ONLY_GUARD + AGENT_OPERATING_RULES`）。

**门禁判据也跟着换了**：`verify-agent-rules.mjs` 原来断言"api.ts 有没有 import 规则"——
那是**实现**，不是事实，换投递方式就误判。现在断言两件真的事：规则**有**投递点
（`agent-context.ts` 引用并放进区块），且**只有这一个**（api.ts 不得再出现 `AGENT_RULES`，
两处投递必然漂移）。**负向对照已做**：临时把 `AGENT_RULES` 加回 api.ts，门禁判红且信息精确；
删除后恢复绿灯。

### 3.8 对象动作铺到第二种对象：知识笔记（P3.2）

- 把动作执行从"只认草稿"泛化成**对象适配表**（`OBJECT_ADAPTERS`）：动作规格只说"改哪个字段、
  怎么整理"（纯函数，可单测），"草稿住在 contents 数组里、笔记住在 knowledge.notes 的映射里"
  由适配器负责。**不这么分，每加一种对象都要改一遍动作执行逻辑。**
- 新增 `note-polish`（AI 润色笔记正文，写回同一条笔记）。笔记是"领域语境"的家——
  笔记写得好不好，直接决定模型下一次拿到的语境质量。
- 笔记正文的整理规则**故意不剥 Markdown 标题记号**：`# 标题` 是笔记的内容，不是外壳
  （这条被自己的用例当场抓出来——第一版走了给标题用的 `stripDecoration`，测试判红）。
- 错误话术分开：先认对象再认动作，"还不支持这类对象"与"这个对象上没有这个动作"是两句话。
- 前端：知识库笔记头部新增「AI 润色」按钮；点之前**先强制保存**编辑器内容，
  否则润色的是服务端旧版本、写回时会盖掉用户刚打的字（那是数据丢失，不是润色）。
- 判据：`object-actions.spec.ts` 扩到 **15 条**（笔记写回、笔记名不动、笔记不存在如实拒绝、
  两种错误话术不同、Markdown 标题保留、代码围栏剥离）。

### 3.9 页面级复核抓出的真 bug（DEF-139）

在给知识笔记接按钮时顺手复核了草稿那个按钮，发现**两处错在同一个契约上**：
`utils/request` 的 `http.post<T>` **返回的是信封** `{code, data, message}`（业务失败不抛错，
只弹一条全局提示），而按钮把它当成了 `data` 本身——读 `result.field` 永远是 `undefined`，
于是**成功也走失败分支**，写回逻辑一次都没跑到。两处都改成自己判 `code`、自己取 `data.data`。

这条值得单独写下来：**构建通过 + 服务端 353 条单测通过，都没有覆盖到它**；
它只会在"真的点一次"时暴露。已登记台账 DEF-139，并如实标注"暂无自动化回归"。

### 3.7 修掉根因：内核包终于有了编译面

**问题**：`products/bosom-friend/kernel` 没有 tsconfig，CI 的 "Typecheck product server" 也不覆盖它——
它只被 `esbuild --bundle` 打包，而 **esbuild 不做类型检查**。这一包的 TypeScript 错误
可以永远存在而不被任何人发现。**类型不查，等于这一包没有类型。**

**修法**（三处，缺一不可）：

| 改动 | 内容 |
| --- | --- |
| `kernel/tsconfig.json`（新增） | 照 `server/tsconfig.json` 的形状：`rootDir: src`、`outDir: lib/types`，引用 vendor/cordis、server、core/tools、llm/llm |
| `kernel/package.json` | 新增 `typecheck: tsc -b`；build 补 `--external:@deepseek-ai/dsh-llm`（见下） |
| `qa/run-gate.mjs` 检查 5l + CI 步骤 | 服务端与内核包一起 `tsc -p … --noEmit`；CI 增 "Typecheck product kernel" |

**一开就抓到两个从没见过天日的类型错误**（都不是本次新写的代码）：

1. `kernel/src/index.ts:506`：把裸 `randomUUID()` 当品牌类型 `MessageId` 用。改为官方构造器
   `MessageId(randomUUID())`——品牌 id 本来就该用构造器造。代价是 `dsh-llm` 从"纯类型导入"变成
   运行时导入，因此把它标为 external（**已实测运行时可解析**：探针照常启动、14 个工具齐全；
   不标的话 esbuild 会把整个 `dsh-llm` 打进内核包）。
2. `kernel/src/jobs.ts:78`：`exactOptionalPropertyTypes` 下给可选属性赋 `undefined`。
   改成"没有结果就 `delete` 这个键"——落盘时 `undefined` 本来也会被 `JSON.stringify` 丢掉，
   删除才是同一个语义。

**未采用的做法**：把内核包接进 `tsconfig.host.json` 的全仓工程引用。产品包各自有独立 tsconfig、
本就不在根聚合里（CI 注释也写明了这一点），单独加一个 leaf 就够，动全仓图是没必要的风险。
