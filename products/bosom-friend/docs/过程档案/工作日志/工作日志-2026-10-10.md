**场景 C（AUTH → AUTH）** —— **`enabled=true` 但 `ready=false`**：

```

TRIGGER ok=false retry=0                               ← 第一次尝试失败
```

### 45.1 结论先行

### 45.2 实测：竞态窗口存在

**方法**：临时诊断以 **100ms 高频**采样 `useAutoPublishOnReady` 的五个 `ready` 来源 + `enabled`/`open`/`selectedCount`（事后已移除）。场景 C（AUTH → AUTH，跟随开）。

**采样 657 点，其中 `enabled=true && ready=true` 共 9 点**：

```
t=0     prefill=false acct=false plug=false i18n=true create=false sel=0
t=0     prefill=false … sel=1
t=181   prefill=false … sel=1
t=203   prefill=false … sel=1
t=331   prefill=false … sel=1
t=407   prefill=false … sel=1      ← 仍在 500ms 预填窗口内
```

**源码依据**（`DraftContentModule:186-208`）：`publishingDraft` 变化时 **cleanup 先执行 `setPrefillLoading(false)`（`:206`）**，而**新 timer 要 500ms 后才执行 `setPrefillLoading(true)`（`:195`）** —— 于是这 500ms 内 `prefillLoading=false`，**若其余来源也为"未加载"，`ready` 即为 `true`，但弹窗内容尚未重填**。

**因此**：若问题 B 被修复（宿主收到 `autoPublishOnReady=true`），`enabled` 会在**预填开始之前**变为 true，而 **`ready` 此时可能仍为 true** → **`triggerPublish` 可能在旧草稿上触发**。

**限定条件（不得夸大）**：
- 本次实测**没有发生误发布**（`pubCalls` 第二轮为 0），因为 **`enabled` 在场景 C 第二轮虽为 true，但 `ready` 恰好被 `createLoading` 挡住**；
- 上述推断是**「修复 B 之后可能出现」的风险**，**不是已发生的缺陷**。

## 五十三、DEF-241 根因查明：不是重复请求

### 53.1 结论

**「动作卡场景每轮两次 `POST /agent/tasks`」的真相是：同名端点承担了两种完全不同的用途。**

```
普通文本响应轮 → 1 次 POST
  body: {"prompt":"PROBE-ALPHA-111","includePartialMessages":true}
  stack: createTaskWithSSE → createTask

动作卡响应轮 → 2 次 POST
  ① body: {"prompt":"PROBE-BETA-222","taskId":"tk","includePartialMessages":true}
     stack: createTaskWithSSE → _ → continueTask
     → 用户输入（续跑同一任务）
  ② body: {"content":"AI 智能体已执行「navigateToPublish」，以下为当前页面截图。",
            "medias":[{"type":"image","url":"data:image/png;base64,iVBOR…"}]}
     stack: request → zs → post → Ko @:659 → (anon) @:661
     → 动作卡执行后的页面截图反馈
```

**第 2 次请求的 body 根本不是 prompt** —— 因此**不存在「一次输入发两次请求」**。

### 53.2 取证方法

`ctx.newCDPSession(page)` + `Network.enable`，监听 `Network.requestWillBeSent`，采集 `initiator.stack.callFrames`；在**同一次会话内**对照「普通文本响应」与「动作卡响应」两条路径（脚本 `analysis/_repro/410-cdp.mjs`，发布端点全部替身）。

### 53.3 对既定四个疑问的回答

| 疑问 | 回答 |
| --- | --- |
| 一次输入是否发出两次请求 | **否 —— 只有 1 次 prompt 请求** |
| 两次请求的 prompt 是否完全相同 | **第二次根本不是 prompt**（是截图反馈 body） |
| 第二次是否由另一条前端调用路径产生 | **是** —— `Ko`/`post` 链，非 `createTask`/`continueTask` |
| 差异是否只出现在动作卡响应之后 | **是** —— 普通文本轮恒为 1 次 |

### 53.4 安全问题评估

**与重复发布无关**：历次测试中发布端点调用次数均正确（自动阶段 0 次、人工确认后恰好 1 次）。本项实为**同名端点承担两种用途造成的观测歧义**，**不构成安全缺陷**。

### 66.1 改前事实（逐条有据）

| 断点 | 现场 |
| --- | --- |
| 产物没编号 | 写稿工具只返回文本，**没有可交接的 id** |
| 交接被掐断 | 出片工具入参是 `topic`（不是上一步的稿件）→ 出片另写一版稿；`POST long-videos` **没有 `scriptText` 入口**（服务端 `startLongVideoTask` 早已支持，HTTP 层没暴露） |
| 白条句柄 | 发布申请返回 `{ taskId: '（待前端执行）' }`（`kernel/src/index.ts:809`）、建草稿返回 `{ draftId: '（待前端执行）' }` —— 不是真编号 |
| 出片 → 发布靠翻仓库 | 成片登记出的草稿 id（`registerLongVideoDraft` 里的 `contentId`）**没有回写任务行**，下游只能 `bosom_material_list` 二次查找 |
| 承诺 > 能力 | `bosom_publish_content` 声明 `location` / `declaration` 必填，内核却 `void` 掉（**DEF-239**） |

### 66.2 本轮实施

**内核 `kernel/src/index.ts`**：新增 `ActionState`（`requested` / `executed` / `verified`）、`requestHandle()`（真实工单号）、`contentAddressedId()`（内容寻址稿件编号）；
- 申请类三工具（发布 / 建草稿 / 改草稿）返回 `{ state: 'requested', handle: 'pub-…' | 'draft-…' | 'upd-…' }`，render 一并向模型带出申请号与状态；
- 写稿返回 `scriptId`（`script-<sha1 前 12>`，**同稿同号**）；出片新增 `scriptText` / `scriptId` 参数并把稿件随请求交给服务端，返回 `state/handle/scriptId`；进度查询输出 `materialId`；
- 发布工具**移除** `location` 与 `declaration`（工具面 = 能力面）。

**服务端 `server/src/api.ts` / `types.ts`**：
- `POST long-videos` 接受 `scriptText`（定稿稿件，编排层不再另写一版）；
- `registerLongVideoDraft` 把草稿 id **回写任务行** `materialId`（新增字段）；
- 动作卡（发布 / 文本解析发布 / 建草稿 / 改草稿）带 `requestId` + `state: 'requested'`；
- 新增 `POST agent/tasks/:taskId/action-result`：前端执行完回填 `executed` / `verified`（`verified` 可覆盖 `executed`，反向拒绝），落 `task.actionResults`。

**门禁 `qa/verify-agent-workflow.mjs`（新增，16 条）**：真跑工具断言三态与句柄格式、稿件编号确定性（同稿同号）；契约断言出片参数含 `scriptText`/`scriptId`、进度输出含 `materialId`、发布参数**恰好**为 `accountId/body/materialId/title/topics`、构建产物里不得再有 `void location`/`void declaration`、规则提到的工具都在注册表、规则不得再承诺"内容标注可填"、回填路由与落库字段存在。
