# 工作日志 2026-09-18（零运行日志 / 内核自愈 / 生成任务停滞兜底）

> 起因：现场（WIN-20251030LYJ）内容创作时一直弹「网络连接失败，请检查网络后重试」，卡片「生成失败」，
> 用户要求 App 自带的 AI 助手「查工作日志」——助手扫内核目录撞上 30 秒工具超时与 20MB 输出上限，什么也没查到。
> 采集回来的证据里**一份日志都没有**，这本身就是最大的发现。

## 1. 现场还原（用户采集包 + 会话日志）

| 时间（本地） | 事实 |
| --- | --- |
| 12:11:08 / 12:15:22 / 12:17:43 | 同一需求（男性，30 岁，叉车教练）发起三次图文生成 |
| 12:11:56 / 12:15:33 / 12:17:55 | 三次的文案**都生成成功**（response.description 完整，与会话 A/B/D 一一对应） |
| 12:14:44 / 12:16:20 | 前两条被标 failed，errorMessage =「上次生成被中断，请重新生成」 |
| 12:16:17 | App 主进程重启（snapshot/processes.txt），3 秒后第二条被判失败 |
| 12:55（采集时） | 第三条仍停在 generating（已 38 分钟）；进程表里**没有 node**、端口表里**没有 31280** → 内核早已不在服务 |

结论：**活儿干完了，前端没收到**——内核在生成途中消失，在途请求全部断开（前端弹「网络连接失败」），
重启后把在途记录判成「上次生成被中断」（卡片「生成失败」），最后一个内核再没起来，界面还开着一直报错。

## 2. 三个缺陷（已登记 DEF-101 / DEF-102 / DEF-103）

| DEF | 一句话 | 根因 |
| --- | --- | --- |
| DEF-101 | 装机版零运行日志，内核死了没有任何痕迹 | 主进程 console 进无人接收的管道；内核 stdout 是 JSON-RPC 独占通道、stderr 只进 SDK 客户端 400 行内存环；装机 app.asar 内没有任何 logger/appendFile（旧 Electron 工程的 electron-log 是另一条不进包的路径） |
| DEF-102 | 生成任务可无限停在 generating，界面永久转圈 | 运行中没有任何基于时间的兜底；媒体步骤整段没有总预算；"按 updatedAt 判停滞"会被心跳绕过（进程活着、await 不返回时仍在刷时间） |
| DEF-103 | 「网络连接失败」是万能兜底且前端零落盘 | 连接被拒 / 超时 / 非 JSON 三类混成一句，用户去查自己的网络 |

## 3. 修法（主线：让"它死了"变成可查、可自愈）

1. **主进程运行日志**（desktop/electron/run-log.cjs + main.cjs）：按天写 userData\logs，
   10MB 滚动 / 保留 7 天 / 单行 4000 字符 / 遮蔽 sk- 与 Bearer / 写失败静默降级；
   接管 console、写启动事实、抄**渲染进程 console**（前端失败因此可查）、把 BF_LOG_DIR 传给内核。
2. **内核自愈**（main.cjs + kernel-host.cjs）：每 10 秒探活；连续 3 次失败判掉线 → 通知界面 → 自动重启一次（5 分钟冷却）；
   内核非主动退出立即落盘（错误消息自带 SDK 保留的 stderr 尾部）。界面加「重启内核 / 打开日志目录」。
3. **产品侧运行日志**（server/src/runtime-log.ts + api.ts）：**只接管 stderr、绝不碰 stdout**，
   与主进程同一套策略，落在同一个目录——用户点一次「打开日志目录」就能看全两侧。
4. **停滞兜底**（server/src/generation-watchdog.ts + api.ts）：媒体步骤 60 秒心跳 + **绝对截止时间**（图文 8 / 视频 15 分钟），
   运行中每 60 秒扫描一次停滞记录（图文 10 / 视频 20 分钟），判失败时**保留已生成的文案**并如实说明。
5. **前端诚实提示**（utils/request/client.ts + KernelHealthBanner + 六语言文案）：失败按真实原因分类落盘与提示。

## 5. 过程中的两个坑（已记）

1. **开发运行时加载的是 pnpm 注入副本**，不是工作区包：改完 server 代码直接重启后端毫无效果，
   必须像 dev-web.ps1 第 3 步那样把 lib 刷进 21 个副本（本次已刷 21/21、9/9、3/3）。
2. **launcher/src/bin-desktop.ts 在 stdin 结束时优雅退出**：用 Start-Process 直接起后端，
   父进程一退出 stdin 就结束、后端随之自行退出（31280 静默掉线）。
   本次排查中我误杀了用户正在用的 31280 开发后端（进程筛选想排除 31280，但命令行里没有端口），
   已按 dev-web.ps1 的方式重启并确认可用；`bf-hold-backend.cjs` 这种 stdin 持有器也解决不了
   "工具调用结束时进程树被回收"的问题，**正式做法仍是用户自己跑 dev-web.ps1**。

## 7. 自查又抓出两条（出包期间并行修掉）

1. **启动期间会被自己判掉线**：探活每 10 秒一次、连续 3 次判掉线，而低配机器冷启动内核要 2-3 分钟——
   旧写法会在第 30 秒判定"内核已停止"并自动重启，**正好把正在进行的握手中断掉**（自己把自己打断）。
   已加"启动期间屏蔽健康判定 + 同一时刻只允许一次启动"两道守卫。
   负向对照实测：假内核只睡觉不握手 + 45 秒预算，启动窗口内"判掉线 0 行、重启 0 行"，到点如实报握手超时。
2. **日志模块进包没有任何检查**（DEF-101 的根因）：新增 desktop/verify-electron-logging.mjs（13 条断言，
   含"打包规则必须覆盖 electron/**"），接进出包链第 3 步、build-win.sh 前置检查与门禁检查 5r——
   从此"日志模块没进包"会判红，不再静默。
