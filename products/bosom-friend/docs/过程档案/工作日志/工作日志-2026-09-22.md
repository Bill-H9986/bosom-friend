# 工作日志 2026-09-22（界面占位符 / 长视频字幕错位 / 长视频成片短四分之一）

> 起因：用户连着三条反馈——① 截图里批量管理工具条显示「已选 {count} / {total}」，界面里还有英文；
> ② 长视频创作的口播文案还是太短，语速和停顿太慢太长；③ 字幕与口播说话时不匹配。
> 三条都在源码里定位到根因，各自补了会判红的回归用例，并把两个"写了没人跑"的脚本接进门禁。

## 1. 三条反馈 → 三个缺陷

| DEF | 用户看到 | 根因（一句话） | 为什么以前没抓到 |
| --- | --- | --- | --- |
| DEF-133 | 批量管理工具条显示 `已选 {count} / {total}` | 语言文件把占位符写成**单花括号**，i18next 只认双花括号，永远不会被替换（DEF-062 的复发形态） | 当时只补了键名，没管占位符写法；`verify-i18n-keys.mjs` 写了却没有任何调用方 |
| DEF-131 | 字幕比口播晚一整句 | 编排层给的已经是**绝对**时间轴，拼接层又按"各镜起点"平移了一次（黑场过渡不重叠，这次平移是纯多余的加倍） | 用例只断言调用方算出的中间结果，没有一条读回真正烧进画面的 ASS |
| DEF-132 | 口播文案太短、停顿太长（成片 80.54 秒 / 目标 90 秒） | 稿件按目标时长校准到 448 字，**排分镜的模型根本看不到它**，自己另写了 335 字的短稿；成片时长由台词决定 | 校验的是稿件、用的是台词，两份文本各自"看起来都对" |

三条的证据都不是推测：占位符用本机 i18next 实测复现；字幕读的是成片同目录的 `long-video-subs.ass` 逐条时间轴
（第 n 条起点 = 前 n 镜时长之和 × 2）；文案短是任务记录里"稿件 448 字 / 18 镜台词合计 335 字"。

## 2. 修法

### 2.1 界面文案（DEF-133）

1. **占位符写法**：全语言 156 个文件扫了一遍，32 处单花括号全部改成双花括号（zh-CN / en 的
   `task.selectedCount`、`batchDeleteConfirmDesc`、`batchDeleteSuccess` 以及 home / pinterest 两处）。
2. **同族的第二种**：`publish.validation.imageMaxExceeded` 在 5 个语言里有 `{{platformName}}`、
   zh-CN 里没有，而 `PubParmasTextarea` 那条调用**不传** platformName——i18next 缺变量时会把
   `{{platformName}}` 原样渲染出来（本机实测）。给调用方补上变量，基准语言也补齐占位符。
3. **门禁**：`qa/verify-i18n-keys.mjs` 从"只查键存在"扩成三条判据（关键键存在、单花括号一律判红、
   各语言取值集合必须与 zh-CN 一致），并接进 `qa/run-gate.mjs` 的「界面文案完整性」。
   负向对照两条都验过会判红。

### 2.2 字幕时间轴（DEF-131）

- 删掉 `alignCuesToTransitions` 与 `alignToTransitions` 选项（以及随之没有调用方的 `segmentStarts`）：
  拼接层**只烧字幕、不挪时间轴**，`ComposeOptions.subtitles` 的契约写明是成片时间轴上的绝对秒数。
- 新增 `subtitleTimelineProblems(cues, filmSeconds)`：时长非正 / 起点为负 / 结束时间超出成片
  （容差 0.05 秒只吸收毫秒舍入）在拼接前报出来（`[COMPOSE_ERR]`）。不因此判整条失败——画面与声音是对的。
- 回归用例用**真 ffmpeg** 拼两段，再读回 `long-video-subs.ass` 断言第 2 条字幕的起点就是第 1 镜的时长。

### 2.3 口播文案短（DEF-132）

- `storyboard.ts` 新增 `fitScriptToShots(shots, script, charsPerSecond)`：把**已定稿的稿件**按镜头数
  均分成一一对应的台词（句末标点 → 逗号 → 按长度硬切，分界点落在标点上），只替换 line 与 seconds，
  模型的 kind / visual / beat / continuity / references 一律保留。覆盖率因此是构造出来的性质。
- `buildStoryboardPrompt` 新增 `script` 选项：稿件进提示词，并要求 line 逐字照抄、覆盖整段。
  （实测模型仍会改写：59% → 72% → 83%，所以台词最终由上面那条决定；提示词的作用是让画面与真实台词对齐。）
- 母时钟对账改用**真正被合成的字数**（`Σ spokenCharCount(shot.line)`）算实测语速，
  不再拿整篇稿件的字数去除以分镜的配音秒数（那会把语速算快、把稿子越补越长而片子不变长）。
- `shotsCoverTarget` 留在排完分镜之后当现场判据：覆盖本该是构造出来的，报出来意味着切分被改坏了。

## 4. 环境发现（顺手修掉，不另开缺陷）

`launcher/scripts/dev-web.ps1 -Frontend` 在本机（只有 Windows PowerShell 5.1，没有 pwsh 7）跑不完：
脚本把 vite / pnpm 的输出用 `2>&1 |` 收进管道，而 5.1 没有 `$PSNativeCommandUseErrorActionPreference`，
原生命令写进 stderr 的进度行会变成 ErrorRecord，配合 `$ErrorActionPreference='Stop'` 直接终止脚本——
**前端构建其实成功了，脚本却报失败**。改法是那两处不再合并 stderr（进度实时打印，构建结果仍取 stdout 末尾）；
改完用 `dev-web.ps1 -Frontend` 完整跑通一次（退出码 0，运行时在 31280 起得来）。

## 5. 教训

1. **"写了没人跑"等于没写**：i18n 门禁脚本存在了很久，却没接进任何门禁，于是同一个缺陷（DEF-062）以
   另一种形态复发。接进门禁比写脚本更重要。
2. **同一份事实要有唯一的家**：时间轴被两个模块各算一遍就加倍；"这条片说多少字"被稿件与分镜各说一遍就短四分之一。
   修法都是把事实收进一处，另一处只做使用与校验。
3. **校验的对象必须是使用的对象**：稿件门槛校验的是稿件，成片时长却由台词决定——
   中间那次"另一份文本"就是缺口。
4. **"让模型照做"不是一条保证**：四次真实调用证明了这一点（覆盖率 58%~83%）。
   能被测试固定住的保证只有一种——把事实收进一处，代码自己把它落实下去。

# 第二轮（同日）：助手的过程与流式、两个面板同步、context 路线

> 起因：用户三条新反馈——①"我的任务里加一个思考过程及流式输出，不要只有两种状态，要么失败要么一下蹦出答案"；
> ②"右侧边栏 AI 助手与我的任务里的数据信息不同步"；③"把 DSH 底层的 context 完全利用起来……实现 hermes agent 的 APP 蒸馏自进化"。
> ①② 已修完并有回归用例；③ 是产品级工程（ADR-003），本轮落了地基并写明路线，**没有**宣称完成。

## 1. 先说证据：为什么"一下蹦出答案"

用官方 SDK 客户端跑一次真实内核会话，收到的通知种类：

```
tool/call ×2   tool/result ×2   assistant/message ×2   assistant/chunk ×0
```

两件事同时成立：**内核真的在调产品工具**（所以答案里有真实的账号 ID），
而**厂商网关不发增量**（正文只在回合结束出现）——产品此前把工具那两条事件全丢了，
于是界面上只剩"空白转圈 → 整段出现"，或者一句"大模型调用失败：未知错误"。

## 2. 修了什么

| DEF | 一句话 | 关键改动 |
| --- | --- | --- |
| DEF-134 | 助手过程可见 + 正文逐字出现 | 内核客户端读出 `tool/call` / `tool/result` / 带时间增量；服务端按前端**既有**事件形状实时转发并落盘；正文按模型真实时间戳回放（总预算 2.5s、单帧 ≤120ms，文本一字不改） |
| DEF-135 | 助手被禁工具、不带知识库 | `streamLlmWithDeltas` 加 `allowTools`（纯文本生成仍禁），助手放开；助手对话注入知识库命中并计入蒸馏账本 |
| DEF-136 | 两个面板不同步 | `forgetTasks`：删除任务时清掉助手那份对话；详情页"新对话"带主区域一起跳 |
| DEF-133 | 界面里的原始占位符 | 32 处单花括号改双花括号；i18n 门禁扩成三条判据并接进 run-gate（详见上一轮） |

## 3. 验证（都跑过）

| 项 | 命令 / 方式 | 结果 |
| --- | --- | --- |
| 过程事件读法 + 回放节拍 | `npx vitest run test/kernel-client.spec.ts` | 17 条全绿 |
| 端到端：过程上 SSE + 落盘 + 正文多帧 | `npx vitest run test/functional/agent-process-steps.spec.ts` | 2 条全绿；负向对照（去掉 onKernelStep）判红 |
| 真实模型端到端 | 打本机 `POST /bosom-friend/api/agent/tasks`（includePartialMessages） | 12 条过程（4 次工具调用 + 参数 + 结果）、**46 帧正文**、答案用的是真实数据 |
| 落盘可回放 | 读 `agent-tasks.json` | 消息序列 = user,stream_event,tool_result ×4,assistant |
| 浏览器两侧 | `#/chat/task-12eac9cd` | 主区域「4/4 工具调用完成」展开是「查平台账号 / 查登录状态」；右侧助手「已完成 4 步」逐条列出结果（截图 `qa/evidence/fix-2026-09-22/assistant-steps-and-stream.png`） |

## 4. context 的现状与路线（ADR-003）

一句话：**这个 APP 今天把 DSH 当"一次性 LLM 调用 + 工具注册表"在用**——
每轮一个新进程、一个新会话，用完即关；多轮历史是服务端把文本折起来重发（上限 12000 字）；
产品规则每轮手拼进提示词；技能/记忆/画像一条都没有；知识库检索出文本块拼进提示词（账本有，但不回流）。

路线（可单独验收的七步）写在 `docs/adr/ADR-003-APP围绕context运转与自进化.md`：
① 过程可见（本轮）② 知识入账（本轮）③ **一个任务 = 一个会话**（会话复用，含跨重启 resume）
④ 产品规则改走 instructions 上下文文件 ⑤ 知识库成为 context provider（注入留痕）⑥ 技能/记忆/画像 + Curator
⑦ 三大核心全部接入（每次调用都带上下文、都留痕、都能在"我的任务"回放）。

## 5. 教训

1. **"只挑自己要的那点数据"会让整条链路变成黑盒**：内核发了工具调用、结果、用量、标题，
   我们只取正文——用户看到的就是"要么失败要么蹦出答案"，而且没人能判断卡在哪一步。
2. **提示词里的两条规则会互相打架**：一条说"不许调工具"，另一条说"先查后答"。
   规则必须按用途分层（纯文本生成 / 助手对话），而不是共用一份。
3. **"同一份数据"必须是同一批事实**：两个面板此前都是"只有正文"，看起来同步；

# 第三轮（同日）：研究飞书×豆包的融合形态，落地"一个任务 = 一个会话"

> 起因：用户要求把 context 这一步当**地基**来做——"我的理想状态是做成飞书和豆包工作的那种融合状态，
> 达到一加一大于三的效果……你去研究研究"。本轮先研究清楚机制，再把地基建起来（ADR-004）。

## 1. 研究结论：1+1>3 是三种乘法，不是"模型更强"

| 一侧 | 提供什么 | 来源 |
| --- | --- | --- |
| 飞书 | 结构化对象（文档/表格/多维表格）、对象关系、权限（可用范围/协作者/审计）、协作痕迹 | 飞书 aily《企业工作伙伴》《角色权限配置》《字段捷径中的多维表格智能体》 |
| 豆包工作 | 自主拆解任务、调用工具、持续推进；与飞书**深度打通**、按"上下文"完成工作；一次指令串联多个应用 | 光明网 2026-08-26 实测报道 |

三条乘法：**对象即上下文**（模型不用猜）·**对象即 AI 入口**（数据自己会动，人不用搬运）·
**执行结果回流成新上下文**（唯一的复利来源：第 N 次靠上下文变厚，不是模型变强）。
三种断裂对应本产品今天的三个缺口（对话是另一个世界 / AI 只在对话框里 / 经验不沉淀），
形态设计与"内容运营操作系统"的对应写在 `docs/adr/ADR-004-飞书与豆包融合形态与本产品设计.md`。

## 2. 本轮落地：一个任务 = 一个 DSH 会话（DEF-137）

- 之前：每轮新进程 + 新会话 + 用完即关；多轮只能靠服务端折文本重发（上限 12000 字，每轮重发）。
- 现在：**任务级内核池**（上限 4，LRU 释放）。同一任务第二轮只送本轮这一句，历史在会话里；
  冷启动那一轮才喂一次历史；**中断作废会话**（模型被掐断后上下文不可信），下一轮重新冷启动。
- 未做：跨重启 **resume**（需要 SDK 侧会话恢复），属 ADR-003 ③ 的后半段。

## 3. 验证

| 项 | 方式 | 结果 |
| --- | --- | --- |
| 会话复用与边界 | `npx vitest run test/functional/agent-session-reuse.spec.ts` | 3 条全绿（只建一次内核 / 换任务换会话 / 中断作废并重新喂历史） |
| 服务端全量 | `npx vitest run` | 312 passed / 32 文件 |
| 真实模型两轮 | 打本机 `POST /api/agent/tasks` 两轮（同一 taskId） | 第 1 轮答"记住了"、第 2 轮答"小A读书圈"；会话目录**只多一个** `task-b89fc5fa-s1`，第 2 轮**零新增目录** |

## 4. 下一步（按乘法排序，见 ADR-004 §4）

S1 焦点对象进上下文（助手知道你在看哪条草稿）→ S2 对象自带 AI 动作并写回 →
S3 产品规则与知识走官方上下文通道 → S4 技能/记忆/画像 + Curator → S5 三大核心全接入。
**S1~S5 都还没做**，本轮只做了它们共同的地基。
   真正缺的是过程那一层——把它补齐之后，两侧显示的是同一批事件。

# 第四轮（同日）：把参考视频里那套「语境」方法论落到本产品（质量语境回流）

> 起因：用户给了抖音参考视频（光羽《AI时代赚到钱的公司，都深度理解了 context 是什么》），要求仔细研究。
> 视频指向的核心文本是 *Context is the new Moat*（《语境才是真正的护城河》）；读完逐条对照本产品，
> 发现一处**机制性缺口**并当场修掉（DEF-138）：语境不复利。

## 1. 研究要点（与飞书官方口径对齐）

- 竞争逻辑：**模型在商品化、语境在分化**——同一个模型，喂了具体语境的那个「像专门训练了几个月」。
- **语境四类**：领域（行业模式与约束）· 历史（试过什么、为什么失败）· 质量（在你的场景里「好」长什么样）· 约束（额度/延迟/可读性）。
- **语境的复利**：好语境 → 更好输出 → 学到哪些语境重要 → 改进语境文档 → 重复；六个月后 B 团队第一天的产出超过 A 迭代一周。
- 飞书官方《飞书豆包怎么用？》的工程侧：**权限即上下文边界**、上下文三准则（相关/时效/可核验）、四层链路（背景→分析→产出→协作）、三个检查点。

## 2. 对照本产品：四类语境的家底

| 语境 | 住哪 | 状态 |
| --- | --- | --- |
| 领域 | agent-rules、平台目录、知识库 13 条经验 | 有料，但每轮手拼进提示词 |
| 历史 | 缺陷台账 138 条、常见坑速查表、失败原因 | **模型完全看不到**（下一步 P0） |
| 质量 | 蒸馏账本 + 用户评分 + 发布数据 | **本轮接线** |
| 约束 | 4~12 秒上限、字数门槛、成本、限频 | 部分在提示词里 |

## 3. 本轮修复：质量语境回流（DEF-138）

- 新增 `buildQualityContext`：同类成功样例（评分 ≥4 或注入过知识）拼成上下文块，单条 ≤400 字、最多 2 条、写明不许照抄事实与数字。
- 接进**助手对话**与**内容创作生成**两条链路；账本新增 `exampleIds` 留痕（数据集与 JSONL 导出都带）。
- 原来的断点：`fewShotExamples` 写好了却只被一个只读接口调用，**从未进过模型上下文**——「越用越好」在机制上不可能发生。

## 4. 验证

| 项 | 方式 | 结果 |
