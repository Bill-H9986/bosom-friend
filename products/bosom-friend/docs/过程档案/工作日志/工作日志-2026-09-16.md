## 2. 根因：Node 解析的基准是**真实路径**

- 联接点布局下，加载 `node_modules/@deepseek-ai/cordis/lib/index.js` 时真实路径落在
  `.pnpm/<hash>/node_modules/@deepseek-ai/cordis/`，它的依赖在**兄弟层** `.pnpm/<hash>/node_modules/` ✔；
- 展开成真实目录后，真实路径就是顶层路径，Node 从顶层逐级向上找 `node_modules`，而
  `.pnpm/<hash>/node_modules` **不在祖先链上** ⇒ 依赖明明在 zip 里却解析不到。

也就是说：**联接点在运行期不是"需要被消除的麻烦"，而是 pnpm 解析模型的一部分**。zip 表达不了它，就必须在打包期
把这套解析关系**改写成不依赖联接点的等价形态**，而不只是把文件搬过去。

## 3. 修法（`repack_kernel.py` 现在两步）

1. **展开**：`os.scandir` 自走目录，遇链接用 `os.path.realpath` 解析真实目标再复制。
   不能用 `shutil.copytree`：它拿 `os.readlink` 的返回值判断链接是否悬空，而 pnpm 写的是**相对**目标
   （`..\.pnpm\@deepseek-ai+dsh-base@file+_0797...\node_modules\@deepseek-ai\dsh-base`），相对路径按当前
   工作目录解析必然判为悬空，于是 `ignore_dangling_symlinks=True` 把**每个链接静默跳过**——实测整棵树只剩顶层
   4 个条目，而脚本还报"成功"。`robocopy /E` 同样不展开 `.pnpm` 兄弟层的联接点。
2. **补齐扁平层**：把 pnpm 自己算好的私有提升层 `.pnpm/node_modules`（`hoist-pattern` 默认 `*`）搬到顶层
   `node_modules`。实测 **387** 个包 + 顶层已有的 **130** 个工作区包 = **517** 个名字，正好是闭包全集；534 个
   `.pnpm/<hash>` 分组里依赖版本与扁平层不一致的 **37** 条边，按包嵌套补一份到 `<包>/node_modules/<依赖>`
   （Node 先看包内 `node_modules`，嵌套副本优先，不会串味）。`.pnpm` 虚拟仓**整份保留**：实测有 17 个多版本包，
   删掉只留一层扁平必然解析错。

## 4. 顺带查出的三处"过时假设"（都假设运行时是一棵普通目录树）

| 位置 | 失效形态 | 改法 |

## 13. DEF-060 收尾：端口隔离的真因是「注入副本按版本缓存」

第一轮只查到「补丁端口写死 31280、探针要 31299」，把补丁改成 `!!js` 读 env 后**仍绑 31280**，当时只能如实记 Open。
收尾时把这条查到底，真因与端口无关：

- `injectWorkspacePackages` 把工作区包物化到 `.pnpm/<id>/`，而这份副本按 **(名字, 版本, peer 集合)** 缓存——
  **改了 `cordis.patch.yml` 却没提版本号，`pnpm install` 不会刷新它**；运行时加载的还是旧配置。
  实测：改文件后 install，注入副本字节不变；把 desktop-bundle 版本 0.2.0 → 0.2.1 再 install，副本立刻变成新内容。
- 修法：端口改成 `!!js Number(process.env.BF_DESKTOP_PORT ?? 31280)` + 提版本号刷新副本。
  实测 `PORT_ISOLATION PASS`：`BF_DESKTOP_PORT=31299` 时只有 31299 在听、31280 不监听。
- 把这条隐式规则变成红线：新增 `desktop/verify-runtime-config-drift.mjs`（逐字节比对三个补丁层与部署根入口，
  版本不一致也判红），接进出包链第 3 步之后。它在这轮**真的红过一次**，指出运行时里是 0.2.0 的旧补丁。

**两个探针的假红也一并修掉**（它们测的是「坏掉的产品」，产品修好后反而必红）：

1. `verify-splash-progress.mjs` 场景 B（端口上没有服务）：端口隔离修好后，应用会**自己把内核拉起来并进入产品页**
   ——那是期望行为。探针改成：进了产品页就记一条 PASS，失败分支的三条断言记 **SKIP**（按项目铁律「SKIP ≠ PASS」，
   单独一类并计入 `skipped`），不再逼着产品去失败。实测 `SPLASH_PROGRESS PASS checks=15 fail=0 skipped=3`，
   场景 A 5/5 全绿（开发态接入既有服务 → 进产品页 → 留痕 2%→80%→100%）。

### 快照仓为什么是无历史提交（实测踩坑，别重犯）

直接 `git push master` 被 GitHub 拒了两次，报的是**远端解包失败**而不是权限错误：

```text
remote: fatal: did not receive expected object 272ffffddd1efd541b7f5f5f16dfb2762dec69e5
error: remote unpack failed: index-pack failed
 ! [remote rejected]   master -> master (failed)
```

原因是这条链要**同时**送出 232 个提交涉及的**全部历史对象**（约 16 MiB pack），
本机到 GitHub 的连接在传输中途反复断（同一时段 `git ls-remote` 也会 20 秒超时）。
换成**无历史快照提交**（`git write-tree` → `git commit-tree <tree>` → 直接推那个 sha）后一次成功：
pack 只含当前树可达的对象，体积小一个量级。

| 事实 | 值 |
| --- | --- |
| 快照提交 | `d17e955e79be288e4b0d0592583a90d8e07cbddf`（无父提交） |
| 校验 | 顶层条目含 `products/` 等全部一级目录；抽查 `products/bosom-friend/docs/结构说明.md`（8,409 B）与 `qa/defects/缺陷台账.md`（45,194 B）与本地一致 |
| 代价 | GitHub 上看不到逐提交历史（本地 `fix/ai-autopublish` 仍是完整历史；每次整理推一个新的快照提交即可） |

### 发布过程里踩到的两个真实问题（都记下来，避免下次重犯）

1. **`Invoke-RestMethod -InFile` 在 Windows PowerShell 5.1 上不是「用文件当请求体」**：它把参数值当正文内容，于是建 Release 的请求体是字面路径 → GitHub 建出一个 **tag 为空**的 Release，并把 Release 名 `0.2.51` 当成了**仓库名**，下载仓一度被改名为 `Bill-H9986/0.2.51`。
   处置：用 `curl.exe --data-binary @file` 重做请求，并把仓库名改回 `zhiyin`（描述、workflow 与内容未受影响）。
2. **`$x.tag_name` 取不到值不代表字段是空的**：`Invoke-RestMethod` 在仓库刚改名时会跟着 301 跳转，把**仓库对象**当成 Release 返回（`id` 就是仓库 id），于是脚本看到 `tag_name` 为空又去建 Release。
   处置：所有 GitHub API 调用改用 `curl.exe` + 显式 `ConvertFrom-Json`，并在关键步骤之间**先读回再决定**（幂等）。

### 16.2 长视频三个症状：根因都在"目标没有翻译成可执行要求 / 生成被当成前端会话内的一次动作"

**症状一：语速太慢、讲解内容太少。** 写稿提示词里从头到尾只有「约 N 秒」这一个尺度，
而模型对秒数没有尺度感——它写出的稿子通常远短于目标；配音时长由字数决定，字数不够只能拖长音。
修法（`server/src/long-video.ts`）：

- 目标折算成**字数下限**（`minScriptChars = 目标秒数 × 4.5`）并入提示词，要求"宁多不少、写成连续口播、不许分点"；
- 写完做**一次**长度校准：不足则用「上一稿只有 N 字、请扩写到不少于 M 字」补写；仍不足就如实生成，不拿重试冒充成功；
- 稿件字数与正文落盘（`scriptChars` / `scriptText`），进度面板与生成记录都能看到"这条片讲了多少内容"；
- `scriptBrief` 带上段数：写稿前就告诉模型"全片约 N 个镜头"，内容要撑满整段。

**症状二：画面场景不搭配而且还少。** 段数在写稿**之后**才由切段结果决定（写稿时没人知道有几个镜头可用），
每段又固定向厂商要 12 秒画面（短文案被拉成慢镜，几段看起来就是同一场景重复）。修法：

- 段数前移：按目标时长算出段数并写进体裁要求——"刚好 N 句，一句一个镜头""相邻句子不许是同一场景的重复描述""画面要在场景之间推进"；
- 每段画面时长按该句文案体量给（`estimateSeconds` 后夹到厂商 4~12 秒），不再一律 12 秒。

**症状三：找不到生成记录、生成过程与等待时间完全不知。** 页面只在内存里持有"我刚起的那条任务"，
从来不读后端任务列表（`GET long-videos` 这个接口一直没有调用方）。修法：

- 进页面即拉「生成记录」（最近 6 条，含进行中的），点任意一条回填参数并继续按真实进度轮询；进行中的任务刷新/重开应用后仍能回来接着看；
- 进度面板补齐可确认的信息：当前阶段（写稿切段 / 逐段生成并拼接）、已用时间、剩余预估（段数 × 每段 1~5 分钟）、稿件字数、已生成秒数 / 目标秒数、每段"等待中"占位。

## 18. Token 与成本记账：Agnes 实测澄清（用户提问驱动）

用户原话：「你知道 Agnes AI 吧！我用的是这个模型！所有 token 消耗没办法记录啊！」。用真实调用把这条链路走了一遍，结论**一半与直觉相反**。

### 18.1 实测（探针 `qa/probes/agnes-usage-probe.mjs`，可重跑）

| 端点 | 用量 | 证据 |
| --- | --- | --- |
| `/chat/completions`（非流式） | **有** | 顶层键含 `usage`：`{prompt_tokens: 58, completion_tokens: 41, total_tokens: 99}`（耗时 770ms） |
| `/chat/completions`（流式 + `stream_options.include_usage`） | **有** | 34 帧，倒数第二帧带 `usage`（含 `completion_tokens_details.reasoning_tokens`），随后 `data: [DONE]` |
| `/images/generations` | 无 | 只有 URL 数组 |
| `/videos` | 无 | 只有 `video_id` 与任务状态 |

顺带一条坑：模型名写错时返回的是 **503**（不是 404），很像网关故障；先 `GET /v1/models` 对齐。可用文本模型为 `agnes-3.0-flash` / `agnes-2.5-pro(-alpha/-beta)` / `agnes-2.5-flash` / `agnes-2.0-flash`。

### 18.2 用量丢在哪一层（这是「记录不了」的真实原因）

`Agnes 响应带 usage` → `DSH 适配器 llm-pi-ai`（`stream.ts` 有 `mapUsage`，但需路由声明 `supportsUsageInStreaming` 才请求 `include_usage`）→ `token-meter` 推导一轮用量 → `agent-loop` 把 `usage` 挂在 `assistant/message` 事件上（`packages/core/session/src/types.ts:313-327`）→ **产品 `kernel-client.ts` 只取文本增量，usage 丢掉** → **`api.ts:2059` 把 `/ai/chat` 的 `usage` 硬编码成 `{0,0,0}`**。

结论：**上游给了，我们的中间层没接**；而硬编码的 0 比「没有字段」更糟——它看起来像实测值。

### 18.3 成本账本的三档口径（已写入学习方案 P3 与条目 14）

| 档 | 内容 | 精度 |
| --- | --- | --- |
| **A 实测** | 文本调用的 input/output/reasoning tokens（取自 `assistant/message` 的 `usage`） | 精确 |
| **B 估算** | 图像/视频按业务量（张数/秒数/段数/重试）；文本按**带标定**的字符换算并给误差带 | 估 |
| **C 墙上时间** | 每步本地计时（含轮询等待） | 精确（自己量的） |

红线：三档分别标注，不许把 B 写成 A、不许把 0 当实测（与 DEF-050「弱信号冒充强信号」同类）。

## 18. P1 第一批：分镜表驱动的通用编排（口播镜与产品镜交替）

用户拍板："A 和 B 都要，但操作多了对客户是灾难" → 设计定稿为**同一条工作流 + 能力降级 + 渐进披露**，

### 18.1 新增的核心中间层：镜头卡片（ZyShot）
