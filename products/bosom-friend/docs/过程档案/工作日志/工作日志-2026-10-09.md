## 十、约束关系检测器（字数口径核验 → 可复用判据模型）

**起因**：核对 `PLATFORM_CONTENT_LIMITS`（平台事实表）与 Prompt 约束语境（`CONSTRAINT_SOURCES`）的字数口径关系。

**核心方法：三个事实物理分开**

| 事实 | 来源 | 谁负责 |
| --- | --- | --- |
| **数值事实** | 代码提取（`MAX_TOPICS = 8`、`PLATFORM_CONTENT_LIMITS.*.topics`） | 检测器只读 |
| **关系声明** | **结构化标记**（`@constraintRelation` + `@constraintTarget` + `@constraintRationale`） | 人工声明 |
| **关系验证** | 检测器**实际计算** | 检测器 |

**四类关系与判定条件**

| 关系 | 含义 | 判定 |
| --- | --- | --- |
| `same-source` | 同一份事实的多处渲染 | 必须追到同一定义 |
| `gen-le-platform` | 生成上限 ≤ 平台上限 | 不等式成立 → `INTENTIONAL_DIFFERENCE`；违反 → `DRIFT` |
| `different-semantics` | 语义不同（如"产品自己的笔记" vs "平台正文"） | 必须登记，否则 `UNVERIFIED` |
| `producer-consumer` | 字段必须有生产者才谈得上执行 | 消费者 > 0 且生产者 = 0 → `DRIFT` |

**三条纪律**

1. **结构化标记声明的是设计意图，不是设计正确性** —— 标记仍在但数值违规，照样 `DRIFT`（自证 D3）。
2. **标记必须绑定字段与目标** —— 缺 `@constraintTarget` 的标记无效（自证 D4）。
3. **自由注释不参与机器判定** —— `MAX_TOPICS` 原本那段写得很清楚的注释只作人工核验依据。

**关系按所有适用平台取最小值，不是只看小红书**

`MAX_TOPICS ≤ min(适用平台已声明的话题上限)`。当前只有小红书声明了 `topics: 10`，故 `8 ≤ 10` 成立；将来新增平台时检测器**自动纳入** min 计算。

**关键：汇总口径分为规则级与事实级**

原先只报规则级，会出现「明细里有 `UNVERIFIED`、汇总却是 0」的矛盾——因为规则级会被更高优先级状态吞掉，**让人误以为整个系统已检查完毕**。现在两行分开：

```
规则级：DRIFT=1  EXTRACTION_FAILED/UNVERIFIED=0  DEAD_CODE(告警不阻塞)=1  其它=7
事实级：DRIFT=1  UNVERIFIED=0（未声明的候选关系在此计数）
```

**本轮产出：DEF-230（接线断裂）**

`maxTotalTextLength` 消费者 2 处、**生产者 0 处**，扫描范围已核实（server/src + kernel/src + 前端 3 个相关文件，无动态构造）。

## 二十八、DEF-240：自动发布意图闸门（事故根因修复）

> **定级说明**：产品负责人明确——**操作失误是触发条件，但系统允许普通提问沿自动发布路径产生外部副作用，这是必须独立处理的工程风险**。仅用 DEF-239（提示词诚实性）无法覆盖。故新增本缺陷，优先级 **P0**。

### 28.1 根因：两条独立缺口 + 一条判据缺口

| # | 缺口 | 证据 |
| --- | --- | --- |
| ① **默认开启** | `store/agentFollow.ts` 的 `enabled: true`；全新 context 无持久化数据（`localStorage` 空）即自动开启 | 实测新 context 读出 `aria-checked=true` |
| ② **执行无闸门** | `executePublishAction` 的 `autoPublish` **完全等同于 `followEnabled`**；服务端已算出的 `wantsPublish` **未随动作卡传递、被前端丢弃**；两张发布卡（`api.ts:2871`/`:2888`）都不带授权标记 | 静态代码 + 调用链追踪 |
| ③ **闸门是关键词级** | `detectPublishIntent = PUBLISH_REQUEST && !PUBLISH_TOPIC && !PUBLISH_NEGATION`；`PUBLISH_REQUEST = /(发布\|发出去\|发到\|…)/` **出现「发布」二字即命中** | **实测**：事故输入（引述+假设+疑问）判为 `true` |

### 29.2 阶段二：统一自动发布入口

**新增共享闸门** `components/Chat/ActionCard/publishAuthorization.ts`：

```ts
export function isAutoPublishAuthorized(action: { explicitPublishIntent?: boolean }): boolean {
  if (action.explicitPublishIntent !== true) return false   // 严格判定，缺失即拒绝
  return useAgentFollowStore.getState().enabled === true     // 还需跟随模式开启

```

**两条路径改为共用同一函数**：

| 路径 | 修改前 | 修改后 |
| --- | --- | --- |

**未授权时的行为**：落到 `IDLE`（显示「去发布」按钮等用户点击）或走发布弹窗人工确认 —— **人工路径未被禁用**。

### 29.3 阶段三：判据从「词表堆叠」改为「优先级判定」

**重构后结构**（顺序即优先级，任一命中即 false）：

```
1. 未出现发布动作措辞                  → false
2. 打听发布（发布记录/频率/流程…）      → false
3. 否定（新增：不打算/没打算/不想/无意…）→ false
4. 讨论语气（新增：问问/想知道/请教…）  → false
5. **句末疑问语气（吗/呢/么/?/？）**     → false   ← 新增判据类别
6. **引述他人指令（他说/让我/要求我…）** → false   ← 新增判据类别
7. 否则 true（启发式结论，非授权证明）
```

**新增的两类判据不是补两个句式**，而是补两个**类别**：原实现只列举具体问法（「可以吗/行不行」），无法覆盖「帮我…吗」这种结构；句末语气与引述结构是更稳的类别级判据。

**函数注释中写明**：`return true` 只是启发式结论，**不等于可靠的用户授权**；调用方不得据此认为「未经授权的发布已被杜绝」。

## 三十二、DEF-240-IMPLEMENT-4：真实 React 组件的隔离执行验证

### 32.1 本轮先发现了一个静态检查看不见的缺口

**在准备组件级测试时，追 SSE → 组件的数据流发现**：服务端写入的 `explicitPublishIntent` **在两条前端转换路径上都被丢弃**，从未到达任何组件。

| 路径 | 位置 | 情况 |
| --- | --- | --- |
| **实时 SSE** | `store/agent/task-instance/sse.handler.ts` 的 `actions.push({…})` | 逐字段映射 `type/platform/accountId/title/description/medias/tags/flowId/draftId/topic/producer/targetSeconds/aspectRatio/_isRealtime`，**没有 `explicitPublishIntent`** |
| **历史加载** | `components/Chat/utils/convertMessages.ts` 的 `.map(item => ({…}))` | 以上一组字段 + **同样没有 `explicitPublishIntent`** |

**后果**：组件里 `action.explicitPublishIntent` **恒为 `undefined`** → `isAutoPublishAuthorized` **恒返回 false** →

- **功能上**：**跟随模式的自动发布完全失效**；

```ts
// sse.handler.ts（实时）
explicitPublishIntent: data.explicitPublishIntent,
// convertMessages.ts（历史）
explicitPublishIntent: item.explicitPublishIntent,
```
