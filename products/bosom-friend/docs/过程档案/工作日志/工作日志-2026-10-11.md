## 三、P1 开工：第一条能力改造（存草稿）

**改前**（kernel/src/index.ts 的 bosom_content_create_draft）：execute 只做校验，然后 `void desc; void platform`，返回 requested + 空 draftId —— 即「只发一张卡给前端，内核自己不写库」。注释写着依据是产品铁律 #2（前端动手执行）。2026-09-29 那次「AI 对用户说已写入草稿箱、而草稿箱里根本没有这条内容」正是这条路径的必然结果。

**改后**：execute 经回环 HTTP 调 POST /bosom-friend/api/contents/drafts，服务端 createPromotion 真的写进草稿箱并回传真实 _id；工具返回 executed + 真实 draftId；render 明确写「已经落库」。

**为什么这么改**：ADR-005 已废止铁律 #2 的「前端动手」；同一文件里出片工具（bosom_content_create_video，L983）早就是「fetch 服务端 → 真执行」的模式 —— 两种模式并存本身就是重构对象。

## 七、P0 故障发现与修复：内核插件树加载失败

**现象**：第一次跑验证时，AI 对话直接返回「大模型调用失败：dsh profile bosom-friend-kernel: DeepSeek Harness runtime is not running」，附 ERR_MODULE_NOT_FOUND。

**根因**：kernel/cordis.patch.yml 新挂的 bosom-computer-use（= @deepseek-ai/dsh-mcp-client）**没有在 bundle/kernel/package.json 里声明依赖**；插件树的解析基准目录是 bundle/kernel/，于是解析不到该包 → **整棵插件树加载失败 → 内核起不来 → 产品 AI 完全不可用**。

**影响面**：从 2026-10-11 挂 Playwright MCP 起，所有 AI 对话都失败（用户侧表现为 AI 没反应或报错）。

**为什么之前没发现**：开发态内核是**懒启动**（第一次对话才 spawn）；HTTP 探测 200 只证明服务端活着，证明不了内核能加载。

**修复**：bundle/kernel/package.json 补 "@deepseek-ai/dsh-mcp-client": "workspace:^" → pnpm install（exit 0）→ 重启开发版 → 内核正常加载，随后一句话链路全程跑通。

**教训（要进标准）**：cordis 配置里挂的裸包名必须在**解析基准目录**的 manifest 里声明；验证「改完能不能用」必须包含**内核握手**这一步，不能只看 HTTP 200。

## 八点十一、DEF-254 修复：SSE 心跳（14:35）

### 根因（有据）

1. 服务端 SSE 只在**有业务事件**时才写流（api.ts 的 safeSse），长工具调用期间**全程静默**；
2. 客户端 fetch（Node undici）的 bodyTimeout 默认 **300 秒** —— 收不到任何数据即判连接死亡，抛 TypeError: terminated；
3. 三次中断全部发生在长任务（发布+引擎、封面生成+多轮）；服务端任务**实际都跑完了**（那次发布甚至成功）。

### 修复

在 api.ts 的 SSE 处理器里加 20 秒心跳：写标准 SSE 注释帧（以冒号开头，客户端按规范忽略），关闭时 clearInterval。只保活，不产生业务事件。

### 验证

改造探针统计心跳帧 → 跑一个 21 秒的真实任务（重新配封面）：**[时长] 21 秒  [心跳帧] 1  [工具序列] bosom_content_list_drafts -> bosom_content_make_cover**，全程未中断。

### 影响

这是「每次对话都可能突然断」的根治：只要心跳在跑，5 分钟以上的长任务（发布、出片、批量生成）不会再被客户端判死。

**验证**：问「草稿箱里现在有什么？哪条已经发过了？」→ 4 条草稿 + 2 条发布记录能对上，作品 ID 7695288326089116991 可见。

### 2. DEF-256：模型编造失败原因（输入质量缺陷）

**现象**：问「我那条发布失败了？原因是什么？」模型答「**封面生成超时**」，而引擎原文是「**标题不能超过20字符，当前: 21字符**」。

**根因（查数据才看清）**：`errorMsg` 原文含 ANSI 颜色码与逐行日志，而 render 截断到 140 字——关键那行**正好被截掉**，模型只看到「小人先检查 cookie、图片和发布时间」，于是推断成「检查封面时出错」。

**修复**：新增 `cleanEngineError()`（去 ANSI、去日志前缀行、保留末 3 行、300 字上限），render 改用清洗后的文本。

**验证**：同一个问题再问 → 模型改口「**标题太长**…回执原文很直接：『标题不能超过 20 字符，当前 21 字符』…把标题压到 20 字以内再发一次就成（例：『35岁转行学无人机？重庆车间实操』17 字）」。

**教训**：模型编造因果，多半是**输入脏了或被截断**，不是它想骗人——修输入质量比反复叮嘱有效。


| 层 | 改了什么 |
| --- | --- |
| **内核工具返回** | `kernel/src/index.ts` 的 generate_script 返回追加：「注意：这只是稿件本身，**还没有进草稿箱**。要对用户说「已存进草稿箱」，必须先调 `bosom_content_create_draft` 拿到草稿 id（cnt-xxxxxxxx）；没拿到 id 就如实说「稿子写好了，还没存」。」 |
| **内容技能** | `.agents/skills/bosom-friend-content/SKILL.md` 加「三条不许违反的硬规矩」：① 生成脚本 ≠ 存草稿 ② 没落库就别说落库 ③ 用户说「做完直接给我看」时必须讲清东西在哪 |
| **如实汇报技能** | `.agents/skills/bosom-friend-truthful-report/SKILL.md` 在第 2 条「已提交 vs 已确认」里补上 `generate_script` 这一对（附实证任务号） |

## 九点零八、★ 发现并修复 DEF-271：45% 的对话撞内核冷启动超时（06:30）

### 怎么发现的（门禁的价值）

上一轮我把 BFS-107.3 做成门禁（`qa/verify-memory-efficacy.mjs`）。**它第一次跑就指出**：
「帮我写一条关于手工皮具工…」这一类 **11 条里一次成功率只有 55%**——而其他四类都是 100%。

我顺着诊断，**11 条逐条看**：

```
16:05 committed 但正文是「大模型调用失败…initialize timed out after 10000ms」  ← 老 bug（DEF-268 已修）
16:09 / 16:18 / 16:26 / 16:28  正常出稿
16:32 / 16:34 / 16:41 / 16:43 / 16:46  全部 error：initialize timed out after 10000ms  ← 真缺陷
16:49 正常（修复线的验证任务，落了草稿 cnt-a8dzwl7z）
```

**根因**：`server/src/kernel-client.ts:463-476` 对新客户端做 `client.initialize()`，**每次握手上限 10 秒（DSH SDK 内部）**，3 次重试共约 30 秒；
而内核要加载 **46 个工具 + 整棵插件树**，**冷启动经常超过 10 秒**。用户第一次说话时必然撞上冷启动 → **实测失败率 45%**。

### 修法：预热（不是把超时调大）

调大超时只是把等待转嫁给用户；**预热**才是把冷启动挪到用户看不见的时候。三处改动：

| # | 文件 | 改动 |
| --- | --- | --- |
| 1 | `kernel-client.ts`（接口） | 加 `warmUp(): Promise<void>`，注释写明 DEF-271 的来龙去脉与「失败不抛」的理由 |
| 2 | `kernel-client.ts`（实现） | `async warmUp() { try { await ensure() } catch { /* 预热失败不影响可用性 */ } }` |
| 3 | `api.ts:7961` 附近（模块顶层启动处） | fire-and-forget 预热：`void (async () => { const warm = createKernelClient(); await warm.warmUp(); await warm.close(); ... })()`——**不阻塞 server 启动**，失败只打一行日志 |

### 验证（严格版）

```
[准备] 杀掉所有 bin-kernel/bin-desktop 进程 + 服务（让冷启动真实发生）
[重启] 服务就绪 12 秒（同时触发预热）
[等待] 40 秒（模拟真实节奏：打开 APP 后过一会儿才说话）

```

- **这是今晚最有价值的缺陷之一**：45% 的对话直接失败，用户会认为「这软件不能用」；
- **发现它的是门禁，不是人**——上一轮刚建的 107.3 门禁第一次跑就把这一类挑出来了；

## 九点一十七、修稳 qa-guard2 的抖动断言（12:20）

### 问题（由 G4 线报告）

**同一份代码三次跑 `qa-guard2`**：26/26、**25/26 BLOCKED**、26/26。
它当时只取了输出尾部，没捕获失败项，但最可能是 `LOGO-官网Hero粒子场-动画进行中(两帧不同)`。

### 根因

`qa/qa-guard2.mjs:306-311` 只采**两帧**（间隔 800ms）比对 dataURL 是否不同；
而粒子场是逐帧重绘的，**800ms 间隔下两帧偶尔恰好完全相同** → 断言随机失败。

### 修法与依据（不是放水）

**判据本身不变**（画面必须在变），只把采样从 **2 帧提到 5 帧**（间隔 400ms）：
任一相邻两帧不同即证明动画在跑，把「采样正好撞上静止瞬间」的概率降到可忽略。
注释里写明了抖动来源与修复理由。

### 验证（三次）

```

修复前：26/26 ｜ 25/26 ｜ 26/26
```

**为什么这条值得修**：qa-guard2 是**最高测试权限**的「陌生人之眼」门禁（产品铁律 #1），
**它自己抖动会掩盖真问题**——某次真失败会被当成「又抖了」而不被追。

| --- | --- | --- |

**第二段（真正让用户受害的那段）：就绪判据太宽，把残缺当成好的。**

```js
// desktop/electron/kernel-extract.cjs:60
function kernelRuntimeReady(target) {
  return fs.existsSync(path.join(target, RUNTIME_MARKER))   // 只判"在不在"
}
```

于是 `ensureKernelExtracted()` 一进门就 `return`（**不兜底**）——而它的注释里明明写着：

> 判据只认入口文件：解压工具可能"退出码 0 但什么都没解出来"（长路径被截断、磁盘写满、杀软拦掉一半文件），
> 只看到退出码就当成功，用户会在下一步收到一个和这里无关的错误。

**它预见到了"什么都没解出来"，却没覆盖"文件在、但是 0 字节"这一种。**

### 我是怎么一步步定位的

1. 端口不监听 → 看安装版日志 → `Cannot find package '@deepseek-ai/dsh-sdk-client'`；
2. 查安装版 runtime：`.pnpm` 不存在、顶层只有 20 个包（**按字母序停在 dsh-api-session-controller，像被截断**）；
3. 查包内 `resources\kernel-runtime.zip`（**64.3 MB，还在**）——注释说"安装器解压成功后就会删掉它"，**它还在＝那次解压失败了**；
4. 用自带解压器把 zip 解到临时目录：**`UNZIP_OK files=23392 bytes=234667457 ms=11740`** → **zip 完好、解压器正常**；
5. 于是问题只能在"解压之后有没有被正确判定"——找到 `kernelRuntimeReady`，只判 `existsSync`。

### 我做的修复（判据收紧）

```js
function kernelRuntimeReady(target) {
  const marker = path.join(target, RUNTIME_MARKER)
  try { return fs.statSync(marker).size > 0 }
  catch { return false }
}
```

**修好之后的行为**：残缺运行时会被判为**未就绪** → `ensureKernelExtracted()` 触发兜底 → 用包里的 zip 重新解压（**11.7 秒 / 23392 个文件**）→ APP 正常启动。
**这就是为什么这个修复对"干净机器"尤其重要**：它们没有旧残留，NSIS 那次失败就是致命的。

| ② **长路径关闭 + tar 优先** | 解压阶梯**先用 SYSDIR 下的 tar.exe**，而 installer.nsh:25-31 自己写明「解开的运行时在 APPDATA 下有 ~290 字符路径，tar/Python/libuv 在 LongPathsEnabled=0 时都过不了」 | installer.nsh:115-117 |

| ④ **app 首次启动的兜底被挡住** | kernelRuntimeReady() 只判 existsSync(入口)，而 tar 留下的入口是 **0 字节** → 判为「就绪」→ ensureKernelExtracted() 提前 return → **兜底没跑** | kernel-extract.cjs:60 |

**第 ④ 环就是我修的那一处**（statSync(marker).size > 0）。修完之后，同样的现场会被识破并走兜底——
**已在 0.3.9 上实测复现并验证自愈**（故意写 0 字节入口 + 删 js-yaml → 启动 40 秒端口 UP → runtime 恢复 23392 个文件）。

### 一个值得记的旁证

installer.nsh:30-31 写着：

> A failure here is **NOT fatal, but it must never be silent**: the app would otherwise unpack 430MB
> on the splash screen and a user would only see a broken app minutes later (**DEF-046**).

**这说明「解压失败要能被兜底」是设计时就写下的契约，而且 DEF-046 已经登记过同类问题**；
本次是它的**复发**——只不过这次不是「静默」，而是「**兜底入口被就绪判据挡住**」。

### 结论

- **不需要再改 NSIS**：静默不改 UAC 是正确取舍，失败保留 zip + 明确告知也是正确设计；
- **要补的是 app 端**：已完成（判据收紧），并有复现级验证；
- **DEF-275 可以结案**，处置栏里「查 NSIS 那一步为什么部分失败」已由本节回答：**因为静默安装不敢开长路径，tar 在深路径上过不去**。

### 剩余（不计入今晚）

若要让**静默安装也不失败**，可选做法是：静默时直接用内置解压器（它自带长路径前缀，不依赖长路径开关），
即**在 IfSilent 分支把阶梯顺序倒过来**——但这会拉长静默安装时间，属「优化」而非「修 bug」，记入待办。

## 九点三十一、静默安装不再留半截运行时（21:00，巡检第 5 次触发后推进的下一项）

### 做了什么

在 `desktop/build/installer.nsh` 的解压阶梯前加一条：**静默安装直接走内置解压器**。

```nsis
; [2026-10-12, DEF-275 follow-up] A silent install (/S) must not raise UAC for long paths,
; and the first rung (tar.exe) provably fails on deep paths when LongPathsEnabled is 0 ...
; A partial failure is worse than a slow one: it leaves a HALF-EXTRACTED runtime in userData
; (measured on 0.3.8: 0-byte runtime\bin-desktop.mjs, 20 of 248 scope packages).
IfSilent bf_kernel_force_builtin

IfFileExists "$SYSDIR\tar.exe" 0 bf_kernel_no_tar
  ...
bf_kernel_force_builtin:
bf_kernel_no_tar:
```

### 为什么这样改

第 36 轮的根因链已经指明：**静默安装（/S）时不为长路径弹 UAC 是正确取舍**（NSIS 原注释：never raise UAC without a visible reason），
但**阶梯第一步的 tar.exe 在 LongPathsEnabled=0 时必然在深路径上部分失败**——
**部分失败比慢更糟**：它在 userData 里留下半截运行时，而把「半截」重新变成「完整」原本要靠 app 端兜底。

app 端兜底已经修好（上一轮的 `kernelRuntimeReady` 判据收紧），**但最好的修法是根本不制造那个半截状态**。
内置解压器自带长路径前缀、不依赖注册表开关，所以静默时直接用它是**从源头消除**这类现场。

### 判据与校验

- `installer.nsh` **必须 ASCII-only**（文件头第 13-14 行写明：makensis 按 ANSI codepage 读包含文件，非 ASCII 会乱码）
  → 我逐字符扫过：**non-ascii chars: 0** ✅
- `IfSilent` 用法与文件里既有的 L58 / L84 一致（同一种两参数/单参数写法）✅
- 标签 `bf_kernel_force_builtin:` 与 `bf_kernel_no_tar:` 前后相邻，静默分支**汇入**原第二步（内置解压器）✅

### 待验证（正在做）

重新打包 **0.4.0**（改了安装行为，所以进次版本号）→ **静默装机** → 验证两件事：
1. **装机后 runtime 直接是完整的**（不用等 app 兜底）；
2. 启动后对话正常。

## 九、发现（待立项）
