## 十五、两个门禁判据被修正，都做了负向对照（17:00–17:35）

### ① 写操作数：从硬编码改成当场计数

上一轮把 `WRITE_OPS` 从查不到出处的 121 改成实测 111，但它**仍是硬编码**——有人加路由不会有人知道。
现在改成门禁自己数（两种独立数法交叉校验），并新增断言：**分母与基线不一致就判红**。

**中间踩了一个坑，值得单独记**：

我第一版断言写的是「两种数法条数不一致就判红」。负向对照证明**它是个假门禁**——
两种数法的扫描窗口完全对称（都是 4 行），一条路由要么两边都数得到、要么两边都数不到，**永远不会分叉**。
也就是说：**那条断言永远为真，等于没有**。

改成「分母与基线比对」之后，负向对照立刻通过：往 `server/src` 放一条临时路由 →

```
MARVIS_PROGRESS_FAIL 方向错误 1 项：
  - 写操作数（覆盖率的分母）变了：基线 111 → 现在 112。
    若确属能力增删，用 --update 重设基线，并在提交说明里写清新增/删除了哪些路由
```

**教训**：门禁写完必须做负向对照——**不是「它能不能跑通」，而是「它能不能判红」**。

### 撞出的真问题：`bosom_content_update_draft` 的描述落后于实现

查它为什么没被算作「已覆盖」，发现**它用 `fetch` 直接打本地接口**（不是 `callProductApi`），所以两版提取都抓不到。
但读它的实现时看到更严重的事——**描述与实现相反**：

| 位置 | 说的是 |
| --- | --- |
| `description`（旧） | 「内核**不直接写库**，改写由页面执行」+「**回话时必须说『已提交改写申请』而不是『已经改好了』**」 |
| `render`（旧） | 「草稿**已改写并落库**…**已经写回**」 |
| `execute`（现） | **真的写库**：`fetch('http://127.0.0.1:.../contents/' + id, { method: 'PUT' })` |

`execute` 里的注释记着这次改动的来龙去脉：旧实现只返回 `state:'requested'` 把改写交给前端，
依据写的是「产品铁律 #2」——**但铁律 #2 是「未经明确发布指令绝不自动发布」，与改一个草稿的标题毫无关系**。
把「发布需授权」泛化成「所有写操作都要页面执行」，结果是**用户说一句话、管家走完 4 步、草稿一个字没动**（DEF-294）。

**实现已经修正，描述没跟上**——于是模型现在**明明改好了，却只能照描述回「已提交改写申请」**。
同一类错，方向相反（早先是描述超前于实现，现在是实现超前于描述）。

**处置**：`description` 改为「改写某条草稿的标题或正文，**直接写回那条草稿**（不是登记申请，说完就生效）」+
「**回话时说『已经改好了』**」，并把这段历史写进注释，注明教训：
**描述与实现必须同一次改动里一起改，任何一个落后都会让模型对用户说错话。**

### 一句话结论

**「从源码静态提取工具调用的 URL」这条路做不到精确，我不再往下钻。**
权威数字仍是棘轮门禁当场算出来的 **52 个工具 / 111 条写路由 = 47%**。

### 三轮改进的过程（每一轮都更准，但都没到精确）

| 轮次 | 方法 | 已覆盖 | 未覆盖 | 撞到的反例 |
| --- | --- | --- | --- | --- |
| 一 | 泛化正则抓路径字面量 | 19 | 92 | — |
| 二 | 专抓 `callProductApi(` 的第一个参数、按前缀匹配 | 40 | 71 | 工具大量用 `'…' + id + '…'` 拼接 |
| 三 | 再追一层封装函数 | — | — | 撞到 `startTaskTurn` |

**第三轮的发现**：`bosom_task_create` / `bosom_task_follow_up` / `bosom_task_abort` 三个工具都不直接调 `callProductApi`，
而是走文件里另一个顶层函数 `startTaskTurn({ prompt })`；它内部用 `fetch` 打 `POST /agent/tasks`，
而 **URL 是 `'http://127.0.0.1:' + port + '/bosom-friend/api/agent/tasks'` 这样拼出来的**——
任何基于字面量的提取都抓不到它。

### 工具落地方式的真实分布（第三轮实测）

| 方式 | 个数 |
| --- | --- |
| 调 `callProductApi` | **29** |
| 读写 `store.files.*` | **7** |
| 走封装函数 / 变量拼 URL（**本次新发现的一类**） | **16** |

**这三类都在真的办事**，只是落点不同。所以「工具数 ÷ 写路由数」这个公式本身是**粗略指标**：
分母是「服务端能写的地方」，分子是「模型能调的工具」，**两者不是一一对应**——
一个工具可能覆盖多条路由，一条路由也可能被多个工具用，还有工具根本不经路由。

### 所以 P1 的精确施工单该怎么做

**只能靠逐个人读 52 个工具**，读的时候看 `execute` 里**真正落到哪里**（HTTP 路径 / store 域 / 封装函数），
并同时标注「这个工具对应哪些写路由」。**没有捷径**——三轮静态提取已经证明捷径的误报率无法接受。

**这一点本身值得记**：与其再写第四版提取脚本，不如承认「有些事只能人读」，
并把省下的轮次用在真正推进 P1（补能力）上。

### 查清的三件事

**① 我数的 111 漏了 9 条——真实是 120。**

门禁里被人补了一段注释（我上轮加的 `countWriteOps` 还在，外面又加了一层）：

```js
// 单行写法 `{ m: 'POST', p: 'login/mail', h: … }`：METHOD_RE 要求 m: 独占一行，会整条漏掉。
// 2026-10-12 实测：漏 9 条（5 条 login/* + 4 条 note-comment-search 分析类）→ 分母报 111，真实 120。
const SAME_LINE_RE = /m:\s*'(GET|POST|PUT|PATCH|DELETE)'\s*,\s*p:\s*'([^']+)'/
```

**我上轮那句「两种独立数法一致所以 111 可信」是不成立的**：两种数法都是单向扫描、窗口也一样，

reception-engine.ts:624  void runReceptionRound(deps)
reception-engine.ts:466  await processComments(...) / processDms(...)

**而且 `reception-engine.ts` 的文件头就是铁律**：

### 第四步：顺手核实 `bosom_reception_reply` 的诚实性（结论：描述是对的）

```
'**只有用户在这一句话里明确要求回复时才能调用**——对外沟通属拍板类动作，猜错就是以用户的名义发出去。'
'提交成功只代表**已交给平台引擎**，回复到底发出去没有要等任务状态回写——不要对用户说「已回复」。'
```

**它同时做到三件事**：要求用户明确指令、明说「提交成功 ≠ 已发出」、明令禁止说「已回复」。
**L596 那句「不执行任何平台发送」指的是「回写待办生命周期」那个函数**（发送由平台引擎执行），两者不矛盾。

## 二十九、手写升级第五条 + 一个被 tsc 抓住的重复（10:50–11:25）

| 拒绝 | 理由（服务端注释） |
| --- | --- |

## 三十、手写升级第六条：把一条「看着只读、其实会写」的能力掰正（11:50–12:35）

### 发现：同一条路径有两个版本，行为相反

`contents/groups/info/:id` 在服务端有**两个 handler**：

```
routes-content.ts:471  POST → 无条件改 updatedAt 并落盘（body 为空也写）   ← 有副作用
routes-content.ts:486  GET  → 纯查，还多回一个 mediaCount               ← 只读
```

登记表原本只登记了 POST 那条，note 也如实写着「真实行为是写库……已加路径判据，无 order 时本地拒绝、零出站」。
**但用户问「这个分组里有什么」要的是 GET 那条**——它不但只读，还多给一个「这一组里有几条内容」，
正是用户问的答案。

**所以手写版走 GET，并把登记表的 route 与 kind 一起改正**（kind: write → read）。

### 门禁当场抓到我改错了两处（这正是它该做的）

**第一次**：我把 POST 那条从登记表里挤掉了，门禁报：

```
FAIL capability-registry-size-matches | 源码写路由 120 条 vs 登记表 119 条（分母必须与源码同步）
FAIL capability-registry-no-missing-route | 未登记 1 条：routes-content.ts:471 POST contents/groups/info/:id
```

**它是对的**：POST 那条确实存在于源码、确实会写库，**不能因为「我不打算用它」就把它从登记表里删掉**。
处置：**两条都登记**——POST 版作为 `write` 能力单独登记（`toolizable: false`，界面内部用），
GET 版作为 `read` 能力由手写工具承接。

**第二次**：我把「只读归宿」加错了段（加进 `READ_ONLY_LIVE` 而不是 `EXCLUDED_READ_ONLY`），门禁连报两条：

```
FAIL read-kind-coverage | kind=read 的 20 条：…bosom_content_group_info 没有归宿
FAIL gate-lists-no-duplicate-keys | ARGS 里 bosom_content_group_info 出现两次（后者静默覆盖前者）
```

**第二条尤其值得记**：`READ_ONLY_LIVE` 是个「真跑名单」，它的循环会**反过来写 `ARGS`**；
我把 `suggest_reply` 那种写法照搬到它里面，结果它的循环覆盖了我手写的入参——
**而去重断言（上一轮刚修好的那条）当场把这件事指了出来**。
上一轮它抓 `bosom_publish_reschedule`，这一轮抓 `bosom_content_group_info`——**它不是摆设**。

### 结果

```
内核工具验收：151/151 通过          FAIL：无
PASS read-kind-coverage | kind=read 的 20 条：真跑 16 条 ＋ 明确排除 4 条（各带理由）
登记表 120 → 121 条（POST/GET 两条都登记）
```

### 这一轮的方法论收获

**「这条路由是读还是写」不能看方法名（POST/GET），也不能看登记表怎么写，只能读 handler。**
这一条路径上，**名字一样的两个 handler 行为完全相反**；
而门禁的「写路由总数对账」保证了我不能图省事把它从表里删掉。
**两条断言从两个方向夹住了我这一次改动**：一条盯「别漏登记」，一条盯「别重复登记」。

## 三十四、P2 准出确认：工具面是「真的没挂上」，不是靠劝（14:50–15:15）

### 先找回准出判据（而不是凭印象说「已完成」）

章程里 P2 的准出只有一句话：

```
| P2 | 同一句话在不同角色下工具面不同（**被拒绝，不是被叮嘱**） |
```

**括号那半句是关键**：工具面必须**真的被切掉**，而不是靠系统提示词劝模型别用。
「劝」和「切」在界面上看不出差别，只有跑起来才知道。

### 证据：门禁第 11 项就是为这条判据写的

`qa/verify-preset-parity.mjs` 共 11 项，前 10 项比对**文件之间**的一致（roles.json ↔ 五份 preset ↔ 前端镜像 ↔ 运行期副本）；
**第 11 项 `runtime-injection-by-owner` 守的是运行期注入点**，它的注释自己说明了为什么这一项不可替代：

> 对话入口按 `task.agentRole` 把角色注入内核、会话池键带上角色，并在**临时 home 里按 `BF_AGENT_ROLE` 重放内核 apply**，
> 断言 creator 的面里没有发布工具，同时**用 steward 的面里有发布工具做对照（防「面为空」的假绿）**。
> **这一处坏掉时，前面十项一项都不会红。**

实跑输出：

```
PASS runtime-injection-by-owner — creator 41 个工具（发布 0）、steward 125 个（发布 10）
=== 门禁结果：PASS（11/11 项） ===
```

| 角色 | 工具数 | 其中发布工具 |
| --- | --- | --- |
| **creator** | 41 | **0** ← 判据要的就是这个 0 |
| **steward**（对照） | 125 | 10 |

**所以 P2 准出判据成立**：同一句话在 creator 名下时，发布工具**根本没挂上**——不是模型被劝住了，是它拿不到那把钥匙。

## 三十五、代码分区第一步：把内核大文件也冻结住（15:50–16:20）

### 为什么做这件事

P0~P3 已全部准出，P4 卡在「写链路端到端需要人在场」（红线禁止无头浏览器验证）。
于是本轮推进一件可独立完成的事——验收表里「代码组织」那半句：

> | 代码组织 | 一能力一文件 + preset 组装 | 🟡 **做了一半** | preset 组装 ✅；「一能力一文件」❌（内核工具仍集中写在 `kernel/src/index.ts` 一个文件里） |

实测现状：`kernel/src/index.ts` **4065 行**（58 个工具集中于此），另有 data/drafts/generated-tools/jobs/runner 五个小文件。

### 选择「先冻结、后拆分」，而不是直接搬

**这不是我发明的顺序**——项目里已有一条同源门禁，它的注释把理由写透了：

> **为什么先做行数冻结而不是先拆文件**：api.ts 承载对话链路与发布闸门，一次搬 472 KB 的风险极高
> （今晚刚因「按行号区间删代码」误删过 generationRecovery）；先立规矩阻止它继续长大，再分批搬到
> `capabilities/`——**这是风险最低的顺序**。

**内核的情况完全同构**：4065 行里 58 个工具互相引用（共享 store / register / 校验函数），一次性搬走风险同级。
而且那条门禁自己留了口子——「未来若要冻结更多大文件，往这里加」。**内核就是那个「更多」。**

### 做了什么

把 `kernel/src/index.ts` 加进 `qa/verify-api-size.mjs` 的 `FROZEN` 名单，并写下它为什么该被冻结：

```
// 【2026-10-13 增加】内核工具面也冻结。理由与上面四个同源，但形态不同：
// 总纲 L197 的目标形态是「一能力一文件」（capabilities/），而内核的 58 个工具至今
// 仍集中写在 kernel/src/index.ts 一个文件里——这正是验收表里
// 「代码组织：一能力一文件 ❌」那半句的落点。
// 同样先冻结、后分批搬。**冻结之后「新增一个工具」这件事就有了明确判据**：
// 要么放进新的能力文件，要么明确决策后 --update 并写明理由。
```

**顺带把输出的「四个大文件」改成动态计数**——加进来之后不改文案，下一个人会以为内核没被管住。

### 这一步的实际约束力（以及它不做的事）

从现在起，**再加一个内核工具就必须回答「放哪儿」**：放进新文件（符合「一能力一文件」），
或者明确决策后 `--update` 并写明为什么。
**它不会自己把 4065 行变小，但它会让「继续变大」变成一个需要解释的动作。**

## 三十六、打包前门禁 8/9：卡在「一句话端到端」，而根因是模型行为不稳定（16:50–18:20）

### 做了什么

章程 901.15 写着「打包前**必须**过 `verify-before-package`」。在等产品负责人下令之前，我先把这道关跑通。
结果 **8/9 通过**，唯一没过的是「一句话端到端只读用例」：

```

PASS 第二份事实漂移 ｜ PASS 前端 dist 固定 ｜ PASS 开发版在跑 ｜ PASS 陌生人之眼 28 项
FAIL 一句话端到端只读用例：PASS 11 ｜ FAIL 3（共 13 条）
=== BEFORE_PACKAGE_GATE FAIL（8/9）===
先修完、在开发版上跑通再来打包——**打包不是验证手段**。
```

### 三轮跑下来的现象

| 轮次 | 结果 |
| --- | --- |
| 第一次（随打包前门禁） | FAIL 1 |
| 第二次（随打包前门禁） | FAIL 3 |
| 单条重跑 `--case=8` | **PASS**（走 B 等价路径） |

**单条能过、连着跑就挂** —— 这个组合把方向指向了「时序 / 模型行为」，而不是代码。

### 三条失败的逐条定位

**① 用例 4「发布」**：问「我最近发过哪些图文？」（纯只读），期望 `bosom_publish_list_records`，
实际**一个工具都没调** → 判红 B（`没有工具返回就是凭印象回答`）。

**② 用例 10「复盘（数据中心）」**：问「数据中心现在是什么情况？」（纯只读），期望 `bosom_data_dashboard`，
实际**自作主张调了 `bosom_platform_sync_works`**（同步作品数据）→ 判红 C（只读问法下出现写工具）。

**门禁的 `WRITE_TOOL` 名单确实含 `platform_sync_works`，这个归类是对的**——同步会改本地 `records`。
**所以这条判红站得住**：用户没要求同步，模型越权了。

**③ 用例 8「发布（平台分布）」**：单独重跑时**通过**——总管把任务**转交给 operator 管家**且转交生效
（`agentRole=operator`、任务 `completed`），走的是判据 B 的**等价路径**（2026-10-12 产品负责人批准）。
而门禁自己如实标注了它的边界：

```
校验④ **未在观测窗内验证**（已延长观测 91 秒仍未见 bosom_publish_list_records；
      轨迹 3 条：bosom_steward_dispatch、skill、bosom_data_works）
      ——本轮按 ①②③ 判过，**这条不是全量证据**
```

### 结论：不是代码 bug，是模型行为不稳定

三类表现——**该调不调**（用例 4）、**自作主张多做**（用例 10）、**转交且异步**（用例 8）——
指向同一个根因：**同一个问法在不同轮次下，模型的工具使用行为不一致**。

**门禁没有做错任何事**：它的三条判据（A 不许改业务数据 / B 必须真调工具 / C 只读问法不许出现写工具）
都是产品负责人定的口径，而且它**如实标注了自己没验全的部分**（校验④）。

### 对「打包」的实际影响

**打包前门禁是硬门（`BEFORE_PACKAGE_GATE`），它要求这一项必须绿。**
而这一项的抖动来自模型侧，不是我们能在门禁里「修」的——可以做的有两件：

1. **把抖动量化**：多跑几轮统计通过率（当前 1/3 轮全绿），把这个数如实写进交付说明；
2. **让门禁对「转交类用例」的观测窗更宽或加重试**——但那要产品负责人同意放宽口径，**我不擅自改**。

**我停在这里并如实上报**：门禁 8/9，唯一红项根因在模型行为，**是否放行由产品负责人决定**。
