## 0. 总则

### 0.1 五条铁律（违反任何一条 = 该项直接 FAIL）

| # | 铁律 | 来源 |
|---|------|------|
| 1 | **页面可见 = 验收**：业务动作由页面发起、结果在页面可见；`code=0`、日志、数据库写入不能单独证明通过 | EXAM_PROTOCOL / 规范 §5.2 |
| 2 | **DSH 是唯一运行时**：大脑（Agent 循环）和躯干（业务能力）都长在 DSH 上；前端无第二份会话状态 | 0.2.0 方案 §三 |
| 3 | **不伪造**：失败如实显示原因；禁止模板冒充成功、禁止编造数据、禁止把模型拒绝改写成成功话术 | 8/31 审计十条款 |
| 4 | **真实外部副作用逐次获批**：真实发布/真实回复前须明确题目、账号、影响范围并获用户授权 | 0.2.0 方案 §七 |
| 5 | **全程留痕**：每步截图 + 事件日志 + Session Log；失败立即停止→修复→重跑该项 | 规范 §4.2 |

### 0.2 测试分层（规范 §2.4）

| 层级 | 内容 | 门禁要求 |
|------|------|---------|
| L1 | 单元测试（工具参数、规则、Provider、存储层） | 关键逻辑 100% 覆盖 |
| L2 | 集成测试（DSH Kernel + Mock/真实 LLM + 真实工具） | 核心链路必须通过 |
| L3 | 端到端（Electron 主进程 + 自研前端） | 主流程必须通过 |
| L4 | S 级前端监考（真实页面、真实数据根） | 业务动作页面可见 |
| L5 | 打包与干净机器（安装/升级/卸载） | 发布前必须通过 |

### 0.3 优先级与判定

- **P0**：核心功能不可用/数据丢失/伪造成功 → 阻塞发布，当天出方案
- **P1**：主流程严重受阻 → 当前版本必须修复
- **P2**：局部异常有规避方案 → 下一版本
- **P3**：体验/文案 → 排期
- 每条用例判定只有两种：**PASS（页面证据完整） / FAIL（记录编号+现象+截图+复现步骤）**，无"基本通过"。

### 0.4 缺陷记录（规范 §3.5）

每个 FAIL 必须登记：复现步骤、期望/实际、环境与版本、截图/日志/Session Log、缺陷类型（ODC-Lite：需求/设计/代码/数据/环境/测试脚本）、5-Why 根因、回归用例。同"类型+根因"第 3 次复发 → 升级架构整改。

## 执行说明

1. **顺序**：A→B→C（环境与门禁先行）→ D~Q（功能域）→ R（真实副作用收官）→ T（发布总检）。不得跳项。
2. **每步留证**：截图编号 + 事件日志 + Session Log 三件套；只认页面证据，不以后端返回替代。
3. **失败处理**：记录【编号+现象+截图】→ 停止 → 根因修复（附回归用例）→ 重跑该项 → 通过后继续。禁止"补丁叠补丁"。
4. **真实副作用**：R 组与 G2/J5 首次执行前，向用户明确题目/账号/影响范围并获授权。
5. **执行记录**：按清单编号实时写入 `qa/reports/桌面端测试执行记录-<日期>.md`。
