## 1. 大厂方法论：三块基石 + 十二项实践

### 1.1 三块基石（Lean / DevOps / Agile 的共同内核）

| 基石 | 含义 | 出处 |
| --- | --- | --- |
| **小批量** | 一次只改一点点，改完立刻验证 | 精益生产（Toyota Production System）→ 精益创业 → 持续交付 |
| **快速反馈** | 几分钟内知道有没有坏 | 持续集成（CI）/ 部署流水线（Jez Humble & Dave Farley, Continuous Delivery） |
| **可回退** | 出事能退回去，所以敢发 | 渐进式交付 / 金丝雀发布（Netflix）/ 特性开关 |

### 1.2 十二项实践（大厂真实在用）

| # | 实践 | 出处 | 解决什么问题 |
| --- | --- | --- | --- |
| 1 | 走通骨架（Walking Skeleton） | Alistair Cockburn | 先让一条最细的端到端跑通，再长肉 |
| 2 | 特性开关（Feature Flag） | Meta Gatekeeper；LaunchDarkly | 没做完的功能关掉就发，不必等它做完 |
| 3 | 发布火车（Release Train） | Google Chrome（约 4 周一个稳定版） | 日期固定、功能可变，防止发布日期无限推后 |
| 4 | 单向门 / 双向门决策 | Amazon（贝索斯 2015 股东信） | 可逆的决策要快，不可逆的决策才慢 |
| 5 | 渐进式交付（Ring / Canary） | 微软 Windows Insider 通道；Netflix 金丝雀 | 先给 1% 的人，出事只影响 1% |
| 6 | 错误预算（Error Budget） | Google SRE | 允许一定故障率，否则永远不敢发 |
| 7 | 停止线（Andon Cord） | Toyota（自働化 / Jidoka） | 发现问题立即停线，而不是继续生产坏件 |

| 12 | 从用户价值倒推 | Amazon Working Backwards（先写新闻稿） | 先写「用户得到什么」，再决定做什么功能 |

## 2. 本项目特性（客观画像，决定哪些能照搬）

| # | 特性 | 事实 |
| --- | --- | --- |
| 1 | 团队规模 | **1 人 + AI 助手**（不是 1000 人） |
| 2 | 产品形态 | Windows 桌面 .exe（Electron 壳 + 自研内核 + Python 引擎） |
| 3 | 交付方式 | 安装包直接给用户（无应用商店审核，**发布门槛是自己定的**） |
| 4 | 核心价值 | 依赖第三方平台（抖音 / 小红书 / 快手 / 视频号）的页面自动化 |
| 5 | 开发节奏（实际） | 12 天出 74 个版本（约每天 6 个），最多一天 25 个 |
| 6 | 验证成本 | 全量门禁单轮 5~15 分钟，且需先把服务拉起来 |
| 7 | 已有资产 | 分层自检 82 项、回滚包 5 个 + 哈希基线、三大核心 83/89 已过 |
| 8 | 已知过度建设 | 12.8 万份证据文件、84 份门禁报告、S 级监考对标 ISTQB/ISO 29119 |
| 9 | 用户数 | 按现有记录：对外交付 0 版、真实用户 0 |

### 由特性推出的五条约束

1. **不能并行**：单人团队的并行 = 全部半成品。**在制品上限 ≤ 2。**
2. **不能重流程**：任何需要「专门安排一轮」的流程都会执行不下去，必须能一条命令跑完。
3. **不能自证**：没有用户就没有真实信号，所有判断都是自说自话。
4. **不能控制对手**：平台页面随时变，任何「保证成功」的承诺都是假的。
5. **不能无限期**：日期必须固定，范围才是变量。

## 6. 落地 C：新增平台接入（Provider 抽象）

### 6.1 原则

当前平台目录：**抖音 / 小红书 / 快手 / 视频号**（闲鱼已有「即将支持」占位）。
「添加频道」新增平台卡片 + 标注「即将支持」**不需要后端改动**，因此**不阻塞交付**。

### 6.2 七步接入流程（缺一步不算完成）

| 步 | 做什么 | 验收判据 | 估时 |
| --- | --- | --- | --- |
| 1 | 平台目录登记（白名单 + 图标 + 参数限制） | 「添加频道」出现该平台 | 0.5 天 |
| 2 | 登录适配（扫码 / 小程序 / OAuth + 持久化 profile） | 扫码一次后长期免登录 | 1 天 |
| 3 | 发布适配（标题 / 正文 / 话题 / 媒体 / 比例） | 真实发布成功并回传作品 ID | 2 天 |
| 4 | 数据读取适配 | 页面数字 = 平台真实值 | 1 天 |
| 5 | 接待适配（评论 / 私信读取与回复） | 待办可见、回复可达 | 1 天 |
| 6 | 风控适配（节律 / 限频 / 熔断） | 通过风控文档第 7 节验收 | 1 天 |
| 7 | 灰度转正（单账号 7 天） | 0 验证码 / 0 限流 / 成功率 > 90% | 7 天（并行） |

**合计约 7 人日 + 7 天灰度。**

### 6.3 架构要求：三个 Provider（本次最重要的架构优化）

| Provider | 职责 | 实现方式 |
| --- | --- | --- |
| LoginProvider | 取得并持久化登录态 | 扫码 / 小程序 / OAuth |
| PublishProvider | 推送草稿并回传作品 ID | 浏览器自动化 / 官方 API |
| ReceptionProvider | 读写评论私信 | 浏览器自动化 / 官方 API |

**不要为新平台复制一套代码。** 同一套业务逻辑，底层可切换实现：
平台改版只换 Provider；有资质时切官方接口（风险归零）；新增平台不再复制。

## 8.0 今日冲刺：AI 机器人自动回复（客户点名功能）

**今日三重约束**：① 三大核心功能一个都不能丢 ② 7×24 AI 自动回复必须真能自动回 ③ 今天必须出成果。

### 今天的成果定义（先说清楚，避免最后扯皮）

| 层 | 今天必须拿到 | 今天给不了（需灰度） |
| --- | --- | --- |
| 功能完整 | 三大核心 89 个功能点全在、可点、可用（含数据中心、热点、知识库、接待） | — |
| 自动回复 | **AI 读到真实消息 → 自动生成回复 → 自动发送成功**，至少 1 条真实证据 | 长时间稳定率（需 7 天灰度） |
| 安装交付 | 安装包 + 干净机 12 步通过 | 大规模用户验证 |

### 决策闸门（今天最重要的一条纪律）

**第 3 步（手动真实发送）是闸门。** 它没过，就不要往下建自动化。

| 闸门结果 | 今天怎么走 |
| --- | --- |
| 发送成功 | 继续第 4 步开自动开关 → 出包 → 交付 |
| 发送失败 | **立即转向**：交付「读取 + 待办 + AI 生成建议」版本，如实告知客户发送受阻并给出定位结论 |

为什么不绕过闸门：`replied = 0` 说明发送链路**一次都没成功过**。
在没验证的地基上盖 4 小时自动化，失败时你连「是自动化写错了」还是「发送本来就不通」都分不清。

### 目标（今天要拿出的成果）

**一条真实成功的自动回复**：AI 读到一条真实评论/私信 → 自动生成回复 → 自动发送成功 → 页面与平台都能看见。

### 关键前提（决定今天能不能成）

`reception-status.json` 显示 **replied = 0**——发送链路**从未成功发出过一条**。
因此顺序不能反：**先手动打通一条真实发送，再打开自动开关。**
没验证过发送链路就开无人值守，等于把「发不出去」和「发错/重发」直接暴露给客户。

### 根因（已定位到代码行）

`server/src/reception-engine.ts` 两处同样的缺陷：

- 第 335-338 行（评论）、第 401-404 行（私信）：未命中规则的消息被 `rememberSeen()` 打上「已读」后 `continue` 丢弃 → **待办永远为空**
- 规则只有「发货 / 物流 / 价格」两条电商模板，与真实消息（粉丝群消息）零匹配

### 实施方案（复用现有能力，不新建轮子）

| 步 | 改什么 | 复用什么 | 估时 |
| --- | --- | --- | --- |
| 1 | 未命中规则也登记待办 | 改 `reception-engine.ts` 两处各 3 行；`matched: false` 的类型与前端渲染早已支持 | 0.5h |
| 2 | AI 生成回复 | 复用前端「生成建议」既有链路，在轮询轮次内调用 | 2h |
| 3 | **手动触发一次真实发送** | `startPlatformInteraction` + `recordReceptionReply`（`routes-content.ts:1077` 已在用同一对函数） | 1.5h |
| 4 | 打开自动发送（带守卫） | 同上，改由引擎在轮次末调用 | 1.5h |
| 5 | 观察 30 分钟 + 出包 | — | 2h |

### 打开自动发送的交换条件（必须同时生效，缺一不开）

| 守卫 | 规则 |
| --- | --- |
| 熔断 | 验证码 / 滑块 / 操作频繁 / 连续 2 次失败 → 立即停该账号自动发送 |
| 限频 | 评论 ≤10 条/天、私信 ≤20 条/天；每轮 ≤3 条（沿用 `maxPendingPerRound`） |
| 延迟 | 扫到消息后随机等 30 秒 ~ 5 分钟再发，**禁止秒回** |
| 去重 | 同一句话 7 天内不重复；禁止固定模板连发 |

`reception-engine.ts` 顶部那条「不允许后端自动发送」的铁律改为：
**「自动发送必须挂载熔断 + 限频 + 去重三个守卫，缺一不可；守卫缺失时降级为登记待办待人工确认。」**

### 今天的判定（拿到这些才叫成果）

- [ ] 待办列表有真实内容（不再是 0）
- [ ] AI 为一条真实消息生成了回复
- [ ] **该回复真实发送成功**（页面可见 + 平台可见）
- [ ] 自动发送开关打开后，连续 2 轮无人值守成功

### 如果第 3 步失败（诚实预案）

说明发送链路本身不通（登录态 / 选择器 / 平台风控）。此时**不带病交付**：
如实告诉客户「读取已通、发送受阻」，并给出定位结论。**不把未验证的自动发送写进交付说明。**
