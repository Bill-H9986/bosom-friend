# ADR-002：DSH 边界与数据所有权（单运行时）

> 状态：已接受
> 日期：2026-09-03
> 关联：0.2.0统一开发方案、项目铁律 #2/#8、ADR-000/001

## 背景

两条开发线并行、对“业务是否都走 DSH”存在分歧：一条要求所有业务都跑在 DSH 上，另一条担心所有操作都变成 Agent 工具会造成 CRUD 灾难。二者需要一次说清。

## 决策

1. DSH 是唯一应用运行时；所有业务能力注册为 DSH 插件/服务（Service seam），前端只做显示层。
2. “跑在 DSH 上”不等于“都是 Agent 工具”：只有 AI 主动决策执行的动作才是工具；普通增删改查经服务缝直调，不进 Agent 循环。
3. 长外部副作用（登录/发布/同步/客服）是任务队列：有状态、重试、审批、可恢复，不是一次性工具调用。
4. 数据所有权分离：DSH Session 日志只存 AI 对话与工具调用；产品数据店（schema 版本化原子存储，DSH 服务提供）存业务数据。
5. 前端不保存第二份会话状态；删除等操作必须多实体一致，失败要报错，禁止假装成功。

## 后果

- 正面：既满足“所有业务都在 DSH 上跑”，又避免 CRUD 硬塞进 Agent 循环；单一事实源消灭一致性类 BUG。
- 负面/代价：服务与工具的边界必须逐条评审；任务队列比直接工具调用复杂。

## 备选方案

- 全部业务都做成 Agent 工具：否决——删除、列表、上传等会绕 Agent 循环，慢且脆弱。
- 业务独立于 DSH：否决——违背唯一运行时目标，会再次“越开发越不像 DSH”。

## 验证方式

- 每个业务能力登记 DSH 服务或工具二选一，门禁按清单检查；
- 删除/发布/同步的 S 级用例验证多实体一致；
- 任务队列用“退出重开状态可恢复”测试验证。
