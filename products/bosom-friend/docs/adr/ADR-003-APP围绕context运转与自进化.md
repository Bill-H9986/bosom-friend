# ADR-003：APP 围绕 context 运转，并实现自进化（Hermes 形态）

> 状态：已接受
> 日期：2026-09-22
> 关联：ADR-001（前端 AI 会话改走官方内核）、ADR-002（DSH 边界与数据所有权）、DEF-134/135/137/138
> 评审：产品负责人确认（2026-09-22）——按本文件的四条口径继续实现
> 读者：产品负责人 + 实现者。本文件是**路线与判据**，不是完成声明——每一节都写明"今天到哪了"。

## 1. 背景：用户的原话与它指向的缺口

> "将 DSH 底层的 context 上下文功能完全利用起来，必须超常发挥作用！整个 APP 的三大核心功能及所有小功能都要围绕 context 运转！
> 内置知识库也要重点围绕 context 进行，并实现 hermes agent 的 APP 蒸馏自进化功能！"

把这句话落到代码上，指向的是一件事：**今天这个 APP 把 DSH 当成"一次性的 LLM 调用 + 工具注册表"在用，
而 DSH 真正值钱的那一层——会话（Session）与上下文（Context）——几乎没被用上**。

### 1.1 现状盘点（逐条可查）

| DSH 能力 | 今天的用法 | 证据 |
| --- | --- | --- |
| **Session 会话**（history / compaction / title / log） | **每轮一个进程、每轮一个会话，用完即关** | `kernel-client.ts` 的 `createKernelClient` 由调用方 `close()`；会话 id 是 `turn-<时间戳>`（`sessions/` 下每轮一个目录） |
| **多轮上下文** | 服务端把整段历史折成文本再拼进提示词，上限 12000 字 | `chatTranscript` + `CHAT_CONTEXT_MAX_CHARS` |
| **Compaction / 结果修剪** | 内核里挂着，但会话活不过一轮，永远用不上 | `bundle/kernel/package.json` 有 `dsh-compaction*`；无会话复用 |
| **agent-instructions 上下文插件**（AGENTS.md → 上下文，改文件后自动刷新） | **没用**：内核工作目录里没有 AGENTS.md；产品规则是每轮手拼进提示词 | `agent-rules.ts` + `TEXT_ONLY_GUARD` 拼进每一次 `prompt` |
| **time-context / session-reference / file-reference** | 内核闭包里**根本没有**这几个包 | `bundle/kernel/package.json` 依赖清单 |
| **Skill 技能**（可复用流程作为上下文注入） | **没用** | 依赖里有 `dsh-skill*`、`dsh-tool-skill`；产品没有任何写技能的地方 |
| **token 用量与 usage** | 忽略 | 会话事件带 `usage`（实测 `assistant/message.usage`），产品不读 |
| **任务标题** | 产品自己算 | 会话里已发 `session/title`（实测），产品另存一份 title |
| **产品知识库** | 每轮检索出文本块拼进提示词；蒸馏账本已存在 | `knowledge-distill.ts`（`buildKnowledgeContext` / `recordDistillation` / `fewShotExamples` / `distillStats`） |
| **助手能否动手** | 助手对话被 `TEXT_ONLY_GUARD` 禁止调用任何工具，而 `AGENT_OPERATING_RULES` 又要求它"先查后答" | 两条互相矛盾的提示词（本轮已修，见 §4） |

一句话概括：**"上下文"今天是我们自己在服务端手搓的（规则 + 历史 + 知识三段文本），
不是会话的上下文**；而"自进化"只有账本，没有把账本变成下一次的上下文。

## 2. 决策：四条必须成立的口径

### 口径一：**一个任务 = 一个 DSH 会话**（会话是上下文的家）

- 同一个任务的多轮对话进**同一个会话**，只把新一轮的用户消息交给内核；
  历史、压缩、标题、用量都由会话承担，服务端不再手搓 `chatTranscript`。
- 会话落盘复用：进程重启后能"接着上次那条任务说"（现在是每轮新会话，所以做不到）。
- 判据：同一任务第二轮之后，提示词里**不再出现**前几轮正文（历史在会话里，不在提示词里）；
  会话目录从"每轮一个"变成"每条任务一个"。

### 口径二：**模型可见的一切都从上下文来**

- 产品规则、知识库命中、用户偏好、平台约束——一律经**官方上下文通道**注入（instructions / context 插件），
  而不是字符串拼接。收益是可读、可编辑、可审计：用户能在数据根里看到"这个 APP 教了模型什么"。
- 判据：`agent-rules.ts` 的文本不再出现在任何一次 `prompt` 参数里；它有一个落盘的家（数据根下的指令文件）。

### 口径三：**每一条功能都留下可回放的上下文**

- 三大核心（内容创作 / 账号管理 / AI 智能体）的每一次模型调用都要回答三个问题：
  ① 这次给了它什么上下文？② 它做了什么（工具/步骤）？③ 结果回去了哪里（落库/上下文）？
- 今天只有 AI 智能体这一条勉强能答，而且**过程不可见**（本轮修掉了可见性，见 §4）。
- 判据：任一页面发起的模型调用，都能在"我的任务"里看到它的步骤与它用到的知识条目。

### 口径四：**自进化 = 成功经验变成下一次的上下文**（Hermes 形态）

参照旧知音内核里已经写明的三件事（`zhiyin-kernel-host.ts`：对齐 Hermes Skills / MEMORY.md / USER.md / Curator）：

| 形态 | 沉淀什么 | 从哪里来 | 下一次怎么用 |
| --- | --- | --- | --- |
| **技能 SKILL** | 一条**可复用流程**（例如"小红书种草笔记九步"） | 成功且有正向评分的任务`recordDistillation` 记录 | 作为技能上下文注入，模型不必重新摸索 |
| **记忆 MEMORY.md** | 运行事实（哪条链路容易失败、哪个平台限频） | 任务结果与失败原因 | 作为上下文，避免重复踩坑 |
| **画像 USER.md** | 用户偏好（口吻、题材、常用平台） | 对话与选择行为 | 作为上下文，让输出越来越像"给他写的" |
| **Curator 归档** | 久未使用 / 重复 / 过时的技能 | 技能的使用计数与评分 | 合并或归档，防止上下文被垃圾淹没 |

- 硬约束：**只有成功且有正向评分的记录才能升格为技能**（账本里已有 `status` / `rating`）；
  记忆与画像有字数上限，满了先合并再写（否则上下文会被自己的历史撑爆）。
- 判据：同一类任务第二次执行时，上下文里出现第一次蒸馏出的技能/记忆条目；
  且"第 N 次"的耗时或轮数**可测地**少于"第 1 次"（以账本里的样本为准，不靠感觉）。

## 3. 落地顺序（每一步都能单独验收）

| 步 | 内容 | 依赖 | 验收判据 |
| --- | --- | --- | --- |
| ①（本轮已做一半） | 让助手的**过程**可见、可用工具：工具调用/结果实时上界面并落盘 | — | `agent-process-steps.spec.ts`：SSE 有过程帧、任务消息有过程记录、正文分多帧到达 |
| ②（本轮已做） | 助手对话注入知识库上下文并入蒸馏账本 | — | 同上 spec + 知识块非空时的账本记录 |
| ③ | 一个任务 = 一个会话：进程内复用（先做单进程多轮），再做到跨重启 resume | SDK `session/prompt` 可对同一会话续轮（实测 `getOrCreateSession` 支持），需解决"落盘会话 resume" | 同一任务会话目录只有一个；第二轮提示词不含历史正文 |
| ④ | 产品规则/知识改走 instructions 上下文文件 | ③（或独立：`agent-instructions` 已在 `dsh-base` 内） | `agent-rules` 文本不再拼进 prompt；数据根里有可编辑的指令文件 |
| ⑤ | 知识库成为 context provider（检索入账 + 注入留痕） | ③④ | 会话事件里能看到"这次注入了哪几条知识" |
| ⑥ | 蒸馏闭环：技能/记忆/画像 + Curator | ⑤ | 同类任务第二次的上下文里有第一次的技能；Curator 归档有计数依据 |
| ⑦ | 三大核心全部接入：创作/账号/发布/接待的每次调用都带上下文并留痕 | ①~⑥ | 每个页面的模型调用都能在"我的任务"里回放上下文与步骤 |

## 4. 本轮已经落地的部分（不夸大为"完成"）

1. **过程可见（DEF-134）**：内核会话的 `tool/call` / `tool/result` 实时转发给界面并写入任务消息，
   "我的任务"里回看能重放整条过程；正文在没有增量通道时按**模型自己的时间戳**回放成逐字出现。
2. **助手不再被禁止用工具（DEF-135）**：`TEXT_ONLY_GUARD` 只留给纯文本生成用途（写稿/分镜/翻译），
   助手对话放开——`AGENT_OPERATING_RULES` 本来就要求它"先查后答"。
3. **助手对话注入知识库并计入蒸馏账本**：`buildKnowledgeContext` 的命中与字数落进账本（自进化的原料）。
4. **两个面板同步（DEF-136）**：删除任务时清掉右侧助手那份对话；"新对话"在详情页会带着主区域一起走。

**没有做的**（不要读成已完成）：③~⑦ 全部。今天的多轮上下文仍然是"服务端折文本"，
会话仍然是每轮一个，技能/记忆/画像的蒸馏与 Curator 一行代码都没有。

## 5. 为什么按这个顺序

- ① ② 是"看得见"的前提：过程不可见时，后面所有"上下文用得好不好"都无从观察（用户的原话正是"不要只有两种状态"）。
- ③ 是一切的地基：会话不复用，"上下文"永远只是提示词里的一段文本，compaction/技能/记忆都没有容器。
- ⑥ 必须有 ⑤ 的留痕才谈得上评价：没有"用了哪条知识/哪个技能"的记录，蒸馏就只是又一次文本拼接。
