# ADR-000：DSH 内核迁移采用绞杀式双入口

> 状态：已接受
> 日期：2026-09-02
> 关联：门禁 DSH 三红灯、REQ-009/017/018、[DSH内核统一执行方案-v2](../../../../DSH内核统一执行方案-v2.md)
> 评审：Codex（执行方）拟定，产品负责人委托确认（2026-09-02）

## 背景

现有产品把 dsh-web-app 当外壳，业务存在直连模型接口与自研 harness，一键门禁 3 项红灯；目标是“官方 DSH 内核 + 自研前端，无 DSH UI”。一次性替换风险高：当前唯一可运行版本就是旧路径，而 4 个安装包是仅有的回滚物。

## 决策

采用行业标准的 Strangler Fig（绞杀式）迁移 + 入口级特性开关：

1. 旧入口 launcher/src/bin.ts 保持不变，作为随时可回退的旧路径；
2. 新增并行内核入口 launcher/src/bin-kernel.ts：dsh-base + dsh-sdk-jsonrpc-server + dsh-bosom-friend-kernel，前端经官方 SDK 客户端 `DeepSeekHarness` 驱动，无任何 UI；
3. 新旧并跑：逐条业务功能（AC）从旧路径迁移为内核工具，S 级前端验收通过一条才切一条；
4. 全部 AC 覆盖 100% 且门禁全绿后，才改默认入口并移除 dsh-web-app；
5. 回滚 = 切回旧入口 / 旧安装包，分钟级。

## 后果

- 正面：每一步可独立验证，任何时刻都能回退，风险被切成小块。
- 负面/代价：迁移期内两套入口并存，维护成本上升；必须防止“永久并行”，第 4 步的清理有明确触发条件。

## 备选方案

- 大爆炸式一次性替换：否决——无法回退，旧系统是唯一可运行版本，风险不可控。

## 验证方式

- 内核入口 smoke：JSON-RPC `initialize` 正常应答、`session/prompt` 走通；
- 门禁 DSH 三红灯按迁移进度逐个清零，而非一次清零；
- 每条迁移的 AC 由 S 级前端验收出页面证据后才改“已覆盖”。
