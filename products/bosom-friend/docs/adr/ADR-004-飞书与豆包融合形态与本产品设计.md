# ADR-004：飞书 × 豆包的融合形态，与本产品的对应设计

> 状态：已接受
> 日期：2026-09-22
> 关联：ADR-003（context 与自进化的七步路线）、S1–S5 落地路线
> 评审：产品负责人确认分工与方向（2026-09-22：「前端就是飞书，后端 DSH 内核充当豆包」）
> 读者：产品负责人 + 实现者。本文回答三件事：**那两家的 1+1>3 到底是什么机制**、**本 APP 差在哪**、**怎么落**。
> 配套：ADR-003。本文是它的产品形态说明；做到哪一步见执行档案（见 `README.md` 的"落地到哪了"）。

## 一、研究的结论：1+1>3 不是"模型更强"，是三种乘法

### 1.1 两家的分工（有据可查）

| 一侧 | 它提供什么 | 证据 |
| --- | --- | --- |
| **飞书**（工作现场） | 结构化对象（文档 / 表格 / 多维表格记录 / 幻灯片）、对象之间的关系（属于哪个项目、谁负责）、权限（可用范围、协作者、审计日志）、协作痕迹（评论、变更） | 飞书 aily《企业工作伙伴》《角色权限配置》《在字段捷径中使用多维表格智能体》 |
| **豆包工作**（理解与执行） | 围绕目标**自主拆解任务、调用工具、持续推进**；与飞书**深度打通**，按"上下文"完成工作；一次指令串联多个飞书应用（检索 → 文档 → 表格 → 幻灯片）；从对话框走到桌面（虚拟桌面 / 远程指令 / 云电脑） | 光明网 2026-08-26《从"帮你想"到"替你做"：豆包工作接管职场待办清单》 |

报道里的一句是关键：**"与飞书深度打通，让 Agent 基于企业办公环境场景，根据'上下文'以更准确地完成工作"**
——"上下文"指的不是用户打的那句话，而是**工作现场本身**（文档、表格、规范、历史、权限）。

### 1.2 三条乘法（1+1>3 的真正来源）

1. **对象即上下文**：模型不用猜，因为每个对象自带结构、关系、权限与历史。
   例：豆包写调研方案前会**读设计规范文档**（这就是把"现场文件"当上下文）。
2. **对象即 AI 入口**：AI 不是另一个页面。多维表格的**字段捷径 / 智能体**让每一行每一列都能跑 AI——
   数据自己会动，人不用把数据搬进对话框。
3. **执行结果回流成新上下文**：产出落回现场（文档/表格/幻灯片），下一次任务读到的是**已经变厚的现场**。
   这是唯一的"复利"来源：第 N 次比第 1 次快，靠的不是模型变强，而是上下文变厚。

**反过来说，1+1<2 的三种断裂**（也正是本 APP 今天的样子，我在这轮量到过）：

| 断裂 | 表现 | 本 APP 的实测证据 |
| --- | --- | --- |
| 对话是"另一个世界" | 助手不知道你在看哪条草稿、哪个账号 | 助手对话被 `TEXT_ONLY_GUARD` 禁止调工具、知识块传空串（DEF-135） |
| AI 只在对话框里 | 业务对象不会自己动，人肉搬运 | 草稿箱/素材库/发布记录都没有"AI 动作"入口；工具只有 9 个只读查询 |
| 结果不回流、经验不沉淀 | 永远停在"第 1 次" | 蒸馏账本有记录但不回流成上下文；技能/记忆/画像一条都没有（ADR-003 §1.1） |

## 二、本 APP 的形态：**内容运营的操作系统**

把"飞书一侧"换成这个 APP 自己的工作现场，"豆包一侧"换成 DSH 内核里的模型与工具，形态就清楚了：

### 2.1 工作现场（上下文的家）

| 现场对象 | 已有的数据 | 缺的上下文能力 |
| --- | --- | --- |
| 草稿箱（内容记录） | 标题/正文/素材/平台/状态 | 每条草稿可被 AI 读写；生成时的上下文（人群/卖点/历史表现） |
| 素材库 | 图片/视频/分组/使用次数 | 素材与内容的对应关系；"这条内容的素材为什么选它" |
| 发布记录与数据 | 作品 ID/播放/点赞/评论 | 复盘上下文（哪条好、为什么好）→ 回流成下一次选题的上下文 |
| 平台账号 | 登录态/粉丝/平台 | 账号定位与人设作为长期上下文 |
| 知识库 | 笔记/蒸馏账本 | 检索命中要留痕、要能回流成技能 |
| 生成记录（长视频/任务） | 稿件/分镜/步骤 | 过程即上下文（本轮已让步骤可见） |
| 接待待办 | 评论/私信/规则 | 客户画像与历史回复风格 |

### 2.2 目标形态（用户看到的四件事）

1. **你说需求，它做完整件事**：拆解 → 查现场 → 出内容 → 落回草稿箱 → 给出发布入口（动作卡）。
   今天已经有骨架（动作卡 + 工具），缺的是"查现场"这一层（工具覆盖 + 上下文通道）。
2. **每个对象上都有一个 AI 动作**：草稿上的「AI 改标题 / 生成话题 / 合规检查 / 配图建议」，
   账号上的「AI 定位与风险评估」，发布记录上的「AI 复盘」。**结果写回那个对象**，不是给你一段文本。
   对应飞书多维表格的"字段捷径/智能体"。
3. **助手知道你正在看什么**：在草稿 A 上问"这条怎么改"，它读的是草稿 A，不需要你复述。
   这要求"焦点对象"进入上下文（页面 → 会话）。
4. **越用越像你的**：第 N 次做同类内容时，上下文里有：你的口吻（画像）、你踩过的坑（记忆）、
   上一次成功的流程（技能）。这就是"自进化"，判据是**轮数/耗时/返工率**下降，不是模型换版本。

### 2.3 与 ADR-003 七步的对应

| 目标形态 | 依赖的 ADR-003 步骤 | 状态 |
| --- | --- | --- |
| ①做完整件事（查现场） | ③会话复用（已落地地基）+ ④上下文通道 + 工具覆盖 | ③ 本轮落地 |
| ②对象自带 AI 动作 | ⑤知识/Focus 作为 context provider + 写回工具 | 未开始 |
| ③助手知道你在看什么 | 焦点对象 → 会话上下文（页面状态进上下文） | 未开始 |
| ④越用越像你的 | ⑥技能/记忆/画像 + Curator | 未开始 |

> 上表的「状态」是**写这份决策时**的快照（2026-09-22 第一轮），不改写：每一步做到哪了、判据是什么，
> 见执行档案 `../过程档案/方案与路线/飞书×豆包-深度优化执行方案.md`（§3.x 逐轮记录）。

## 三、本轮落地的地基：**一个任务 = 一个 DSH 会话**

这是所有乘法的前提：上下文得有容器。

- 之前：每轮新进程 + 新会话 + 用完即关，历史靠服务端折成文本重发（上限 12000 字，每轮重发，成本平方级）。
- 现在：**任务级内核池**（上限 4 个，LRU 释放）。同一任务的第二轮只送**本轮这一句**，
  前几轮由会话承担（压缩、标题、用量、后续的技能注入都在会话里）。
- 三条边界都写了代码与用例（`agent-session-reuse.spec.ts`）：
  ① 冷启动喂一次历史，续轮不再重发；② 换任务换会话；③ **中断作废会话**（模型被掐断后上下文不可信，
  下一轮冷启动并把历史喂回来）——这条如果不做，中断过的会话会带着半截上下文继续答。
- 已知限制（写进代码注释）：会话注册表在**进程内**，进程重启后同名会话的日志已存在，创建会失败；
  所以会话 id 带进程内序号，跨重启的 **resume** 仍是 ADR-003 ③ 的后半段（未做）。

## 四、路线（按"乘法"排序，每一步都可验收）

| 步 | 内容 | 验收判据（可测） |
| --- | --- | --- |
| **S1** | 焦点对象进上下文：页面当前对象（草稿/账号/记录）随每轮请求进会话 | 在草稿 A 上问"这条怎么改"，回答里出现 A 的标题/正文特征；换到草稿 B 再问，回答跟着换 |
| **S2** | 对象自带 AI 动作：草稿/账号/发布记录上的 AI 动作写回对象 | 点一次「AI 改标题」，对象字段真的变了（服务端回读），不是只弹一段文本 |
| **S3** | 上下文通道：产品规则与知识库检索走 instructions/context provider，并在会话里留痕 | `agent-rules` 文本不再出现在 prompt 参数里；会话事件里能看到注入了哪几条知识 |
| **S4** | 自进化闭环：技能（成功流程）/记忆（坑）/画像（口吻）+ Curator | 同类任务第二次的上下文里出现第一次蒸馏的技能；轮数或耗时下降（账本可证） |
| **S5** | 三大核心全接入：创作/账号/发布/接待的每次调用都带上下文、都留痕、都能回放 | 每个页面的模型调用都能在"我的任务"里看到步骤与用到的知识条目 |

**先说清楚写这份决策时（2026-09-22 第一轮）到哪了**（此后每一轮的进度与证据见执行档案 §3.x，本文不再改）：
S1~S5 **当时都还没做**；那一轮做的是它们共同的地基（会话复用）+ 前一轮的
过程可见与知识入账。ADR-003 的 ③ 已完成前半段（进程内复用），④⑤⑥⑦ 未开始。

## 附录 A（2026-09-22 第二轮研究）：视频里那套「语境」方法论，与本产品的四类语境对照

用户给的参考视频（抖音「光羽的平行世界」：《AI时代赚到钱的公司，都深度理解了 context 是什么》，
话题 #豆包工作 #2026飞书未来无限大会 #context #公司AI化；该账号也是本产品分镜节奏的标定来源）
指向的核心文本是 *Context is the new Moat*（《语境才是真正的护城河》）。读完把它**可执行的部分**落到本产品上。

### A.1 那套方法论讲了什么（要点）

| 要点 | 原文口径 |
| --- | --- |
| 模型在商品化、语境在分化 | 「当所有人都能用上最先进的模型时，真正的竞争优势不再是模型本身，而是语境」 |
| 同一个模型，不同结果 | 两个开发者用同一个模型：一个得到通用客服机器人，另一个「感觉像专门训练了几个月」——差别只在喂了什么语境 |
| **语境有四类** | **领域**（行业特定模式与约束）· **历史**（试过什么、为什么失败）· **质量**（在你的场景里「好」长什么样：好/坏样例）· **约束**（免费额度、延迟、可读性这类真实限制） |
| 语境会复利 | 飞轮 = 好的语境 → 更好的输出 → 学到哪些语境重要 → 改进语境文档 → 重复；六个月后 B 团队第一天的产出就比 A 迭代一周还好 |
| 语境的形态 | 不是「提示词里多写点」，而是**结构化、可维护、可更新的语境文档** |

飞书官方《飞书豆包怎么用？》给的是同一件事的工程侧：**权限即上下文边界**（豆包工作沿用用户本人在
飞书里的身份与对象权限）、上下文三准则（**相关性 / 时效性 / 可核验性**）、四层链路
（背景理解 → 问题分析 → 成果生产 → 团队协作）与**检查点**（背景、结论、交付三处确认）。

### A.2 本产品的四类语境：有什么、缺什么

| 语境 | 本产品里它住哪 | 今天的状态 |
| --- | --- | --- |
| **领域语境** | server/src/agent-rules.ts（身份/红线/平台规则）、平台目录、知识库 13 条经验 | 有料，但**每轮手拼进提示词**，还不是可维护的语境文档（ADR-003 步④） |
| **历史语境** | 缺陷台账（138 条）、知识库「常见坑速查表」、生成记录的失败原因 | **模型完全看不到**——最刺眼的一处：真金白银踩出来的坑，没进过一次上下文 |
| **质量语境** | 蒸馏账本（每条生成/对话都留样本，用户可评分）+ 发布后的真实数据 | **本轮接线**：评分 ≥4 或注入过知识的成功样本进上下文（见 A.3） |
| **约束语境** | 厂商 4~12 秒上限、字数门槛与语速、成本账本、平台限频 | 部分在提示词里（字数门槛），部分只在代码与文档里 |

### A.3 本轮落地的「复利第一环」：质量语境回流（DEF-138）

fewShotExamples 早就写好了（成功 + 评分 ≥4 或注入过知识），但**只被一个只读接口调用过**，
从未进过任何一次模型上下文——用户评了五分的稿子，下一次生成看不到。「永远停在第一次」就是这么来的。

现在：

- 新增 buildQualityContext(knowledge, task, limit)：把同类成功样例拼成
  【你自己的成功样例（同等水准交付；可借用结构与口吻，不要照抄其中的事实与数字）】块，
  单条产出上限 400 字、最多 2 条；
- 接进**助手对话**与**内容创作生成**两条链路（各自按任务类型取，聊天样例不会串到图文生成上去）；
- 账本新增 exampleIds：这一次用了哪条样例**留痕**，数据集接口与 JSONL 导出都带上它——
  没有这份记录，「第 N 次是否真的用上了前几次的经验」就只能靠感觉。

判据（quality-context.spec.ts 6 条 + quality-context-wiring.spec.ts 2 条端到端）：
第一轮对话 → 给那一轮评五星 → 第二轮送进内核的提示词里**出现第一轮的产出**，且新样本记下了样例 id；
未评分且未注入知识的产出不算基准；对话样例不串到图文生成。

### A.4 由此重排的下一步

| 优先级 | 做什么 | 对应四类语境 |
| --- | --- | --- |
| **P0** | 历史语境入上下文：把「常见坑速查表」与最近的真实失败原因做成上下文块（138 条缺陷与速查表是现成资产） | 历史 |
| **P0** | 约束语境入上下文：成本/限频/时长上限与字数门槛收敛成一份可维护的约束块 | 约束 |
| P1 | 领域语境改成数据根里可编辑的指令文件（ADR-003 步④） | 领域 |
| P1 | 用发布后的**真实数据**给样本打分（播放/点赞/评论），而不是只靠手点五星 | 质量 |
| — | （上一条已落地 2026-09-22，见执行档案 §3.18：同账号内比、只有跑赢的给分、用户的分绝不覆盖、样本太少不排名）| — |
| P2 | 检查点：复杂任务在「背景/结论/交付」三处让用户确认（飞书那套的可验收性做法） | 全部 |

> **两条 P0 的落地结论**（2026-09-22，证据见执行档案 §3.17）：
> ① 历史语境：**常驻 + 检索两条通道**——产品行为级的坑常驻在语境文件里，
> 「最近的真实失败原因」从本机数据实时渲染；「常见坑速查表」的 56 条是开发/交付级的坑，
> **不整份塞进常驻语境**（对内容助手是噪音），它们作为知识库条目按相关度检索进上下文。
> ② 约束语境：已收敛成**从唯一出处派生**的一份块（各上限 import 自各自模块），
> 并补齐了 P0 点名的成本与时长口径；核对时修掉了两处与代码对不上的手抄数字。
> 表里其余条目的进度同样只看执行档案。
