## 1 背景与目标

### 1.1 背景

旧《商用上架准出准则 v1.0》把「保证所有功能都能正常用」拆成了可执行门槛，这个思路是对的；
但它的判据落点是**「功能能不能点」**（S 级前端监考 + 30 条页面硬验收），
与本轮重构后的唯一口径 **「一句话办得成」**（BFS-104-R）冲突。

**本版要解决的问题**：发布前逐项核对时，每一项都必须是**可判定、有出处、能复算**的，
而不是「看起来没问题」。

### 1.2 目标（编号化）

| 编号 | 目标 | 判据 |
| --- | --- | --- |
| **G1** | 每次发布有唯一判据集 | 本件 R1~R9 覆盖交付全部硬要求，模板不额外增删 |
| **G2** | 四项硬证据可复算 | 数据指纹 / 回退包 / 版本单源 / 验收记录各自给出命令或文件路径 |
| **G3** | 签字的含义明确 | 签字 = 本件 R1~R9 全部通过；任一项不通过即不签字 |
| **G4** | 不通过有处置路径 | 第 6 节给出冻结、修复、复验、上报四步 |

## 4 四项硬证据（怎么取、怎么判）

### 4.1 数据指纹

**为什么单列**：升级或卸载把用户数据写坏，是运营期最贵的事故；而「数据还在」这句话本身不可判定，
必须换成两个数字：**文件数**与**总字节数**。

| 步骤 | 动作 | 判据 |
| --- | --- | --- |
| 1 | 升级/卸载**前**取指纹 | 记录文件数与总字节数 |
| 2 | 执行升级（覆盖安装）或卸载 | 过程无报错 |
| 3 | 升级/卸载**后**取指纹 | 与第 1 步**完全一致**（任何差异都要给出解释并登记） |
| 4 | 装回后核对业务可读 | 账号、草稿、作品数据在页面上仍可见 |

**取指纹的命令**（数据根 `%USERPROFILE%\.bosom-friend\bosom-friend`）：

    Get-ChildItem -LiteralPath "$env:USERPROFILE\.bosom-friend\bosom-friend" -Recurse -File |
      Measure-Object -Property Length -Sum |
      Select-Object Count, Sum

**格式样例**（取自 0.2.61 的历史记录，仅示范写法）：`2,813 文件 / 581,755,123 字节`，卸载前后逐字节一致。

**反例（判红）**：只说「数据保留策略与说明一致」而没有任何前后数字；指纹不同却解释为「正常波动」。

### 4.2 回退包

| 项 | 判据 |
| --- | --- |
| 回退网口径 | **当前出货版本 + 上一版本**，两份都在库在 |
| 存放位置 | 仓库外固定目录（`qa/baseline/installer-checksums.json` 的 `dir` 字段指向它） |
| 校验 | 每份包的 `sizeBytes` 与 `sha256` 与清单逐字节一致 |
| 判色 | 目录不在位判**黄**（可恢复）；文件缺失或哈希不一致判**红**（禁止发布） |
| 留存 | 每次发布追加一条，并同步更新清单与只读保护清单 |

**复算命令**：

    Get-FileHash -Algorithm SHA256 "<回退库目录>\<安装包文件名>"

### 4.3 版本单源

| 项 | 判据 |
| --- | --- |
| 唯一权威来源 | `products/bosom-friend/desktop/package.json` 的 `version` |
| 必须一致的三处 | ① 上述字段；② 安装产物 FileVersion；③ 变更日志首条版本号 |
| 发布记录 | 版本号一经发布不得复用；回退目标写进清单 |

**反例（判红）**：页面或报告里出现与 `desktop/package.json` 不同的版本号；改了版本号但没重出包。

### 4.4 验收记录项

每次发布**必须**留以下字段（格式见 BFS-104-R 附录 A）：

| # | 字段 | 说明 |
| --- | --- | --- |
| 1 | **那句话** | 用户会说的原话（不是菜单路径） |
| 2 | **时间与任务 id** | 可回放定位 |
| 3 | **工具序列** | 工具名、参数、返回（SSE 原文） |
| 4 | **三方交叉** | 工具返回 / 助手回复 / 落库或页面数据 |
| 5 | **结论** | PASS 或 FAIL（FAIL 必须带缺陷编号） |
| 6 | **异常清单** | 本轮发现但未修的项，逐条写明规避方案 |

**失败路径必须至少走一次**：模型不可用、账号未登录、素材缺失、超时、限流（BFS-104-R 第 5 节）。

## 5 一次发布的操作顺序

| # | 步骤 | 产出 | 不通过怎么办 |
| --- | --- | --- | --- |
| 1 | 冻结「见一个修一个」 | 确定缺陷清单 | 继续修，不进发布 |
| 2 | 跑 R1 门禁 | 门禁输出原文 | 修到绿为止 |
| 3 | 核对 R2 版本单源 | 三处一致截图/字段 | 改版本号并重出包 |
| 4 | 出包 | 安装产物 + 哈希 | 失败即停，不带病发布 |
| 5 | 跑 R3 干净机装机 | 装机报告 | 判红即停 |
| 6 | 跑 R4 数据指纹 | 前后对照表 | 指纹不一致即停并立缺陷 |
| 7 | 核对 R5 回退包 | 清单 + 哈希 | 缺失即补，补不上不发布 |
| 8 | 走 R6 主链路验收 | C 档证据 + 三方交叉 | 未走通即停 |
| 9 | 核对 R7 / R8 / R9 | 缺陷台账 / 变更日志 / 哈希留存 | 逐项补齐 |
| 10 | 产品负责人签字 | 模板里的签字栏 | 拒绝即回到第 1 步 |

**签字口径**：签字 = 确认 R1~R9 全部通过；任何一项不通过仍签字，按 L1 违规处置（BFS-100 附录 C）。

## 6 不通过的处置

| 情形 | 处置 |
| --- | --- |
| 单项判红 | 冻结发布，定位根因，修复后**全量复跑**（不跳项复验） |
| 两轮修复后仍红 | 连同证据上报产品负责人决策：延期 / 降级发布 / 不做 |
| 门禁假红或假绿 | 先修断言，并用负向对照证明「改回旧写法能判红」（BFS-108.5） |
| 发布后发现 P0 | 立即启动回退包回滚，并出复盘报告（BFS-500 第 506.3 条） |

## 附录 C · 诚实边界

1. **平台风控不可控**：封号、限流、H5 用户确认通道属第三方行为，只能如实告知概率与边界，**不得**承诺「必成功」（BFS-203.5）。
2. **未实现的能力必须从界面移除或明示「未开放」**：禁止以「能点」代替「能用」（BFS-103.4）。
3. **本清单不保证零缺陷**：它保证的是——判据有出处、证据可复算、门禁不撒谎、干净机能装上、主链路真跑通、出事能回退。
