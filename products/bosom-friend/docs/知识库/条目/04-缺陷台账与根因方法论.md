# 04 缺陷台账与根因方法论

**一句话**：这个项目的质量保证不是"测得勤"，而是**每条缺陷都必须带着根因、关联需求和可复跑的回归证据关闭**——少任何一个字段，门禁直接判红。

## 台账字段（`qa/defects/缺陷台账.md`）

`| DEF编号 | 标题 | 严重度 | 状态 | 缺陷类型 | 根因归类 | 关联REQ | 回归用例 | 责任人 | 计划版本 | 重开次数 |`

门禁 `run-gate.mjs` 会解析每一行：状态是 `Fixed/Verified/Closed` 的行，**根因归类、关联 REQ、回归用例三列都不能为空**，否则「缺陷闭环留痕」判红。所以"修好了但没写清怎么复现"不算关闭。

严重度按影响面而不是按代码量：
- **P0**：数据事故 / 对外发布事故（例：模型配置被整份清空 DEF-034、没让发布却发布 DEF-044）；
- **P1**：主要功能不可用或用户卡死（例：打不开、启动页永远停住、发布按钮无反应）；
- **P2**：次要功能、诚实性、交付体验（例：假进度、假兜底文案、安装失败静默）；
- **P3**：体验瑕疵、重复功能（例：页签恒为空、多余的双层包装）。

## 修现象 vs 修根因

- 「同根因复发」是硬规矩：**第二次出现就必须落成不变量断言 + 负向对照**，不允许再修一次现象（例：DEF-016 的"假新鲜度"复发后，改成"读接口不得写盘"的断言 + 隔离实例验证）；
- 修完要问"这类问题还有几处"：DEF-036（握手无超时）修完，顺手补齐启动链路其它无界等待；DEF-045（tar 依赖 PATH）修完，顺手补齐"CWD 无效""目录不存在"等同族成因；
- **测试有效性缺陷也要登记**：假红/假绿不是"环境问题"，是缺陷（DEF-012 守卫正则不一致、DEF-021 定位器范围过大、DEF-039 一条用例串 3 次模型调用还写死 120 秒、DEF-041 断言依赖上一条用例残留的搜索状态）。它们的价值极高——**假绿会让真问题溜走**。

## 一条缺陷的标准闭环（模板）

1. **现象**：用户视角一句话 + 可复现读数（截图/日志/探针输出）；
2. **定位**：哪一行、哪条契约被违反；能反推的都写清反推链；
3. **根因归类**：写"为什么会写成这样"（例：对"zip 是否随包留存"的假设不一致），不是重述代码；
4. **修法**：最小必要改动 + 为什么不是别的改法；
5. **回归证据**：可复跑的命令/探针/截图，最好带**负向对照**（旧写法必判红）；
6. **留痕**：台账一行 + 工作日志一节；复发则重开次数 +1。

## 别让门禁"空过"

2026-09-10 的教训（DEF-014）：台账长期是空的「（暂无）」，门禁照样绿——**没有 DEF 行就没有可校验字段**。同理适用任何"清单型"检查：空表、空目录、SKIP 都会让检查看起来健康。凡是"应该有 N 条"的检查，都要断言 N>0，并区分"如实跳过"与"假装通过"。
