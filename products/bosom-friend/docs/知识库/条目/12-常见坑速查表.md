# 12 常见坑速查表（78 条）

> 排障先扫这一页；命中后跳到对应条目或原文。

## 启动与交付

1. Windows 上 `spawn X ENOENT` 有**三种**成因：系统没有 X / X 不在进程 PATH 上 / 进程当前目录不存在——**报错一模一样**，别急着下结论。
2. 兜底解压不要用裸名 `tar.exe`（靠 PATH 解析），用 `%SystemRoot%\System32\tar.exe` 绝对路径。
3. 系统没有解压工具时，用户唯一能做的是重装——文案必须把这句写出来。
4. 解压/启动类子进程**必须显式给 `cwd`**，否则"当前目录不存在"会伪装成"找不到程序"。
5. `tar -C` 与 `python -m zipfile -e` 都不会自己创建目标目录，先 `mkdir`。
6. **MAX_PATH 260 是默认开启的限制**：Windows 的"长路径支持"（注册表 `LongPathsEnabled`）默认是 0，只有"进程声明 longPathAware **且** 开关为 1"才能越过——Python 的 zipfile 与 libuv 都吃这一条。
7. 判断"解压工具能不能用"不能只在本机试：开发机常见把 `LongPathsEnabled` 打开了，于是 tar/Python 都"实测可用"，到默认设置的用户机上第一个深路径就失败（DEF-055 就是这么复发的）。
8. 越过 260 的唯一稳妥办法是**自己显式加 `\\?\` 前缀**（UNC 走 `\\?\UNC\`）；Node 能直接读写这种路径，不需要注册表开关。带这种路径的 zip 用纯 Node 解压器解（`desktop/electron/kernel-unzip.cjs`），别指望系统工具。
9. 解压"成功"的判据是**运行时入口文件在位**，不是子进程退出码 0：长路径被截断、磁盘写满时工具可能只警告。
10. 装好的机器上 `resources\kernel-runtime.zip` 还在 ⇒ 安装期解压**失败过**（成功才删）。
11. 错误文案里出现 `ENOENT`/`spawn`/`code` 这类词 = 还没写完（普通用户看不懂）；但**真实原因**（stderr 末行、WinError 号）必须留着，否则连排查的人也不知道发生了什么。
12. `execFile` 失败消息的首行是**整行命令行**，原因在后面的 stderr 里（取末行才是异常落点）；只保留首行 = 把最有用的一行扔掉（DEF-056）。
13. 进度条不确定态**不要拉满**，百分比冻结就冻结，语义要自洽；能数出长度的步骤（解压 N/M 个文件）要用真实计数推进。
14. 内核对不上话必须有超时预算，无限等待等于"永远打不开"。
15. 端口被占时优先"接入既有服务"，不要硬起第二个实例（EADDRINUSE 后必然卡死）。

## 打包与产物

16. 打包读的是 `dist/`，不读源码——改了 `server/src` 必须同步进运行时才生效。
17. pnpm 的 `.pnpm/<dir>/node_modules` 里有**第二份物理副本**，同步时要一起（否则"改了没生效"）。
18. electron-builder 只认默认文件名 `installer.nsh`，自定义钩子要用 `nsis.include` 显式声明，否则静默忽略。
19. 安装期解压成功才删 zip；失败要保留 + 当场告知（静默安装留日志）。
20. 安装器（NSIS）跑不了 asar 里的代码：要被安装器调用的脚本必须用 `extraResources` 放到 `resources/` 根。
21. **产物放在会被清理的地方 = 没有产物**：`dist`/`lib`/`release` 都会被整理动作清掉。
22. 回滚网这类安全资产要放仓库外，并在基线里写清存放目录。
23. 基线文件缺失/被删，要么补回来、要么按流程改基线留痕；**不要注释掉检查**。
24. 构建与门禁**不能并发**（构建会改写 dist/release，门禁读到半成品）。
25. 版本只有 `desktop/package.json` 一个权威来源，别在别处写死。
26. 构建退出码 0 不等于跑的是新代码——看产物时间戳与新进程启动时间。

## 质量与门禁

27. 产物不存在 → 门禁判**黄**（环境未就绪）；产物在但行为坏了 → 判**红**。
28. 清单型检查必须断言"非空"，否则空台账/空目录会让门禁**空过**。
29. 台账里 `Fixed` 的行缺根因归类 / 关联 REQ / 回归用例，门禁直接红。
30. 同根因**第二次**复发，必须落成不变量断言 + 负向对照，不许再修现象。
31. "单跑绿、连跑红"几乎总是测试缺陷（共享状态或超时预算不足）。
32. 断言不要依赖上一条用例的残留状态；自己走完整用户流程。
33. 真模型调用一条用例只调一次，等待给足，整套设总预算。
34. SKIP ≠ PASS：环境不满足要如实跳过并写原因。
35. 读接口不要写盘（会造成"假新鲜度"）；副作用放在所有校验之后。
36. 需要命令行/改配置才能完成的步骤，按"未完成"算。

## 现场脚本（37-38）

37. PowerShell 里把参数数组 splat 给**脚本**（`& $script @arr`）是按**位置**绑定：`'-AppDir'` 会变成第一个位置参数，安装目录就"变成"了字符串 `-AppDir`（实测踩过）。给脚本传参一律用具名形式。
38. `.cmd` 文件的内容不能用中文：cmd.exe 按 OEM 代码页（简中为 936）读文件，UTF-8 的中文路径在里面会变成乱码 → "找不到文件"。中文**文件名**没问题，中文**内容**才有问题；入口用 ASCII 文件名，中文提示放进带 BOM 的 `.ps1`。

## 内核运行时打包与启动链（39-48）

39. **zip 存不了 Windows 目录联接点**，Python 的 `os.scandir`/`os.walk` 也不穿透它（`followlinks=True` 只覆盖一部分形态）。pnpm 11 的部署产物恰恰是用联接点挂依赖的：照原样打包，解压后顶层包下只剩 `.bin`（实测 24,741 条目，而正常应是 17 万条）。
40. **把联接点展开成真实目录仍然不够**：Node 解析的基准是**真实路径**。联接点布局下加载 `node_modules/@deepseek-ai/cordis/...` 时真实路径落在 `.pnpm/<hash>/node_modules/@deepseek-ai/cordis/`，它的依赖在兄弟层 `.pnpm/<hash>/node_modules/`；展开后真实路径变成顶层路径，兄弟层**不在祖先链上**，于是依赖明明在包里却报 `Cannot find package`（实测 `js-yaml`、`@deepseek-ai/cosmokit`）。补齐办法：把 pnpm 的私有提升层 `.pnpm/node_modules` 原样搬到顶层 `node_modules`（实测 387 个包 + 顶层 130 个工作区包 = 517 个名字，正好是闭包全集），版本与扁平层不一致的边（实测 37 条）按包嵌套补一份到 `<包>/node_modules/<依赖>`；`.pnpm` 虚拟仓整份保留（有 17 个多版本包，删了换一层扁平必然解析错）。
41. 「条目数 / 字节数对得上」**不是**可交付的证据：坏包在这两项上也对得上（171,301 条目 / 354.8 MB）。唯一判据是**从解压结果真握一次手**（`qa/probes/handshake-kernel.mjs`，走装机路径 `runtime/bin-kernel.mjs`）；出包流程第 6 步就靠它挡住坏包，失败不换 zip。
42. pnpm 11 部署产物的顶层 `node_modules/@deepseek-ai/*` **只有部署根的直接依赖**（实测 130 个）：第三方依赖与被间接依赖的工作区包（如 server）都在 `.pnpm/<hash>/node_modules` 下。任何「顶层有没有这个包」的检查在 pnpm 11 上都会误判（`verify-runtime-deps.mjs` 与出包第 2 步都因此改写）。

43. pnpm 11 的部署产物与工作区构建输出是**硬链接**（实测 nlink = 10：同一 inode 被 `server/lib`、多个 `.pnpm` 副本与运行时共享）。就地 `Copy-Item -Force` 覆盖会报 `being used by another process`——源与目标是同一个文件。同步 lib 要**先删后拷**（`Remove-Item` 只摘掉这个目录项，工作区里的构建输出另有名字，内容不会丢），并且只写真副本：`.pnpm/<dir>/...` 与公共提升层里那些联接点指向同一份文件，逐个写只会反复覆盖同一批文件。

44. 配置里的插件写成**裸包名**时，Node 按**配置文件所在目录**解析：宿主包必须声明**完整的插件闭包**，否则第一处就 `ERR_MODULE_NOT_FOUND`（实测 `launcher` 缺闭包 → `@deepseek-ai/dsh-spill-policy`；`bundle/kernel` 有 131 条闭包就没事）。开发态与出货态用**同一个入口文件**最省事，也免掉两份入口各自漂移。
45. pnpm 11 部署产物的顶层 = 部署根的**直接依赖**："间接依赖能解析到" 在部署产物里是假象。凡是「从运行时顶层按绝对路径 import」的宿主（Electron 主进程加载 `dsh-sdk-client`），或「配置里按裸名引用」的包（桌面 bundle 引用 server），都必须写成部署根的直接依赖，否则开发态与随包版会以同一个错误失败。

46. PowerShell `Copy-Item -Destination <不存在的路径>`：源是**单个文件**时，目标会被当成**新文件名**写成文件（不是目录）。同步一个可能只有一个文件的构建目录（`kernel/lib` 只有 `index.js`）时，先 `New-Item -ItemType Directory` 建好目标目录再拷，否则运行时里会多出一个名叫 `lib` 的文件，内核启动报 `Cannot find module '...\lib\index.js'`（DEF-061）。
47. SDK 的 `session/prompt` 是**创建**语义：对已存在的会话 id 会回 `-32603 session already exists`，没有「打开既有会话」的请求。产品每次都发 `ai-chat-<Date.now()>`，所以老的 DSH 会话日志（v0）在产品的正常使用里**不会被重新打开**，v0→v3 迁移也就不会被触发——实测升级后老日志原样留在盘上（无损坏）。要验证迁移链本身，跑基座的 `packages/session/session-format*`（实测 32 文件 / 1260 用例通过）。

48. `injectWorkspacePackages` 的注入副本按 **(名字, 版本, peer 集合)** 缓存：改了工作区包的**非 lib 文件**（`cordis.patch.yml`、根配置等）后，`pnpm install` **不会**刷新 `.pnpm/<id>/` 里的副本，运行时/依赖方加载的还是旧内容（实测：改端口补丁后 install，注入副本字节不变；版本 0.2.0→0.2.1 再 install 立刻刷新）。所以改这类文件必须**提版本号**，出包链现在用 `desktop/verify-runtime-config-drift.mjs` 逐字节盯着这条（DEF-060）。

## AI 视频生成（49-56，2026-09-16 实测）

49. **模型出现在 `/v1/models` 里不等于你有权限**：Agnes 按 key 白名单放行，本 key 实测 `agnes-image-2.5-flash` 返回 403 `team_model_access_denied`——"图片生成失败"的真因是配置里的模型名无权限，与网络/配额无关。保存模型配置前用一次最小真实调用校验权限。
50. **"参数被接受"不等于"参数被使用"**：图像端点的 `image` 字段返回 200 却**完全没用参考图**（实测输出换成了另一个产品/另一个人）；而视频端点的 `audios` 塞错类型会明确报 `invalid_media`（说明它真读）。判断一个参考字段是否生效，要用"参考图上带模型猜不到的特征"做对照实验，别看状态码。
51. **图像端点靠响应域名区分队列**：带 `image` 的响应来自 `platform-outputs.agnes-ai.space`，不带的来自 `cos-platform-outputs.agnes-ai.cn`。响应域名变了就该怀疑走了另一条链路，别当成同一件事的两种写法。
52. **别把"展示产品"交给文生视频/文生图**：模型会自由发挥包装与文字，实测生成出臆造品牌（`ALTLONE / MUSKIRY CADEE`）。品牌文字只能走**后期叠加**，或画面避开产品正面。
53. **厂商单段 4~12 秒是硬上限，段间硬切在人脸上是"一眼 AI"的主因**：切点要落在产品/场景镜头上，人脸段之间用溶解；参考值见光羽案例实测的平均镜头长度 6.18 秒。
54. **多参考图能锁人，但要配固定 seed**：实测 `mode:reference` + 2 张参考图 + `seed` → 成片与参考图同一人；参考图集一旦固定就不要中途替换。
55. **各段独立生成必然有接缝**：光线、色温、音量都会飘。组装层必须有统一调色与响度归一化（`loudnorm`），否则单段再好也像拼的。
56. **真实音频要用真音频试**：探针里用图片 URL 冒充 `audios` 被厂商拒绝（`invalid_media`），这才是"字段真被解析"的证据；顺带说明"参数合法"必须用**正确类型**的样本验证。

57. **两个模块互相 import 时，常量可能是未初始化的绑定**：ESM 循环依赖不报错，但某一方在某些加载顺序下拿到的是 `undefined`（TDZ 内的 `const`）。实测症状：`SHOT_MIN_SECONDS` 为 `undefined` → `Math.max(undefined, 5)` = `NaN` → 序列化成 `null`，而 **TypeScript 编译完全通过**。修法是**从结构上切断**（把共用的"语言基本量"抽成叶子模块 `speech.ts`，依赖变单向），不是在调用点绕开——绕开只是把下一次留给了别人（DEF-070）。
58. **"先把配音定下来"是长视频编排的前提**：厂商按你给的秒数出片，而口播的真实时长只有合成后才知道。顺序反了（生成时才逐镜合成）就会出现"镜头按估算时长排队 → 实际配音更长"的错位。母时钟的判据：**所有配音调用都排在第一次画面生成之前**（实测调用序列 `tts, tts, video, video, video`）。

59. **随包 ffmpeg 是 2018 年的构建，没有 `xfade`**（该滤镜 2020 年才进 ffmpeg）。用之前先 `ffmpeg -filters` 查实：实测有 `concat/fade/eq/loudnorm/ass/acrossfade/overlay`，没有 `xfade`。想"不硬切"就用**每镜首尾淡出淡入 + concat**（黑场过渡）：它不重叠，成片时长与字幕时间轴都不受影响；交叉溶解每次会吃掉一个过渡时长，字幕要跟着平移。
60. **libass 找不到指定字体时不报错，而是静默换字体**：ASS 里写 `Source Han Sans CN`（真名少了一个 ` Regular`）时，字幕照常烧出来、字体悄悄变成 Microsoft YaHei。要靠渲染器的 `fontselect` 调试输出才验得出来（`-loglevel debug`），并把它做成断言。字体真名从字体文件 name 表读，别猜。
61. **`join()` 会归一化路径，别用它数`向上几层`**：从 `server/src` 出发的 `join(here, '../../..')` 只爬了两层（`..` 吃掉了 `src`），会算出 `products/desktop/...` 这种不存在的路径。逐级 `dirname` 才稳。实测后果：随包 ffmpeg 永远找不到 → 4 条"真实 ffmpeg"用例长期被 skip → 拼接功能从未端到端验证。
62. **"套件被跳过"与"套件通过"在输出里长得几乎一样**：本轮把 skip 的原因修掉后，真实 ffmpeg 用例立刻抓出三个问题（没有 xfade、字体名错、滤镜集不全）。看到 `skipped` 要问一句"为什么跳"，尤其当跳过的正是**最接近真实环境**的那几条。

63. **非代码资源要放在"编译产物会跟随"的位置**：`tsc` 只处理 TypeScript（`.ttf` 不会被搬到 `lib/`），出包链也只同步 `lib/`（包根目录永远进不了运行时）。实测后果：随包字幕字体没随包，装机版字幕**静默退化**成系统字体。修法：源文件放 `src/assets/`、构建钩子复制到 `lib/assets/`，运行时解析用**逐个候选查存在**（源码在 `src/`、编译产物在 `lib/types/`，两者相对层级不同，写死一个 `'./assets'` 或 `'../assets'` 必然在其中一种下算错——同一类错误实测在一轮里犯了两次）。
64. **"源码态测试全绿"不等于"打出来的包能用"**：资源路径、ffmpeg 定位、依赖解析在源码旁边与编译产物旁边会给出不同结果。装机版必须有专项验证：`qa/probes/verify-installed-compose.mjs` 用**已安装运行时**的代码 + 随包 ffmpeg 真跑一次拼接与字幕烧录。DEF-071 就是源码态全绿、装机版才暴露。

65. **"生成中"是一个隐含前提的状态**：它意味着"有个活着的进程在推进它"。把这种状态落盘、却没有对应的存活证据时，进程一没记录就永远停在它上面——用户看到永远转圈，返工入口（"这一镜还在生成"）也被自己挡住。修法：启动时对账（把遗留的 `generating` 定格为失败并写明已生成几镜），且**对账要在注册路由之前做**（那一刻进程内必然没有在跑的任务）。实测一次被 Ctrl+C 中断就留下 3 条卡死记录（DEF-074）。
66. **进度要能"接着跑"，前提是事实都落了盘**：分镜表、稿件、每镜成片路径都落盘之后，续跑就只是"找第一条还没跑成的镜"这一个判据（按序号找第一处空洞，既不重复也不跳过）。反面是把任务当一次性运行：一个 18 镜的任务撞一次 429 就要整条重跑，已花的调用全废（DEF-075）。
67. **失败原因在返回那一刻就丢了**：把失败建模成一个值（`null`）时，所有失败路径只能表达同一句话。实测厂商 429（限流，该等）与 400（参数被拒，该改）在界面上都是"厂商未返回可用成片"。修法：失败带上**原因**（判别联合），并把 HTTP 状态码翻成可行动的话（DEF-076）。
68. **回执先到、状态后变时，轮询的第一跳必然读到旧状态**：起任务/续跑都是"立即回执 + 300ms 后真的开跑"，紧接的一次读取拿到的是上一个终态，按"读到终态就停"的规则轮询会当场停住，用户以为没生效（实测要点一次刷新才活）。修法：给轮询一个**保活窗口**（回执后若干个间隔内即使读到终态也继续）（DEF-077）。

69. **Windows 上"文件内容变了"与"文件元数据变了"是两件事**：连续 rename 覆盖同一个文件时，`mtimeMs`（甚至 `size`）会长时间停在旧值，而 `readFileSync` 读到的内容已经是新的（实测：400 次交替读写里 329 次指纹未变；同一探针"写完立刻读内容"300 次全部正确）。所以**用元数据当内容变化的代理一定会读到旧值**。定案要靠内容（sha256 摘要），元数据只能当快筛；跨进程改不动对方内存时，用"至多每 N 毫秒真读一次盘"的时效窗兜住（DEF-078）。

70. **厂商能力是稳定事实，别当一次性状态用完就丢**：厂商只收 `720P` 而产品默认 `1080P` 时，每镜都要先被 400 拒一次再降档——18 镜就是 18 次白花的下单，在限流窗口里直接吃掉约三成额度。正确做法是把"这家厂商这个模型认哪一档"记住（键按基址+模型分组），并且**只在证实可用之后才写**（下单成功或降级成功），写进去的是结论不是猜测（DEF-079）。

71. **暂时性失败与确定性失败必须分开**：厂商 429/5xx/超时是"等一会儿再来"，参数被拒/密钥无效是"改配置"——混成一档就会出现"一次限流把整条 18 镜的长片判死，用户得盯着点 5~6 次"。判据要落在**原因里的机器标记**（前缀）而不是中文文案；厂商层的短退避（3s/8s）跨不过限流窗口，重试得更久、而且在编排层做（那一层才知道"这一镜还能再试"）。重试期间要如实把"第 N 镜第 k 次重试、X 秒后自动重试"写进任务，别假装在正常推进（DEF-080）。

72. **"同一份事实算两遍"迟早会走岔**：字幕时间轴按配音时长累加，而画面长度是厂商成片文件的长度——厂商出片时会重新配音，两者差 0.2~1 秒；单镜看不出，但时间轴是**累加**的，任何一镜差一点，后面每一镜的字幕都跟着平移（实测逐镜重做一镜后，上一镜的台词出现在下一镜的产品空镜上）。拼接层其实已经探到了文件真实时长（转场与响度都用它），只是没回到字幕那一路。修法：把那份时长显式交接（编排层探一次、拼接层收下、字幕用同一份），别在两处各算一套（DEF-081）。

## 平台发布与交付安全（73-78，2026-10-13/14 实测）

73. **HTTP 200 ≠ 平台收单**：小红书在风控/校验失败时同样返回 200，只把结果写在响应体里（`success:false`/`code≠0`）。成功判据必须读响应体；`success:false` 要抛专用异常**穿透重试**（继续点发布只会反复提交同一条）。详见条目 29。
74. **账号"禁言/处罚"是发布被拒的常见真因**：引擎报成功、创作者中心零作品时，按「读响应体 → 创作者中心直查（全部/已发布/审核中/未通过）→ 产品同步」三步判定；平台原文示例见条目 28。
75. **发布链的超时预算必须同一张表**：引擎回读（墙上时钟）、服务端看门狗、调度轮询三处任何一个单独改数字都会把真实发布拦腰杀掉；落地做法＝单一常量＋跨文件数学断言＋「进程死即收」。详见条目 30。
76. **发布失联时的保守链**：收尸文案统一为「可能已发出 → 先同步确认、不要重复发布」；管家据此**拒绝盲目重发**是正确行为；人工复核日志后把记录订正为「确认未发出、可安全重试」再重发。
77. **平台上传页改版**的速修法：页签有渲染竞态（等 20 秒再点）、文件选择器要限定类型（`input[accept*='image']`，否则会命中同页的视频输入框）、**所有等待必须有界**并留现场截图——先用只读探针 dump 真实 DOM 再改。详见条目 31。
78. **出包窗口纪律**：打包前置门禁的「整轮哨兵」会把并发进行的真发布判成"用例改了业务数据"（假红）——出包窗口内别跑真发/清数据；`kernel-runtime-unpacked` 是手工前置产物（`pnpm deploy` 物化），缺失时脚本 fail-loud、按 `kernel-upgrade-plan.md` 补跑。详见条目 32。
