# 30 超时预算必须同一张表：引擎回读 / 服务端看门狗 / 调度轮询

> 来源：DEF-305（2026-10-13 真机第五轮现场：`pub-7m0x83qx` 在回读第 21 轮被服务端 20 分钟看门狗整树杀掉）。
> 落点：`engine/worker.py` 的 `READBACK_BUDGET_S` ↔ `server/src/platform-login.ts` 的 `PUBLISH_TASK_BUDGET_MS` ↔ `server/src/routes-channels.ts` 的轮询 deadline。

## 现象

一次真实发布：引擎 22:16:32 已报「发布成功」并进入作品列表回读；22:35:06 服务端看门狗按 **20 分钟**阈值
`taskkill /T /F` 终止 worker 整树，记录判超时失败。而引擎自己的回读预算是 **30 轮 × 20 秒＋每轮重抓列表
（每轮要开一次浏览器 ≈ 半分钟）≈ 30+ 分钟**——两边预算没过同一张表，真实发布被拦腰杀掉，且无从回读。

## 约束（写死成数字）

```
引擎总量 = 发布步骤（PUBLISH_COMMAND_TIMEOUT_S ≤ 1020s）+ 回读（READBACK_BUDGET_S 1200s）+ 收尾
服务端总预算 = PUBLISH_TASK_BUDGET_MS = 45 分钟（必须 > 引擎总量）
调度轮询 deadline = PUBLISH_TASK_BUDGET_MS（同源引用，不许各写各的）
```

门禁 `qa/verify-publish-pipeline.mjs` 对这三个数字做**跨文件数学断言**（1020+1200 < 2700 秒）；
任何一侧单独改预算都会被门禁拦下。

## 配套纪律

1. **进程死即收**：state 还在「跑」但 `worker.pid` 进程已不存在 → 立刻判 failed（不必等预算耗尽）；
2. **回读按墙上时钟**：轮数×间隔是名义值，必须给总时限（每轮重抓的真实耗时不可忽略）；
3. **收尸文案统一**：「本次发布可能已经在平台上执行——先同步确认，确认前不要重复发布」。

## 一句话口诀

**凡是「等另一方」的超时，两侧必须是同一张预算表，并留出真实的时间差余量。**
