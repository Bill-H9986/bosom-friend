# 02 启动链路与内核运行时（含 DEF-045 / DEF-055 全过程）

**一句话**：应用启动最脆弱的一环是"把 385MB / 20 万个文件的内核运行时解压到位"；这条链路一旦失败，用户看到的是启动页上一个红色错误框，而错误文案必须让他知道下一步做什么。**解压这件事不能依赖用户机器上的任何外部条件**——tar 在不在、PATH 对不对、系统开没开长路径支持，都不该决定应用能不能打开。

## 启动阶段（启动页进度就是这几步）

`检查运行环境 → 清理旧版运行时残留 → 校验内核运行时 → 启动内核服务 → 加载产品界面`

- 百分比**只在真实里程碑推进**；测不出长度的阶段（握手、等待前端）走"扫光"不确定态并**冻结百分比**（DEF-038 的教训：不确定态不能把进度条拉满）；
- 解压是唯一"长但有数"的步骤：自带解压器每 500 个文件上报一次，启动页显示 `正在解压内置运行时 N/M` 并用真实比例推进；
- 主进程保留最近 40 次里程碑留痕（`status.progressLog`），用户说"卡在某一步"时能直接看出走到哪；
- 等产品服务的上限按性能档位给：标准 90 秒 / 低配 240 秒（`BF_STARTUP_WAIT_SECONDS` 可覆盖）。

## 内核运行时放在哪（`kernelRootForVersion()`）

1. 首选固定目录 `%APPDATA%\Bosom Friend\kernel-runtime`，判据是 `runtime\bin-desktop.mjs` 存在 → **安装期**由 `build/installer.nsh` 解压，所以内容必然与安装版本一致；
2. 固定目录没有时退回 `kernel-runtime-<版本>`（应用自己兜底解压到这里）；
3. 启动时还会清理除当前版本以外的全部 `kernel-runtime*` 目录（曾堆到 8 份 / 8.9GB）；删除必须走**异步** `fs.promises.rm`——同步递归删除会把主进程事件循环占满几分钟，低配机器上表现为启动页卡死（DEF-037）。

## 兜底解压的四条路（`desktop/electron/kernel-extract.cjs`）

| 优先级 | 工具 | 说明 |
| --- | --- | --- |
| 1 | `%SystemRoot%\System32\tar.exe`（**绝对路径**） | Windows 10 1803+ 随系统提供，最快；**只在长路径可用时排第一** |
| 2 | PATH 上的 `tar.exe` | Git/msys 的 tar 也能用；只在没有系统 tar 时兜 |
| 3 | **自带解压器** `kernel-unzip.cjs` | 纯 Node 实现 + 显式 `\\?\` 前缀，**唯一不受 MAX_PATH 260 限制的一条**；长路径不可用时排到最前 |
| 4 | 随包便携 Python `python-base\python.exe -m zipfile -e` | 仅在"自带解压器文件缺失"时还有意义；长路径没开的机器上**必然失败** |

顺序不是拍脑袋定的：主进程先解压前用 `probeLongPaths()` 在目标目录里**实写一条超过 260 字符的路径**（读注册表没用——`LongPathsEnabled` 按进程缓存，且只对声明了 longPathAware 的进程生效）。写得进去就按 1→2→3→4 走快路；写不进去就直接把自带解压器提到最前，不让用户白等一次注定失败的 tar。

每一步的成败判据是**运行时入口 `runtime/bin-desktop.mjs` 是否在位**（`kernelRuntimeReady()`），不是子进程退出码：长路径被截断、磁盘写满、杀软拦掉一半文件时，解压工具可能只警告不报错。失败后完整事实写进 `%APPDATA%\Bosom Friend\kernel-extract.log`（计划、每步来源与真实原因、长路径探测结果），错误框只留一句脱敏的话（AC-021-3）。

## DEF-045：应用装完打不开，屏幕上只有一句 `spawn tar.exe ENOENT`

**现象**：低配机（4 核 / 7.9GB）装完 0.2.42，启动页停在 80%「加载产品界面」，等待产品服务（已等待 10 秒 / 最长 240 秒），错误框 `spawn tar.exe ENOENT`，重试无效。

**两条反推**（不靠猜）：
1. 屏幕上出现的是 spawn 错误、而不是「内核运行时缺失」⇒ `resources\kernel-runtime.zip` **还在**（两条分支文案不同）；
2. zip 只在安装器**解压成功**时才被删（成功省 417MB）⇒ **安装期那次解压也没成功**；
3. 11 秒就报错 ⇒ 不是解压到一半失败，是进程根本没起来。

**三种成因在本机实测复现，报的是同一句话**（Windows 11 + Node 24）：

| 条件 | 结果 |
| --- | --- |
| 正常 PATH + 正常当前目录 | OK |
| `System32\tar.exe` 存在，但进程 PATH 里没有 System32 | `spawn tar.exe ENOENT` |
| 绝对路径 + 进程当前目录不存在 | `spawn tar.exe ENOENT`（连绝对路径也一样） |
| 机器上真的没有 tar.exe | `spawn tar.exe ENOENT` |

**根因**：老代码 `execFile('tar.exe', …)` 靠 PATH 解析、且从不判断 tar 在不在；三种完全不同的故障给出同一句话，现场无法区分，用户也看不懂。
**修法**：绝对路径优先 + 显式 `cwd`（无效 cwd 也是 ENOENT）+ 多级兜底 + 人话文案 + 解压成功后删 zip。
**验收**：`qa/probes/verify-kernel-extract.mjs`（含真进程正负对照：真 zip 解开 / 假工具名必须抛人话，断言输出里不含 `ENOENT`）。

## DEF-055：同一台机器上第二次打不开——修法本身过不了 MAX_PATH

**现象**（0.2.47，同一台 4 核 / 7.9GB 机器）：启动页 80%，错误框
`内核运行时解压失败（PATH 上的 tar.exe 失败（spawn tar.exe ENOENT）；随包 Python 失败（Command failed: … python.exe -m zipfile -e …））`。

**反推**：
1. 失败清单里**没有**「系统自带 tar.exe」这一项 ⇒ 那台机器上 `%SystemRoot%\System32\tar.exe` 真的不存在（成立阶梯里的绝对路径判断没命中）；
2. 随包 Python 报的是 `Command failed` 而不是 `ENOENT` ⇒ python.exe 起来了，是**解压过程**失败；
3. 错误框里只有一整行命令行、没有 Python 的异常 ⇒ 文案把 `stderr` 丢了（这就是 DEF-056，也是这次"看不懂"的直接原因）。

**根因**：这份 zip 的最深相对路径 **232 字符**（运行时文件里最深 226），解到 `%APPDATA%\Bosom Friend\kernel-runtime` 之后最深 **289 字符**，超过 MAX_PATH 260；而 Windows 的长路径支持**默认关闭**（`HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled=0`，且该值按进程缓存），Python 3.6+ 的 zipfile 与 libuv 都只在"进程 longPathAware **且** 开关为 1"时才越过 260。于是这台机器上：系统没有 tar → PATH 上没有 tar → 随包 Python 撞上 MAX_PATH → 三条路全断。

**为什么上一轮没发现**：0.2.42 那轮"随包 Python 深路径实测（352 / 459 字符全部成功）"是在**开发机**上做的，而那台开发机的 `LongPathsEnabled=1`——测试结论只在"已经开了长路径的机器"上成立。这是典型的测试有效性缺陷：把环境特性当成了产品能力。

**修法**：
1. 新增 `desktop/electron/kernel-unzip.cjs`：纯 Node 解压器（ZIP64 + 中央目录解析 + 逐条 CRC 校验 + zip-slip 防护），Windows 上超过 200 字符的路径**自己加 `\\?\` 前缀**，因此不依赖 PATH、不依赖随包 Python、不依赖注册表开关；CLI 形态 `node kernel-unzip.cjs <zip> <target>` 供安装器与现场修复使用，输出 `UNZIP_PROGRESS` / `UNZIP_OK` / `UNZIP_FAIL` 三行契约；
2. 阶梯加入这条保底，并用 `probeLongPaths()` 决定顺序（不可用时提到最前）；
3. 每一步改用"运行时入口是否在位"判定成败（退出码 0 不算成功）；
4. `installer.nsh` 在 Python 之前调用同一份解压器（`resources\runtime\node.exe` + `resources\kernel-unzip.cjs`，由 `electron-builder.yml` 的 `extraResources` 放到 resources 根——NSIS 读不到 asar 里的代码）；
5. `qa/probes/repair-kernel-runtime.ps1` 现场修复同阶梯，并先打印 OS / 两个 tar / `LongPathsEnabled` / zip 大小等事实。

**验收**（本机实测，2026-09-15）：
- `verify-kernel-extract.mjs` **39 项全绿**：含"探针自造 233 字符条目、目标绝对路径 290 字符 → 自带解压器解得出且读得回"、"命令返回 0 但入口不在位 → 该步不算成功并继续下一步"、"损坏 zip 给可读原因"、"CLI 成功/失败两种退出码与输出契约"；
- 真 zip `desktop/dist/kernel-runtime.zip`（385MB / **200537** 条目）用自带解压器解到临时目录：条目数一致、入口在位、最深条目可读，**约 3 分钟**（NVMe + 开启 Defender 实时防护）；
- 现场修复脚本用"安装目录 + 自带解压器"跑通（造一个含 `runtime/bin-desktop.mjs` 的小 zip，`PASS` + marker 在位）；
- `ELECTRON_RUN_AS_NODE=1` 用已安装的 `Bosom Friend.exe` 实测可当 Node 跑（v20.18.3），这是"随包 node.exe 缺失"时的兜底命令形态。

## 长路径与"读取"：解压之外的同一根因（仍未闭环）

- 自带解压器解决的是**解压**。Node/libuv 自己读超过 260 的路径**同样**需要 `LongPathsEnabled=1`（longPathAware manifest + 注册表开关，两者缺一不可）——内核进程读运行时文件时不受我们控制。
- 运行时里相对路径 190~226 字符的条目有 **8452 个**（绝大多数是 `schemastery/release/staging/<版本>/node_modules/...` 这份重复副本），加上 `%APPDATA%\Bosom Friend\` 前缀就会超过 260。
- 结论：在长路径关着的机器上，解压一定成功，但**内核启动时若加载到这些深文件仍可能失败**。所以现场除了用自带解压器解压，建议同时把系统开关打开（管理员 `reg add` + 重启）。
- 0.2.48 的候选做法（待决策，不在本轮改动内）：安装期检测 `LongPathsEnabled` 并经 UAC 征得同意后置 1；把运行时放到更短的根（如 `C:\ProgramData\BosomFriend\rt`，203 字符的条目加前缀也只有 231）；或把 schemastery 的 `release/staging/*` 重复副本从 zip 里剔掉（顺带瘦身）。在那台机器上闭环实测之前，这一条按"未完成"记。

## 0.2.49 起：安装器自己开长路径（现场只剩"双击安装"）

`installer.nsh` 在解压之前检测 `LongPathsEnabled`：为 0 且是可视安装时，用 `ExecShell "runas"` 起一个提权的
`reg.exe add ... /d 1 /f`（**一次 UAC**），然后**轮询注册表直到真读到 1 才算成功**——命令跑过不算成功，
30 秒仍未生效就写日志 + 弹一条明确提示（内置运行时仍已装好）。静默安装（`/S`）不弹 UAC，只留一行日志。

这样"解压"和"读取"两件事都不再需要用户动手。下面的修复包仍然保留，用途变成：**0.2.49 之前的安装包**、
离线/无网络场景、以及需要"不改安装包就修一台机器"的现场支持。

## 现场恢复（0.2.49 之前，或需要不换安装包时）：修复包一次做完 A + B

那台机器打不开应用、也没有这个仓库，所以修复要走"一个文件夹 + 双击"：

```powershell
# 在开发机上生成修复包（默认 %USERPROFILE%\BosomFriend-Repair-Kit，-Zip 同时出一个 zip）
powershell -NoProfile -ExecutionPolicy Bypass -File products\bosom-friend\qa\make-repair-kit.ps1 -Zip
```

包里的东西与各自职责：

| 文件 | 职责 |
| --- | --- |
| `修复内核运行时.cmd` | 双击入口。**必须 ASCII**：cmd.exe 按 OEM 代码页读文件内容，中文路径写在里面会找不到文件 |
| `run-repair.ps1` | **A**：读 `LongPathsEnabled`，不是 1 就提权（一次 UAC）写 1；然后调用阶梯脚本；最后提示重启应用/重启系统 |
| `repair-kernel-runtime.ps1` | **B**：打印环境事实（OS / 两个 tar / `LongPathsEnabled` / zip 大小 / 剩余空间）+ 同一套解压阶梯（自带解压器优先） |
| `kernel-unzip.cjs` | 自带解压器（`\\?\` 长路径，不依赖 tar / Python / 注册表） |
| `说明.txt` | 给用户看的：症状、原因一句话、三步操作、跑完会看到什么 |

**A 与 B 都要做**：解压只需要 B；但内核进程（Node/Electron）读取运行时里超过 260 的路径同样需要 A。用户拒绝 UAC 时脚本会如实说明"解压照样做，但读取仍有风险"，不会假装成功。

不想用修复包时，两条单独的路：

```powershell
# 只做 B（不需要管理员）：应用自带的 Node 跑自带解压器
& "$env:LOCALAPPDATA\Programs\Bosom Friend\resources\runtime\node.exe" .\kernel-unzip.cjs `
  "$env:LOCALAPPDATA\Programs\Bosom Friend\resources\kernel-runtime.zip" `
  "$env:APPDATA\Bosom Friend\kernel-runtime"

# 只做 A（需要管理员）：打开长路径支持
reg add "HKLM\SYSTEM\CurrentControlSet\Control\FileSystem" /v LongPathsEnabled /t REG_DWORD /d 1 /f
```

`LongPathsEnabled` 按进程缓存，改完要**完全退出应用（含托盘）再启动**；微软文档注明"部分进程可能已经启动"时建议重启一次系统。**0.2.48 之前的安装包里没有 `kernel-unzip.cjs`**，用仓库脚本时加 `-UnzipScript <仓库里的 kernel-unzip.cjs>` 即可，不需要重新安装任何东西。

修复包入口的实测（本机，2026-09-15）：造一个含 `runtime/bin-desktop.mjs` 的小 zip + 硬链接的 `runtime\node.exe` 冒充安装目录，PS1 入口与 .cmd 双击入口各跑一遍 → 退出码 0、marker 在位、中文输出正常；探针另断言"入口 .cmd 必须是纯 ASCII""入口必须用具名传参（数组 splat 会按位置绑定，把安装目录变成字符串 `-AppDir`）"。

## 同族缺陷（都在这条链路上，别重复踩）

| 编号 | 教训 |
| --- | --- |
| DEF-010 | 端口被占时握手失败后不再加载产品页 → 现在会"接入既有服务" |
| DEF-036 | 内核子进程活着但不回应时无限等待 → 握手必须有预算 |
| DEF-037 | 同步递归删 8.9GB 残留卡死启动页 → 异步 + 进度上报 |
| DEF-038 | 不确定态把进度条拉满、百分比却冻结 → 语义要自洽 |
| DEF-040 | 承诺了做不到的"自解压兜底"（安装器会删 zip）→ 注释与文案必须写真实契约 |
| DEF-045 | 兜底解压依赖 PATH 上的 tar.exe → 绝对路径 + 多级兜底 + 人话 |
| DEF-046 | 安装期解压失败只打日志、静默继续 → 失败必须当场可见 |
| DEF-055 | 修法本身过不了 MAX_PATH：tar 与随包 Python 都越不过 260 → 自带解压器显式 `\\?\` 前缀 + 长路径探测决定顺序 + 以入口在位判定成败 |
| DEF-056 | 失败文案只留 `execFile` 首行（一整行命令行），真实原因（stderr 末行 / WinError）被丢掉 → 文案必须带真实原因，完整事实另落诊断日志 |
