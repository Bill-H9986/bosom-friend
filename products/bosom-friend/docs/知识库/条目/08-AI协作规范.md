# 08 AI 协作规范（vibe coding 的硬约束）

**一句话**：用 AI 写这个项目的代码，必须走"先方案 → 小步改 → 跑门禁 → 留证据"的闭环；任何"看起来做完了"的声明，没有证据一律视为未完成。

## 八条硬约束（仓库根 `Vibe-Coding-避坑实战指南.md` 的约束版）

1. **先方案、后代码**：先说清"改哪些文件、每处为什么改、影响面、怎么验证"，确认后再动手；
2. **原子化、小步提交**：一个任务只做一件事，做完立即提交；提示里显式写"不要顺手改无关代码"；
3. **复用优先**：优先用既有 utils / components / 成熟方案；新建文件必须说明"现有文件为什么放不下"；
4. **先跑门禁再交付**：lint / build / test 或 `qa/run-gate.mjs`，红灯不放行；
5. **证据高于结论**：每个"已完成/已修复/已通过"都要有截图、可复现步骤或可复跑命令；
6. **实事求是**：做不到就说做不到，失败如实记录原因，禁止假成功；
7. **安全红线**：密钥只走环境变量/独立数据根，输入必须校验，认证与数据操作人工复核；
8. **普通用户视角**：需要命令行/控制台/改配置才能完成的步骤，视为未完成。

## 本项目的落地形态

- **工作日志 `工作日志-YYYY-MM-DD.md`**：现象 → 定位（含反推链）→ 修复 → **验收证据（真跑出来的命令与输出）** → 仍未闭环（如实）；
- **缺陷台账**：每条缺陷必须有根因归类 / 关联 REQ / 回归用例（门禁校验）；
- **探针即证据**：`qa/probes/verify-*.mjs`，退出码语义固定，带负向对照；
- **提交分批**：源码 / QA / 文档 三次提交，互不混杂；
- **未闭环如实写**：需要外部条件（模型额度、干净机器、更新源）的条目不冒充完成，写在日志的"仍未闭环"一节。

## 与"AI 容易犯的错"的对应

| AI 常见毛病 | 本项目的对策 |
| --- | --- |
| 一次性铺开大量改动 | 先方案后代码；一个任务一件事 |
| 顺手重构无关代码 | 提示里显式禁止；提交按主题拆分 |
| 用 mock 冒充真实链路 | 关键链路必须真进程/真安装包 |
| 报"已修复"但没验证 | 证据高于结论；探针 + 工作日志 |
| 把失败写成成功 | 铁律 #7；门禁区分 SKIP 与 PASS |
| 注释/文案承诺做不到的事 | DEF-040 的教训：注释也是承诺，要能指出对应分支 |
