# 06 测试有效性专题（假红与假绿）

**一句话**：这个项目里"测试骗人"比"代码有 bug"更常见，也更贵——**假绿会让真问题溜走，假红会让人不再相信门禁**。两类都要当缺陷登记。

## 真实案例

| 编号 | 表现 | 根因 | 修法 |
| --- | --- | --- | --- |
| DEF-012 | 自检判 PASS | 守卫正则和实际提示文案不一致，"还没有配置大模型 API"的固定提示被当成真实模型回复 | 补齐 4 处守卫；断言真实回复特征 |
| DEF-021 | 断言必红 | 定位器范围过大，把整个页面（含硬编码区块）都算进来 | 收敛到"增长趋势/作品排行"两个板块，保持断言强度 |
| DEF-023 | 门禁红 | 断言时序缺陷（在收尾窗口里读状态） | 修断言时序，不改产品 |
| DEF-039 | 单跑 5/5 绿、整套连跑必红 | 一条用例串了 3 次真实模型调用，等待却写死 120 秒 | 拆成 3 条独立用例 + 单次等待 180 秒；整套预算 15→30 分钟，并区分"超时被杀"与"用例失败" |
| DEF-041 | 单跑 23.4 秒绿、整套连跑红 | 断言"页面上已有搜索结果"，吃的是上一条用例的残留状态 | 改成自己走完整流程（输入→搜索→断言统计/原文/导出）；外部服务不可用时如实 skip |

## 可复用的判断与做法

- **"单跑绿、连跑红"几乎总是测试缺陷**：用例之间共享状态（搜索残留、账号登录态、文件）或超时预算不够；
- **"改一行就绿"要警惕**：先问改的是断言还是产品行为；改断言必须能解释"为什么原来的断言不成立"；
- **断言要自带前置条件**：不依赖"上一条用例留下的状态"，自己准备数据、自己走用户流程；
- **负向对照是硬要求**：新写的回归断言，要能证明"还原旧写法必判红"（本项目多处这么做，例如缺陷闭环留痕、拦截不被二次确认的删除、幂等性断言）；
- **区分三种"没通过"**：PASS / FAIL / SKIP（环境不满足）。SKIP 必须写清原因，且**不能计入通过率**；
- **关键链路用真实进程，不用 mock 顶替**：启动页、内核握手、装机链路都用真实 Electron/真安装包跑（`verify-splash-progress.mjs --packaged`），单测只补边界；
- **真模型调用的用例要限量**：一次用例一次调用，等待时间给足，整套设总预算。
