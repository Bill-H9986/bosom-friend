# 18 · 自动降级必须带恢复路径：一次"保护用户"的降级把界面拖垮了两天

> 结论先说：**任何"一次异常就长期改变运行方式"的机制，都必须同时有（a）判据只认真异常、
> （b）降级后的联动、(c) 自己恢复的路径**。缺任何一条，保护代码本身就会变成缺陷来源。
> 实证：DEF-120。

## 一、事发形态（用户的感受 vs 机器的实情）

用户口径："使用起来有明显的吊针卡顿！"——每一步操作都黏。机器实情：20 核 / 15.6GB，
被判**标准档**（重特效全开），而**硬件加速已经被自动关掉**，所有界面合成落在 CPU 上。

三份落盘证据把链路钉死（这也是能定位的唯一原因）：

| 文件 | 关键内容 |
| --- | --- |
| `<userData>/perf-profile.json` | `tier=standard`、`caps.heavyEffects=true`、`gpuFallback="显卡加速连续 4 次崩溃"` |
| `<userData>/gpu-crash.json` | `{crashes: 4, lastReason: "crashed"}`，从 9-20 一直挂到 9-21 |
| `<userData>/logs/YYYY-MM-DD.log` | 每次启动都打 `[GPU_FALLBACK] 已关闭硬件加速` |

## 二、三条教训

### 1. 判据要只认"真异常"

`child-process-gone` 里凡是 `type === 'GPU'` 就记一次崩溃，不区分 `reason`。
而**应用正常退出也会收到一次 `reason=killed`**（进程树收尾）——开两次关两次就够阈值。

做法：白名单真崩溃原因（`crashed / abnormal-exit / oom / integrity-failure`），
其余记日志但**不计入**，并在日志里写明"正常退出，不计入留痕"。
判据写进注释时要说清"为什么这几个不算"，否则下一个人会把 `killed` 加回去。

### 2. 降级要联动，而不是只关一个开关

项目里本来有一条正确的联动：`tier=low` → `caps.heavyEffects=false` → 服务端注入
`__BF_PERF_TIER__` → 前端 `<html data-perf="low">` → CSS 关掉毛玻璃与长动画（注释里就写着
"全屏模糊在集显上每帧都要重算"）。但 GPU 兜底走的是另一条路，它只关硬件加速、不动档位，
于是软件渲染下继续开着 50 多处 `backdrop-filter`。

做法：降级动作要"成组"——关掉硬件加速的同时，把与之冲突的重特效一起关掉（其余上限不动，
它们跟硬件加速无关，跟着降就是误伤），并把理由写进留痕。

### 3. 降级必须能自己恢复

"稳定 5 分钟就清除留痕"的计时器只在 `gpuFallback === ''` 时创建——**恰恰在降级之后永远不会启动**，
机器就永久停在软件渲染上。

做法：给留痕加**有效期**（7 天），而不是等一个永远不会到来的信号；
"开始尝试"与"尝试成功后转正"这两件事都要有明确的触发点。

## 三、怎么把它变成可回归的判据

纯函数 + 门禁（`qa/probes/verify-perf-profile.mjs`，本轮 15 → 18 条）：

- 关硬件加速时 `heavyEffects` 跟着关，且**档位仍是 standard**（不误判成低配机器）；
- 关硬件加速**不动**与它无关的上限（堆 / 备份份数 / 轮询间隔）；
- 降级的理由写进落盘留痕（现场一眼看出"为什么关了特效"）。

主进程里的判据（哪些 `reason` 算崩溃、留痕多久过期）是常量集合，改了要连注释一起改——
它们是"现场解释为什么这台机器被降级"的唯一依据。
