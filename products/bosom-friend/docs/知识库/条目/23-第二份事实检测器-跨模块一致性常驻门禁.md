# 23 · 第二份事实检测器（跨模块一致性常驻门禁）

> 归属：D 公共底座 / 工程质量
> 日期：2026-10-09
> 结论：**"同一语义在两处各有一份定义"从人工审计变成可机械检测、可 mutation 自证、且已进 CI 的约束。**

## 一、为什么必须做

本产品反复出现同一类缺陷：**同一份事实存在两个来源，其中一个没跟上**。已踩到的实例：

| # | 实例 | 关系类型 |
| --- | --- | --- |
| ① | 三套平台键（`PlatType` / engineKey / CLI parser 名） | 映射一致 |
| ③ | `ENGINE_PUBLISH_PLATFORMS`（平台级） vs `sau_cli` action（动作级） | 集合包含 |
| ⑤ | optional 判据（`contract.mjs` vs 边界层硬编码） | 判据唯一性 |
| ⑦ | 平台显示名（`PLATFORM_KEYS.name` vs `PLATFORM_CONTENT_LIMITS.name`） | 字符串相等 |
| ⑨ | 登录能力（`ENGINE_LOGIN_PLATFORMS` vs `worker.module_paths`） | 集合相等 |
| ⑩ | 同步能力（`DATA_CAPABLE` vs `SYNC_ADAPTERS.canSync`） | 集合相等 |

靠人记是记不住的。所以做成**门禁**。

## 二、分类学：先想清楚"靠什么判为一致"

**关系类型决定了能不能机械化**：

| 关系 | 可机械化 | 说明 |
| --- | --- | --- |
| 映射一致 / 集合相等或包含 / 数值或字符串相等 | ✓ | 直接可判 |
| **判据唯一性** | ⚠ 降级实现 | 不做"表达式等价"（静态分析地狱），只数**同一语义的判据出现在几处** |
| **蕴含**（类名 ⇒ 可用性） | ✗ | 静态分析无法证明正向；**只能找反例**（`TencentNote` 类存在但三个方法 `NotImplementedError`） |
| **死代码** | ✓ | 但**不是漂移** —— 它是「一份从未被使用的第一份事实」，必须单独结果码 |

**结果码**：`CONSISTENT` / `DRIFT` / `SINGLE_SOURCE` / `DECLARED_EXCEPTION` / `DEAD_CODE` / `EXTRACTION_FAILED`。

**`EXTRACTION_FAILED` 是自我防御**：提取器返回空集时**绝不报「一致」**。这条规则来自一次真实事故——vendored 目录被 `.gitignore` 排除，ripgrep 静默 0 命中，被误读成「不存在」。

## 四、例外表的纪律（**最容易退化的地方**）

`qa/drift/exceptions.mjs` 每条必须带 `category`，**只允许两类**：

- `cross-world`：两个世界本来就不同（产品 ID vs 引擎 ID），不可能消除；
- `planned`：后端已登记为「计划中」（如 `coming_soon`），属于有意的时间差。

**禁止「为了让检测通过」的例外。** 这类必须报 `DRIFT`。
（本轮真实发生过一次：作者一度想把真漂移 `wxGzh` 写进例外表以使检测变绿——**该表本身的这条纪律就是为此设的**。）

## 五、自证方式（**没有自证的检测器不可信**）

```bash
node products/bosom-friend/qa/verify-drift.mjs              # 跑规则；有 DRIFT → exit 1
node products/bosom-friend/qa/verify-drift.mjs --selftest   # 验门禁自身 6 个条件
node products/bosom-friend/qa/verify-drift.mjs --mutate <id> # 注入漂移，断言必须报 DRIFT
```

`--mutate` **只在内存里篡改事实源，不写任何文件**。
本轮 4 项自证全部通过，并且**靠它抓出了 mutate 方向错误**（删元素不会触发，必须**加**一个不存在的对象）。

**关键约定**：CLI 契约**每次门禁运行时现提取**（`extract-contract.py` 用 ast 解析 vendored `sau_cli.py`，写到临时文件、跑完删除）。**不读快照** —— 快照本身会成为新的漂移源。

## 六、以后修改平台声明必须遵守的约束

1. **加平台**：先在 `PRODUCT_CHANNEL_PLATFORMS`（或 `PLANNED_PLATFORMS`）登记，再动前端 `PlatType`；两边不一致时 `platform-keys` 会红。
2. **删平台**：删枚举成员之后**必须跑一遍残留扫描**（同名但语义无关的引用要人工判定，例如"客服公众号"不是发布平台）。
3. **新平台能力**：不要靠 `uploader` 类名推断可用性——那是 `implication`，不可靠。要同时看 CLI action 是否注册、参数契约是否匹配。
4. **要压制一条 DRIFT**：只能在例外表里加 `cross-world` 或 `planned` 条目，并写可复核的 `reason`。**加不进去就说明它是真问题。**

## 七、已修复：QA 目标地址漂移（`default-vs-actual`）

**曾经的问题**：`qa-guard`/`qa-guard2` 等 8 个脚本的 `BF_QA_BASE` 默认值停留在旧端口（3080/3086/3099），
而权威值是 `dev-web.ps1` 实际监听的 **31280**。后果**双向**：假红（连不上页面 → 报产品坏）**与**
假绿（`API-响应全部code=0` 因为一个请求都没发出而通过）。

**已修复并验证**（2026-10-09）：

- 新增规则 `qa-base-address`，权威值取自**启动脚本实际监听端口**（不是"某台机器的当前值"）；
- 修复 8 处；端口分布复核 **50/50 全部 31280**，`DRIFT=0`；
- **两种场景都验证过**：不设 `BF_QA_BASE` → `23/23 pass`；显式设置 → `23/23 pass`。
  **隐藏前提已消除**，其他开发者不会因为缺少环境变量而遭遇假红。

**两条值得记住的教训**：

1. **往文件里写正则，不要经过模板字符串的转义**（`\n` 会落盘成真实换行）。改用按行号替换。
   这次靠 `EXTRACTION_FAILED` 兜住——**规则报的是"提取失败"，不是"一致"**。
2. **DEF-226 的修复抄错了口径**：它把 `rebaseline-visual.mjs` 改成"与 qa-guard2 同口径"，而 qa-guard2 本身就是错的。
   **没有唯一事实来源时，连"改对"都没有可抄的正确对象。**
