# 01 项目全景与交付链路

**一句话**：Bosom Friend 是"Electron 桌面壳 + DSH 内核 + 产品服务端 + 随包 Python 平台引擎"的四层桌面应用，交付物是一个约 947MB 的 NSIS 安装包。

## 四层职责（谁负责什么）

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 桌面壳（主进程） | `products/bosom-friend/desktop/electron/main.cjs` | **唯一的产品生命周期所有者**：窗口/托盘/启动页、解压与启动内核、退出时清进程树。不开外部浏览器、不关沙箱、不按名字杀进程 |
| 内核 | `kernel-runtime/runtime/bin-desktop.mjs`（DSH 组合） | 提供 DSH 会话与工具能力，由 `kernel-host.cjs` 启动并握手（`BF_KERNEL_ROOT` 指根目录） |
| 产品服务端 | `products/bosom-friend/server`（HTTP + SSE） | 业务路由、数据存储（`store.files.*`）、模型链路、知识库、发布任务 |
| 前端 | `products/bosom-friend/project/bosom-friend-electron` | 产品页（Vite 构建到 `dist/`，打包为 `resources/frontend-dist`） |
| 平台引擎 | `products/bosom-friend/engine`（Python） | 10 家国内平台的登录/发布/数据采集；随包便携 Python + patchright 浏览器 + social-auto-upload + biliup |

## 数据在哪（排障第一步）

| 目录 | 内容 | 能否删 |
| --- | --- | --- |
| `%USERPROFILE%\.bosom-friend` | **用户数据根**：`bosom-friend/*.json`、sessions、storages、credentials/settings | **绝对不能删**（账号、模型密钥、知识库、创作数据都在这） |
| `%APPDATA%\Bosom Friend` | Electron userData：kernel-runtime、Chromium profile、perf-profile.json | 可重建（卸载钩子会整体清掉） |
| `%LOCALAPPDATA%\Programs\Bosom Friend` | 安装目录：`resources\{engine,frontend-dist,runtime,kernel-runtime.zip}` | 卸载即清 |

## 从源码到安装包（8 步，约 40~70 分钟）

脚本：`products/bosom-friend/desktop/rebuild-kernel-and-installer.ps1`

1. 构建 server + kernel 包（`pnpm --filter @deepseek-ai/dsh-bosom-friend-server --filter @deepseek-ai/dsh-bosom-friend-kernel build`）；
2. 把两份 `lib` 同步进 `dist/kernel-runtime-unpacked` 的**每一份物理副本**：顶层 `node_modules/@deepseek-ai/<pkg>`（若有）、每个 `.pnpm/<dir>/node_modules/@deepseek-ai/<pkg>`、公共提升层 `.pnpm/node_modules/...`。pnpm 11 的顶层只挂部署根的直接依赖（实测 130 个），server 这类间接依赖只在 `.pnpm` 里，只同步顶层会出现"改了没生效"甚至直接 throw；
3. 依赖齐全性校验（`verify-runtime-deps.mjs`）：按 **Node 的解析规则**从服务端每一份物理副本逐级向上找 `node_modules`，逐个核对 `package.json` 的运行时依赖；
4. 组装便携引擎（`build-engine-portable.ps1`，约 1.9GB）；
5. 重打 `kernel-runtime.zip`（`repack_kernel.py`：先把 pnpm 的目录联接点展开成真实目录，再把私有提升层 `.pnpm/node_modules` 搬到顶层补齐解析链，见知识库 12 的 39~42 条）；
6. **解压新 zip 真握手**（`qa/probes/handshake-kernel.mjs`）：用装机同款 `tar.exe` 解到临时目录，从 `runtime/bin-kernel.mjs` 发一次 `initialize`，失败就中止、不换 zip——这是"做完了"的唯一判据；
7. 换入新 zip（旧 zip 留 `.bak`）；
8. electron-builder 出包（`build-win.sh`，产物落 `desktop/release/<版本>/`）。

**版本只有一个权威来源**：`products/bosom-friend/desktop/package.json` 的 `version`；前端 `__APP_VERSION__` 与注册表 DisplayName 都从它派生（门禁「产品版本单源一致」盯着这条）。

## 验收体系（怎么证明"做完了"）

- `products/bosom-friend/qa/run-gate.mjs`：一键门禁，输出红/黄/绿报告到 `qa/reports/gate-*.md`；
- `qa/probes/verify-*.mjs`：真实进程探针（启动页、性能档位、内核握手、兜底解压…），**新增门禁断言要同时给负向对照**；
- `qa/defects/缺陷台账.md`：每条缺陷必须有根因归类、关联 REQ、回归用例三个字段，否则门禁判红；
- `qa/reports/release-*.md`：每次出包的产物哈希与装机实测记录。

## 关键约束（踩过的坑，别重复）

- **构建与门禁不能并发**（09-11 踩过）：`dist/`、`release/` 会被构建过程改写，并发跑门禁会读到半成品；
- **产物放在会被清理的地方 = 没有产物**：`dist`、`lib`、`release` 都会被整理动作清掉，回滚网必须放仓库外（见 `03`）；
- **打包读的是 dist，不是源码**：改了 `server/src` 不同步进运行时，装出来的包还是旧行为。
