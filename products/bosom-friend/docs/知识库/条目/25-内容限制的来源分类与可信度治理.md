# 25 · 内容限制的来源分类与可信度治理

> 一条限制值写进代码之后，会**自动获得"事实"的外观**：变量名像平台规则、注释像平台依据、
> 界面把"未声明"和"上限"渲染成同一个东西。这篇条目给出可复用的分类原则，以及一次整表审查的结论。
>
> **正式审查记录（证据与逐项明细的家）**：
> - 缺陷台账 `qa/defects/缺陷台账.md` → **DEF-238**（状态与待办）、**DEF-231**（同源检索结论及其局限）
> - 工作日志 `docs/过程档案/工作日志/工作日志-2026-10-09.md` → **第二十节**（审查过程、关键证据、差异记录）
> 本篇**只保留可复用原则与结论**，不复制长报告，避免出现多个需要分别维护的版本。

## 1. 可复用原则（核心）

**平台事实、实测观察、产品策略、来源未定的历史口径，必须明确区分。**

> **无法证明为平台规则的数字，不得仅凭变量名、注释或历史配置被描述成平台硬性限制。**

四类标签（**规则来源类别，与项目的运行时/静态代码证据等级是两个维度，不得混用**）：

| 类别 | 含义 | 判定条件 |
| --- | --- | --- |
| **A 平台官方规定** | 平台官方规则 / 帮助中心 / 开放平台文档 | 需可核实来源，且适用于对应平台、内容类型与规则范围 |
| **B 实测支持的实际限制** | 有可追溯的实际运行证据 | 须写明测试环境、时间、输入条件、观察结果与可重复性；**不得扩展为所有版本/地区/内容类型** |
| **C 产品内部策略** | 有产品决策、明确需求或其他可追溯内部依据 | 能证明该值是产品自己制定的校验策略，而非平台客观限制 |
| **D 来源未定的历史口径** | 有配置值或历史注释，但不足以判断归属 | **不得**仅凭注释自称（如"产品既定口径"）就升级为 C |

## 3. 三个关键矛盾（本次最重要的发现）

### 矛盾 1 · `xhs.topics = 10` 的历史来源

DEF-153 早已指出旧的"所有平台同一套"常量（含话题 10）**"谁也不是真的"**（`platform-catalog.ts:38-39`）。
该值随后**被归位进新表**，但**现有证据没有证明其来源被重新核实** → 只能列 **D 类**。

### 矛盾 2 · 一条错误的依据传播链

```
历史统一常量（来源未定）
   └─ 被当作「平台最严上限」
        └─ 用于解释 MAX_TOPICS = 8 的产品策略
```

`MAX_TOPICS = 8` 的注释以"**低于平台最严的 10**"为理由 —— 它**混合了两种不同性质的陈述**：
"8 是产品策略"（成立）与"平台最严是 10"（**未证实**）。

### 矛盾 3 · 建议值与硬上限的语义差异

`agent-rules.ts:188` 建议小红书用 **5~8 个**话题，而 `PLATFORM_CONTENT_LIMITS.xhs.topics` 配的是 **10**。
**这不自动构成逻辑冲突**（8 可为建议区间上界、10 可为产品硬上限），
但**目前没有足够依据确认两者确实承担这两种不同职责** → 列为产品决策事项。

## 4. 来源可信度缺口（如实记录）

- **A 类为 0**：本次审查**未找到**能支持这 9 项为平台官方规则的依据。
- **C 类 7 项不代表每项都有完整、正式的产品决策档案** —— 其中依据需进一步确认的已在表中标注（#2、#5、#8）。
- **唯一 B 类（#7）** 仅证明**对应测试条件下**的运行观察，**不得**扩展为所有平台/版本/内容类型均成立。
- **D 类（#9）不得作为已确立的平台事实继续引用。**
- **表覆盖范围问题**：`agent-rules.ts:187` 中抖音的正文规则（≤1000 字）**未登记进该表**，需单独评估。
- **检索局限**：本次来源审查**复用了 DEF-231 的公开检索结论及其局限**（仅保存查询语句与结果列表，未抓取全文逐条核对）。
  **不得**表述为"9 项限制都经过独立的官方全文验证"。

## 5. 给后续开发的做法

1. **新增限制值前先归类**：这一条是平台规则、实测结论，还是我们的策略？**归不出类就先不写**。
2. **平台规则必须有可核实来源**（URL + 标题 + 适用范围 + 原文/准确摘要 + 核验日期）；找不到就写"未找到权威来源"。
3. **第三方教程/博客不能作为平台规则的依据**，只能作为继续找官方来源的线索。
4. **产品策略要写明是策略**，理由应当**独立可追溯**，不要引用未经核实的外部上限。
5. **不要把静态存在当成已验证**，也不要把一次观察扩大为普遍结论。
6. 需要区分平台规则与产品策略时，优先**先解决数据语义，再决定数据结构**（是否加来源元数据、是否拆两张表）。

## 7. 消费路径补充：一个字段同时影响「用户看到的」与「模型收到的」

2026-10-09 的消费者分析（DEF-238-AUDIT-3）发现，`PLATFORM_CONTENT_LIMITS.xhs.topics` 的影响面
**比"发布前校验"更宽** —— 它有**两条前端路径**：

| 路径 | 位置 | 作用 |
| --- | --- | --- |
| **发布前校验** | `usePubParamsVerify.tsx:469-476` | `topicsAll.length > topicMax` → `addErrorMsg` → **阻断发布** |
| **AI 批量生成提示词** | `useAiBatchPlatformPromptState.ts:78-79` | `limits.push(t('detail.topicLimitPrompt', { max }))` → **把上限写进给模型的提示** |
| UI 展示 | `PlatformLimitsInfo/index.tsx:28` | `{ key: 'topicMax', labelKey: 'detail.topicLimit' }` |

**证据等级：B 级（静态代码事实）** —— 以上均为代码路径可追踪的读取关系。

**因此该字段同时承担两种语义**：用户看到的限制 + 模型收到的约束。这使得"来源未定"的影响不止于校验提示，
还会影响**生成阶段的提示词内容**。

**仍待运行时验证（不得凭代码断言）**：
- 模型是否**实际遵循**提示词中的上限（代码只证明提示词被构造，不证明模型照做）。
- UI 在 `topicMax === undefined` 时**实际显示什么**（代码有 null 分支，未实测）。
- 服务端平台元数据 API 是否**实际下发** `topic.maxCount`。

**另注**：话题**不参与** CLI 参数的数量校验 —— `worker.py:725-726` 的 `--tags` 只做逗号拼接，**无数量检查**。
