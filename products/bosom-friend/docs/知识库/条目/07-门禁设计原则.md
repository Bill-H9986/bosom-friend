# 07 门禁设计原则（run-gate 的红黄绿）

**一句话**：门禁的价值不在"绿灯好看"，而在**它红的时候你一定得改点什么，它绿的时候你一定可以放心**。任何破坏这两条的写法（空过、假红、把环境问题判成代码问题）都会让整套体系失效。

## 三色语义（`qa/run-gate.mjs`）

| 颜色 | 含义 | 动作 |
| --- | --- | --- |
| 红 | 存在真缺陷 | **禁止合并 / 发布** |
| 黄 | 环境未就绪或需要外部条件（模型额度、干净机器、开发服务未起） | 可以继续开发，发布前必须处理或明确豁免 |
| 绿 | 该项通过 | — |

## 五条设计原则（都是踩出来的）

1. **产物依赖要判黄，不能判红**：`dist`/`lib`/`release` 都是可清理产物。清理工作区后如果把"产物不存在"判红，久而久之大家就习惯性忽略红灯——这比漏检更危险。**只有"产物在、但行为坏了"才判红**。（2026-09-14 修订：`内核工具可执行` 从红改黄，与 `内核握手超时` 的口径统一；同因不同色本身就是缺陷。）
2. **清单型检查必须断言"非空"**：台账空表、目录为空、全是 SKIP，都会让检查"看起来健康"（DEF-014 就是台账长期空白、门禁照样绿）。
3. **选手兼裁判要自证**：门禁自己写的断言，必须有**负向对照**证明它会红（还原旧写法 → 必须判红）。
4. **报告要标注工作区状态**：有未提交改动时必须写进报告，否则一次绿灯会被当成"这版代码没问题"引用。
5. **不与构建并发**：构建会改写 `dist`/`release`，并发跑门禁读到半成品（09-11 踩过）。构建与门禁分时执行。

## 报告里要有"证据尾巴"

每条检查除了结论，还要带**可复跑的命令**与**截断的输出尾部**（tail）——排查时不用再去猜是哪一步、跑的是什么。

## 检查怎么加（本项目的做法）

1. 先在 `qa/probes/` 写一个能独立跑、退出码明确的探针（0=过，1=失败，2=环境不满足）；
2. 探针里带**边界值断言**与**负向对照**；
3. 再在 `run-gate.mjs` 里加一条检查，把 2 映射成黄、把 1 映射成红；
4. 探针的最终行必须有固定前缀（如 `KERNEL_EXTRACT PASS checks=22 fail=0`），门禁抓这行做摘要。
