## 0 前言

### 0.1 目的

本体系规定 Bosom Friend（下称「本产品」）在**管家形态**下必须遵守的产品、工程、运营与流程标准。
它回答一个问题的全部细节：**这条能力算不算做完了、凭什么说做完了、没做到怎么办。**

**目标唯一表述（2026-10-13 产品负责人拍板）**：**全面对标腾讯 Marvis Agent 功能的一站式工具**——用户说一句话，管家自己拆解、自己调工具、自己操作电脑与平台把事办完；页面只是过程与结果的可视化（详见 ADR-005 顶部「统一口径」）。

### 0.2 适用范围

本体系适用于：

1. 本产品全部代码：server/、kernel/、project/bosom-friend-web、launcher/、engine 胶水层；
2. 全部文档、脚本、门禁与测试；
3. AI 实现者与任何参与协作的人。

**不适用**：DSH 官方源码（packages/、docs/、vendor/）——那部分遵循仓库根的 AGENTS.md。

### 0.3 与其他文档的关系

| 文档 | 关系 |
| --- | --- |
| ADR-005 | 上位依据（形态为什么是管家） |

### 0.4 术语与定义

| 术语 | 定义 |
| --- | --- |
| **管家** | 由一份 preset（agent.cordis.yml + 技能 + 人设）组装出来的专职 agent |
| **能力** | 一句用户会说的话 + 一个管家可调用的工具 + 一个页面上可见的结果，三者合称一条能力 |
| **工具** | 注册到 DSH 工具运行时的可调用单元（ctx.tools.register） |
| **preset** | packages/preset/agent-presets 机制下的 agent 组装目录 |
| **一句话端到端** | 人话输入 → 管家自行拆解并执行 → 页面可见结果 |
| **内核握手** | 启动 DSH 内核并完成一次 initialize，证明插件树可加载 |
| **发卡** | 工具只登记请求、把执行交给前端页面的旧模式（**已废止**） |
| **自证** | AI 自己执行、实时监测调用链、交叉举证，不让用户代劳 |
| **在制品** | 同一时刻正在推进的工作条目 |

| **应当** | 强烈建议。不遵从必须在工作日志写明理由 |

## 1 第一编 · 产品标准

### BFS-101 能力定义

**目的**：保证「能力」是可判定、可验收的单位，而不是一句功能描述。

**条款**

- 101.1 一条能力**必须**同时具备三要素：① 用户会说的那句人话；② 管家可调用的工具；③ 页面上可见的结果。
- 101.2 三要素缺一，该能力**必须**登记为「未完成」，**不得**计入完成数。
- 101.3 每条能力**必须**登记在《能力台账》，字段包括：能力名、那句话、归属管家、调用工具、现状、缺口。
- 101.4 只做进页面、未注册工具的，**必须**标注「未管家化」。
- 101.5 反例判据：只做进脚本、界面上看不见的，**必须**判为「没做」。

**判据**：台账里每一条都能回答「用户说什么、调哪个工具、看到什么」。

**证据要求**：台账条目 + 工具注册代码位置。

**违规处置**：不得进入验收；已宣称完成的能力若发现工具缺失，状态回滚为未完成并记缺陷。

---

### BFS-102 架构：能力先于界面

**目的**：杜绝「按钮软件」，让能力长在管家身上。

**条款**

- 102.1 新功能的开发顺序**必须**是：定义能力 → 注册工具（管家立刻会用）→ 页面呈现。顺序颠倒即为按钮软件。
- 102.2 同一份业务实现**必须**同时被页面与工具调用；**禁止**维护两套实现。
- 102.3 内核工具调用服务端能力**必须**经回环地址（127.0.0.1）；**禁止**在业务代码里直连非回环厂商地址（厂商 HTTP 只能出现在 Provider 包）。
- 102.4 工具描述**必须**写明「**必须调用本工具完成，不要自己直接做**」。实测：不写这句时模型会绕过工具自己写（提示词增强第一次实测工具序列为空，加上后立刻触发）。
- 102.5 工具 execute **必须**真正执行并返回真实产物标识（executed + 真实 id）；**禁止**返回「已交给前端执行」的发卡模式。
- 102.6 启动类工具**必须**自证可用：验证含内核握手，**不得**以 HTTP 200 代替。

**判据**：关掉页面，管家仍能办成这条能力。

**证据要求**：SSE 工具序列 + 工具返回 + 落库/页面数据（三方交叉）。

**反例（判红）**：只发动作卡；工具描述无强制语；工具返回空 id 却声称完成。

---

### BFS-103 交互

**条款**

- 103.1 每条能力**必须**能从一句话触发。
- 103.2 页面**应当**只承担三类职责：展示过程、展示结果、接收拍板。
- 103.3 面向用户的文案**必须**说人话；**禁止**暴露内部路径、堆栈、接口名、英文错误原文。
- 103.4 不可用时**必须**给出可读原因与下一步，**禁止**假装成功。

**判据**：新用户不看说明，只说一句话，事情被办完，且他知道发生了什么。

---

### BFS-104 验收：一句话端到端

**条款**

- 104.1 验收**必须**以一句话端到端为准。
- 104.2 证据分三档：A 构建/单测/门禁绿（**不算**）；B 接口响应/落库/日志（**只作诊断**）；C 一句话在页面上走通（**唯一算数**）。
- 104.3 C 档证据**必须**三方交叉：工具返回、AI 对用户的回复、落库或页面数据，三者一致。
- 104.4 验收**必须**包含失败路径；失败**必须**给三个选择（断点继续 / 重新生成 / 放弃）。
- 104.5 验证**必须**包含内核握手（内核为懒启动，首次对话才 spawn）。
- 104.6 用例**必须**可重复执行；同一缺陷第二次出现**必须**升级为门禁断言。

**判据**：给定那句话，任何人按记录都能复现同样的结果。

**反例（判红）**：接口 code=0 就宣布完成；页面上出现历史消息里的关键词就判成功；只走成功路径。

**细则**：见《验收标准-一句话端到端》。

---

### BFS-105 权限

**条款**

- 105.1 只有四类动作需要用户拍板：**发布、删除、花钱、对外沟通**（评论、私信、分享）。
- 105.2 其余动作**必须**自动完成，**不得**用确认弹窗打扰用户。
- 105.3 拍板点**必须**给出人话原因与不可撤销的后果。
- 105.4 未获得用户明确指令，**不得**执行上述四类动作（DEF-240 事故教训）。
- 105.5 把拍板点放错位置（该问的不问、不该问的乱问），与静默失败同为缺陷。

---

### BFS-106 技能

**条款**

- 106.1 专业流程（选题方法、文案规范、封面规则、平台风控、复盘口径）**必须**写成 Skill 文件，**禁止**硬编码进代码。
- 106.2 修改一条业务规则**应当**只改 Skill，不改代码。
- 106.3 每份 Skill **应当**包含：适用场景、步骤、判据、反例、来源。
- 106.4 管家**应当**在开工前加载对应 Skill（实测：一句话创作会自动加载 bosom-friend-content）。

---

### BFS-107 记忆

**条款**

- 107.1 管家会话**必须**长期存活；**禁止**任务级用完即销毁（旧 ADR-003 口径废止）。
- 107.2 记忆分四层：总管记忆（用户偏好）、管家记忆（业务上下文）、技能（方法）、画像（用户与账号是谁）。
- 107.3 同一类任务第二次执行，用时或返工率**应当**下降；不降即视为记忆失效，须诊断并登记。
- 107.4 每次完成节点**必须**写入活记忆并同步（memory-sync），保证新会话自动读到。

---

### BFS-108 门禁

**条款**

- 108.1 每条能力上线**必须**同时产出一条可重复的门禁用例。
- 108.2 门禁判的是「**办成了没**」，不是「页面点得对不对」。
- 108.3 同一问题第二次出现**必须**升级成门禁断言。
- 108.4 规则不进门禁**等于没有规则**。
- 108.5 新增门禁断言**必须**附负向对照（证明它会红）。

---

### BFS-109 交付

**条款**

- 109.1 交付 = 打包 + 端到端跑通 + 装机验收；三者缺一，**不得**说「完成」。
- 109.2 每次交付**必须**留：产物哈希、安装/卸载记录、真实业务验收记录。
- 109.3 **禁止**为验证开发改动而打包（开发期一律用 Web 端迭代）。

## 2 第二编 · 运营期地基标准

> 本编回答「长期运营会不会头痛」。第一编保证跑得通，本编保证跑得久。

### BFS-201 数据

- 201.1 业务数据**必须**只有一个写入入口。
- 201.2 一次业务动作**必须**整体成功或整体回滚（事务语义）。
- 201.3 数据结构变更**必须**带迁移器；**禁止**直接改文件格式而不管存量数据。
- 201.4 测试**禁止**写用户数据根；**必须**使用隔离数据根并在结束后比对回滚。
- 201.5 数据异常**必须**能定位到「哪次动作写坏的」，留痕不可缺。

### BFS-202 成本

- 202.1 每一次模型/厂商调用**必须**记账：调用方、能力、用量、耗时、成败。
- 202.2 **必须**有预算闸门：超额在调用前拦截，不是事后发现。
- 202.3 免费档能力边界（如 RPM=1）**必须**在开跑前如实告知用户。
- 202.4 「一次任务大概花多久、花多少」**应当**在开跑前给出预估。

### BFS-203 风控

- 203.1 平台操作**必须**限频并拟人化。
- 203.2 账号之间**必须**隔离（登录态、浏览器指纹、操作节奏互不串味）。
- 203.3 每一次对外动作**必须**可回放：谁、何时、对哪个账号、做了什么、结果如何。
- 203.4 **禁止**任何绕过平台规则的实现路径。
- 203.5 封号、限流等不可控结果**必须**如实告知概率与边界，**不得**承诺保证。

### BFS-204 升级与备份

- 204.1 版本升级**必须**能带数据迁移。
- 204.2 用户数据**必须**能一键备份、恢复、换机搬迁。
- 204.3 升级失败**必须**可回退到上一版本。
- 204.4 升级过程**不得**破坏用户数据（装机验收必须核对升级前后的数据指纹）。

### BFS-205 可观测

- 205.1 **必须**看得见：谁在干活、干到哪、卡在哪。
- 205.2 失败**必须**有可读原因与下一步动作。
- 205.3 **禁止**静默失败、空原因、假成功。
- 205.4 关键链路（生成、发布、接待）**必须**有可回放的执行留痕。

### BFS-206 自证与举证

> 产品负责人 2026-10-11 定：「你应该自己去执行并实时监测……这条办法你一定要坚持！」

- 206.1 每条能力、每次改动**必须**由 AI 自己执行验证；**禁止**让用户代劳试错。
- 206.2 验证**必须**实时监测调用链（工具序列、参数、返回），不是只看最终文字。
- 206.3 **必须**三方交叉举证：工具返回 / 对用户的回复 / 落库或页面数据。
- 206.4 **必须**包含内核握手；HTTP 200 **不得**作为可用性结论。
- 206.5 过程中的任何异常**必须**当场登记：工作日志 + 缺陷台账 + 活记忆（含 memory-sync）。
- 206.6 反面教材：2026-10-11 只看 HTTP 200 宣布「开发版已恢复」，而内核插件树其实加载失败（bundle/kernel 缺依赖），产品 AI 整段不可用。

## 3 第三编 · 流程

### BFS-301 开工三问

开工前**必须**回答三问，答不上不动手：

1. 今天要让**哪一句话**成立？
2. 它挂在**哪个管家**、主链路的哪一环？
3. 走通它的 **C 档证据**是什么？

### BFS-302 在制品上限

- 302.1 同时在制**不得超过 2 条线**。
- 302.2 挂不上主链路的改动**必须**排队，不得插队。

### BFS-303 记录义务

每个节点完成**必须**当场写入三处：

1. 工作日志（过程与证据）；
2. 缺陷台账 / 能力台账（状态变更）；
3. 活记忆（当前状态 + 流水），并执行 memory-sync。

**没有实时记录的完成 = 未完成。**

### BFS-304 缺陷升级

- 304.1 同一问题第二次出现**必须**升级成门禁断言。
- 304.2 缺陷**必须**挂到具体能力上，禁止只写现象不写归属。
- 304.3 缺陷字段（标题、严重度、状态、类型、根因、关联需求、回归用例、责任人、计划版本）**必须**齐全。

### BFS-305 禁止绕过

- 305.1 管家做不到时，**必须**补工具或如实说办不了；**禁止**写脚本绕过。
- 305.2 脚本只允许两种用途：**能力门禁**（可重复、有 PASS/FAIL）与**一次性诊断**（查清即删，登记后不得沉淀）。
- 305.3 一次性诊断脚本**必须**在结论产出后删除或升级为门禁。

### BFS-306 变更影响三行

任何改动前**必须**写清三行：

1. 改哪个文件；
2. 为什么（根因证据）；
3. 会影响谁（谁在调用它、会不会成环）。

改完**必须**立刻跑类型检查 + 定向门禁。
