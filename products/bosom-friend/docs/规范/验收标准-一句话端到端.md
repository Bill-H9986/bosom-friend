## 1 适用范围与角色

### 1.1 适用

本细则适用于本产品全部能力的验收，以及任何「改完能不能用」的判定。

### 1.2 角色

| 角色 | 职责 | 禁止 |
| --- | --- | --- |
| **执行者**（AI 实现者） | 发起那句话、实时监测、交叉举证、记录、立缺陷 | 让用户代劳试错；只看最终文字 |
| **产品负责人** | 定能力优先级、拍板四类动作、最终否决 | —— |
| **管家**（被验对象） | 自己拆解、自己调工具、自己完成 | 把执行推给前端页面（发卡模式已废止） |

**2026-10-11 定**：验证由执行者自己跑（原话：「你应该自己去执行并实时监测……这条办法你一定要坚持！」）。

---

## 1.3 术语与定义

| 术语 | 定义 |
| --- | --- |
| **验收单元** | 一次一句话端到端的完整记录（四行：那句话 / 归属 / 预期可见结果 / 失败预期） |
| **C 档证据** | 一句话在页面上走通的证据；唯一可作为完成依据的证据档 |
| **三方交叉** | 工具返回、助手对用户的回复、落库或页面数据三者一致 |
| **内核握手** | 启动 DSH 内核并完成一次 initialize，证明插件树可加载 |
| **假阳性** | 看起来通过、实际没办成的判定（见第 7 节清单） |
| **发卡** | 工具只登记请求、把执行交给前端页面的旧模式（已废止） |
| **门禁化** | 把一次性用例升级为可重复执行、有 PASS/FAIL 的检查 |

## 1.4 关键词约定

| 关键词 | 含义 |
| --- | --- |
| **必须** | 强制；违反即返工，不得以任何理由绕过 |
| **应当** | 强烈建议；不遵从必须写明理由 |
| **可以** | 可选 |

> 三级语义的完整定义见《管家化标准体系（BFS-100）》第 0.5 节。

## 2 验收单元：一句话

### 2.1 构成

一个验收单元由四行组成，缺一行不成立：

1. **那句话**：用户会说的原话（人话，不是菜单路径、不是参数表）。
2. **归属**：哪个管家、主链路的哪一环。
3. **预期可见结果**：用户在页面上看到什么（对象、字段、变化）。
4. **失败预期**：不可用时用户看到什么（人话原因 + 三个选择）。

### 2.2 编号

用例编号格式：AC-<能力编号>-<序号>，例如 AC-A2-08-1。编号一经使用不得回收。

## 3 证据规则

### 3.1 三档证据

| 档 | 内容 | 能否作为完成依据 |
| --- | --- | --- |
| A | 类型检查 / 单测 / 门禁绿 / 构建成功 | **不能** |
| B | 接口响应体 / 落库数据 / 日志 / worker 成功 | **只能作诊断** |
| C | 一句话在页面上走通（含过程与结果） | **唯一依据** |

### 3.2 三方交叉（C 档的必要条件）

以下三项**必须**同时具备且互相一致：

| # | 证据 | 从哪取 |
| --- | --- | --- |
| ① | **工具返回** | SSE 里 tool_result 的原文（工具报了什么） |
| ② | **对用户的回复** | 助手最终回答（它对用户说了什么） |
| ③ | **落库/页面数据** | 对象字段的真实值（页面读的就是它） |

**不一致即判失败**：例如工具说「已挂到草稿」，而草稿 coverUrl 没变 —— 判红并立缺陷。

### 3.3 留存格式

每条验收记录**必须**留：那句话、时间、任务 id、工具序列、三方证据摘要、结论（PASS/FAIL）、异常清单。

## 4 六步执行流程

| 步 | 动作 | 产出 |
| --- | --- | --- |
| 1 | **发起**：经产品对话主通道说那句话（读 SSE），不写脚本硬点页面 | 任务 id |
| 2 | **监测**：记录工具序列（工具名、参数、返回），不看最终文字就下结论 | 工具序列 |
| 3 | **交叉**：抓三方证据并逐项比对 | 三方一致记录 |
| 4 | **握手**：确认内核插件树可加载（见第 6 节） | 握手掌证据 |
| 5 | **记录**：工作日志 + 能力/缺陷台账 + 活记忆（含 memory-sync） | 三处记录 |
| 6 | **立缺陷**：任何异常当场登记 | 缺陷编号 |

---

## 5 失败路径验收

- 每条能力**必须**验失败路径：模型不可用、账号未登录、素材缺失、超时、限流。
- 失败**必须**给三个选择：**断点继续 / 重新生成 / 放弃**。
- 失败**必须**给人话原因；**禁止**把内部异常、堆栈、接口名直接抛给用户。
- 只验成功路径的用例**视为未完成**。

---

## 6 内核握手规程

**为什么单列**：内核是懒启动（首次对话才 spawn），HTTP 200 只证明服务端活着。

**判据（满足其一即通过）**：

1. 跑内核握手探针并成功完成一次 initialize；或
2. 一次真实对话成功返回（模型有回应、工具可调用）。

**必须失败即中止**：插件树加载失败（例如配置里挂了未声明依赖的包）时，**不得**继续做端到端验收 —— 先修启动，再谈功能。

**已登记教训**：DEF-252（bundle/kernel 缺 @deepseek-ai/dsh-mcp-client 依赖 → 整棵插件树加载失败 → 产品 AI 全不可用）。

## 7 假阳性清单（出现即判红）

1. 接口返回 code=0，但页面上没有结果；
2. 页面上出现某段文字（可能是历史消息），业务对象没变；
3. 后端先执行、前端补显示；
4. 直接调后端接口或写数据文件冒充「用户办成了」；
5. 用 data-testid / 源码内部 id 定位成功，页面可见文字走不通；
6. 只走成功路径，没走失败路径；
7. 工具返回「已交给前端」却当成已完成（发卡模式）；
8. 只跑类型检查或构建就宣布可用；
9. 只看 HTTP 200 就宣布服务可用（未验内核握手）。

## 8 门禁化

| 阶段 | 做法 |
| --- | --- |
| 能力上线 | 同时产出该能力的「一句话」用例 |
| 缺陷首次出现 | 记入缺陷台账，附复现步骤 |
| **同一缺陷第二次出现** | **必须**升级为门禁断言（可重复、有 PASS/FAIL） |
| 新增门禁断言 | **必须**附负向对照，证明它会红 |
| 脚本用途 | 只允许门禁与一次性诊断；一次性诊断查清即删（BFS-305） |

## 9 与旧体系对照

| 旧 | 新 |
| --- | --- |
| S 级前端监考（只认页面 fill/click，业务动作必须由页面发起） | 一句话端到端（认「谁在动手」是管家） |
| 铁律 #1 前端数据为主 | 页面结果是交付证据，但入口不再限于页面 |
| 铁律 #16 自检落库证据 | 升为三方交叉的必要一项（第 3.2 节） |
| 铁律 #18 不准脚本测试 | 保留并加强：禁止一切绕过管家的脚本（BFS-305） |

## 10 违规处置

| 情形 | 等级 | 处置 |
| --- | --- | --- |
| 无 C 档证据宣称完成 | L1 | 停止、回滚状态、重做 |
| 三方证据不一致仍报成功 | L1 | 判失败、立缺陷 |
| 未验内核握手即宣布可用 | L1 | 重验，补记录 |
| 只验成功路径 | L2 | 当期补失败路径 |
| 用例不可重复 | L2 | 补可重复步骤或升门禁 |

## 附录 A · 用例模板

    【编号】AC-XXX-1
    【那句话】「……」
    【归属】创作管家 / 主链路第 2 环
    【预期可见结果】草稿箱出现 1 条，标题与主题相关
    【失败预期】模型不可用时：人话原因 + 断点继续 / 重新生成 / 放弃
    【证据】工具序列 / 工具返回 / 助手回复 / 落库字段
    【结论】PASS 或 FAIL
    【异常】缺陷编号（若有）

## 附录 B · 三方交叉记录模板

    【任务】task-xxxx（时间）
    【工具序列】skill -> bosom_content_generate_script -> bosom_content_create_draft
    【工具返回】已写入草稿箱（草稿 id cnt-xxxx）…… 已经落库
    【助手回复】已经存进草稿箱，打开内容创作就能看到
    【落库核对】contents 总数 0 -> 1，_id = cnt-xxxx，字段齐全
    【结论】三方一致 → PASS

## 附录 C · 本细则的三条硬底线

1. **没有 C 档证据，不许说完成**；
2. **三方不一致，判失败**；
3. **没验内核握手，不许说可用**。
