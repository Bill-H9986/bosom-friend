# 工程化流程与可追溯体系规范

> 版本：v1.2
> 日期：2026-09-08
> 适用：Bosom Friend（Electron + DSH 内核桌面应用）
> 读者定位：零开发经验的产品负责人 + 开发执行方（人/AI）共同执行
> 一句话：流程保证“每一步都有规矩”，追溯保证“每一步都有证据”，复盘保证“规矩越用越好”。

## 0. 给零基础读者：这份文档怎么用

- 你不需要看懂代码。你只负责三件事：看红绿灯、看追溯表、签字。
- 每次发布前，开发方必须给你一张《发布就绪清单》，每项只有 通过 / 不通过 / 不适用 三种答案，并附证据文件路径。任何一项不通过，你不签字。
- 每周你只看三份自动生成的报告：门禁红绿灯、缺陷台账、追溯矩阵，不需要你手工统计。
- 所有要求都用“必须 / 禁止 / 可以”表达，没有含糊的“尽量”。遇到不懂的词，查文末术语表。
- 配套文档：[DSH内核统一执行方案-v2.md](DSH内核统一执行方案-v2.md)、[Vibe-Coding-避坑实战指南.md](Vibe-Coding-避坑实战指南.md)（AI 协作开发约束，技能 `.agents/skills/vibe-coding-guide/SKILL.md`）、[客户端APP工程与Bug控制规范.md](客户端APP工程与Bug控制规范.md)、[项目铁律.md](项目铁律.md)、[S 级前端验收协议](products/bosom-friend/qa/acceptance/EXAM_PROTOCOL.md)。

## 1. 体系的标准来源（均已网上核实）

我们用成熟行业标准，但按本项目规模裁剪——取其实质，不做大厂官僚流程。

| 借用的做法 | 来源 |
| --- | --- |
| 软件质量保障流程（规划/执行/控制/评审） | IEEE 730 |
| 缺陷统一分类 | IEEE 1044 |
| 生命周期阶段与文档信息项 | ISO/IEC/IEEE 12207、15289 |
| 成熟度五级、持续改进 | CMMI |
| 任务准入准出（DoR/DoD） | Scrum.org |
| 需求双向追溯矩阵（RTM） | Tricentis 需求追溯指南 |
| 需求→测试双向追溯与孤儿需求检测 | Tuleap（req-to-test）；DO-178C / IEC 62304 / ISO 26262 同源要求 |
| 验收测试与验收准则编写 | ISTQB CT-AcT |
| 验收准则四态与未实现阻断门禁 | universal-dev-standards（对齐 ISO/IEC/IEEE 29119-3） |
| 可执行规范 / 活文档 | Cucumber / Specification by Example（BDD） |
| 架构决策记录（ADR） | 英国政府 ADR 框架 |
| 无指责事故复盘 + 5-Why | Atlassian / Google SRE |
| 提交信息规范与自动变更日志 | Conventional Commits / Keep a Changelog |
| 发布就绪清单（责任人 + 证据） | IOHK 质量工程发布清单 |
| 变更/问题/事件管理与审计痕迹 | ITIL |
| 计划-执行-检查-改进（PDCA） | ISO 9001 质量管理体系 |

裁剪原则：本项目是小团队 + AI 协作，成熟度目标定为“**可重复（CMMI 2 级）+ 已定义（CMMI 3 级）**”，保留 PDCA 复盘闭环，不上量化统计与层层审批（CMMI 4/5 级）。

## 2. 六条总原则

1. 流程化：没有流程的活不干。每个阶段有明确的输入、输出、准入、准出。
2. 标准化：每个产物有统一模板和编号，不搞一人一个写法。
3. 专业化：每个角色只做职责内的事，验收只看证据，不看人情。
4. 有痕迹：谁、何时、做了什么、为什么，四要素齐全，缺一不可。
5. 可追溯：任何一条需求都能正着查到代码和测试；任何一行代码或测试都能反着查到它的理由。
6. 可改进：每次迭代、每次发布、每次事故都复盘；结论要么改流程、要么改测试、要么改架构，并且下一轮验证是否真的有效（PDCA）。

## 3. 角色与职责（零基础版）

| 角色 | 谁 | 必做清单 | 不做什么 |
| --- | --- | --- | --- |
| 产品负责人 | 你 | 确认需求与验收条件；批准需求变更；每周看三份报告；发布前签《就绪清单》；参与事故复盘 | 不改代码、不替执行方做技术决策 |
| 开发执行方 | 开发人员 + AI | 按 ADR/设计编码；提交留痕；自测；缺陷登记与修复；补全追溯链接 | 不跳门禁、不自证通过、不绕过需求直接改代码 |
| 质量保证 | 测试脚本 / AI 监考 | 自动跑门禁与 S 级前端验收；生成红绿灯与证据包；登记缺陷 | 不替产品负责人做业务判断 |
| 审核人 | 指定负责人 | 代码评审、ADR 评审、缺陷根因评审、复盘评审 | 评审必须写结论和日期 |

关键规则：**验收人与执行人分离**。开发方不能既写代码又宣布“已通过”；通过与否由自动化门禁和你的签字共同决定。

> AI 协作开发（Vibe Coding）遵循 [Vibe-Coding-避坑实战指南.md](Vibe-Coding-避坑实战指南.md) 与技能 `.agents/skills/vibe-coding-guide/SKILL.md`：先方案后代码、小步原子提交、复用优先（能搬则搬）、证据验收（截图/可复现步骤）、如实报告失败。

## 4. 六个阶段与阶段门（准入准出）

每个阶段结束必须过“阶段门”：准出条件全部满足才能进下一阶段，结果记录在《阶段门记录》并由负责人签字。

### 4.1 需求阶段

- 准入：有明确要解决的问题或要做的功能。
- 输出：PRD，每条需求有唯一编号 REQ-xxx、验收条件、影响面。
- 准出：需求冻结；每条需求有可验证的验收条件；需求评审通过。

### 4.2 架构与设计阶段

- 输出：ADR-xxx（模板：标题/日期/状态/背景/决策/后果/参与人/链接）、接口与数据设计。
- 准出：ADR 评审通过；DSH 边界确认（前端不碰内核，业务全走 Tool/Provider）；设计与需求一一对应。

### 4.3 开发阶段

- 输出：代码提交（Conventional Commits，每条关联 REQ/DEF 编号）、单元/集成测试。
- 准出：类型/静态检查零错误；代码评审通过；DoD 全部满足。

### 4.4 测试阶段

- 输出：测试用例 TEST-xxx、测试报告、缺陷记录 DEF-xxx、S 级前端验收证据（页面可见结果 + 截图）。
- 准出：P0/P1 清零；关键回归通过；追溯矩阵无缺口（每条需求都有实现和验证，每个测试都有对应需求）。

### 4.5 发布阶段

- 输出：发布就绪清单、变更日志（Keep a Changelog 格式）、签名安装包 + SHA256、灰度计划与回滚预案。
- 准出：你签字；清单每一项为 通过/不适用；干净机器安装启动验证通过。

### 4.6 运维与复盘阶段

- 输出：监控数据（崩溃率）、用户反馈登记、复盘报告。
- 准出：改进项有责任人和期限；流程如需修订，规范升版本。

## 5. 追溯链：需求 → 验收准则 → 页面证据（两级闭环）

行业标准做法是两级追溯，缺一级就会漏功能：

- 需求级：每个功能一个 REQ，保证“功能清单”完整；
- 验收准则级：每条 REQ 拆成若干可验证的 AC（用 Given-When-Then 写），保证“做完”有明确标准。

AC 只有四种状态，其中“未实现”单独成红灯，专门抓“功能根本没做”：

```text
已覆盖：全部条件有测试断言 + S 级页面证据
部分：只测了主路径，缺边界/异常
未覆盖：代码在，但没有任何测试证明它符合验收准则
未实现：代码不存在——这是功能缺口，不是测试缺口，UAT/发布前必须清零
```

主链：

```text
REQ-xxx（功能需求）
  → ADR-xxx（设计决策）
  → 代码提交（脚注 Refs: REQ-xxx）
  → AC-xx 验收准则（Given-When-Then）
  → S 级前端证据（qa/evidence/ 页面截图）
  → 发布版本

缺陷反向挂回：DEF-xxx → REQ-xxx / 代码提交 / 回归用例
```

规则：

1. 每个功能必须有 REQ；每条 REQ 至少一条 AC；AC 逐条登记进 docs/trace/RTM.md；
2. “未实现”AC 数量必须为 0 才能发布——功能没做，任何覆盖率都不能放行；
3. AC 覆盖率 =（已覆盖 + 部分×0.5）÷ AC 总数，发布要求 100%，合入要求 80%（行业通行阈值）；
4. 没有对应 AC 的代码是“孤儿实现”，没有对应 REQ 的测试是“孤儿测试”，门禁发现即红灯；
5. 追溯表随开发同步更新，不事后补表——行业共识是“过期的追溯表比没有更糟”。

## 6. 痕迹规范：谁、何时、做了什么、为什么

六种痕迹是强制项：

### 6.1 代码提交（Conventional Commits）

格式：`<类型>(范围): 描述`，脚注关联编号。示例：

```text
feat(bosom_kernel): 新增内容发布工具
Refs: REQ-007
```

- fix 对应修缺陷，脚注 Refs: DEF-xxx；
- feat 对应新功能，脚注 Refs: REQ-xxx；
- 破坏性变更必须标 BREAKING CHANGE；
- 提交历史不可重写，保证痕迹真实。

好处：变更日志自动生成，版本号自动升级，任何一次改动都能查到为什么改。

### 6.2 架构决策（ADR）

- 编号从 ADR-000 起，文件存 docs/adr/ADR-000-主题.md；
- 状态只有四种：提议 / 已接受 / 已废弃 / 被替代；
- 必填：背景、决策、后果、参与评审的人、关联需求；
- 没有 ADR 的重大改动等于私自跑偏，门禁拦截。

### 6.3 变更日志（CHANGELOG）

- 每个版本一段，倒序排列，日期用 ISO 格式（如 2026-09-02）；
- 分组：Added（新增）/ Changed（变更）/ Fixed（修复）/ Removed（移除）/ Security（安全）；
- 上线失败被撤回的版本标 [YANKED]，不许删记录。

### 6.4 缺陷记录（DEF）

- 编号 DEF-xxx，模板见《客户端APP工程与Bug控制规范》§3.3；
- 必须包含：复现步骤、期望/实际、环境版本、根因（5-Why）、回归用例、责任人、计划版本；
- 修复提交脚注必须写 Refs: DEF-xxx，实现“缺陷 ↔ 代码”双向链接。

### 6.5 发布就绪清单

每次发布前，开发方必须提交清单（简化自 IOHK 发布清单），每项标：通过/不通过/不适用 + 责任人 + 证据文件路径：

```text
- 无未关闭 P0/P1
- 冒烟测试通过
- 关键回归通过
- DSH 边界门禁通过（无 dsh-web-app、无直连 /chat/completions、业务全走 Tool）
- S 级前端验收通过（页面可见证据）
- 干净机器安装/启动/升级/卸载通过
- 签名 + SHA256 校验
- 变更日志齐全
- 回滚预案演练过
```

任何一项不通过，你不签字，不得发布。

### 6.6 复盘报告（事故/迭代）

- P0/P1 事故必做复盘，24–48 小时内成稿；模板含时间线、影响、5-Why 根因、改进项（每项必须有责任人和期限）；
- 无指责原则：复盘问“系统和流程哪里出错”，不追责个人，否则没人敢说实话，根因找不出来；
- 改进项必须进入下一迭代计划，下轮复盘检查“上次的改进是否真的生效”。

## 7. 复盘与持续改进：防止原地打转

PDCA 是这套体系的心脏：

```text
计划（Plan）：需求 + 门禁 + 验收标准
执行（Do）：开发 + 留痕
检查（Check）：门禁 + 追溯检查 + 复盘
改进（Act）：改流程 / 改测试 / 改架构，并规定下一轮怎么验证
```

三条硬规则，专治“原地打转”：

1. 复盘禁止写“以后注意”这类空话。每条改进项必须有：做什么、谁负责、哪天完成、怎么验证有效。
2. 同一类问题第 3 次出现，停止局部修补，升级为架构级整改；流程漏洞同理。
3. 流程本身也版本化。每次发现“规矩有漏洞”，修订本规范并升版本号，下一轮按新版本执行——方案才真的越做越好，而不是同一套东西反复重来。

## 8. 自动化门禁：你不用懂代码也能查

开发方必须提供一键命令，输出《门禁红绿灯报告》。本项目当前命令（根目录 package.json 属官方 DSH，暂不改动，因此用 Node 直跑）：

```text
node products/bosom-friend/qa/run-gate.mjs          # 快速门禁
node products/bosom-friend/qa/run-gate.mjs --full   # 追加 S 级前端验收
```

| 门禁 | 结果 | 证据 |
| --- | --- | --- |
| DSH 内核组合 | 绿/红 | 启动器与依赖扫描 |
| 禁止直连模型接口 | 绿/红 | 命中文件:行号 |
| 依赖边界（禁 dsh-web / dsh-client） | 绿/红 | 禁止依赖清单 |
| 功能完整性（未实现 AC 清零） | 绿/红 | 未实现功能清单 |
| 验收准则覆盖率 | 绿/黄 | RTM 覆盖率与缺口 |
| 缺陷闭环留痕 | 绿/红 | 台账缺口 |
| S 级前端验收（--full） | 绿/红/黄 | 截图 + 页面日志 |

规则：任何红灯 = 不能合并、不能发布。你不看代码，只看绿灯是否齐全，以及每盏绿灯背后有没有证据文件。

当前快速门禁覆盖上表全部检查项；类型检查、静态检查、单元测试等仓库级门禁待官方 scripts 恢复后接入（Phase 1）。

## 9. 你的每周 / 每发布 / 每事故动作

每周（约 15 分钟）：

1. 打开《门禁红绿灯报告》，全绿才继续；
2. 打开缺陷台账，看 P0/P1 是否清零、重开率是否下降；
3. 打开追溯矩阵，看有没有需求缺验证、有没有孤儿测试。

每次发布前：

1. 收《发布就绪清单》，逐项核对证据文件存在；
2. 全部通过 → 签字放行（签字 = 姓名 + 日期 + 结论，留痕）；
3. 任何一项不通过 → 拒绝发布并写明理由。

每次事故后：

1. 要求 48 小时内交复盘报告；
2. 逐条确认改进项有责任人和期限；
3. 下一轮检查改进项是否闭环。

## 10. 术语表（大白话）

- PRD：产品需求文档，写清楚“做什么、给谁用、验收标准是什么”。
- 验收条件：怎么算“这个功能做对了”的可检查标准。
- ADR：架构决策记录，把“为什么这么设计”存档，防止反复争论、反复返工。
- RTM：追溯矩阵，一张表把需求、代码、测试、证据串起来。
- 回归测试：改完一处，重跑相关老功能，确保没把旧的弄坏。
- 门禁：一道自动检查，红灯就卡住，不让继续。
- 灰度发布：先给 5% 用户更新，看没事再逐步放开到 100%。
- SemVer：版本号规则（主版本.次版本.补丁），机器据此判断改动大小。
- Conventional Commits：统一的提交信息写法，让机器能自动生成变更日志。
- DoR/DoD：任务“开始前要满足什么”“做完的标准是什么”。
- RCA / 5-Why：根因分析，连续问“为什么”直到挖到根上。
- PDCA：计划 → 执行 → 检查 → 改进，质量管理里的持续改进循环。
- 基线：一个阶段冻结下来的、经过评审的正式版本，后续改动要审批。
- 审计痕迹：谁、何时、做了什么、为什么，四要素齐全且不可篡改的记录。
