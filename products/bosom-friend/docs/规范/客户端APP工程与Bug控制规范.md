# 客户端 APP 工程与 Bug 控制规范

> 版本：v1.4（2026-09-14 新增 §5.5 实时留痕与知识库同步）
> 适用对象：Bosom Friend（Electron + DSH 内核桌面应用）
> 目的：建立从需求到发布、从缺陷发现到根因收敛的工程流程，避免“改不完的 Bug”和“补丁叠补丁”。
>
> v1.1 新增：准入准出（DoR/DoD）、缺陷 SLA、ODC-Lite 缺陷分类与 5-Why 模板、发布工程（冻结/可复现构建/签名/灰度/回滚）、崩溃监控、收敛判定指标。
> v1.2 新增：§3.6「同根因复发」硬规矩——第二次出现就必须落成不变量断言 + 负向对照，不允许再修一次现象。
> v1.3 新增：§5.4「重启门禁」——构建退出码 0 不算产物已更新，只有产物时间戳与新进程启动时间能证明跑的是新代码。
> v1.4 新增：§5.5「实时留痕与知识库同步」——每个可交付节点完成即记录，不等提醒（见铁律 #17）。

## 0. 核心结论

没有流程可以保证零 Bug，但规范流程可以把 Bug 变成可预测、可分类、可回归、可收敛的问题。

行业共识是：

1. 缺陷发现得越晚，修复成本越高；
2. 大多数重复 Bug 来自需求变更、架构边界不清和“只修表面症状”；
3. 防止 Bug 的关键是 Shift-Left：在需求、设计、编码阶段就拦截，而不是上线后补。
4. 收敛不等于没有新 Bug：重开率、线上泄漏数、同根因重复、崩溃率四条曲线持续下降才算收敛。

## 1. 客户端 APP 标准生命周期

### 1.1 需求分析阶段

- 输出 PRD、用户流程、界面原型；
- 明确 MVP 与二期边界，禁止“开发中临时加需求”；
- 每条需求必须有验收条件；
- 高风险平台功能先做可行性验证。

### 1.2 架构设计阶段

- UI 与业务逻辑分离；
- 主进程、渲染进程、DSH 运行时子进程职责分离；
- 数据、模型、平台引擎边界清晰；
- 架构文档必须评审通过后才能开发。

### 1.3 迭代开发阶段

- 1-2 周一个可运行版本；
- 需求锁定在 Sprint 内；
- 每轮迭代结束做代码评审；
- 关键模块必须同时提交测试。

### 1.4 测试验收阶段

必须覆盖：

- 功能测试；
- 兼容性测试；
- 性能测试；
- 安全测试；
- 真机/干净环境测试；
- 前端可见结果验收。

行业参考指标：

- 缺陷率低于千分之三；
- 崩溃率低于 0.1%；
- 网络响应平均不超过 500ms；
- 高危安全漏洞为 0。

### 1.5 发布与运维阶段

- 签名、版本号、变更日志齐全；
- 安装、卸载、升级、数据保留实测；
- 上线后监控崩溃率、留存、性能；
- 用户反馈进入需求池。

## 2. Bug 预防：开发前和开发中

### 2.1 需求防 Bug

- 没有 PRD 不开发；
- 没有验收条件不排期；
- 需求变更必须评估影响面；
- Sprint 内冻结需求。

### 2.2 架构防 Bug

- 模块边界明确；
- 平台登录、发布、接待、数据等能力只能通过 Service Provider 暴露；
- 前端不重复保存会话状态；
- DSH Session 是唯一事实源。

### 2.3 编码防 Bug

- 静态检查、类型检查必须为零错误；
- 代码评审覆盖所有非机械改动；
- 禁止复制粘贴式业务逻辑；
- 高风险代码必须由两个人检查。

### 2.4 测试防 Bug

测试金字塔原则：

```text
大量单元测试
   ↓
适量集成测试
   ↓
少量端到端测试
```

Bosom Friend 的测试分层：

| 层级 | 内容 | 门禁 |
| --- | --- | --- |
| L1 | 工具参数、规则、Provider 单元测试 | 100% 关键逻辑覆盖 |
| L2 | DSH Kernel + Mock LLM + 真实工具集成测试 | 核心链路必须通过 |
| L3 | Electron 主进程 + 自研前端端到端测试 | 主流程必须通过 |
| L4 | S 级前端监考 | 业务动作必须页面可见 |
| L5 | 干净机器安装、启动、升级、卸载 | 发布前必须通过 |

### 2.5 持续集成防 Bug

每次提交必须自动执行：

```text
类型检查
静态检查
单元测试
DSH 架构边界门禁
关键集成测试
```

任何一个失败，不允许合并或发布。

### 2.6 准入准出（Definition of Ready / Definition of Done）

每个开发任务进入开发前必须满足（DoR）：

- PRD 或需求条目已冻结，禁止“边做边定”；
- 验收条件可执行、可验证；
- 影响面已评估（涉及哪些 DSH 能力、哪些页面、哪些数据）；
- 依赖已确认（平台接口、DSH 版本、模型能力）。

任务完成必须满足（DoD）：

- 代码评审通过，类型检查、静态检查零错误；
- 对应单元/集成测试通过，并覆盖验收条件；
- 涉及前端可见行为的，同步更新 S 级验收用例；
- 关键改动附变更说明或 Agent Note；
- 关联需求关闭并保留验证证据。

## 3. Bug 处理：发现到关闭

### 3.1 缺陷生命周期

```text
New
  → Confirmed（确认可复现）
  → Assigned（分配责任人）
  → Fixed（已修复）
  → Verified（测试验证）
  → Closed（关闭）
       ↓ 问题复现
      Reopened
```

按优先级约定响应与关闭时限（SLA），超时自动升级：

| 级别 | 响应时限 | 目标关闭时限 |
| --- | --- | --- |
| P0 | 30 分钟内响应，当天必须出方案 | 48 小时内 |
| P1 | 2 小时内响应 | 当前版本发布前 |
| P2 | 1 个工作日内响应 | 下一个迭代 |
| P3 | 排期处理 | 视版本计划 |

状态变更必须通知责任人与测试；逾期未处理自动上报项目负责人。

### 3.2 严重度和优先级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0/Critical | 核心功能不可用、数据丢失、安全事故 | 立即停止发布，当天处理 |
| P1/High | 主流程严重受阻 | 当前版本必须修复 |
| P2/Medium | 局部功能异常，有临时规避方案 | 下一版本修复 |
| P3/Low | 文案、样式、轻微体验问题 | 排期修复 |

严重度描述技术影响，优先级描述业务紧迫性，两者必须分开填写。

### 3.3 每个 Bug 必须包含

- 复现步骤；
- 期望结果与实际结果；
- 环境、版本、账号、平台；
- 截图、日志、Session Log；
- 影响范围和发生频率；
- 负责人和计划版本。

### 3.4 没有根因分析不得修复

修复流程：

```text
复现问题
定位根因
确认影响范围
提出修复方案
增加回归测试
验证修复
验证没有引入新问题
```

只改表现、不改根因的修复禁止合入。

如果同一类问题第三次出现，执行 §3.5 的架构级整改流程。

### 3.5 缺陷分类与根因模板

每个缺陷必须打两类标签：**缺陷类型**（在哪一类对象上出错）与**根因**（为什么出错），用于每周统计同根因复发，而不是只数数量。

缺陷类型（ODC-Lite，参考 IBM ODC）：

- 需求遗漏 / 需求误解；
- 设计（接口、状态机、边界划分）；
- 代码实现（逻辑、空值、异常、并发、资源）；
- 数据（schema、迁移、脏数据、同步）；
- 环境/集成（DSH 版本、平台接口、第三方依赖）；
- 测试脚本/用例本身缺陷。

根因分析模板（5-Why）：

```text
问题现象：
直接原因（为什么发生）：
为什么 1：
为什么 2：
为什么 3：
根本原因（归类：需求/设计/代码/数据/环境）：
修复方案（改根因，不是压表现）：
回归用例：
```

同一“缺陷类型 + 根因”组合第 3 次出现时：冻结局部修补，升级为架构级整改，排入技术债偿还计划。

### 3.6 「同根因复发」硬规矩（不等第三次）

**触发条件**：同一「根因归类」在这条产品线上**第二次**出现，无论现象是否相同、严重度高低。
（第一次出现仍可按 §3.4 正常修复；第二次起执行本节。）

**为什么不等第三次**：Bosom Friend 已有实例——DEF-001「停止生成点了没用：abort 只改落库状态，流式生成继续跑完并覆盖为 completed」
在 2026-09-10 19:20 修复，4 小时后 DEF-022 以同一形状在收尾窗口复发（早期读一次状态、后期再写回去）。
当时两次修复都只改了"现象发生的那一处"，所以第三次、第四次一定会换个窗口回来。

**强制动作（三条缺一不可）**：

1. **禁止再修现象，必须落成不变量断言**。
   把根因写成一条对状态/数据/接口的普适约束，而不是针对本次现象的采样点。
   例：不要断言"某次中断后落库是 aborted"，而是断言"任务终态一旦落定就不得再变"＋"abort 回报 interrupted=true ⇒ 终态必须是 aborted"。
   断言落在门禁（`qa/run-gate.mjs`）或验收脚本里，并登记进 `qa/acceptance/TEST_TIERS.json`。
2. **必须附负向对照**：把修复回退（或还原旧写法）后重跑，新断言**必须判红**。
   命令与结果原文贴进工作日志与 PR；只有正向证据的修复不算完成。
3. **覆盖时间/并发维度**：凡"流程中途某个值可能被后写覆盖"的缺陷，断言必须扫**多个时间点**并做**高频轮询状态序列**
   （同一任务/记录连续多次读必须单调不变），不允许单点采样——单点采样既会假红（同一份代码跑两次结论不同）也会假绿。

**记录要求**：缺陷台账「回归用例」列必须写明**不变量断言 + 负向对照的实际结果**（含判红条数）；只写脚本文件名不算。
状态用词收紧：只有"正向通过 + 负向判红"才可写 `Fixed`；缺负向对照的只能写「已改待验证」，不得进入 `Verified`。

**判红/判绿的证据纪律**：门禁报告必须对应当前工作区（报告头标注是否有未提交改动），
且"应用没运行导致检查跳过"只能算黄灯——跳过的检查不得被读成通过，更不得据此宣布"没问题"。

## 4. 后期修复与收敛

### 4.1 Bug 分类会审

每周会审一次：

- 复核严重度和优先级；
- 识别重复、关联问题；
- 确认责任人和目标版本；
- 更新回归测试。
- 输出模块缺陷热力图，同模块高频缺陷列入技术债偿还计划。

### 4.2 回归测试制度

每个修复必须附带：

- 该 Bug 的复现测试；
- 受影响功能的回归用例；
- DSH Session Log 验证；
- 前端可见结果验证。
- 修复提交后自动触发回归，未通过自动退回处理人，杜绝“假闭环”。

### 4.3 发布工程与门禁

发布按固定工程步骤执行，缺一步不得发布：

1. 需求冻结：发布范围锁定，新需求只能进下一版本；
2. 代码冻结：上线前 2 个工作日冻结主干，只允许带缺陷单号的修复合入；
3. 可复现构建：只从 tag 构建，锁定依赖版本，产物附 SHA256 校验和；
4. 签名：Windows 产物统一 Authenticode 签名，安装器与可执行文件都要签；
5. 版本门禁（任何一条不满足即否决发布）：
   - 无未关闭 P0/P1；
   - 冒烟测试通过；
   - 关键回归用例通过；
   - DSH 架构边界门禁通过；
   - S 级前端验收通过；
   - 干净机器安装/启动/升级/卸载通过；
6. 灰度发布：5% → 25% → 50% → 100%，每档观察崩溃与错误指标，超标立即停止；
7. 监控与回滚：上线后 24 小时观察窗口；更新清单指向可回滚的上一稳定版本，回滚步骤事先演练；
8. 变更日志：列出用户可见变化与已知问题。

### 4.4 Bug 度量指标与收敛判定

每周记录并公示：

```text
新增缺陷数 / 关闭缺陷数 / 存量
重新打开率
按严重度、按模块（热力图）分布
按缺陷类型与根因分布
平均关闭时长（按严重度）
缺陷发现阶段（需求/设计/编码/测试/线上）
同根因重复次数
```

目标与判稳标准：

| 指标 | 目标 |
| --- | --- |
| 重新打开率 | < 5%，持续下降 |
| 测试阶段未发现、上线后才发现（缺陷泄漏） | P0/P1 泄漏为 0 |
| 同根因重复缺陷 | 连续 2 个迭代为 0 |
| 线上崩溃率 | < 0.1%（crash-free ≥ 99.9%） |
| P0/P1 平均关闭时长 | 不超过 SLA |

判定“收敛”不是看“没有新 Bug”，而是看：重开率下降、泄漏为 0、同根因归零、高严重度提前到测试阶段被发现。任一指标连续恶化，立即启动 RCA 专项，而不是继续堆修复。

### 4.5 崩溃监控与线上缺陷闭环

- 主进程与渲染进程接入 Electron crashReporter（Crashpad）并上报（如 Sentry），上传前征得用户同意，不采集对话内容；
- 未捕获异常、崩溃 minidump、DSH 子进程退出码集中归档，带应用版本与平台信息；
- 线上反馈按缺陷生命周期登记：用户报障 → 复现 → 定位 → 修复 → 回归 → 灰度验证 → 全量；
- 线上 P0 走热修复补丁通道，但补丁同样必须过门禁，禁止“免测试直改线上”。

## 5. Bosom Friend 专项门禁

### 5.1 DSH 融合门禁

每次发布前检查：

```text
前端没有第二份会话状态
AI 路径没有直接调用 /chat/completions
业务动作全部通过 DSH Tool/Provider
DSH Session Log 完整
没有 dsh-web-app / dsh-client-* 依赖
```

### 5.2 前端验收门禁

业务动作必须由页面发起，结果必须在页面可见：

```text
页面操作
→ 前端请求
→ DSH 执行
→ 结果回传页面
→ 页面可见
→ Session Log 一致
```

后端 `code=0`、日志、数据库写入不能单独证明验收通过。

### 5.3 打包验收门禁

发布安装包前必须在干净环境验证：

```text
安装
启动
自研前端加载
DSH 运行时启动
一次完整 AI 业务
升级保留数据
卸载清理
```

### 5.4 重启门禁：跑起来的必须是刚编的

**触发条件**：任何一次「改完源码 → 构建 → 重启服务或应用」（开发运行时的 `launcher/lib/types/bin.js` 与打包运行时同样适用）。

**为什么单列**：2026-09-11 实测踩中——`server/src/api.ts` 15:25 改过，
`pnpm --filter @deepseek-ai/dsh-bosom-friend-server run build` 退出码 0、tsdown 也正常输出，
但 `tsc -b` 的增量状态误判为最新，**没有重新生成 `lib/types/api.js`**（仍是 13:28 的旧产物）。
若不核对时间戳直接重启，跑起来的仍是旧代码，而所有"构建成功"的输出都显示一切正常。

**强制动作（三条缺一不可）**：

1. **构建退出码不算证据**：退出码 0、`Build complete`、门禁全绿都不能证明产物已更新；
   唯一证据是**产物文件时间戳晚于对应源码**。
2. **产物不新就强制重编**：`tsc -b` 判定为最新但源码确实改过时，用 `tsc -b --force` 全量重编，
   再跑一次打包（`tsdown`）；不允许"再跑一遍试试"式重试。
3. **重启后核对进程启动时间**：新进程的启动时间必须**晚于**产物时间，否则它加载的是上一份产物；
   并用实测请求/页面确认（HTTP 200 且业务 `code:0`）——"进程在跑"不等于"新代码在跑"。

重启前逐对核对产物与源码：

| 产物 | 必须晚于 |
| --- | --- |
| `server/lib/types/*.js`、`server/lib/*.js` | `server/src/**` |

只写"已重启"不算完成，因为这三个时间正是本条规矩唯一能自动判定的证据。

### 5.5 实时留痕与知识库同步（2026-09-14；对应铁律 #17）

- **触发**：每完成一个可交付节点（修复 / 决策 / 踩坑 / 发布 / 调研结论 / 口径变更）**当场记录**，不攒、不等人提醒；
- **三处同时落**：`工作日志-YYYY-MM-DD.md` + `qa/defects/缺陷台账.md` + 桌面 Obsidian 知识库（`01-Bosom Friend 主线/` 对应笔记与总索引）；
- **判定**：没有实时记录的"完成"视为**未完成**（与 §5.4 重启门禁同一精神：可复核的留痕才算交付）；
- **AI/代理执行同样适用**：代理在每轮收尾必须自问"工作日志？台账？知识库？"，三项缺一即不得宣称完成；
- **禁止占位**：记录里不出现"待补""稍后整理"；数字与结论要有出处（哈希、条数、命令输出）。

## 6. 结论

Bosom Friend 后续开发采用：

```text
需求冻结 + DoR/DoD + 分层测试 + 缺陷分级/RCA + 回归自动化 + 发布门禁 + 灰度发布 + 线上监控闭环
```

这套机制不能承诺“零 Bug”，但能承诺三件事：

1. 缺陷在开发阶段被尽早发现，上线后泄漏最小化；
2. 每个 Bug 必须定位根因、带回归测试才能关闭，杜绝“补丁叠补丁”；
3. 用固定指标（重开率、泄漏数、同根因数、崩溃率）持续度量，任何恶化都有强制升级动作。
