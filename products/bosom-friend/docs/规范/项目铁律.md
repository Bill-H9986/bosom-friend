# 项目铁律（Rule #0）

> 遇到问题→先上网找解法；优先找成熟稳定的开源方案；能搬则搬、能抄则抄；
> 严格控制 BUG 率；禁止闭门造车。

## 最高测试权限：S 级前端监考（2026-09-02 升级至 v4）

1. **监考脚本只能操作 APP 前端页面。** 用户动作必须通过真实页面
   `fill/click/select/refresh` 完成；不得用 Node 脚本直接调用后端 API、
   HTTP 客户端、`page.request`、`context.request`、CLI、子进程或 worker。
2. **所有业务数据必须走前端→后端→前端闭环。** 前端先发请求，后端处理，
   数据返回前端并渲染为页面可见结果；不允许后端先执行、前端补显示。
3. **后端只是被前端触发的处理方，不是监考操作方。** 禁止监考官私自调用
   后端创建/修改/删除数据，禁止绕过前端造数据、清数据、执行发布或登录。
4. **S 级验收证据只认页面。** 截图、可见文案、列表、弹窗、图片、
   页面自身发出的请求与响应都要记录；`code=0`、日志、JSON、worker 成功
   永远不能单独作为 PASS。
5. **禁止“越俎代庖”。** 出题人不能替考生执行，监考官不能替代前端动作，
   修复者不能自己改判分，任何角色都不能利用后端接口绕过页面。
6. **测试数据默认隔离。** 使用独立 `BOSOM_FRIEND_HOME`、干净浏览器上下文；
   真实账号/真实平台副作用必须显式批准、备份并记录。

### 违规清单（立即 FAIL）

- 监考脚本出现 `fetch(api...)`、`axios`、`http.request`、`page.request`；
- 监考脚本 import/require 产品源码、后端服务或内部函数/worker；
- 脚本直接写 `.bosom-friend` 数据、SQLite、JSON、cookie、worker 日志；
- 脚本调用后端接口完成“考试动作”或“考试清理”；
- 页面没有成功结果，但后端返回 `code=0`；
- 页面显示成功，但对应请求不是页面发起；
- 报告把接口冒烟或后端审计写成 S 级通过；
- 同一场监考中脚本或修复者修改产品代码。

### 强制门禁

```powershell
cd products\bosom-friend\qa\acceptance
node frontend-supreme-gate.mjs

```

门禁不绿不得归档验收报告，不得宣称“已通过”。协议见
`products/bosom-friend/qa/acceptance/EXAM_PROTOCOL.md`，层级见
`TEST_TIERS.json`。

## 铁律 #1：所有测试以前端数据为主，后端服务为辅（2026-09-01 强化）

1. **用户验收看前端，不看接口返回值**：测试必须从用户可见页面读取真实 DOM、图片、
   toast、列表、详情、弹窗和交互结果；`code=0` 只是后端辅助证据，不能单独算通过。
2. **前端优先，后端交叉验证**：先证明“前端用户做了什么、看到了什么”，
   再用后端只读接口交叉核对落盘数据；后端不能代替用户执行。
3. **禁止用接口能力测试冒充产品验收**：例如“后端能创建记录”不等于“普通用户能在页面发布成功”。
4. **所有测试必须前端可复现**：测试记录必须包含页面路径、操作步骤、可见文本、截图/资源状态。
5. **数据安全让步于一切测试结果**：禁止任何 QA/审计脚本默认写产品数据根；
   必须使用隔离数据根、测试后指纹比对并自动回滚。
6. **接口冒烟不等于产品验收**：后端契约、SSE、持久化、worker 成功只能用于
   诊断后端，不能判“用户已完成”。

## 铁律 #2：DSH 官方基座与前端动手执行（2026-08-31 增补）

1. **产品定位**：本项目是基于 DeepSeek Harness（DSH）官方基座打造的 AI Agent Harness 应用软件；
   agent 执行必须走 DSH 的 agent/session/tool 扩展点，禁止在 REST 路由里重新实现一套独立 agent 循环。
2. **前端动手**：账号登录、内容创作、发布、同步、客服等业务动作必须由 APP 前端智能体在 Web 页面操作完成；
   后端接口只能用于只读佐证和持久化由前端动作触发的落盘。
3. **禁止后端越权**：任何“后端先执行、前端补显示”的实现都判为违规，必须回退到前端按钮/动作链路。
4. **禁止接口伪造**：不得用后端 `code=0` 或直接写 JSON 文件冒充前端业务成功；验收证据必须是前端可见结果。
5. **业务都在 DSH 上跑，但工具不是全部**（2026-09-03 增补）：业务能力一律注册为
   DSH 插件/服务；只有 AI 主动决策执行的动作才做成工具；普通增删改查经服务直调，
   长外部任务走任务队列。详见 ADR-002。

## 强制流程（每个问题必须走完）

1. **先查再动手**：遇到任何问题，先搜索成熟开源方案/官方文档/社区解法
   （GitHub、PyPI/npm、官方文档、Issue 讨论），禁止凭感觉直接写代码。
2. **能搬则搬，能抄则抄**：优先整体引入成熟项目；其次复制其成熟实现；
   复用其选择器、流程、构建方式，避免重写一遍重新踩坑。
3. **自研是最后手段**：只有确认没有可复用方案时才自研，并且要在代码/文档中
   写明「为什么没有可搬的方案」。
4. **严格控制 BUG 率**：
   - 复用上游已稳定验证的路径，不魔改其核心流程；
   - 需要小改动时，记录补丁与原因（见 engine/VENDORED.md）；
   - 每个改动必须实测/解码验证（如登录二维码必须解码确认真实登录码）；
   - 线上数据改动先备份，恢复/清理脚本化，禁用手改生产数据。
5. **事后复核**：每完成一个问题，说明「搬了什么/抄了哪段/为什么」，
   以及实测证据，禁止只给出结论不给证据。

## 已落实到位的实例（记录备查）

- 平台登录/发布 → 直接引入 MIT 开源项目 `social-auto-upload`，复用其主维护线
  （patchright 真实 Chrome + CDP）登录/发布流程，仅做最小文档化补丁。
- 浏览器自动化 → patchright/Playwright（成熟方案），不自研驱动。
- 大模型接入 → OpenAI 兼容 `/chat/completions` 标准协议（行业成熟方案）。
- 二维码校验 → 每次产码后解码确认真实登录码（cv2.QRCodeDetector 实测）。
- 依赖安装/浏览器下载 → 官方镜像（清华 PyPI、npmmirror），不手搓下载。

## 监督机制

若发现「闭门造车」：立即停止、指出问题、按本铁律重做，并记录到工作日志。

## 铁律 #3：永远站在普通用户角度开发（2026-09-01 增补）

1. **一切功能以“普通人双击就能用”为准**：不需要懂命令行、浏览器控制台、接口、
   Cookie、内部路径。任何需要技术操作的步骤都算未完成。
2. **每个参数必须看得懂、点得动、生效**：内容创作的模型、分辨率、画幅、时长、
   数量、平台、文案要求等控件，必须能被普通用户修改，并且修改后真实影响生成结果；
   只展示不生效的控件视为 BUG。
3. **界面文案与交互通俗**：错误要说人话（哪里错了、怎么办），不允许把内部异常、
   堆栈、接口名直接暴露给用户。
4. **验收视角**：每项验收都以“用户第一次打开 APP”的视角走一遍：页面在哪、
   点什么、看到什么、出错了如何自救。任何一步需要开发知识即 FAIL。
5. **APP 全功能 AI 全自动**：本 APP 的每一项功能（账号登录与管理、
   内容创作、图片/视频生成、发布、数据同步、监控、评论/私信客服、
   设置等）都必须能由 AI 自动完成。普通用户只需与 AI 对话说需求，
   AI 就自动操作 APP 把事办完，不需要用户自己找按钮、记步骤。
   任何功能若只能手动操作、AI 无法代劳，都视为未完成。

## 铁律 #4：说到做到，禁止阳奉阴违（2026-09-01 增补）

1. **承诺必须可验证**：每说“已完成/已修复/已通过”，必须附同一时刻的页面截图、
   可见结果或可复现步骤；没有证据的结论一律视为未完成。
2. **禁止偷换概念**：不得用“流程走完”“接口返回 0”“后台已执行”冒充
   “用户已看到成功”；不得先口头 PASS 再补证据。
3. **进度即事实**：每一步完成都以会话中可见的“步骤截图 + 结果说明”为准；
   报告只能引用真实发生过的事，禁止写计划当结论。
4. **失败同样留档**：失败、超时、平台报错都要如实记录并给原因，
   不允许悄悄跳过或改成 PASS。

## 铁律 #5：AI 智能体每步截图反馈（2026-09-01 增补）

1. AI 智能体每完成一步操作，必须当场截图当前页面，并把「截图 + 步骤说明」
   作为消息发到会话里，代表该步骤已完成。
2. 无截图、无说明、页面无痕迹的过程一律视为“没做”，禁止声称完成。
3. 全流程（创作→生成→发布→同步→数据）必须在会话中形成可回看的
   “操作图 + 文字”流水账。

## 铁律 #6：发布必须走平台，强化平台存在感（2026-09-01 增补）

1. **发布由平台引擎在真实平台完成**：普通用户只需在 APP 内点“发布”，
   产品内置平台引擎自动在真实平台执行；不允许本地模拟、假成功、
   后台写假数据。登录使用官方扫码。
2. **不使用官方开放平台通道**：官方开放通道对普通用户不现实，不作为实现路径。
   ⚠️ **平台风险与产品定位（2026-09-09 拍板）**：小红书 2026-07-17 治理公告禁止"用自动化工具代替真人操作实现自动发布/自动互动"。
   产品定位不变：**AI 全自动是核心卖点，任何情况下不改**——本节继续执行，不降级为半自动。
   风险按《0.2.0统一开发方案与路线图.md》第 4.2 节 9 条缓解措施处理（账号隔离、限频拟真、健康巡检、
   失败如实、风险告知），并逐条进 RTM。自动互动（点赞/评论/私信/关注/浏览）**同样全自动**，见该文档 4.3。
3. **平台身份可见**：账号页展示平台头像、昵称、粉丝/作品等真实画像；
   数据中心展示真实作品、真实链接、真实互动数据。
4. **发布成功 = 平台真实作品 ID/链接**：只有平台返回作品 ID/链接才算发布成功，
   本地记录必须能打开平台真实作品。
5. **互动有来路**：评论、私信必须来自平台真实数据，前端展示来源与时间，
   禁止本地伪造。

## 铁律 #7：AI 实事求是，不许说假话（2026-09-01 增补）

1. **能做到才说能做**：AI 只承诺真实存在的能力；做不到时立即明确告知
   “当前不能做”，绝不用假话、空话、模板话术冒充完成。
2. **未配置大模型必须固定提示**：没有填写 API（Key/地址/模型）时，
   AI 必须固定回答“未接入任何大模型，请先在 设置 → 配置大模型 中填写
   你的 API 地址和密钥”；禁止假装生成、编造内容或给出看似有用的假回答。
3. **配置了就真调用**：已配置 API 时，AI 必须真实调用大模型并返回真实结果；
   调用失败要如实说明原因（超时/限流/无效 Key），不得用兜底文案冒充成功。
4. **问什么答什么**：用户问“能不能做某事”，AI 直接给出能力边界和依据，
   不回避、不绕弯。

## 铁律 #8：对标 WorkBuddy，做成纯正 .exe 桌面软件（2026-09-03 增补）

1. **交付形态是纯正 Windows .exe 桌面软件**：对标腾讯 WorkBuddy 的安装体验——
   双击安装包、按向导下一步、桌面出现图标；普通用户不需要命令行，
   不需要安装 Node/pnpm/Python 或任何开发环境。
2. **开箱即用**：装完就能启动；首次启动有清晰引导；登录只用扫码/本地账号，
   不允许要求用户改配置文件、改环境变量。
3. **桌面体验完整**：独立应用窗口、桌面图标、系统托盘（按需）、
   自动更新、安装/升级/卸载干净，升级保留数据。
4. **内核不变**：继续只用官方 DSH 内核 + 自研前端；对标 WorkBuddy 的是
   “桌面软件形态与普通用户体验”，不是照抄腾讯云服务，也不引入其闭源组件。
5. **验收标准**：干净机器上双击安装→启动→完成一次完整 AI 业务→升级保留数据
   →卸载无残留，全部通过才算“纯正 .exe”达标；与本规范 #3 普通用户视角合并判定。
6. **能力对齐方向（按优先级逐步补齐）**：自然语言下达任务、多模态输入
   （文字/语音/文件/图片）、技能库、定时自动化、产物下载与分享、本地+云双模式。

## 铁律 #9：四不原则 + 编码铁律（2026-09-09 增补）

> 来源：同类 VibeCoding 项目复盘——「禁用假数据 / 完整增删改查 / 所有交互有效 /
> 明确数据存储方式」是 AI 生成应用能落地的最低门槛；乱码一律由编码问题引起。

1. **禁用假数据**：任何列表、统计、详情都不得用占位/示例/模板数据冒充真实结果；
   没有数据就显示空态并说明原因（与铁律 #7 一致）。
2. **完整增删改查**：每个业务域四个动作必须在**前端页面**上走通且即时可见——
   新增→列表出现，编辑→列表/详情立即反映，删除→列表消失且详情不可再读。
   只做「增+查」不算实现；接口通了但页面没反应同样算未实现（铁律 #1）。
3. **所有交互有效**：每个可点元素必须有确定结果（成功态或可读错误），
   禁止「点了没反应」「假成功」「静默失败」；新增交互必须附可复现步骤与截图。
4. **明确数据存储方式**：每个域必须写清数据落在哪个文件、主键是什么、
   「谁写/谁读/何时刷新」；同一实体只能有一套集合——禁止两套互不可见的集合
   （例：推广素材 `promo-*` 与素材库 `mat-*` 互不可见）。
5. **编码铁律（乱码按数据损坏处理）**：所有数据文件与进程间交换一律 UTF-8 无 BOM；
   禁止用 PowerShell `Set-Content`/`Out-File` 或任何非 UTF-8 工具重写 JSON 数据；
   一旦发现 `?`、`??????` 等替换字符即为已损坏，必须
   ①定位写入方并修复 ②修复数据 ③补门禁防复发。
6. **门禁**：第 1–4 条每域各一条可执行检查（CRUD 四步 + 空态断言）进
   `qa/run-gate.mjs`；编码检查扫描产品数据根与仓库内数据文件，命中替换字符即红灯。

## 铁律 #10：AI 全自动一站式服务平台（2026-09-09 拍板，不可更改）

> 用户原话：「我们的驱动核心是 DSH，我们的理念是 AI Agent 全自动一站式服务平台！
> 面向普通用户使用场景开发！由 AI 驱动全自动是我们的核心卖点！这点在任何情况下都不能改！」

1. **驱动核心是 DSH**：DSH 是唯一运行时；业务能力注册为 DSH 插件/服务，不得另起一套独立 agent 循环。
2. **理念是 AI Agent 全自动一站式服务平台**：一站式 = 用户不用在多个软件/网页之间来回跳；
   全自动 = AI 自己决策并执行到完成，不需要用户学操作。
3. **面向普通用户**：验收一律以"第一次打开 APP 的普通人"视角判定，任何需要开发知识的步骤即 FAIL。
4. **全自动是核心卖点，任何情况下不改**：禁止把功能降级成"必须真人点最后一下"来规避风险；
   每个功能的目标形态都是"用户说一句话 → AI 全自动办完 → 页面可见结果 + 每步截图"。
   **全自动覆盖全链路且包含互动**：创作 → 素材 → 发布 → 点赞/评论/私信/关注/浏览 → 数据同步 → 客服 → 账号运维，
   均无人工兜底节点（2026-09-09 二次拍板）。
5. **风险用缓解措施解决，不用降级解决**：平台合规风险按《0.2.0统一开发方案与路线图.md》第 4.2 节处理，
   并以大白话告知用户（4.4）。
6. **验收口径**：RTM 里的"部分/未覆盖"必须补到"用户一句话全自动完成"的 S 级证据，才算已覆盖。

## 铁律 #11：拟人化优先 + 按平台规则适配（2026-09-09 修订）

> 用户原话：「你那个分控限额太离谱了！我说的是不要太频繁自动化操作！
> 还有你得根据各平台规则来优化自动化规则啊！比如平台不允许脚本发布！
> 那我们就不能通过浏览器拟人操作控制？！这不就是避免风控的最有效的方法之一吗！」
>
> 结论：抗风控靠**拟人化行为 + 按平台规则适配**，不是靠"一天只发一条"的一刀切限额。

1. **拟人化是主手段**：平台操作一律走"真实浏览器 + 拟人行为"——patchright 反检测浏览器、
   真实鼠标轨迹与键盘节奏、随机停顿与滚动、非固定时间点；禁止接口直灌、固定秒级节奏、
   后台无痕批量提交。
2. **按平台规则适配，逐平台建表**：

   | 平台 | 平台规则要点 | 本产品策略 |
   | --- | --- | --- |
   | 小红书 | 禁止脚本/自动化代替真人发布与互动 | 浏览器拟人操作 + 真人可读内容 + 合理限频；不接官方开放接口 |
   | 抖音 | 开放接口滥用会被处罚 | 同上，走浏览器拟人；不做接口批量调用 |

   新平台接入前必须先写清"平台规则 → 我们的做法"，写进开发文档第 4 章。
3. **合理限频（可配置，非一刀切）**：默认每账号每天发布 ≤3 条、互动 ≤20 次；
   同一动作两次间隔随机 5–25 分钟；单次会话只发 1 条；参数按平台可调，写进配置而非隐藏常量。
4. **不并发轰炸**：同一账号同一时刻只允许一个平台任务；禁止多任务并发操作同一账号。
5. **内容质量门槛**：低质、重复、敏感内容不自动发（开发文档 4.2 第 3 条）。
6. **失败即停**：同一场景连续失败 2 次即停止定位，不反复重试刷。
7. **留痕**：每次真实发布/互动记录时间、账号、作品或互动 ID、内容摘要。

## 铁律 #13：没有端到端证据，不许说"完成"（2026-09-09 增补）

> 用户原话：「为什么BUG老是改不完？！！！就是这个原因！！！」
> 复盘：同一个"保存模型没作用"的问题反复出现，根因不是单点代码错，而是
> ①改完后端却没构建/重启，跑的还是旧代码；②只看到"构建成功/页面渲染出来了"就宣布完成；
> ③链路跨四个环节（前端→服务端→DSH 设置与凭据→内核注册表），缺一个断言就会漏。

1. **改后端必须重建**：开发版加载的是 server/kernel 的 `lib` 产物；`dev-web.ps1` 已内置构建步骤，

2. **禁止以"构建成功/页面能渲染"作为完成依据**：那只能证明编译通过，证明不了功能可用。
3. **跨层链路必须有端到端门禁**：涉及"配置 → 持久化 → 内核 → 实际调用"的功能，

   `qa/verify-llm-config.mjs`（模型配置链路）、`qa/verify-agent-rules.mjs`（智能体规则结构）。
4. **验收前先跑门禁**：任何"已修复/已完成"的结论，必须附门禁输出（PASS 原文）。
5. **同一问题第二次出现即升级为门禁**：不允许靠"再改一次"解决；必须补一条自动检查，防止复发。

## 铁律 #14：知识库必须是"被用上的记忆"，不是摆设（2026-09-10 增补）

> 用户原话：「知识库目前在APP中的作用还是太小了！你看怎么让知识库的作用发挥到最大！
> 这个是大模型做蒸馏的关键！」
>
> 结论：知识库 = 模型的可检索记忆 + 可蒸馏样本源。只做「能写笔记」不算实现。

1. **必须被注入**：AI 对话与内容生成前，先按用户指令检索知识笔记，
   命中即作为「已知知识」进模型上下文；每次注入都要留痕（命中了哪几篇、多少字）。
2. **必须能验证**：提供注入预览接口/页面——输入一句话，就能看到这次会命中哪些笔记，
   不允许"注入了但没人知道注入了什么"。
3. **必须可蒸馏**：每次生成/对话留一条结构化样本（指令、输出、模型、注入来源、评分、状态），
   可聚合为 JSONL 微调数据集（OpenAI messages 结构）并一键导出。
4. **审计记录不参与注入**：`自动沉淀/` 目录是给人看的审计日志，
   禁止作为模型知识注入（它们天然含业务关键词，会稀释真正的知识）。
5. **门禁**：检索/注入/蒸馏三条链路各有一条可执行检查（`qa/knowledge-distill.mjs`）。

## 铁律 #16：自检断言必须落到"落库/请求"证据，页面文案不算（2026-09-10 增补）

> 背景：账号管理专项 debug 时发现——**自检自己会骗人**。断言写在页面/弹窗文案上时，

   说不清"什么情况下会红"的断言等于没写。
