## 1 目的与适用范围

### 1.1 目的

规定本产品的**缺陷定义、分级、预防、处理、收敛与度量**，使缺陷可控、可追溯、不复发。

**判定线**：每一个缺陷都有编号、根因、回归用例；同一根因**不得**出现第三次。

### 1.2 适用范围

适用于 products/bosom-friend 全部代码、文档、脚本、门禁与交付物。

---

## 2 术语与关键词

| 术语 | 定义 |
| --- | --- |
| **缺陷（DEF）** | 产品行为与「能力定义（那句话 + 可见结果）」不一致，或用户明确感知的坏体验 |
| **假成功** | 系统宣称完成而实际未完成（最严重的一类，见第 3.4 节） |
| **根因** | 导致缺陷的直接机制；不是「不小心」「疏忽」这类描述 |
| **复发** | 同一根因导致的缺陷再次出现（换表象也算） |
| **DoR / DoD** | 准入门槛 / 完成定义 |
| **回归用例** | 能证明该缺陷被修好、且以后不会再犯的检查 |

| 关键词 | 含义 |
| --- | --- |
| **必须** | 强制；违反即返工 |
| **应当** | 强烈建议；不遵从须写明理由 |
| **可以** | 可选 |

## 3 缺陷的定义与分级

### 3.1 什么算缺陷

| 编号 | 判据 |
| --- | --- |
| 601.1 | 用户说了那句话，结果与预期可见结果不一致 |
| 601.2 | 结果正确但**用户看不到**（可见性缺陷） |
| 601.3 | 系统宣称成功而实际未完成（假成功，见 3.4） |
| 601.4 | 失败时未给出人话原因或三个选择 |
| 601.5 | 需要开发知识才能用（违反 BFS-103.3） |

### 3.2 严重度分级

| 级别 | 定义 | 例子 |
| --- | --- | --- |
| **P0** | 核心能力完全不可用 | 产品 AI 全不可用（DEF-252）；未授权自动发布（DEF-240） |
| **P1** | 主链路某一步走不通 | 发布状态不回填（DEF-247）；按钮点了没反应（DEF-250） |
| **P2** | 可用但有明显缺陷 | 状态不显示（DEF-248）；台账结构不合规（DEF-246） |
| **P3** | 体验与一致性问题 | 文案不统一、排序不合理 |

### 3.3 响应与处置要求

| 级别 | 处置要求 |
| --- | --- |
| P0 | 立刻停止其它工作，先修；修完当场补门禁 |
| P1 | 当期修，未修不得进入打包 |
| P2 | 当期或下期修，必须在台账可见 |
| P3 | 排队，可合并处理 |

### 3.4 「假成功」专项（最严重一类）

**定义**：系统或实现者宣称某件事已完成，而事实并非如此。

| 编号 | 判据 |
| --- | --- |
| 604.1 | 工具返回空 id 却声称完成 → 缺陷 |
| 604.2 | 接口 code=0 而页面无结果即宣布通过 → 缺陷 |
| 604.3 | 只看 HTTP 200 就宣布服务可用（未验内核握手）→ 缺陷 |
| 604.4 | 用「应该没问题」「基本可用」代替证据 → 缺陷 |
| 604.5 | 假成功**必须**按 P0~P1 处理，且**必须**补一条门禁 |

**历史教训**：2026-09-29 AI 对用户说「已写入草稿箱」而草稿箱无内容；2026-10-11 只看 HTTP 200 宣布开发版恢复而内核插件树加载失败。

## 4 缺陷预防

### 4.1 需求防缺陷

| 编号 | 要求 |
| --- | --- |
| 611.1 | 需求**必须**写成四行（那句话 / 归属 / 可见结果 / 失败预期），缺一行不进开发（BFS-501） |
| 611.2 | 「只展示不生效」的控件视为缺陷（旧铁律 #3.2 保留） |

### 4.2 架构防缺陷

| 编号 | 要求 |
| --- | --- |
| 612.1 | 同一份实现只允许一个入口（禁止页面与工具两套实现，BFS-102.2） |
| 612.2 | 影响 DSH 边界、进程结构、数据格式、对外接口的改动**必须**先写 ADR |
| 612.3 | 启动类改动**必须**自证内核握手（BFS-102.6）——DEF-252 的直接教训 |
| 612.4 | 配置里挂的包名**必须**在解析基准目录的 manifest 里声明 |

### 4.3 编码防缺陷

| 编号 | 要求 |
| --- | --- |
| 613.1 | 类型检查**必须** exit 0；**禁止**以「esbuild 不做类型检查」为由放过（DEF-252 关联发现） |
| 613.2 | 错误**必须**带原因与下一步，禁止静默吞掉 |
| 613.3 | 每个校验分支**必须**告诉模型怎么改（工具报错是模型唯一的自我纠正渠道） |
| 613.4 | 厂商 HTTP **只能**出现在 Provider 包（BFS-102.3） |

### 4.4 测试防缺陷

| 编号 | 要求 |
| --- | --- |
| 614.1 | 每条能力**必须**有一句话用例 + 失败路径用例 |
| 614.2 | 验证**必须**由实现者自己执行并实时监测（BFS-206） |
| 614.3 | **禁止**只跑成功路径 |

### 4.5 持续集成防缺陷

| 编号 | 要求 |
| --- | --- |
| 615.1 | 每条能力上线**必须**带门禁；新增断言**必须**有负向对照 |
| 615.2 | 同一根因复发**必须**升级为门禁断言 |

### 4.6 准入准出

**DoR（准入）**：能力已登记 + 四行齐全 + 影响面三行已写。
**DoD（准出）**：C 档证据 + 三方交叉 + 内核握手 + 失败路径 + 三处记录 + 门禁。

## 5 缺陷处理

### 5.1 生命周期

发现 → 登记 → 定级 → 根因分析 → 修复 → 回归验证 → 关闭 → 门禁升级（如复发）

**状态取值**：Open / In Progress / Fixed（待验证）/ Verified / Closed / Wontfix（须写明理由）。

### 5.2 每个缺陷必须包含的字段

编号、标题、严重度、状态、缺陷类型、根因归类、关联需求/能力、回归用例、责任人、计划版本、重开次数 —— 缺一不得登记。

**证据要求**：现象的可复现步骤 + 至少一项结构化证据（接口/落库/日志/页面）。

### 5.3 没有根因分析不得修复

| 编号 | 要求 |
| --- | --- |
| 623.1 | 根因**必须**写成可验证的机制描述，禁止「疏忽」「没注意」 |
| 623.2 | 根因**必须**带定位证据（文件 + 行号 / 命令输出 / 会话时间） |
| 623.3 | 修复方案**必须**针对根因，禁止只改表象 |

### 5.4 根因分类模板

| 类别 | 含义 | 例 |
| --- | --- | --- |
| 需求歧义 | 四行没写清 | 控件只展示不生效 |
| 架构错配 | 实现方式与形态不符 | 发卡模式代替真执行 |
| 配置/依赖 | 声明与解析不一致 | DEF-252（bundle 缺依赖） |
| 数据/状态 | 写入点不唯一、无事务 | 状态覆盖回 completed |
| 可见性 | 做了但看不见 | DEF-248 |
| 假成功 | 宣称完成而实际未完成 | 604 系列 |
| 外部依赖 | 厂商限流、平台风控 | 免费档 RPM=1 |

### 5.5 同根因复发硬规矩

| 编号 | 要求 |
| --- | --- |
| 625.1 | **不等第三次**：同一根因第二次出现即升级为门禁断言或流程改动 |
| 625.2 | 升级动作**必须**在同一轮完成，不得挂账 |
| 625.3 | 复发缺陷**必须**在台账标注重开次数 |

## 6 后期修复与收敛

### 6.1 缺陷分类会审

按根因分类聚合，优先修「同一根因影响多条能力」的那一类。

### 6.2 回归测试制度

| 编号 | 要求 |
| --- | --- |
| 632.1 | 修复后**必须**跑该能力的用例 + 受影响能力的用例 |
| 632.2 | 回归**必须**在隔离数据根上进行（BFS-201.4） |

### 6.3 发布工程与门禁

打包前**必须**满足：P0/P1 清零、门禁绿、发布就绪清单勾完、版本单源一致。

### 6.4 度量指标与收敛判定

| 指标 | 定义 | 收敛判据 |
| --- | --- | --- |
| 未闭环 P0/P1 数 | 台账中 Open/In Progress 的 P0+P1 | 打包前必须为 0 |
| 假成功数 | 604 系列缺陷数 | 持续为 0 |
| 复发率 | 重开次数 > 0 的缺陷占比 | 持续下降 |
| 门禁覆盖率 | 有门禁的能力数 / 已上线能力数 | 逐轮提升至 100% |
| 管家化率 | 有工具的能力数 / 台账写操作总数 | 逐轮提升至主链路 100% |

## 8 反例与违规处置

| 反例 | 等级 | 处置 |
| --- | --- | --- |
| 假成功（宣称完成而实际未完成） | L1 | 回滚状态、按 P0/P1 重做、补门禁 |
| 无根因分析就修复 | L1 | 停止，补根因 |
| 同根因复发未升级门禁 | L1 | 当场升级 |
| 缺陷字段不全 | L2 | 当期补齐 |
| 绕过类型检查 | L2 | 当期修到 exit 0 |
| 回归未跑 | L2 | 当期补跑 |

## 附录 A · 缺陷登记检查清单

- [ ] 编号唯一、未回收
- [ ] 11 个字段齐全
- [ ] 根因是可验证机制 + 定位证据
- [ ] 有回归用例（或登记为待建）
- [ ] 挂到具体能力上
- [ ] 严重度与响应要求匹配
- [ ] 复发则已升级门禁

## 附录 B · 从现象到根因的四问

1. **在哪里断的**？（文件 + 行号 / 接口 / 落库字段）
2. **为什么之前没发现**？（探活方式、覆盖盲区）
3. **同类还有几处**？（全仓搜索同一模式）
4. **怎么让它不再犯**？（门禁 / 流程改动）
