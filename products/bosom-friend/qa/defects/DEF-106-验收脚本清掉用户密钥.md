# DEF-106 验收脚本按旧式单配置写 llm-user.json，会把用户密钥清成占位串

| 项 | 值 |
| --- | --- |
| 编号 | DEF-106 |
| 发现日期 | 2026-09-18 |
| 发现方式 | 我在做 30 秒端到端验收时，写完配置后发现对话通道回「未接入任何大模型」，逐份比对配置备份才定位 |
| 严重级 | P1（会静默破坏用户已保存的凭据） |
| 状态 | Fixed（本机已恢复；脚本侧待补护栏） |

## 现象

`%USERPROFILE%\.bosom-friend\bosom-friend\llm-user.json` 里四把密钥原本是同一把（51 字符，见 2026-09-16 的备份 `llm-user.json.before-image-model-fix-20260916-143421`：顶层 / image / video / providers[0] 全等）。
验收脚本跑完之后：顶层 `apiKey`、`videoApiKey`、`providers[0].apiKey` 变成 **19 字符**，只有 `imageApiKey` 还是 51 字符。
后果：对话通道自检回「未接入任何大模型。请先在设置里填写 API 地址和密钥」——而界面里图片/视频还能用，因为那两个通道读的是各自的密钥。

## 根因

服务端的 `PUT ai/user-llm` 有两条路径：

1. 提交体里带 `video` 且 `video.apiKey` 非空时，会把它同时写进顶层与视频通道；
2. 提交体里**不带** `apiKey` 时，才走「沿用已保存的那把」的保留分支。

验收脚本为了把视频通道临时指向本机假厂商，提交了 `video: { baseUrl, apiKey: 'sk-...' }`，
于是一把**占位密钥**被写进了真实配置文件的顶层与视频通道。同类的 19 字符串 `preserve-stored-key` 也出现在更早的一轮尝试里——两种写法都把占位串当成了真密钥。

另有一条同族陷阱：`GET ai/user-llm` 返回的 `providers` **不含密钥**（只有 `hasApiKey`），把它原样回传等于把对话通道的密钥清空。

## 处置

1. 按 2026-09-16 备份确认「四把本是同一把」，把顶层 / image / video / providers[0] 统一回那把已知可用的密钥（图片通道当时刚成功出图，证明它可用）；
2. 重启内核（内存里的旧配置不会因文件变新而重载）；
3. 验证：`POST ai/chat` 返回真实模型回复（`model=agnes-3.0-flash`，正文是模型写的引导语，不再是模板兜底）。

## 待补的护栏（尚未实现）

- 服务端：拒绝把明显的占位串（`preserve-stored-key`、`sk-fake-*`）写进真实配置；或把「不传密钥」与「传了一把新密钥」在接口层彻底分开（例如改用 `apiKeyMode: keep|replace`）；
- 验收脚本：改配置前先落一份**可校验**的备份，结束时按备份逐字段比对（含密钥长度），不一致就判失败并提示恢复命令；
- 现状：脚本只比对了地址/型号/`hasApiKey` 三个粗粒度字段，密钥被换掉它照样报 PASS——这正是它没能自己发现问题的原因。
