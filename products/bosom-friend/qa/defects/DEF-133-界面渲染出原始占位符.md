# DEF-133 界面渲染出原始占位符（批量管理工具条显示 `已选 {count} / {total}`）

| 项 | 值 |
| --- | --- |
| 编号 | DEF-133 |
| 发现日期 | 2026-09-22 |
| 发现方式 | 用户截图（我的任务 → 批量管理工具条）→ 本机 i18next 实测复现 |
| 严重级 | P2（用户可见：中文界面里冒出生词串） |
| 状态 | Fixed（2026-09-22：占位符改双花括号 + 门禁扩成三条判据并接进 run-gate） |

## 现象（实测证据）

截图：`qa/evidence/fix-2026-09-22/batch-toolbar-count.png`（修复后）、用户截图（修复前：`已选 {count} / {total}`）。

用本机 i18next（26.4.0）实测三种写法：

| 语言文件写法 | 渲染结果 | 说明 |
| --- | --- | --- |
| `已选 {count} / {total}` | `已选 {count} / {total}` | **单花括号永远不会被替换** |
| `已选 {{count}} / {{total}}` | `已选 2 / 9` | 正确 |
| `{{platformName}} 图片不能超过 {{maxCount}} 张`（调用方不传 platformName） | `{{platformName}} 图片不能超过 9 张` | 缺变量时同样原样渲染 |

## 根因

**i18next 的取值语法是 `{{name}}`，而语言文件写成了 `{name}`。**

1. 全语言 156 个文件里共 32 处单花括号：`chat.json` 的 `task.selectedCount` / `batchDeleteConfirmDesc` /
   `batchDeleteSuccess`（zh-CN 与 en），以及 home / pinterest 两个命名空间的 26 处。
2. 同族的第二种：`publish.validation.imageMaxExceeded` 在 de/en/fr/ja/ko 里带 `{{platformName}}`、
   zh-CN 里没有，而 `PubParmasTextarea` 那条调用**不传**这个变量 → 缺变量时 i18next 同样把
   `{{platformName}}` 原样吐到界面上。
3. 为什么复发：DEF-062 当年只补了**键名**，没管占位符写法；而 `qa/verify-i18n-keys.mjs` 虽然存在，
   **却没有任何调用方**（写了没人跑）。

## 修复

1. 全语言扫一遍，32 处单花括号改双花括号；`PubParmasTextarea` 补上 `platformName`，基准语言补齐占位符。
2. `qa/verify-i18n-keys.mjs` 从"只查键存在"扩成三条判据：关键键存在（新增 7 个 task 批量键）、
   单花括号一律判红、各语言 `{{name}}` 取值集合必须与 zh-CN 一致。
3. 接进 `qa/run-gate.mjs` 的「界面文案完整性」——脚本存在但没人跑，等于没写。

## 回归判据

- `node products/bosom-friend/qa/verify-i18n-keys.mjs` → `I18N_KEYS PASS checked=14 files=156 keys=22679`
- 负向对照（两条，均实测判红）：把 `task.selectedCount` 还原成单花括号 → 报
  「单花括号占位符不会被替换 zh-CN/chat.json :: task.selectedCount :: {count}」；
  给某个语言多写一个变量 → 报「占位符与基准语言不一致」。
- 浏览器实测：工具条 `全选 | 已选 1 / 1 | 删除选中 | 退出批量管理`；确认框 `确定删除选中的 1 条任务记录吗？此操作不可恢复。`
