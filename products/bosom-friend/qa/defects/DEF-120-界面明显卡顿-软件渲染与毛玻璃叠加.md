# DEF-120 界面明显卡顿：显卡加速被误判关掉，重特效却还在开

> 编号：DEF-120（唯一、终身不变）
> 状态：Fixed
> 严重度：P1　　优先级：高（不是"某个功能不好用"，是整台机器上每一步操作都拖）
> 缺陷类型：性能/体验
> 关联需求：REQ-021（客户端工程与低配适配）
> 报告人 / 日期 / 环境版本：用户报障（"使用起来有明显的吊针卡顿！"）/ 2026-09-21 / 0.2.59
> 责任人 / 计划版本：Jay / 0.2.60
> 重开次数：0

## 复现步骤

1. 打开装机版（0.2.59）；
2. 任意页面做日常操作（切页、滚动、开设置弹窗、打字）；
3. 主观感受：每一步都"黏"，动画一顿一顿。

## 期望结果 vs 实际结果

- 期望：20 核 / 15.6GB 的标准档机器上，UI 操作跟手。
- 实际：整台机器被判成"标准档"（重特效全开），而**硬件加速已经被自动关掉**——所有合成落在 CPU 上。

## 现场证据（本机 userData，非推测）

| 证据 | 值 |
| --- | --- |
| `perf-profile.json` | `tier=standard`、`caps.heavyEffects=true`、`gpuFallback="显卡加速连续 4 次崩溃（crashed）"` |
| `gpu-crash.json` | `{crashes: 4, lastReason: "crashed", at: 2026-09-20T13:37:10Z}`（连续两天启动都还在） |
| `logs/2026-09-21.log` | `[GPU_FALLBACK] 已关闭硬件加速：显卡加速连续 4 次崩溃（crashed）` |
| `logs/2026-09-20.log` | 当天每次启动都打同一条；`13:37:10` 那次紧跟在 `[boot] 正在退出：关闭内核与后代进程` 之后 |
| Windows 系统日志 | 近三天**没有**任何显卡驱动错误（Display/4107 是信息级"显示模式已切换"） |

## 根因（两处独立成因叠在一起）

### 1. 正常退出被当成显卡崩溃（误判来源）

`main.cjs` 的 `child-process-gone` 里，凡是 `type === 'GPU'` 就把 `details.reason` 记一次崩溃，
不区分原因。而**应用正常退出时也会收到一次 `reason=killed` 的 GPU 子进程事件**（进程树收尾），
于是"开两次、关两次"就能凑够阈值，把一台好显卡的机器判成"跑不了硬件加速"。

现场留痕的最后一条正是 `crashed`，而它前面几条里混着收尾事件——留痕里**没有**任何
驱动层证据（系统日志干净），根因归为"判据把正常退出算成了崩溃"。

### 2. 软件渲染与重特效没有联动（卡顿被放大的原因）

低配适配本来有一条正确的联动：`tier=low` → `caps.heavyEffects=false` → 服务端注入
`__BF_PERF_TIER__='low'` → 前端给 `<html data-perf="low">` → CSS 关掉毛玻璃与长动画。
注释里原本就写着"全屏模糊在集显上每帧都要重算"。

但 GPU 兜底走的是另一条路：它只 `app.disableHardwareAcceleration()`，**档位仍是 standard**，
`heavyEffects` 照样是 true。于是标准档机器在软件渲染下继续开着 50 多处毛玻璃——
每帧都要在 CPU 上把背后像素重算一遍，这正是用户摸得到的"黏"。

### 3. 降级是永久的（为什么两天都没自己好）

留痕一旦写成就再没人清：软件渲染模式下那条"稳定 5 分钟就清除留痕"的计时器**根本不会启动**
（它只在 `gpuFallback === ''` 时创建）。于是这台机器会一直降级下去。

## 修复

| # | 改动 | 文件 |
| --- | --- | --- |
| 1 | 只有 `crashed / abnormal-exit / oom / integrity-failure` 计入留痕；`killed / launch-failed / clean-exit` 记日志但不计（并写明"正常退出，不计入留痕"） | `desktop/electron/main.cjs` |
| 2 | 留痕**7 天过期**：系统/驱动更新之前的旧崩溃不再把机器永久摁在软件渲染上 | 同上 |
| 3 | 关硬件加速时联动关重特效：`disableHeavyEffects()` 只改 `heavyEffects`（档位、堆、备份、轮询间隔都不动），并在内核子进程起来之前**重写环境变量** | `perf-profile.cjs` + `main.cjs` |
| 4 | 落盘留痕写的是**生效后**的档位（`PERF_EFFECTIVE`），排查时看到的就是真正跑的那一套 | `main.cjs` |
| 5 | 低配 CSS 从"只关弹窗遮罩的模糊"扩到**所有毛玻璃**（`backdrop-filter: none !important`），保留原半透明底色，不动布局与信息 | `project/bosom-friend-electron/src/index.scss` |

## 回归判据

`qa/probes/verify-perf-profile.mjs`（本轮从 15 条扩到 **18 条**，全绿）：

- 关硬件加速时 `heavyEffects` 跟着关，且**档位仍是 standard**；
- 关硬件加速**不动**与它无关的上限（堆 4096 / 备份 30 / 轮询 10 分钟）；
- 关硬件加速的理由写进 `perf-profile.json` 的 `reasons`（现场能看出为什么关了特效）。

## 现场处理（本轮已做）

删掉 `%APPDATA%\Bosom Friend\gpu-crash.json`：下一次启动即恢复硬件加速。
装机版要先装上新包才带上上面 5 条改动（主进程与前端 CSS 都在包里）。

## 为什么值得记

1. **"能自动降级"不等于"降级是对的"**：降级链路的判据（什么算崩溃）与联动（降级后还开不开重特效）
   都缺了，于是"保护用户"的那段代码本身成了卡顿的来源；
2. **永久降级是设计缺陷**：任何"一次异常就长期改变运行方式"的机制都必须有恢复路径，
   否则用户只能重装或等人来查；
3. **性能问题也要留痕**：这一次能定位，全靠 `perf-profile.json`、`gpu-crash.json` 与运行日志
   三份落盘证据——没有它们，只能猜"是不是机器不行"。
