## DEF-029：图片分辨率回退成正方形像素档，与视频档位不一致，用户选的比例作用不到成品

- 严重度：P1　缺陷类型：代码（回归）　关联需求：REQ-001 / REQ-007
- 复验版本：0.2.40 → 修复后待发

### 复现步骤

1. 打开内容创作，切「生成草稿(图文)」；
2. 点分辨率胶囊；
3. 观察下拉项，并与「生成草稿(视频)」的分辨率下拉对比。

### 期望结果 vs 实际结果

- 期望（RELEASE_GATE 门槛 10/11/12）：图文档位与视频一致，均为 720p/1080p；成品尺寸随画面比例变化（1080p + 3:4 → 1080x1440，9:16 → 1080x1920），且不出现其它比例的尺寸。
- 实际：图文档位是 `512x512 / 768x768 / 1024x1024 / 1536x1536 / 2048x2048`（全是正方形），视频是 `720p / 1080p`；生成的图片一律写死 `size=1024x1024`，用户选的档位与画面比例都没有作用到成品。

### 根因分析（5-Why）

- 直接原因：`GET ai/draft-generation/pricing` 给图片模型下发的是正方形像素档，且 `generateAiImages` 把请求体写死为 `size: '1024x1024'`。
- 为什么 1：图片档位表 `RATIO_TIERS`（档位 × 画幅 → 成品像素）虽然还在 `server/src/image-ratio.ts`，但没有任何调用方——定价接口没接它。
- 为什么 2：同一份文件里的 `cropImageToSize` / `ratioPromptHint` 同样成了死代码，成品尺寸这条链路整体断在"最后一公里"。
- 为什么 3：`createDraftGeneration` 只读 `resolution`，不读图文请求实际用的 `imageSize`，于是任务记录里 `resolution` 恒为空，媒体生成永远回落 720p。
- 根本原因归类：P-012/P-013 的修复只改到接口与前端，档位表被留在服务端无人调用；没有门禁断言"图片档位 = 视频档位"，回退无人发现。

### 修复方案（改根因）

1. `server/src/image-ratio.ts`：导出 `IMAGE_RATIOS` 与 `imagePricingRows()`，定价行由档位表派生（档位 × 画幅 → 成品像素），档位表成为唯一权威；
2. `server/src/api.ts` 定价接口：图片模型改用 `imagePricingRows()`，不再手写像素档；
3. `server/src/api.ts`：`createDraftGeneration` 的 `resolution` 回退读取 `imageSize`；`generateAiImages` 接受档位/画幅，把"画面比例"写进提示词、首选目标尺寸请求厂商，并在落盘前按档位 + 画幅裁剪缩放；
4. 前端 `ImageSizeSelect`：选项文字保持与视频档位逐字一致（720p/1080p），成品像素按当前比例显示在弹层说明行；
5. `ImageModelPricing` 增 `size`，随定价下发，前端不再自己算尺寸。

### 回归用例

- 服务端功能测试 `server/test/functional/content-params.spec.ts`：图片档位 = 视频档位；每行都有唯一成品像素且等于档位表；未知画幅不编造尺寸；1080p+9:16 的成品正好 1080x1920。
- E2E `qa/e2e/specs/content-params.spec.ts`：真实页面里图文档位与视频档位逐字一致、胶囊不出现像素文本、切 3:4 后只显示 3:4 的尺寸。
- 真实生成实测：`imageSize=1080p, aspectRatio=9:16` → `ai-img-ddcae155.png` 实测 **1080x1920**（generatedBy=ai，模型 agnes-image-2.5-flash），任务记录 `resolution` 从空串变为 `1080p`。

## DEF-030：源图不可解码时裁剪谎报成功，成品指向一个不存在的文件

- 严重度：P1　缺陷类型：代码（诚实性）　关联需求：REQ-001

### 复现步骤

1. 造一个内容为 `not an image` 的文件；
2. 调用 `cropImageToSize(source, target, 1080, 1920)`；
3. 观察返回值与 target 是否存在。

### 期望结果 vs 实际结果

- 期望：解码失败返回空串，调用方保留厂商原图（这正是设计里"失败保留原图"的兜底）。
- 实际：返回 target 路径，但 **target 根本没有生成**——PowerShell 里 `System.Drawing` 抛错后脚本继续往下跑，照样打印 `OK`，Node 侧只看 stdout 就判定成功。

### 根因分析（5-Why）

- 直接原因：成功判定只看 `stdout` 含 `OK`，且 PowerShell 段没有 `ErrorActionPreference='Stop'` 与 try/catch。
- 为什么 1：原实现把多行 PowerShell 用 `;` 拼成一行执行，异常不会中断后续语句。
- 为什么 2：没有断言"成品文件真的存在"，也就没有测试能发现这条假成功路径。
- 根本原因归类：外部进程的成败判定依赖其自报字符串，而不是可验证的产物。

### 修复方案

`cropImageToSize` 整段包进 `try/catch` + `$ErrorActionPreference='Stop'`，`catch` 里 `exit 1`；末尾用 `Test-Path` 复核；Node 侧再校验成品文件存在，两者都成立才返回路径。

### 回归用例

`server/test/functional/content-params.spec.ts`：坏源图必须返回空串（本用例正是发现该缺陷的用例）。

## DEF-031：频道白名单只有小红书/抖音，引擎已落地的快手进不来，闲鱼在产品里完全没有定义

- 严重度：P2　缺陷类型：需求遗漏　关联需求：REQ-003 / REQ-007

### 现象

- 「添加频道 → 连接新频道」只有小红书与抖音两张卡：引擎早已带 `ks_uploader`（快手扫码登录 + 视频/图文发布）却进不了白名单；
- 产品里搜不到"闲鱼"：没有平台枚举、没有图标、目录清单里也没有这一项，用户无从得知路线图。

### 根因分析（5-Why）

- 直接原因：前端 `CHANNEL_PLATFORMS` 是手写白名单，只列了小红书/抖音。
- 为什么 1：白名单与引擎能力清单（`platform-catalog.ts` 自动发现）是两份数据，谁也没校验它们是否一致。
- 为什么 2：闲鱼这类"产品已确定要接、引擎还没带模块"的平台没有第三种状态，只能"要么全有要么全无"。
- 根本原因归类：能力清单与产品白名单缺一致性来源，缺"已列入但未落地"的中间态。

### 修复方案

1. 前端白名单加入 `PlatType.KWAI` 与 `PlatType.Xianyu`（含平台枚举、图标、本地化名、账号描边色）；
2. 服务端目录新增"计划平台"声明：引擎没有 `xianyu_uploader` 模块时以 `coming_soon` 出现，接口如实下发该状态；
3. 界面按状态渲染：coming_soon 置灰、点击提示"闲鱼 暂未开放，敬请期待"，不进授权流程；
4. 内容创作的目标平台只取 `available`，所以闲鱼不会被选成"发不出去"的目标；
5. 服务端两个入口（`startPlatformLogin` / `startPlatformPublish`）先查目录状态再决定要不要拉起引擎：
   计划平台直接如实回"闲鱼 暂未开放，敬请期待"。没有这一步时，因为目录里登记了 engineKey，
   原来的"未支持平台"判断会被绕过，请求被丢给引擎、由引擎回一句"不支持的登录平台: xianyu"——
   用户看不懂，也白拉一次进程。实测：`GET v2/channels/accounts/auth/xianyu` → `{"code":50000,"message":"闲鱼 暂未开放，敬请期待"}`。

### 回归用例

- 服务端功能测试：快手 `available` 且可授权；闲鱼 `coming_soon` 且不宣称可发布。
- E2E `content-params.spec.ts`：连接列表同时出现快手与闲鱼；点闲鱼出"暂未开放"提示；内容创作目标平台含快手、不含闲鱼。
- `qa/acceptance/full-chain-loop.mjs` A5 的可连接平台卡片断言由"正好 2 张"更新为白名单四张（小红书/抖音/快手/闲鱼）——旧断言绑死数量，加平台就会假红。

## DEF-034：模型配置被整份清空（P0）

- 严重度：P0　缺陷类型：数据/设计　关联需求：REQ-005

### 现象

设置 → 自定义大模型 里配好的服务整份消失：`llm-user.json` 变成 `providers: []`、`activeProviderId: ""`、
顶层 `baseUrl/apiKey/model` 全空，只剩 `image*/video*` 字段（因为空 providers 的提交不会动媒体通道）。

### 已查明与未查明

- **已查明（前端无责）**：打开设置页期间只发 `GET ai/user-llm`，不发任何写请求——
  用 `qa/probes/diagnose-settings-writes.mjs` 监听 network 证明，所以不是"打开设置就回写"。
- **已查明（真正的设计缺陷）**：`PUT ai/user-llm` 的两条路径都无条件接受"清空"：
  多服务分支收到 `providers: []` 就照写，旧式单配置分支缺字段就 `writeStoredLlm(null)`（连图片/视频一起抹）。
  也就是说 **任何** 脚本探针、自动化脚本、旧客户端的一次空提交，都能把用户配置整份带走——
  门禁里的 `qa/verify-llm-config.mjs` 正是"先用探针配置替换整份列表、再靠写回文件恢复"的写法。
- **未查明**：18:10 那次写入的确切发起方。当时的日志没有记录 PUT 来源，无法回溯；
  同一工作区还并行跑着别的会话的门禁与探针，存在交叉写入的可能。

### 修复（改设计，不只是补数据）

服务端两条写入路径都加硬护栏：
1. 多服务分支：已有服务时提交空 `providers` 必须带 `allowEmptyProviders: true`，否则报错且**不落盘**；
2. 旧式单配置分支：已有多个服务时，缺字段的提交同样拒绝，除非显式 `clear: true`；
3. 设置页删除最后一个服务时才带 `allowEmptyProviders`（这是用户看得见的显式动作）。

### 数据恢复

配置已按权威来源还原：提供方/地址/模型取自内核投影 `~/.bosom-friend/settings.yaml`，
密钥取自 `~/.dsh/.credentials.yaml` 的 `AGNES_API_KEY`，图片/视频模型取自残留字段并标回用途。
还原脚本留在 `qa/probes/restore-user-llm-config.mjs`（一次性工具，可复用）。

### 回归用例

`server/test/functional/content-params.spec.ts` 两条：静默清空被拒且服务仍在 / 显式确认与显式 clear 放行；
旧式空提交（历史"启动回灌"的形状）同样被拒。

## DEF-033：频道里的快手点了没反应——worker 固定传参与引擎 `*_setup` 的默认值冲突

- 严重度：P1　缺陷类型：代码　关联需求：REQ-003

### 复现步骤

1. 打开「添加频道 → 连接新频道」，点「快手」；
2. 等授权页。

### 期望结果 vs 实际结果

- 期望：进入扫码页，出现可扫的二维码。
- 实际：直接失败（引擎回「cookie 文件不存在或已失效」），扫码流程从未启动。

### 根因分析（5-Why）

- 直接原因：`worker.py` 对**所有**平台固定传同一套登录参数（`qrcode_callback/headless/cdp_url`），从不传 `handle`。
- 为什么 1：插件引擎的登录入口分两族——`*_cookie_gen`（一进来就登录）与 `*_setup`（`handle=False` 时"没 cookie 就直接返回失败"）。快手只导出 `ks_setup`，于是 worker 这条路径必然走"直接返回失败"分支。
- 为什么 2：能力清单（`platform-catalog.ts`）是**扫源码正则**判"有没有登录函数"，能扫出"有 `*_setup`"，但扫不出"调用参数对不对"——所以白名单加进来时看起来一切正常。
- 为什么 3：我上一轮加快手只做了接口层验证（catalog 显示 available、auth=true），**没有真的走一遍"点平台 → 出二维码"**。同一处固定传参还压着第二个雷：alipay/weibo 的 `*_cookie_gen` 没有 `cdp_url` 参数，固定传它会直接 TypeError。
- 根本原因归类：跨进程调用契约靠"调用方记住每个平台的签名"维持，而不是按被调方签名传参。

### 修复方案

`worker.py` 新增 `login_kwargs()`：按 `inspect.signature(func)` 决定传哪些参数——`handle` 一律 True（worker 的语义就是"现在开始登录"），`headless`/`cdp_url` 只在函数真的声明了才给。这样快手这类 `*_setup` 会真的进入登录，alipay/weibo 这类缺 `cdp_url` 的也不会再 TypeError。

### 回归用例

`qa/probes/verify-channel-login-start.mjs`：对每个白名单平台走一遍**真实产品链路**（`v2/channels/accounts/auth/:platform` → `platform-login/qr/:sessionId`），断言真的拿到二维码图。实测：
快手 125x125、视频号 470x470、闲鱼 148x148，三张都是真图，证据落 `qa/evidence/二维码-*.png`。
**这条探针不扫码也能判红**——"点了没反应/参数不对"是产品缺陷，"扫不扫"才是人的动作。

## 产品改动：设置 → 自定义大模型改为收纳列表（同一时刻只展开一个）

- 需求：模型服务列表做成 DSH 设置里那种"列表收纳"版式（收起时一行、点开就地编辑），不再把编辑面板另起一块。
- 实现：`ProviderList` 换成 `<ul>` 收纳卡（行头 = 名称 + 状态徽标 + 接口/当前模型/模型数 + 动作 + chevron，展开区 = `ProviderEditor` 就地渲染）；状态由 `selectedId` 单值驱动（同一时刻只开一个）；默认全部收起，只有"缺密钥"的服务自动展开；切换"设为当前"不再改动正在编辑的那张卡。
- 版式对齐 DSH：展开态用换色 + 描边表示而不是增高动画，chevron 只做 140ms 旋转并受 `prefers-reduced-motion` 保护。
- 回归用例：E2E `content-params.spec.ts`「设置 · 自定义模型收纳列表」——默认 `aria-expanded=false`、点开出现 API Key 输入框、再点第二张时第一张收起、再点收起。
- 证据：`qa/evidence/设置-自定义模型-收纳列表.png`、`qa/evidence/设置-自定义模型-展开编辑.png`。
