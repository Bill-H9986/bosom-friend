# DEF-109 备份轮转按目录名排序删除，外部写入的备份会被当作最旧的一份立即清掉

| 项 | 值 |
| --- | --- |
| 编号 | DEF-109 |
| 发现日期 | 2026-09-19 |
| 发现方式 | 我为一次数据清理手工创建了 `backups/matrix-cleanup-<ISO时间戳>/`，几分钟后该目录消失；核对代码后确认是产品自己的备份轮转删的 |
| 严重级 | P2（不影响正常使用，但会让人「以为有备份」） |
| 状态 | Open |

## 机制（代码事实）

`server/src/security.ts` 的备份轮转：把 `<root>/backups/` 下的目录**按名字排序**，超过性能档位上限（标准档 30 份 / 低配档 10 份，见 `perf.ts` 的 `backupKeep`）就从**排序最前**的开始删（`rmSync(..., { recursive: true, force: true })`）。

产品自己生成的快照目录名是纯数字时间戳（`security.ts`：`<时间戳>/`），按名排序等于按时间排序，所以对它自己的快照是正确的。

## 问题

排序是**字符串排序**，任何命名不以数字开头的备份目录都会排到 `0-9` 之前，也就是被当成「最旧的一份」优先删除：

- 我写的 `matrix-cleanup-2026-09-19T03-42-06-881Z` 以字母开头 → 排在最前 → 下一次轮转时第一个被删；
- 同理，用户手工放进 `backups/` 的任何备份（`my-backup/`、`手工备份-2026/`）都会被优先清掉；
- 已存在的一类名字也受影响：`pre-delete-account-<时间戳>` 同样以字母开头，只是因为数量还没到上限才还在（实测现场残留 12 个，最新的是 9/16）。

## 影响

「把备份放进产品的 backups 目录更安全」这个直觉是错的：放进去反而比留在原地更容易被删。用户以为有备份，实际没有。

## 建议（未实施）

1. 轮转改为**按目录的 mtime 或目录内的快照时间字段排序**，而不是按名字；
2. 或者只轮转自己生成的命名格式（数字时间戳），遇到无法识别的目录名**保留并提示**，而不是当作最旧的一份删除；
3. 删除前把被删目录名记进运行日志，让「备份消失」可追溯。

来源：2026-09-19 实测（手工备份目录消失、`security.ts` 的排序+删除实现、`perf.ts` 的 backupKeep 上限、现场残留的 12 个 `pre-delete-account-*` 目录）。
