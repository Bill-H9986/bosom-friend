# DEF-116 内容创作选 21:9 的 30/60 秒档：片段是 21:9，拼出来的成片却是 9:16

| 项 | 值 |
| --- | --- |
| 编号 | DEF-116 |
| 发现日期 | 2026-09-19（逐档真跑矩阵跑到 21:9 时暴露） |
| 发现方式 | 12 个真厂商组合矩阵：读成片真实像素（ffmpeg）与所选画幅对不上 |
| 严重级 | P2（用户选了 21:9，拿到的是竖屏 9:16 的片子；画幅是「参数生效」最直观的一条） |
| 状态 | **Fixed**（拼装画布补上视频独有的 21:9 尺寸；单元级与真 ffmpeg 拼接双回归） |

## 现象（实测证据）

一条 720p / **21:9** / 30 秒的生成请求（记录 `gen-78fd37bc`，`status=success`）：

| 层 | 实测 | 证据 |
| --- | --- | --- |
| 厂商出的每一段片段 | **1470x630（21:9）** —— 七段全对 | `ai-vid-5a442201.mp4` / `ai-vid-ccd0f4d5.mp4` / `ai-vid-32f38755.mp4` 等 ffprobe |
| 拼出来的整条成片 | **720x1280（9:16）**，30.02 秒 | `ai-vid-fe87dc47.mp4` ffprobe |
| 记录里写的画幅 | 21:9 | `draft-generations.json` 的 `request.aspectRatio` |

对照组：同一晚同一路径跑出来的 4:3（960x720）、3:4（720x960）、1:1（720x720）、16:9（1280x720）**全部正确**，
只有 21:9 这一档被压成竖屏——所以不是「拼接整体有问题」，是这一档的尺寸没被认识。

## 根因

`video-compose.ts` 的目标画布取自**图片**的档位表：

```ts
// 修复前
function canvasFor(options) {
  const size = pixelFor(options.resolution ?? '720p', options.aspectRatio ?? '9:16')
    || pixelFor('720p', '9:16')   // ← 未知画幅就回退竖屏
}
```

而 `pixelFor` 查的是 `image-ratio.ts` 的 `RATIO_TIERS`，它的画幅来自 `IMAGE_RATIOS`——
**只有 1:1 / 4:3 / 3:4 / 9:16 / 16:9 五种**（图片模型官方不支持 21:9，那张表里当然没有）。
视频模型支持 21:9（`AGNES_VIDEO_RATIOS` 六档），于是：

```
pixelFor('720p', '21:9')  →  ''  →  回退 pixelFor('720p', '9:16') = '720x1280'
```

拼接滤镜是「等比缩放 + 居中补边」（`canvasFilter`），所以七段 1470x630 被完整地塞进 720x1280 的画布：
画面上下补黑边、成片画幅变成竖屏。

为什么直到今天才暴露：>12 秒的拼装档位此前被 DEF-107（媒体硬预算 15 分钟）钉死，逐档矩阵把它们标成
「结构性跳过」；而且 21:9 的**单片**档位（4~12 秒）不走拼装，厂商直接出 1470x630，历史上一直是绿的。
DEF-107 修好后逐档真跑，这一档才第一次真正走到拼接步骤。

## 修法（已实施）

```ts
/** 视频独有的画幅尺寸（图片档位表里没有的那几档）。 */
const VIDEO_ONLY_SIZES = {
  '720p': { '21:9': '1470x630' },   // 厂商在 720p 下 21:9 的真实出片尺寸
  '1080p': { '21:9': '2205x945' },  // 同比例放大，仍是精确的 21:9
}
const size = VIDEO_ONLY_SIZES[tier]?.[ratio] ?? (pixelFor(tier, ratio) || pixelFor('720p', '9:16'))
```

只补视频独有的那一档，图片表已有的五种继续走 `pixelFor`，两张表不会分叉；
真未知的组合（例如 7:3）仍回退产品默认口径，不编造尺寸。
