# DEF-119 设置页「系统与升级」里的更新控件是死的（接线属于旧工程）

| 项 | 值 |
| --- | --- |
| 编号 | DEF-119 |
| 发现日期 | 2026-09-20 |
| 发现方式 | 核对 AC-021-4（独立窗口/托盘/更新能力）时逐条查接线 |
| 严重级 | P2（点了没反应，且界面承诺了"检查更新"这个能力） |
| 状态 | Open（未修；修法与口径待定） |

## 现象

设置 →「系统与升级」标签里有：更新服务器地址输入框、「检查更新」按钮、以及"发现新版本 / 最新版本 / 灰度放量"等提示分支。
在**装机版**里点它们不会有任何结果——这些控件调到的主进程通道不存在。

## 根因（逐条取证）

| 前端调用（`OtaTelemetryTab.tsx`） | 装机版里的实际情况 |
| --- | --- |
| `window.ipcRenderer.invoke('zhiyin:update:check')`（L109） | `desktop/electron/main.cjs` 没有任何 `zhiyin:` 前缀的 `ipcMain` 处理器；`preload.cjs` 也没暴露 `ipcRenderer` 本体 |
| `window.ipcRenderer.getStoreValue('zhiyin-update-url')` / `setStoreValue`（L77、L95） | 同上：既没有 `getStoreValue/setStoreValue` 的暴露，也没有对应处理器 |
| `window.ipcRenderer.on('update-downloaded' / 'update-error')`（L151-152） | 没有发送方 |
| 全局搜索 `autoUpdater` / `electron-updater` / `feedURL` | **0 处**——静默升级从来就没接线 |

打包产物核对（`app.asar` 全文字符串检索）：`zhiyin:update:check` = **0** 次、`setStoreValue` = **0** 次、
`zhiyin-update-url` = **0** 次。也就是说这些字段名只存在于前端 bundle 里的那段调用代码，
主进程与 preload 两个层面都没有承接。

## 结论与建议（未实施）

产品的"更新"能力当期口径应是：**通知用户有新版本 + 给出下载入口**，不做静默升级。
按这个口径，界面上不该出现"更新服务器地址"这种需要后端通道的控件。建议二选一：

1. **接线（真做）**：主进程加一个最小更新检查（拉一个版本清单 JSON，比对 `__APP_VERSION__`，
   有新版本就从主进程 `shell.openExternal` 打开下载页），并把设置页那三个控件接到它上面；
2. **如实收敛（先做）**：去掉更新服务器地址与"检查更新"按钮，改成一句人话的"当前版本 + 新版本发布在 GitHub 下载页"，
   把"静默升级"登记为明确不做的能力（见 RTM 的 AC-021-7）。

无论选哪种，都要把这条的判据写进用例：**界面上出现的每个控件，点到都必须有一个用户看得见的结果。**
