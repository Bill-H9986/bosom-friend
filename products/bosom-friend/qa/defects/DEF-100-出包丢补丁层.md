# DEF-100：出包丢补丁层——运行时副本里根本没有 cordis.patch.yml，而同步步骤用补丁判断"要不要同步"

> 编号：DEF-100（唯一、终身不变）
> 状态：Fixed
> 严重度：P1　　优先级：高（出包的运行时不加载产品补丁层 = 装出来的应用不是这个产品）
> 缺陷类型：打包/完整性
> 关联需求：REQ-021（桌面形态与打包闭环）
> 报告人 / 日期 / 环境版本：本轮打包实测 / 2026-09-17 / 0.2.54
> 责任人 / 计划版本：Jay / 0.13.10
> 重开次数：0

## 复现步骤

1. 跑 `desktop/rebuild-kernel-and-installer.ps1`；
2. 第 2 步直接抛错：`the kernel runtime holds no desktop-bundle copy; deploy the kernel bundle first`；
3. 手工执行第 3 步的漂移核对，红在：
   `@deepseek-ai/dsh-bosom-friend-desktop-bundle 运行时缺 cordis.patch.yml`（两条：软链 + .pnpm 实副本）。

## 期望结果 vs 实际结果

- 期望：`dist/kernel-runtime-unpacked` 里那份桌面 bundle 带着工作区当前的 `cordis.patch.yml`，
  第 3 步字节与版本都一致、PASS，第 5 步把它打进 `kernel-runtime.zip`，装出来的应用才会加载产品补丁层。
- 实际：那份副本**只有 package.json**，没有补丁文件；而同步步骤是"发现已有补丁才去刷新它"，
  于是整段**静默空转**（一行输出都没有），紧接着第 3 步判红。

## 根因分析（两层）

- **A：副本里的补丁文件不见了。** 运行时是更早一次 `pnpm deploy` 的产物，注入副本不随非 lib 文件刷新
  （DEF-060 的老账）。而上一轮我把这个步骤写成"先删目标、再复制"，第一次跑时复制那一步
  因 `Copy-Item` 遇到 `.pnpm` 路径里的 `+` 抛 `Illegal characters in path` —— **文件已删、新文件没来**，
  于是副本里的补丁被这次失败的复制清掉了。当时只修了复制调用（换 `[System.IO.File]::Copy`），没有重跑，
   这个"文件已被删除"的残缺状态就一直留在构建产物里。
- **B：候选判据用了"补丁在不在"。** `if (Test-Path (Join-Path $pkgDir 'cordis.patch.yml'))` ——
  恰恰在补丁缺失时（也就是最需要同步的时候）判出"没有候选"，把"缺失"变成了"无事可做"。
- 为什么没早发现：这个断言的失败信息指向"deploy 物化"，看起来像环境问题；而它实际是本步骤自己造成的。
- 根本原因归类：**"先删后写"没有把目标文件的最终存在性当成前置条件**，加上**用要修的东西判断要不要修**。

## 修复方案

1. 候选判据改为 `<pkgDir>/package.json` 存在即可（包在就行，补丁缺了才更要同步）；
2. 复制后立刻校验目标存在，缺了就抛错——不允许再出现"同步步骤静默什么都没做"；
3. 复制改用 `[System.IO.File]::Copy`（绝对路径，绕开 `Copy-Item` 对 `+` 的 provider 解析）并覆盖写入，
   于是这一步从"刷新已有文件"变成"**保证文件等于工作区**"（创建 + 覆盖都管）。

## 回归用例

无自动化用例（打包脚本）。验收方式：清掉副本里的补丁文件后重跑流水线，第 2 步必须打印
`synced desktop-bundle/cordis.patch.yml (...)`，第 3 步必须 `RUNTIME_CONFIG_DRIFT PASS`。

## 关闭条件

- 第 2 步打出补丁同步行；第 3 步 PASS；第 5 步重打的 zip 里该文件与工作区逐字节一致（本轮已实测）。
