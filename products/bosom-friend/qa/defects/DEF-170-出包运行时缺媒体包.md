# DEF-170 出包运行时缺媒体包：部署树是旧一次 pnpm deploy 的产物，核对脚本又放行了它

| 项 | 值 |
| --- | --- |
| 编号 | DEF-170 |
| 发现日期 | 2026-09-23 |
| 发现方式 | DEF-169 的**打包态复核**：在打包树里按名字找 `dsh-media`，一个都没有 |
| 严重级 | P0（装出来的包在用户机器上打不开：产品服务端 `import '@deepseek-ai/dsh-media'`，而运行时里没有这个包） |
| 状态 | Fixed（2026-09-23：重新 `pnpm deploy` 物化运行时 + 修核对脚本 + 重打安装包） |

## 现象（实测证据）

| 事实 | 值 | 证据 |
| --- | --- | --- |
| 部署树里的包数 | **132**，其中 `media-ish = 0` | `desktop/dist/kernel-runtime-unpacked/node_modules/@deepseek-ai` |
| 同一次 deploy 的清单 | 部署树 `package.json` 只声明 4 个依赖（工作区是 5 个） | 缺的正是 `@deepseek-ai/dsh-media` |
| 部署树 lockfile | 不含 `dsh-media`（工作区 lockfile 有 32 处） | 两侧 `pnpm-lock.yaml` |
| 出包核对的结论 | `runtime dependencies OK (1 deps × 1 server copies)` —— **假绿** | `verify-runtime-deps.mjs` 修前输出 |
| 部署树里的服务端 | `lib/types/media-gateway.js` 里有 `import '@deepseek-ai/dsh-media'` | 反查导入点 |
| 装出来的包 | 0.2.60 安装包（16:46 重打那份同样带着旧运行时） | `desktop/release/0.2.60/BosomFriend-Setup-0.2.60.exe` |

在开发机上这一切**看起来正常**：仓库就在上面几层，Node 从运行时里往上找，能在工作区找到那个包。
装到用户机器上没有仓库，`ERR_MODULE_NOT_FOUND` → 内核加载失败 → 产品页起不来。

## 根因

**两层，缺一层都不会漏到这个程度。**

1. **运行时是"上一次 `pnpm deploy` 的产物"**：`rebuild-kernel-and-installer.ps1` 第 2 步只把**代码**（`lib/`）同步进现有副本，
   依赖不跟着走。给 `server/package.json` 加一个依赖（这一轮加的 `@deepseek-ai/dsh-media`）不会让运行时重新物化——
   必须手动跑 `pnpm --filter …-kernel-bundle deploy --prod <运行时目录>`（`结构说明.md` 里写着，但出包链不问"跑了没有"）。
2. **核对脚本看不见这件事**（`verify-runtime-deps.mjs`）：它按"只核对第三方依赖"的规则**跳过所有 `@deepseek-ai/*`**，
   于是从工作区清单里读到的期望集里根本没有 `dsh-media`；而它的解析器又会**一路向上走出运行时根**，
   在仓库里找到同名包——两次都让"缺包"表现成"通过"。

## 为什么值得记

1. 这类缺陷**只在用户机器上现形**：开发机、单测、门禁全绿（服务端类型检查、功能测试都在源码面上跑）；
2. "部署树"与"工作区"是两棵不同的树，**共享文件名的解析会互相掩盖**——核对必须问"解析结果落在哪棵树里"；
3. 出包链的第 4 步本来就是干这个的（"依赖核对 + 配置漂移检查"），是**规则的盲区**（跳过工作区包）而不是缺步骤。

## 修复（2026-09-23）

1. **重新物化运行时**：`pnpm deploy` 到空目录再换入（`ERR_PNPM_DEPLOY_DIR_NOT_EMPTY`：deploy 不接受非空目标，
   `结构说明.md` 的那条命令要先清空/换入）——物化后 `@deepseek-ai` 132 → **134**，`dsh-media` 与 `dsh-media-pi-ai` 都在。
2. **核对脚本改成两个判据**（`desktop/verify-runtime-deps.mjs`）：
   ① 期望集 = 服务端 `dependencies` 的**全部**（工作区包一起核对）；
   ② 解析结果必须**落在运行时根内**（跑到仓库里的算缺失）。
3. **出安装包**：重跑 `rebuild-kernel-and-installer.ps1`（第 4 步现在会在换 zip 之前把这类缺失拦下）。
4. **顺带修掉一个"重新部署后必然卡住"的坑**（同一轮实测）：`pnpm deploy` 把工作区的 `cordis.patch.yml` 以**硬链接**物化进运行时，
   而重建脚本第 2 步的**两处**同步（`dsh-bosom-friend-desktop-bundle` 与 `dsh-bosom-friend-kernel` 各自那份 patch）
   都用 `[System.IO.File]::Copy` 把源文件复制到它自己的硬链接上——Windows 直接回 "being used by another process"，
   重建在第 2 步中止（换目录名、重试都无效：源与目标是同一个 inode；只有"重新 deploy 之前"的旧树才碰不到这一脚）。
   两处现在都先判"目标是不是源自己的硬链接"：是就跳过（内容必然一致，后面还有内容比对兜底），不是才删掉再复制。

## 负向对照（实测）

| 树 | 修前的脚本 | 修后的脚本 |
| --- | --- | --- |
| 旧运行时（缺 `dsh-media`） | `runtime dependencies OK (1 deps …)` 退出 0（**假绿**） | 退出 1：`- @deepseek-ai/dsh-media is not resolvable from …\dsh-bosom-friend-server` |
| 重新物化后 | — | `runtime dependencies OK (5 deps × 1 server copies = 5 resolutions)` 退出 0 |

## 装机闭环（2026-09-23 已做）

1. 重打后静默安装：`qa/probes/verify-installed-package.ps1 -Install` → **INSTALLED_PACKAGE PASS checks=13 fail=0**
   （安装包 744.2 MB / SHA256 已记 / 装机端解压 23376 个文件）。
2. 启动装出来的应用：`http://127.0.0.1:31280/bosom-friend/` 10 秒内 **HTTP 200**，API（`long-videos/producers`）也是 200。
   这一条同时证明了两件事：① 运行时里确实带着 `@deepseek-ai/dsh-media`（产品服务端在**模块加载期**就 import 它，
   缺了它连页面都起不来）；② 媒体能力面的插件真的**激活**了——桌面运行时的启动契约是"每个条目都必须激活"，
   少挂一半会直接启动失败（工作日志 2026-09-23 §5 踩过）。
