# DEF-076：失败只报「厂商未返回可用成片」，看不出是限流还是参数错

> 编号：DEF-076（唯一、终身不变）
> 状态：Fixed
> 严重度：P2　　优先级：中（不丢数据，但让用户无法判断该等还是该改）
> 缺陷类型：诚实性/交互
> 关联需求：REQ-022（长视频创作）
> 报告人 / 日期 / 环境版本：2026-09-16 真实全流程测试中连续撞 429 时发现 / 0.2.52
> 责任人 / 计划版本：Jay / 0.2.53
> 重开次数：0

## 复现步骤

1. 起一条长视频任务，让厂商侧返回限流（实测 429）或参数拒绝（实测 400）；
2. 看任务面板与那一镜的错误文案。

## 期望结果 vs 实际结果

- 期望：用户能看出这次失败**该等一会儿再来**还是**该改参数**——两者的动作完全不同。
- 实际：所有失败都收敛成同一句"厂商未返回可用成片"，看不出原因；
  内核日志里其实有确切的 `status=429` / `status=503` / `AbortError`，只是没有传到用户面前。

## 影响范围与发生频率

所有厂商侧失败：限流、服务不可用、参数被拒、密钥失效、超时。
实测在一条 18 镜的片子里连续出现（429 与 503 交替），每次都只给同一句话。

## 根因分析（5-Why）

- 直接原因：`generateAiVideoDirect` 的失败出口统一 `return null`，调用方只看到"没有结果"，
  原因在返回的那一刻就丢了。
- 为什么 1：函数签名把"失败"建模成一个值（`null`），而不是"失败 + 原因"；
  于是所有失败路径只能表达同一件事。
- 为什么 2：限流是可以照着行动的信息（等一会儿），但代码里它只是一个被 `continue` 掉的循环分支。
- 为什么 3：验收只看"失败时任务是不是 failed"，没有断言"失败原因对用户是否可行动"。
- 根本原因归类：**错误信息在类型层面就被抹平了**。

## 修复方案（改根因）

1. 新增 `VideoOutcome = { ok: true, url, model } | { ok: false, reason }`，替换原来的 `… | null`；
2. `videoFailureReason(reason, status)` 把状态码翻成可行动的话：
   429 →"厂商限流，稍后再试"、5xx →"厂商服务暂时不可用，稍后再试"、
   400/422 →"厂商拒绝了这次生成参数"、401/403 →"厂商拒绝了这次调用（密钥或权限）"；
   其余按事实给（超时→"厂商超时没出片（排队过久）"、没有 Key→"还没有配置可用的视频模型"）；
3. 三处长视频生成器的失败出口都改成返回 `video.reason`，逐镜错误文案与任务级文案自然带上原因。

## 回归用例

`long-video.spec.ts` 的续跑用例已经把"厂商 400"这条路径跑通（失败原因进入 `outcome.error` 并落盘）；
原因文案本身是纯函数映射，随 `videoFailureReason` 一起在源码里可读。
