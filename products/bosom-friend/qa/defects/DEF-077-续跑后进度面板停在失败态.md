# DEF-077：点了「从断点继续」，进度面板停在失败态不动（要手动刷新）

> 缺陷类型：交互/诚实性
> 关联需求：REQ-022（长视频创作）
> 报告人 / 日期 / 环境版本：2026-09-16 前端接入续跑后浏览器实测发现 / 0.2.52
> 责任人 / 计划版本：Jay / 0.2.53

## 复现步骤

1. 在失败的长视频任务上点「从断点继续」；
2. 接口回执 200（后端确实开跑了，实测任务在 17 秒后变成 `generating`）；
3. 盯着页面看。

## 期望结果 vs 实际结果

- 期望：点完就进入"生成中"，进度按镜数往上走。
- 实际：页面**一直显示失败态**、进度停在原来的镜数，直到手动刷新页面。
  实测网络日志：`POST …/resume => 200` 之后紧跟的 `GET …/lv-f7730022 => 200` 返回的仍是旧的 `failed`，
  轮询因此判定"到终态了"并停止。

## 影响范围与发生频率

所有"回执先到、状态后变"的异步起任务路径：起任务与续跑。
后端是"立即回执 + `setTimeout` 300ms 后才真的开跑"，所以紧跟的那次读取天然会读到旧状态。

## 根因分析（5-Why）

- 直接原因：`poll` 的第一跳读到旧状态 `failed`，按"到终态就停"的规则停止轮询。
- 为什么 1：轮询没有区分"任务真的停在终态"与"状态还没来得及变"。
- 为什么 2：`poll` 唯一的停止依据是**一次读取的结果**，而这一次读取与写入之间存在 300ms 的窗口。
- 为什么 3：验收只测了"轮询能拿到进度"，没测"回执之后立刻读一次会读到什么"。
- 根本原因归类：**把异步状态变更当成同步的**（读-写之间没有保活窗口）。

## 修复方案（改根因）

1. 新增 `pollHoldUntilRef`（保活截止时间）：起任务与续跑成功后设成"当前 + 3 个轮询间隔"；
2. `poll` 的停止条件改成 `next.status === 'generating' || Date.now() < pollHoldUntilRef.current`——
   窗口内即使读到终态也继续轮询，窗口过后仍按真实状态收尾；
3. 续跑成功时把本地任务状态先置回"生成中"（同时清掉上一次的失败文案），与后端即将写入的状态一致。
