# DEF-137 每轮一个新会话：上下文只能是服务端重发的文本，"上下文功能"名存实亡

| 项 | 值 |
| --- | --- |
| 编号 | DEF-137 |
| 发现日期 | 2026-09-22 |
| 发现方式 | 读会话目录（`~/.bosom-friend/sessions`）发现**每轮一个 `turn-*` 目录** → 对照 DSH 的 Session/Context 能力盘点（ADR-003 §1.1） |
| 严重级 | P1（"整个 APP 围绕 context 运转"的正面缺口：会话不复用，压缩/标题/用量/技能注入全都用不上） |
| 状态 | Fixed（2026-09-22：任务级内核池，一个任务 = 一个会话；跨重启 resume 仍未做） |

## 现象（实测证据）

- 会话目录按**轮**生成：`sessions/<cwd>/turn-<时间戳>-<随机>/`，每条对话几轮就有几个目录，
  进程用完即关（`kernel-client` 的调用方在每轮结束时 `close()`）。
- 于是多轮上下文只能由服务端把历史折成文本重发：`chatTranscript` + `CHAT_CONTEXT_MAX_CHARS = 12000`，
  **每轮重发一次**（长对话的成本与延迟是平方级）。
- 内核里挂着的压缩、标题、用量（实测 `assistant/message.usage`）、以及未来的技能注入，全都因为
  "会话活不过一轮"而用不上。

## 根因

**上下文没有容器。** 产品把 DSH 当"一次性 LLM 调用"用：起进程 → 送一整段文本 → 收正文 → 关进程。
会话（Session）本来是上下文的家（历史、压缩、标题、用量、技能），却每轮都被丢掉。

## 修复（2026-09-22）

1. `kernel-client` 新增 `sessionId` 选项：给了它，同一个 id 的多次 prompt 进**同一个会话**
   （SDK 服务端 `getOrCreateSession` 取回既有会话），调用方只送本轮这一句。
2. `api.ts` 新增**任务级内核池**（`AGENT_KERNEL_LIMIT = 4`，LRU 释放；中断、超限时关掉）：
   - 池里有这条任务 → 续轮，提示词只含本轮；
   - 池里没有 → 冷启动（会话 id = 任务 id + 进程内序号）并**喂一次**历史；
   - 中断 → 关掉会话（模型被掐断后上下文不可信），下一轮重新冷启动。
3. 会话 id 带进程内序号：会话注册表在进程内，持久化日志已存在的同名 id 在新进程里创建会
   以 `session "…" already exists` 整轮失败（前一轮踩过），序号避开这条路。

**未做（如实标注）**：跨重启的 **resume**（进程重启后接着上一次会话继续）——需要 SDK 侧的
会话恢复能力，属 ADR-003 ③ 的后半段。

## 回归判据

| 判据 | 用例 |
| --- | --- |
| 同一任务两轮只建一次内核，第二轮不重发历史 | `server/test/functional/agent-session-reuse.spec.ts` 第 1 条 |
| 换任务换会话 | 同上第 2 条 |
| 中断作废会话，下一轮重新冷启动并喂历史 | 同上第 3 条（用挂起桩让中断落在生成途中） |
