# DEF-078：Windows 上文件元数据延迟，跨实例读到旧值（偶发红的那条存储用例）

> 编号：DEF-078（唯一、终身不变）
> 状态：Fixed
> 严重度：P2　　优先级：中（数据不丢，但会让用户看到旧数据、让测试不可信）
> 缺陷类型：数据/可靠性
> 关联需求：REQ-021（工程化与可追溯）
> 报告人 / 日期 / 环境版本：2026-09-16 全量测试偶发红时定位 / 0.2.52
> 责任人 / 计划版本：Jay / 0.2.53
> 重开次数：0

## 复现步骤

1. 同一数据根上开两套 store（产品里真实存在：server 与内核宿主各一套 `openStore`）；
2. 交替 save/load 同一个 JSON 文件；
3. 实测：**400 次交替读写里 329 次读到旧值**（修复前），单次往返偶发红。

## 期望结果 vs 实际结果

- 期望：任何一次 load 都拿到磁盘上的当前内容（磁盘是唯一事实源）。
- 实际：另一个实例刚写完、本实例 load 到的还是上一次缓存；在 CI 上表现为
  `store-integrity.spec.ts` 的"另一个实例写入后本实例读得到新值"偶发红（本轮 6 次里红 5 次）。

## 影响范围与发生频率

所有"两个实例靠文件交换数据"的路径：server ↔ 内核宿主、以及同进程内的多套 openStore。
写入密集时（连续 rename 覆盖）必现；单次写入通常是好的——所以它极容易被当成"环境抖动"。

## 根因分析（5-Why）

- 直接原因：`JsonFile` 用 `mtimeMs` 作为缓存再校验键，而两次 save 的 mtime 可能**完全相同**。
- 为什么 1：**Windows/NTFS 的元数据刷新有延迟**——实测连续三次 rename 覆盖，
  第二、三次的 `mtimeMs` 一模一样，`size` 也可能停在窗口期的旧值，而文件内容确实已经变了。
  （同一探针在"每次写完立刻读内容"时 300 次全部正确，说明**内容可见、元数据不可见**。）
- 为什么 2：把"元数据"当成了"内容"的代理：只要 mtime 没变就认为磁盘没变。
- 为什么 3：验证只覆盖了单实例（自己写、自己读，永远命中自己的缓存），
  没有"另一个实例写、本实例读"的压力用例。
- 根本原因归类：**用一个不可靠的信号判断"内容是否变了"**。

## 修复方案（改根因）

三级判据，最后按**内容**定案：

1. 进程内写版本号（模块级 `storeWriteVersion`）：任何实例 save 都 +1，
   同进程的其他实例下一次 load 必须重新读盘——这一条把 329 次旧值降到 **0**；
2. 时效窗 `FRESHNESS_MS = 250`：跨进程（内核宿主）改不动本进程的版本号，
   至多每 250ms 真读一次盘，把跨进程窗口兜住（代价约 4 次读/秒/文件）；
3. 读到的字节算 sha256 与缓存摘要比对：内容一致才命中（元数据变了不算变化），
   内容不一致就重新解析。

同时把"保存后记录新指纹"改成"记录新指纹 + 新摘要"。

## 回归用例

`server/test/functional/store-integrity.spec.ts` 新增压力版：
