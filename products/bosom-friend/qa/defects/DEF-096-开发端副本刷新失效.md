# DEF-096：开发端副本刷新失效——新模块加载不到、补丁层改动不生效

> 编号：DEF-096（唯一、终身不变）
> 状态：Fixed
> 严重度：P2　　优先级：高（开发端直接起不来 / 改了配置以为生效其实没生效）
> 缺陷类型：开发环境/流程
> 关联需求：REQ-021（桌面形态与开发闭环）
> 报告人 / 日期 / 环境版本：本轮加"远程访问"时连撞两次 / 2026-09-17 / 0.2.54
> 责任人 / 计划版本：Jay / 0.13.10
> 重开次数：0

## 复现步骤（两条，独立）

1. 新增一个服务端模块（本轮是 `server/src/remote-access.ts`）→ 跑 `dev-web.ps1` → 运行时启动即失败：
   `ERR_MODULE_NOT_FOUND … dsh-bosom-friend-server/lib/types/remote-access.js`；
2. 改补丁层配置（本轮是 `bundle/desktop/cordis.patch.yml` 的监听地址）→ 跑 `dev-web.ps1` →
   启动日志说"本次监听 0.0.0.0"，`Get-NetTCPConnection` 上仍然是 `127.0.0.1`。

## 期望结果 vs 实际结果

- 期望：重建工作区包之后，开发端加载的就是刚构建出来的内容（含新增模块与新配置）。
- 实际：两种偏差各有一条根因，见下。

## 根因分析（5-Why）

- **A：副本刷新整段失效。** `dev-web.ps1` 用 `Copy-Item -Path <src>\* -Destination <copy>\lib -Recurse -Force`
  刷新注入副本。而 pnpm 的注入式安装让副本与工作区包**共享同一批文件（硬链接）**——
  把源文件复制到它自己的硬链接上，Windows 报"文件正被另一个进程使用"，21 个副本**全部**跳过
  （实测每次都是 `0/21 copies refreshed`）。已有文件靠硬链接勉强还是新的，**新增文件永远不会出现在副本里**。
- **B：补丁层根本不在刷新范围内。** 刷新循环只处理 server / kernel 两个包的 `lib/`，
  而桌面 bundle 包的运行内容就是它的 `cordis.patch.yml`——副本里的那份停留在安装那天。
  于是"改了配置却没生效"，而且是**静默**的：日志按新配置打印，socket 按旧配置监听。
- 为什么 1：脚本的注释写着"重新构建会就地刷新内容但不会新增文件"，说明作者知道 A 的现象，
  但把结论定成了"复制一遍就行"，没意识到复制本身会失败。
- 为什么 2：没有任何检查断言"副本里的内容 == 工作区构建产物"。校验缺席，偏差就只能靠人撞。
- 根本原因归类：**开发端的物化步骤没有把"副本 = 构建产物"当成一条要验证的事实**。

## 修复方案（改根因）

1. 刷新改为**先删目标再整份复制**（`Remove-Item -Recurse -Force $destLib` → `Copy-Item -Path $srcLib -Destination $destLib -Recurse`）：
   删掉的只是那些硬链接，工作区源码不受影响；新增模块随整棵树一起过去；
2. 刷新范围补上桌面 bundle 包：`cordis.patch.yml` 一并刷新（与 `lib/` 同一循环、同一"先删后拷"口径）；
3. 补丁里的 `!!js` 表达式改用 `&& / ||` 写法：三元运算符里的 ` : ` 会被 YAML 当成映射，
   补丁层会以 `bad indentation of a mapping entry` 直接拒绝启动（本轮实测踩到）。

## 回归用例

无自动化用例（开发脚本）。验收方式：跑一次 `dev-web.ps1`，三行输出都必须满编——
`dsh-bosom-friend-server: 21/21`、`dsh-bosom-friend-kernel: 9/9`、`dsh-bosom-friend-desktop-bundle: 3/3`，
且新模块能被运行时加载、补丁改动真的作用到监听地址。

## 关闭条件

- 三行满编 + 新增模块可加载 + 监听地址按配置变化（本轮均已实测）。
