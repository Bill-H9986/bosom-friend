## 一、AI 智能体没有上下文

### 现象

问一句、答一句；再追问"标题再短点"，它当成一个全新的问题重新开场。

### 根因（两处，都在"以为传了、其实没传"）

| # | 位置 | 实际发生的事 |
| --- | --- | --- |
| 1 | `api.ts` 的 `POST agent/tasks` | 只把**本轮那一句**送给模型，另外拼了一句"（这是同一话题的继续，请接着上文自然延续）"——**上文一个字都没发出去**。模型看到的就是孤零零的一句话，只能重新开场 |
| 2 | `kernel-client.ts` 的 `prompt()` | 每次都用 `'ai-chat-' + Date.now()` 当内核会话 id。SDK 的 `session/prompt` 是**按 id 复用会话**的（`getOrCreateSession`），每轮换 id 等于每轮新建会话，内核侧也留不住上下文 |
| 3 | `api.ts` 的 `POST ai/chat`（侧栏对话走的另一条路） | 同理：只取 `messages` 里的最后一条用户消息，其余全丢 |

也就是说：**前端一直在把整段对话送上来，服务端只用了最后一句**。

### 修复

1. `kernel-client.ts` 新增 `chatTranscript()`（把整段对话折成 `用户：/助手：` 的对话稿，带 12000 字预算、**从最新往前保**）与
   `chatSessionId()`（用"这段对话的第一条用户消息"当身份——前端没有对话 id，但开头那条在同一段对话里是不变的）；
   `prompt()` 接受 `sessionId` 并真的把它传给 SDK。
2. `agent/tasks`：把任务里已存的 `messages` 折成对话稿一起送进模型，会话 id 用 `task.id`（同一任务的多轮 = 同一会话）。
   双保险：会话 id 让内核留住上下文，对话稿让"内核换进程/会话丢了"也照样有上下文。
3. `ai/chat`：同样用 `chatTranscript` + `chatSessionId`，不再只看最后一条。

## 二、内容创作参数不对

### 现象

用户在参数区选的东西没有全部作用到成品上。

### 根因（三处写死/漏读，加上一处分隔符丢失）

| # | 位置 | 实际发生的事 |
| --- | --- | --- |
| 1 | 生成提示词 | 写死"创作一条 **60 秒内**短视频口播脚本"——用户选 30 秒或 180 秒，稿子照样按 60 秒写 |
| 2 | 生成提示词 | 图文路径写死"创作一篇**小红书**图文笔记：20 字内标题、带 emoji 与分段"——选了抖音/快手/视频号也得到同一篇小红书笔记 |
| 3 | `platforms` 参数 | 生成时**完全没读**，只落进生成记录的 `accountTypes`（发布时用）。模型不知道内容要发到哪，写出来的是"通用文案" |
| 4 | `platforms` 的形状 | 实测盘上存在 `"xhs douyin KWAI wxSph"`（空格分隔的字符串）这种记录。只认数组的读取方式会把这种记录的平台**整条丢掉**——生成没平台、发布也拿不到 `accountTypes` |
| 5 | 发布动作卡的平台 | `promptText.includes('抖音') ? 'douyin' : 'xhs'`：说"发布到快手"也得到一张指向小红书的卡片，点下去就到错的平台 |

### 实地证据

本机一条真实生成记录（`gen-acb93014`，2026-09-21 03:19）：`request.platforms = "xhs douyin KWAI wxSph"`（五个平台），
而产出的正文是**地道的小红书笔记**（"姐妹们…📝✨💡#科技数码博主"）——平台参数确实没作用到内容上。

### 修复

1. 提示词里的时长改为**用户选的档位**（`约 N 秒`），体裁不再写死小红书；
2. 新增 `buildPlatformBlock()`：把选中的平台写进提示词，并给出"按各平台习惯写、不要站外导流话术、话题数量按平台"的要求；
3. 新增 `readPlatformList()`：**数组与空格/逗号/顿号分隔的字符串都认**，生成与落草稿两条路径都用它；
4. 新增 `detectPublishPlatform()`：发布动作卡的平台来自用户那句话里的平台名（抖音/小红书/快手/视频号/公众号/B 站），认不出来才回落小红书；
5. `buildLongVideoScript()` 的标题与话题标签不再写死"抖音"，改用选中的平台。

## 回归判据

| 判据 | 用例 |
| --- | --- |
| 对话稿带上前面几轮、超长从头截断且**保留最后一条** | `kernel-context.spec.ts` |
| 会话 id 同一段对话稳定、换一段就变 | 同上 |
| 空格分隔的老记录读得出来 | `platform-prompt.spec.ts` |
| 发布卡平台来自用户那句话，认不出才回落 | 同上 |
| 平台块写进提示词且禁掉站外导流话术 | 同上 |

## 为什么值得记

1. **"我传了"与"它收到了"是两件事**：前端一直在送整段对话，服务端只取最后一条——
   这种缺陷在类型上完全看不出来（`messages` 的类型是对的，代码也真的读了它）；
2. **写死的字面量是参数失效的常见形态**：提示词里一个"60 秒"、一个"小红书"，
   就让参数区整片失去意义。提示词里的每个数字与名词都该能追溯到用户的选择；
3. **容忍旧的坏数据**：盘上已经存在空格分隔的平台串。修完写入端还不够，
   读取端要同时认两种形状，否则老记录永远修不好。
