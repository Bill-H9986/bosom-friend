# DEF-107 30 秒 / 1 分钟档位被产品自己的 15 分钟媒体超时判死（片子其实已经出来了）

| 项 | 值 |
| --- | --- |
| 编号 | DEF-107 |
| 发现日期 | 2026-09-18 |
| 发现方式 | 逐档出片矩阵跑「视频 720p / 9:16 / 30 秒」时，生成记录报媒体超时；查运行日志发现拼接其实成功了 |
| 严重级 | P1（档位超出自身预算导致状态误判与文案误导） |
| 状态 | **已修复（0.2.58）**，真实慢厂商复现已通过 |
| 修复版本 | 0.2.58 |

## 现象（实测证据）

选 30 秒档位生成视频，生成记录报：

```
status=partial
errorMessage=媒体生成超时：超过 15 分钟没有结果（厂商无响应或下载卡住）。文字/脚本已保留，可直接使用或稍后重新生成媒体。
```

而同一时刻的运行日志与磁盘上是**成功**的：

```
[AI_VID_CLIP] 7/7 seconds=6                                      22:41:09
[AI_VID_COMPOSE] id=ai-vid-c3ae2ea6.mp4 clips=7 target=30 actual=30.02 adjust=trim   22:48:45
```

成片文件 ai-vid-c3ae2ea6.mp4 在盘上：**30.02 秒 / 720x1280 / 8.1MB**，规格完全正确。
生成记录里 videoUrl 也写着它，但状态是 partial、错误文案是「超时」。

前端在 partial 状态下仍会用 response.videoUrl 渲染生成卡片，所以**用户能拿到这条成片**。真正的危害收敛为两条：
① 状态被误判成部分成功/超时，把一次成功记成失败；② 提示文案说超过 15 分钟没有结果，而事实是结果已经有了。
对逐档矩阵的影响：这些档位的记录状态不是 success，矩阵按状态判定即记 FAIL。

## 根因

server/src/generation-watchdog.ts：

```ts
const MEDIA_BUDGET_MS = { 'image-text': 8 * 60_000, video: 15 * 60_000 } as const
```

server/src/api.ts 用它做 Promise.race 的**绝对截止时间**：到点就把记录判成 partial / failed 并写超时文案，
**不管媒体步骤其实还在跑**。媒体步骤不会因此停下（实测：判死之后它继续跑完，并把成片写进了 uploads），但结果被丢弃。

## 为什么这是结构性的，不是偶发

同一版产品在界面上给这两档的**诚实耗时预估**是：

| 档位 | 界面标注耗时 | 旧硬预算 | 实测 |
| --- | --- | --- | --- |
| 30 秒 | 约 5~30 分钟（7 片 × 4 秒） | 15 分钟 | 16.5 分钟完成，**必被误杀** |
| 1 分钟 | 约 9~63 分钟（15 片 × 4 秒） | 15 分钟 | 预估下限已远超预算，**必被误杀** |

这两个档位从设计上就超出 15 分钟预算，不是厂商慢导致的偶发，而是产品自己承诺了做不到的时限。
短档位（4~12 秒）不受影响：单片几十秒到 2 分钟，远在预算内。

## 修复方案（0.2.58 已实施）

预算改成**按档位推导**，并保留部署上限：

1. `video-duration.ts` 新增 `clipLatencyCeilingMs(clips)` 与 `videoMediaLatencyBudgetMs(seconds)`：
   预算 = 片段数 × 单片实测耗时上限（250 秒）+ 拼接固定开销（5 分钟）。
   片段数取产品已有的 `planClipSeconds`，与真正下单的规划**同一份事实源**。
2. `generation-watchdog.ts` 的 `mediaBudgetMs(kind, { duration, maxMs })`：
   无档位时保持旧的 15 分钟（行为不变）；有档位时取推导值与下限（15 分钟）中的较大者，
   再被部署上限收紧——上限默认 4 小时，可用 `BF_MEDIA_BUDGET_MAX_MS` 压低（配 0 或非法值按没配处理）。
3. 停滞预算同步按档位放大（`generationBudgetMs(kind, duration)` = 媒体预算 + 20 分钟），
   否则心跳停了之后媒体还在正常拼接时会被看门狗提前判失败。
4. 超时文案里的分钟数跟着真实预算走，不再固定写「15 分钟」。

30 秒档 34 分钟、1 分钟档 68 分钟、5 分钟档取默认上限 4 小时。

## 回归用例

| 用例 | 命令 | 结果 |
| --- | --- | --- |
| 预算数学与边界 | `cd products/bosom-friend/server && npx vitest run test/media-budget.spec.ts` | 10 passed |
| 看门狗行为门禁 | `node products/bosom-friend/qa/verify-generation-watchdog.mjs` | 38 checks，全 PASS |
| **真实慢厂商复现（30 秒档）** | `node products/bosom-friend/qa/probes/verify-composed-gears.mjs` | 见下（假厂商每片延迟 150 秒，整条耗时超过旧的 15 分钟预算） |
| **真实慢厂商复现（1 分钟档）** | 同上（`BF_PROBE_TARGET_SECONDS=60`，每片 70 秒） | 见下 |

复现口径：旧预算 15 分钟是**定值**，所以只要让整条拼装真实耗时超过 15 分钟，旧代码必然判死、新代码必然等到成片。
探针把假厂商每次下单的响应延迟做成注入点（`BF_PROBE_VENDOR_DELAY_MS`），并按真实厂商的慢档取值。
