# DEF-062：批量删除确认框显示的是英文键名（task.batchDeleteConfirmTitle / common.cancel / common.delete）

> 关联需求：REQ-007（内容创作与任务记录）
> 报告人 / 日期 / 环境版本：用户截图 / 2026-09-16 / 0.2.51
> 责任人 / 计划版本：Jay / 待定

## 复现步骤（别人照着做必须能复现）

1. 打开「我的任务」（`#/tasks-history`）或 AI 社媒的「任务预览」，让列表里有至少一条任务；
2. 点「批量管理」，勾选任意一条，点「删除选中」；
3. 确认框里标题、说明与两个按钮显示为 `task.batchDeleteConfirmTitle` / `task.batchDeleteConfirmDesc` / `common.cancel` / `common.delete`。

## 期望结果 vs 实际结果

- 期望：中文界面下显示「批量删除任务 / 确定删除选中的 N 条任务记录吗？此操作不可恢复。/ 取消 / 删除」。
- 实际：四处全部漏出英文键名（见 `qa/evidence/lv-fix-2026-09-16/` 同批截图对应缺陷）。

## 影响范围与发生频率

`TaskHistoryList` 的两个使用方（任务记录页、AI 社媒任务预览）**每次**批量删除都命中；单条删除不受影响（走的是 `TaskCard` 里已有的键）。

## 根因分析（5-Why，没写完禁止修复）

- 直接原因：`t('task.batchDeleteConfirmTitle')` 等键在 `chat` 命名空间里**根本不存在**，i18next 找不到时返回键名本身，于是键名被当成文案渲染出来。
- 为什么 1：代码写的 `|| '批量删除任务'` 兜底永远不执行——i18next 缺键返回的是**键名字符串**（不是空串），JS 的 `||` 判不出来。
- 为什么 2：`common.cancel` / `common.delete` 写法本身也错：组件用的命名空间是 `chat`，`common.*` 只能通过 `fallbackNS` 解析成 `common` 命名空间下的 `cancel`/`delete`，写成带前缀的键会去找 `chat.common.cancel`，两级都落空。
- 为什么 3：这些键从来没被加进语言文件——新增批量删除功能时，界面文案是**新增**的，语言文件没有跟着改。
- 根本原因归类：**缺一条"代码里用到的翻译键必须真的存在"的门禁**。构建能过、类型能过（键名被 `as any` 抹掉）、单测不覆盖渲染，于是四处在用户面前同时漏出来而无人发现。

## 修复方案（改根因，不是压表现）

1. 补键：`zh-CN/chat.json` 与 `en/chat.json` 的 `task` 下新增 `selectRequired / batchDeleteConfirmTitle / batchDeleteConfirmDesc / batchDeleteSuccess / batchManage / batchExit / selectAll / deselectAll / selectedCount / deleteSelected`；
2. 去掉"兜底字符串 + `as any`"：缺失就该在开发期暴露，而不是生产期漏英文；确认框按钮改用 `t('actions.delete')` / `t('actions.cancel')`（`common` 命名空间里确实存在的键，经 `fallbackNS` 解析）；
3. 顺手把同文件里硬编码的中文（全选/已选 N/M/删除选中/退出批量管理/批量管理）一并搬进语言文件，同一处不再两套写法。

## 回归用例（必须写，验证修复且不破坏旧功能）

- 渲染级：`confirm()` 收到的 `title/content/okText/cancelText` 必须都是中文文案而不是键名（本组件暂无客户端单测，由本轮浏览器实测截图 + 语言文件键存在性共同覆盖）；
- 键存在性：新增键在 `zh-CN/chat.json` 与 `en/chat.json` 中同时存在且同名（本轮用 JSON 解析逐键核对）。
