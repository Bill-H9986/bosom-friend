# Bosom Friend 交付测试规则 v1.0

> 给谁看：项目主人 + 所有参与交付的人。
> 管什么：**要不要测、谁测、按什么顺序测、什么算通过、通过要留下什么、不通过怎么办**。
> 不管什么：具体有哪些功能要测（看清单）、某条功能怎样算做完（看 DoD）。分工见第 0 节。

## 1. 交付测试是什么

交付测试 = 从「开发说做完了」到「用户在真机上能正常用」之间的**全部**测试。
它产出的不是一份漂亮报告，而是两样东西：**能不能交付的判定** + **支撑这个判定的证据**。

三种交付形态，顺序不可颠倒，每一层都用上一层通过的那**同一个安装包**：

| 形态 | 从谁到谁 | 在哪测 | 判据 |
| --- | --- | --- | --- |
| 内部交付 | 开发 → 测试 | 开发机 | DoD 6 条 + 功能全量清单 |
| 出厂交付 | 测试 → 出包 | **干净机 + 安装包** | 出厂验收 12 步 |
| 客户交付 | 产品 → 客户 / 上架 | 客户机 + 真实账号 | 真人剧本 + 准出 R1~R9 |

## 2. 七条铁律（违反任一条，这一轮测试作废）

1. **只认成品**：交付结论必须来自安装后的成品。开发服务（31280）跑出来的只能算开发自测，不算交付证据。
2. **只认页面**：用户在界面上看得见才算过。接口返回 200、日志正常、数据文件里有记录，都不算。
3. **证据先行**：每条「通过」必须附一张截图或一条可复跑的命令。没有证据 = 没测。
4. **失败如实**：不许把「接口正常」写成「功能通过」，不许美化报告，失败的轮次必须留失败记录。
5. **角色分离**：谁开发，谁不能签收；谁修缺陷，谁不能判缺陷关闭。
6. **一次一变量**：每轮只改一处；改完必须全量回归，不许「顺手改」。
7. **不可逆动作先批**：真实发布、真实同步、删数据，先说清对象与影响范围并获批准，并留存操作前后截图。

## 3. 角色（谁做、谁不能做什么）

| 角色 | 做 | 明令禁止 |
| --- | --- | --- |
| 开发 | 单元测试、自测、修缺陷 | 给自己的功能签收；改测试结论 |
| 测试 | 全量回归、S 级监考、证据归档 | 绕过前端直接调接口来「证明功能可用」 |
| 出包 | 出安装包、算 SHA256、留产物台账 | 门禁未达标就出包 |
| 项目主人（你） | 真人盲测、UAT、最终签字 | —— |
| AI 助手 | 执行、记录、如实汇报 | 自评通过；把没跑说成跑了 |

## 4. 交付流水线（六段，顺序不可跳）

| 段 | 什么时候 | 在哪测 | 谁做 | 通过判据 | 产物 |
| --- | --- | --- | --- | --- | --- |
| D0 冒烟 | 每次改完 | 开发机 | 开发 | 门禁零红 | `reports/gate-*.md` |
| D1 功能全量 | 出包前 | 开发机 | 测试 | 功能全量清单 A~L 全过 | 逐步截图 |
| D2 专业验收 | 出包前 | 开发机 | 测试 | E2E + S 级监考全绿 | 监考报告 |
| D3 出厂验收 | 出包后 | **干净机** | 出包 + 测试 | 出厂验收 12 步全过 | `evidence/release/<版本>/` |
| D4 交付验收 UAT | 交付前 | 客户机 + 真账号 | 项目主人 | 真人剧本 + 真实发布链路 | 验收报告 |
| D5 上线观察 | 交付后 7 天 | 生产 | 产品 | 无 P0；P1 在 24 小时内修 | 观察记录 |

**换包即重来**：D3 必须用 D2 通过的那个包，D4 必须用 D3 通过的那个包。中间任何一次重新出包，全部从头再来。

## 5. 关键两段怎么做

### D3 出厂验收（最容易漏，也最要命）

1. **干净机定义**：没装过本产品、没装 Node/pnpm 的 Windows（虚拟机或新建系统账户）。
2. 只用安装包，**不许用源码目录、不许用开发脚本启动**。
3. 从双击安装包开始，到控制面板卸载结束，全程只点界面。
4. 必测五件事：装得上、起得来、**升级覆盖不丢数据**、关窗进托盘不残留进程、卸得干净。
5. 必测两个环境：**断网启动**、**125%/150% 缩放 + 双屏**。
6. 证据命名 `释放-NN-说明.png`，存 `evidence/release/<版本>/`；新版本开新目录，**禁止覆盖旧证据**。
7. 任一步不通过 = 整版不发，回到 D1。

### D4 交付验收（真人盲测）

1. 执行人是**不懂技术的人**，只拿 `RELEASE_GATE.md` 第二部分那 14 个问题。
2. 只允许回答「看见 / 没看见」，没看见就写 × 并截图（Win+Shift+S）。
3. 测试人**不许提示、不许代操作、不许解释**；解释一句，这一题作废。
4. 出现 ≥1 个 × 就停，登记缺陷，回到修复轮。
5. 真实发布（D1 条）必须由账号主人本人授权并扫码，发布前后各留一张截图。

## 6. 用例书写规则

1. 一条用例只验一件事；标题写动作与结果，不写「测试功能」。
2. 必须含五项：**编号 / 前置条件 / 动作 / 页面必须看到 / 证据文件名**。
3. 禁止不可判定的写法：「检查功能正常」「界面美观」「体验流畅」。判据必须是别人能照着复现并得出同一结论。
4. **正例反例成对**：能做 X，就要另有一条验「不能做 X 时如实报错」。
5. 编号与 RTM 的 AC 对应；暂时对不上的标 NA，不许留空。
6. 一条用例只允许一个结论：**PASS / FAIL / 阻塞**。不许写「基本通过」「部分通过」。

## 7. 环境规则（专治假红假绿）

1. 每轮开始先记录 **版本号 + git 提交号 + 工作区是否 dirty**；三者与产物不符，本轮结论作废。
2. 走 HTTP 的测试必须关代理：`--noproxy` / `NO_PROXY`（历史上代理导致过假 502）。
3. 端口约定：**31280 = 开发版**、**3081 = 产品实例**、**3080 = 助手**。测错端口，结论作废。
4. 数据根隔离：用 `BOSOM_FRIEND_HOME` 指向独立目录；动真实数据前先备份。
5. 门禁出红先复跑一次；**红变绿必须在报告里写明「间歇」**，并追到断言层修掉，不许当没发生。
6. 任何「改断言让它变绿」的动作，必须配**负向对照**：把旧写法改回去能判红，才算真修好。

## 8. 缺陷与返工规则

- 分级沿用 `RELEASE_CHECKLIST-v1.0.md` 第 2 节（P0 / P1 / P2）。
- 状态机：**新建 → 已确认 → 修复中 → 待回归 → 已关闭**。禁止跳过「待回归」直接关闭。
- 每条缺陷必须写全七项：编号 / 现象 / 复现步骤 / 引入版本 / 证据 / 修复版本 / 回归证据。
- 返工：冻结 → 一轮批量修复 → 全量回归，**最多两轮**；两轮仍红，连同证据交决策，不发布、不声称完成。
- **台账为空不等于没有缺陷，等于没有登记。**
