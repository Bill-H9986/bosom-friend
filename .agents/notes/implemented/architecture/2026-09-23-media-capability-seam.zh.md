# Agent Note: 媒体能力缝

Status: implemented

[English](2026-09-23-media-capability-seam.md) | 中文

## Problem

Harness 拥有文本生成能力，却没有图片、视频或语音生成能力。于是各个应用直接连厂商端点：每一处都要重新推导端点布局、鉴权头、超时、尺寸协商与轮询，换一家厂商就要改应用代码，密钥住在应用的文件里而不是凭据能力缝里，也没有任何门禁能说清"哪个包被允许开厂商连接"。

## Decision

`ctx.media` 就是媒体能力缝。`@deepseek-ai/dsh-media` 定义三个操作——`generateImage`、`submitVideo`、`pollVideo`——外加一张提供方注册表、一套请求/结果词汇与 `MediaError` 分类。视频请求的参考素材走 `MediaTalkingHead`；`MediaTalkingHead.videos`（`MediaReferenceVideo`）把一段参考片段作为公网可读的 URL 或 data URI 带进来，可选起始秒与「是否必须有音轨」。语音不在这条缝里，那个决定由[厂商原生发声](2026-09-25-vendor-native-speech.zh.md)承载。选择在每次调用时解析，从不依赖注册顺序：指定了提供方 id 就必须已注册且可用；没有指定时要求恰好一个可用。

`@deepseek-ai/dsh-media-pi-ai` 是官方随包的提供方，也是媒体厂商 HTTP 唯一出现的地方。它解析每个请求的路由与凭据（经凭据能力缝；该能力缝缺席时用环境变量），讲 OpenAI 兼容方言或 Agnes 方言，并把回来的东西归一：图片与视频产物在提供方内部下载或解码，非 2xx、无应答或不可用的厂商应答分别变成 `MEDIA_VENDOR_REJECTED`（带状态码）、`MEDIA_VENDOR_UNREACHABLE`、`MEDIA_VENDOR_NO_RESULT`。

路由来自提供方的插件配置与 `media-pi-ai` 用户设置段——与模型侧提供方读 `llm-pi-ai` 是同一形状；没有凭据 ref 的路由不带鉴权头调用，本机服务需要的正是这种。重试、预算、调度与持久化留在调用方：这条缝只负责厂商的那一次往返。

## Alternatives considered

**只发提供方包，不发服务定义。** 应用仍然会在自己的代码里指名厂商，换厂商就又要改应用；门禁也分不清"被允许的提供方包"和"应用自己直连厂商"。

**把厂商原始响应返回给调用方。** 调用方就得对厂商状态码与响应形状做分支，等于把方言又塞回每个消费方，而加第二种方言对所有消费方都是破坏性变更。

**把重试、退避与轮询收进能力缝。** 消费方的诉求彼此矛盾：交互式请求要一次有界尝试加一句可读的失败原因，长流程管线要自己的重试预算与可续跑的任务。策略留在消费方，双方才能共用一份线上契约。

## Consequences

没有配置任何路由的组合里，每个操作都以 `MEDIA_PROVIDER_UNAVAILABLE` 或 `MEDIA_ROUTE_UNKNOWN` 失败，且不产生任何网络访问；裸挂载是休眠，而不是偷偷直连。媒体产物在交给调用方之前会在内存里汇聚，所以这条缝面向厂商交付的短片，而不是几十 GB 的渲染。路由不提供参考视频通道时以 `MEDIA_OPERATION_UNSUPPORTED` 失败，而不是悄悄把片段丢掉。这条缝不记录请求日志与用量合计；需要回放的部署在消费方记录。

验证：两个包都带规格，逐文件 100% 覆盖；回环假厂商覆盖两种方言、经凭据能力缝解析密钥、设置段热替换，以及拒收、不可达、无可用结果三类失败路径。
